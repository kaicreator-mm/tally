# Tally v1.4 Target Architecture

This document summarizes the v1.4 Final PRD in implementation terms. The PRD and Decision Locks remain authoritative.

## 1. Product loop

```text
Intent
  ↓
Contract
  ↓
Execute
  ↓
Verify
  ↓
Repair
  ↓
Accept / Escalate
```

v1.4 is not a full SDLC platform. It closes one coding-agent task reliably.

## 2. Brownfield target

```text
existing TaskContract + VerificationContract
              │
              ▼
      ContractSnapshot / Compiler
              │
        ┌─────┴─────┐
        ▼           ▼
      Policy      Context
        │           │
        └─────┬─────┘
              ▼
        Coding Agent
              │
              ▼
      immutable ChangeSet
              │
              ▼
         Verification
              │
      ┌───────┴────────┐
      ▼                ▼
    PASS              FAIL/ERROR
      │                │
      ▼                ▼
 ACCEPTABLE     Failure Classification
                       │
                ┌──────┴───────┐
                ▼              ▼
              Repair        Escalate
                │
                ▼
        new CodegenRun
                │
        new ChangeSet
                └──────→ Verify again
```

## 3. Contract compatibility strategy

The PRD uses one product concept, `Contract`.

The current source has mature:

- TaskContract;
- VerificationContract.

v1.4 should first add a compile/snapshot aggregation seam rather than physically merging those persisted/artifact models in a broad migration.

A later task may simplify storage only if real implementation evidence justifies it.

## 4. Policy

v1.4 introduces a minimal versioned Engineering Policy concept.

Primary v1.4 enforcement is `gate`.

`requires[]` has two effects:

1. it tells the Agent before execution what evidence/constraints must ultimately be satisfied;
2. it compiles required assurance/evidence after execution.

An independent Guidance authoring platform is deferred.

## 5. Project engineering context

Tally can consume existing project context:

- `AGENTS.md`;
- `CLAUDE.md`;
- architecture docs;
- ADRs;
- existing tests/conventions.

v1.4 does not build a new project Wiki/Guidance authoring system.

## 6. Assurance

MVP levels:

```text
L0 self-check
L1 deterministic tools
L2 independent LLM judge + deterministic protection/mutation checks
L3 protected / held-out verifier
L4 human authority required
```

These are initial implementation levels, not a claim that human authority is mathematically “stronger” than held-out deterministic evidence.

A0 bake-off must determine practical defaults.

## 7. Repair

Outer Repair is a new loop.

It is not the same as inner Agent iteration.

Each repair attempt must have:

- a fresh CodegenRun;
- a fresh disposable workspace;
- a new immutable ChangeSet;
- the same frozen Contract unless an explicit append-only amendment occurs;
- append-only supersession lineage;
- finite RepairPolicy.

## 8. Failure classification

At minimum distinguish:

```text
repairable
contract_defect
policy_conflict
environment_failure
provider_failure
verification_inconclusive
requires_human_judgment
unknown
```

Unknown fails safe.

Verification `FAIL` and verification `ERROR` stay different.

## 9. VerifiedBasis

Do not add a second mutable state authority.

Extend the current derived task-state/evidence model toward:

```text
verdict
required assurance
achieved assurance
evidence coverage
policy coverage
matched policy
unmatched risk
satisfied requirements
waived requirements
residual risk
```

## 10. Minimal persistent product model

Longer-term v1.4 product semantics:

- WorkItem
- Contract
- Policy
- ChangeSet
- Evidence
- append-only OutcomeLog

This does not mean every object requires an immediate new table.

Prefer existing artifacts/facts where they already provide the semantics.

## 11. MVP Harness scope

Implement only:

- Bug Fix;
- Database Migration.

Defer:

- full Public API Harness;
- Auth/Security Harness;
- Release;
- Incident;
- Project Engineering Model;
- Adaptive Harness;
- full Requirements authoring;
- full Jira-like navigation.

## 12. UI target

Minimum:

- Launch;
- closed-loop Task detail;
- Change detail;
- Attention.

The existing `/v13/*` UI is a source asset to evolve, not a separate product to preserve forever.

## 13. Runtime boundary

### Tally

Coding Agent execution plane:

- Runtime;
- session/workspace;
- patch/events;
- candidate identity.

### shared AI Runtime

Generic inference plane:

- provider/model routing;
- retry/fallback;
- cost;
- trace;
- rollout.

## 14. Architecture-freeze prerequisites

Before downstream v1.4 implementation is considered fully frozen:

- Codex session isolation spike;
- Assurance L1/L2/L3 bake-off;
- Repair/held-out feedback ADR;
- Architecture Freeze Gate.
