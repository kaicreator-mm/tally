# K05 — 软件测试与质量验证 / Software Testing & Quality Verification

> 版本：[v2.1.2 #521](https://github.com/kaicreator-mm/tally/issues/521) · 模块：[Tally #526](https://github.com/kaicreator-mm/tally/issues/526) · [总索引](README.md)。`DETAILED_CONTENT_CANDIDATE / NOT_QUALIFIED / NOT_ACTIVATED`。ADS 为 Agent 开发实践与版本化规范的来源，Tally 负责选择合格的知识并在具体开发任务中消费。文中案例为**可证伪教学情景**，除非另有精确来源，不声称已在真实 Host 上执行。

## 1. 模块定位与目标

让 Agent 能从实际需求和接口合同设计**能揭露错误**的测试，而不是把测试数量、CI 状态或 Mock 成功等同于正确性。测试覆盖有效行为、失败/边界、不变量、真实组件和最终关键用户路径；执行证据必须反映真实测试被发现并运行的事实。

**适用触发：** 新增或修改行为、公共契约、错误状态、集成边界、修复回归、构建或发布入口；只改变注释时不强制重做整个测试体系。

**本模块最重要的边界：** 测试是一种可证伪行为证据；测试设计与执行、CI Provider、真实 Host、独立 Reviewer、Release Qualification 有不同语义，不能互相自动晋升。本文不另建代码库逆向分析或软件安全/供应链两个专项；当前实际工程已经生效的权限、源代码和必要安全标准不会因专项暂缓而失效。

## 2. 术语与领域模型

| 概念 | 具体含义 | 易错判断 |
| --- | --- | --- |
| Test Oracle | 从已确认需求、合同或不变量导出的预期行为/不允许结果 | 用实现者本人猜想作为唯一正确答案 |
| Positive / Negative | 代表正常条件与应当拒绝或失败的条件 | 只追求所有测试通过而不设计失败场景 |
| Boundary Value | 输入规模、时间、状态、类型等切换边界 | 只测平均输入/常规状态 |
| Unit / Contract / Integration | 分别检查局部行为、公开接口合同和真实组件组合 | Mock 测试通过就当真实数据库 E2E |
| User Critical Journey | 对用户有意义的真实业务闭环 | 把一堆不相关 API 调用拼成大测试 |
| Test Discovery | 测试运行器实际选择并执行了哪些用例 | 命令 exit 0 就猜测相关文件被执行 |
| Regression Test | 锁定既有接受行为或历史已修复问题 | 修改期望值以配合错误实现 |
| Source/Tested Ref | 精确代码/测试版本和环境 | 用过去的 CI 结果证明新 HEAD |
| False Pass | 测试或证据显示绿，但关键行为未被测试或真实入口未调用 | 把该现象当作没有缺陷 |

这些术语不是全局强制新增的 Tally Schema；仅当实际 Workflow/Business 的输入输出需要区分语义时，才形成有来源的可复用类型或术语。

## 3. 知识正文：核心工程方法

### 3.1 从要求生成 Oracle

先把业务规则、设计合同和已批准示例写成可观察的输入/状态→结果对，标明为什么这个结果是正确的。不能把 Agent 凭空虚构的业务规则变成 Test Oracle。一个重要不变量应同时有可满足的正例与违反时被拒绝的反例，测试假阳性往往来自仅检查内部调用而不检查用户状态。

### 3.2 测试层级与代价

Unit 优先验证局部纯逻辑，Contract 锁定外部 API/Schema/序列化/CLI 行为；Integration 使用真实 DB/filesystem/队列和对外适配 seam；E2E 覆盖少量关键用户结果；Build/Packaging 检查可交付入口与真实产物。各层不能互相取代，也不要求每个小修补都跑完整分布式 E2E。

### 3.3 边界、状态与组合测试

等价类帮助减少冗余组合，边界值覆盖 0/1/max、空值、过期时间、状态转换边界；状态机测试检查非法转移、重复提交、取消、失败恢复。对高价值复杂逻辑可考虑性质/变异测试，但必须有合法不变量作为断言，并评估生成数据的真实来源和成本。

### 3.4 Mock 与真实消费者的分界

Mock/Stub 适用于快速隔离业务算法和对某个稳定合同做初步判断，不能替代真实外部 DB/queue/Host 的副作用行为。测试应该核实选定构建实际加载新模块、公开入口实际调用修改后的代码、界面/CLI 或服务实际观察到正确结果；否则“测试已写但没有消费”仍是未验证。

### 3.5 实际测试发现与执行证明

有些测试命令 exit 0，却没有发现目标测试文件，或者测试套件忽略了变更目录。验证时需读取 runner 枚举结果、用例计数、具体路径/调用或有代表性的失败探针；报告写实际执行命令、环境、退出码、测试 SHA 和失败明细。不要用成功的 npm install 替代 TypeScript build 和测试结果。

### 3.6 最小充分验证策略

按影响范围与风险做测试选择：语法/类型/受影响单元、必要契约、跨模块真实组合、可交付产物。若目标工作区已有等价通过的有效证据不重复 CI；但真正要求独立 Provider/真实 Host/特定 OS 的合同仍需现场证明。对未运行测试诚实标 NOT_RUN，不为“安全感”无限增加独立审查。

### 3.7 测试质量、Flaky 与长期回归

失败测试应反映真实缺陷而不是随机等待、固定日期、外部网络偶然波动；对 flaky 原因归类并选择确定性 fixture/隔离/轮询机制，不能通过增加无限重试掩盖稳定错误。Golden/Snapshot 必须有合法 Oracle，不得随着变更无审查地更新基准使所有回归自动变绿。

## 4. 可执行的 Decision Procedures

决策程序定义可复用的方法及终止条件，不创建第二套运行时状态机、审批权威或 Agent 调度器。

### DP-K05-01 · Requirements→Oracle→Test Matrix

**输入：** 已确认 Need/Rule/Acceptance、L2 API 和关键状态

**步骤：**
1. 提炼可观察的成功与禁止行为，标注原始来源。
2. 选择有代表性的正常、边界、无效、重复/失败输入。
3. 根据行为所在边界安排 Unit/Contract/Integration/Critical Journey 层次。
4. 给每个测试写输入前置、断言、不允许结果和运行环境。
5. 审查断言是否会在目标实现有错时真的失败。

**产物：** 最小风险适配 Test Matrix、验证来源及测试命令

**失败/停止：** 业务规则未确认时保留 Oracle UNKNOWN 而非虚构预期。

### DP-K05-02 · 选择受影响验证集

**输入：** 实际 changed paths/Task 目标/当前测试布局/部署合同

**步骤：**
1. 检查项目现有真实测试发现范围及构建工具版本。
2. 运行必要 syntax/types/build，并选行为直接受影响用例。
3. 按公开合同、跨模块/真实 Host 要求增加必要验证。
4. 复用合法且未失效的先前 PASS 证据，明确哪些没重跑。
5. 在当前源码 exact SHA 上验证执行结果。

**产物：** 可解释的测试选择、真实命令和执行收据

**失败/停止：** 不可调用真实 Host 时声明 NOT_RUN/BLOCKED，不冒充成功。

### DP-K05-03 · False PASS 取证

**输入：** CI/测试结果、真实入口/消费者、被修改源码及构建产物

**步骤：**
1. 确认目标源码确实出现在选定构建和模块加载路径。
2. 确认相关测试确实被发现，非 0 用例退出。
3. 确认实际断言观察到需求结果而非仅函数 mock 调用。
4. 发现缺口后设计最小会因错误实现而失败的反例。

**产物：** 验证缺口与最小修复/额外测试建议

**失败/停止：** 有明确证据缺失就不能宣告正式 PASS。

## 5. Tally 消费路径与跨模块接口

**主要 Workflow：** L3 Verification / Review / Delivery

| 工作环节 | 读取的当前事实 | 本模块的输出 | 原有权威/禁止推断 |
| --- | --- | --- | --- |
| L1/L2 | 接受要求、设计不变量和数据来源 | 可信 Oracle 与验收测试候选 | 未确认业务真相不写死期望 |
| Task design | 实际受影响代码/合同 | 各层最小测试和正反矩阵 | 不强制全套 E2E |

## 6. Agent Skills（输入、输出和验证）

### SK-K05-01 · Test Matrix Designer

- **调用时机：** 需求已被接受且待验证行为明确
- **最低输入：** 业务来源、API/状态、实现目标与适用测试层
- **产出与格式：** 带来源的成功/失败/边界/不变量测试方案
- **自查及异常路线：** 故意反转实现应该触发至少一个失败断言
- **不能做：** 模仿新实现结果定义需求

### SK-K05-02 · Executed Test Evidence Reader

- **调用时机：** Builder 声称测试已通过
- **最低输入：** 真实测试命令/用例输出/exit code/环境/HEAD
- **产出与格式：** 实际发现测试、已测范围、未测/失败及 provenance
- **自查及异常路线：** 确认受影响用例被 runner 选择，失败源头可定位
- **不能做：** 将空套件或旧 SHA 的 green 认定当前成功

### SK-K05-03 · Selected Path Verifier

- **调用时机：** 涉及跨组件、UI/CLI、安装产物或外部服务
- **最低输入：** 用户入口、选定构建和必要真实依赖
- **产出与格式：** 入口→调用→结果的可重复收据，真实/Mock 资格区分
- **自查及异常路线：** 若还缺 Host/Provider 权限则保留明确 UNKNOWN
- **不能做：** 仅用 stub 的结果代替实际端到端行为

## 7. 端到端教学案例与故障反例

**情景：** 新增订单状态变更接口。Builder 写了 8 个 Unit Test 并报告“全绿”；真实 API 使用另一条包装路径，错误状态仍可被修改。

**正确处理：**
1. 从已确认规则提炼允许状态、非法状态、重复请求与权限错误的 Test Oracle。
2. 检查现有 Unit Test 是否通过 Mock 绕开真正的 API/DB 更新入口，不能从数量判断质量。
3. 增加一个公开合同测试和最小真实 API→持久化集成负例，覆盖非法状态拒绝及状态不变。
4. 验证 runner 真正发现并执行新增测试，输出命令/环境和受测试的 SHA。
5. 若部署用户关键路径受影响且项目实际需要，补选定应用真实入口验证；无需每次重复全系统 suite。

**可以观察的正确性：** 非法状态变更必须失败并保持记录未改变；当前测试真实运行且在错误实现下能失败。

**故意错误的候选：** 只在内部方法的 Mock 上检查调用一次；test 命令实际选中 0 个测试仍 exit 0，然后将 UI/Host/Release 都标 PASS。

**变更条件后如何调整：** 若仅改测试文件注释，已有构建/行为证据不失效时无需重复真实 Host；如 public API 变更需恢复相关契约和真实消费者验证。

## 8. 常见反模式与止损条件

1. **Zero Test Green**：通过命令成功不代表选择到目标测试
2. **Mock-as-E2E**：所有外部边界由 Mock 替代却标真实 Host
3. **Oracle Leakage**：从错误实现反向定义 expected 值
4. **Golden Rebaseline**：未经来源核对就更新 Snapshot 将回归变绿
5. **Endless Verification**：不区分影响和环境要求，反复跑所有 CI 造成无效成本

## 9. 训练与知识资格验证案例

以下是**未来**测试/案例设计，不代表测试或知识资格已经完成。

| 案例 | 期望推断或行为 | 需要拒绝的结论 | 验证依据 |
| --- | --- | --- | --- |
| 空测试集 exit 0 | 发现缺口并标 INVALID/UNKNOWN | “CI GREEN 即通过” | 真实测试 runner 用例清单 |
| 非法状态被实际修改 | 真实接口负例必须失败 | 内部单元测试绿就足够 | 业务规则 + API/DB 运行 |
| 外部第三方仅 Mock | 限定资格为模拟合同 | 直接写生产 E2E PASS | Mock/真实依赖拓扑 |
| 同 SHA 受影响测试已有通过 | 有条件复用，不无意义重跑 | 必须额外反复 CI | 已接受收据+当前性 |
| 测试源变更但版本没绑定 | 重新执行或明确不足 | 使用旧提交结果 | 实际 source/tested SHA |

真实测量时先固定任务、输入、预期标准及基线，再比较直接 Agent 与 Tally 选中知识后的实际质量/修复/成本。不得用文档样例或图谱问答成绩替代实际编码效果；没有结果就标明 `UNKNOWN/NOT_RUN`。

## 附录 A · Agent 直接调用的工作示例（非正式 Wire Schema）

**教学输入：** 订单状态变更的内部 Unit Test 全绿，但 API→DB 真实路径仍存在非法状态写入。
- 使用知识：TestOracle、Contract、Integration、TestDiscovery，执行 DP-K05-01/03。
- 期望产物：由业务不变量导出的正例、非法状态拒绝/数据库状态不变负例，以及相关层次的测试矩阵。
- 验证：先确认实际 runner 发现目标测试，再验证公开入口确实执行新逻辑；记录测试 SHA、环境和失败明细。
- 停止与交接：只有 Mock 收据时把其**证据适用范围**描述为 `MOCK_ONLY`，不新增 Validation Gate 状态；未调用 Host 时对对应 Gate 使用现有 `NOT_RUN`（若已明确外部阻塞，则按现有权威记 `BLOCKED`），不能发布真实 E2E PASS。

**来源基线：** 本文 ADS `standards/` / `prompts/` 引用已固定到正式发布的 `v4.19.0@933c4fd3e0e1b9f1a73ed6a9b552077baaf5376c`，并核查路径确实存在。固定来源只证明**引用身份与可读性**，不等于逐个知识 Claim 已经获得独立资格审核。ADS [#1383](https://github.com/kaicreator-mm/ai-development-standard/issues/1383)/[Draft #1384](https://github.com/kaicreator-mm/ai-development-standard/pull/1384) 是后继设计候选，不能倒推成为 v4.19.0 已生效规则。此示例用于人工/Agent 推理和 Tally 消费方案，不是要求 Tally 新增这些字段或消息格式。
