## 一、生命周期方法是风险的响应，不是身份标签

瀑布、增量、迭代、探索性原型、风险驱动研究各有使用边界。主要区分需要早期固定的外部合同、未决研究、可回退成本和反馈周期，而不是把“敏捷”当作不需要系统设计的许可。

示例：明确的 API 字段更改、接口依赖少，可能一次完成并验证；分布式结算的 exactly-once 语义有大量未知，应先做限定研究或 Failure Demo。如果两者都被强制进入同一多级计划，就会浪费验证和协作成本，甚至掩盖风险。

## 二、估算要给区间与假设，不能伪装精确承诺

任务估时的主要未知包括：范围、受影响接口、团队熟悉度、基础设施状态、测试真实覆盖、外部 Owner 决策和后续返工。单个点估算无法表达对这些未知的敏感性。可使用类似“最乐观/常见/保守”的**情景区间**，但在没有历史样本时，权重模型不等于可靠的预测分布。

**教学情境**：工作 A 预估 2–3 单位，B 预估 1–8 单位，C 必须在 B 后完成。不能仅以均值比较 A/B 的风险；应明确 B 的长尾来源是否为外部审批、共享写集还是不可测的技术假设。真实关键路径有时由等待 Owner 或环境而非编码行数决定。

## 三、研究与实施应分开评价，但不要产生双重权限

一个架构未知的 Research Work Unit 的合法结果可以是“选项 A 在条件 X 下被反例推翻，缺条件 Y”，而不是强迫它输出合并代码。若实际 Product/Task 已授权实现，则最小交付工作可在同轮完成修复和等价验证。两者应由真实任务意图区分，不因形式标签在 GitHub 创建新的虚假依赖。

研究 STOP：当剩余不确定性不会材料性改变选项或风险小于继续研究成本时，形成限定建议并停止。实施 STOP：遇到未决权威政策、无法满足真实必要验证或当前 SHA 已过期时，不能自报完成。

## 四、重规划基于事实变化而不是 Agent 反馈情绪

| 新事实 | 应当更新 | 不应自动更新 |
| --- | --- | --- |
| L2 核心接口获得确认 | 受该接口影响的依赖/写集 | 所有独立文档 Task |
| 目标 Runner 没发现测试 | 受影响验证工作与阻塞 | 已通过且不受影响的 Unit |
| 外部 Approval 不可得 | 相关 Goal 的 UNKNOWN/WAIT | 用 Agent 自签替代审批 |
| CI 每个 Workflow 都重复 clone | 构建阶段时间/可复用策略候选 | 立即删掉 Provider 必需隔离 |
| 一个独立 Agent 意外迟到 | 与其 Attempt/HEAD 对应的消费状态 | 重新执行整个项目 DAG |

更新计划时记录“前一假设→新事实→受影响节点/边→停止/恢复条件”，保留历史判断供 K11 后续实证比较。计划学习材料来自可验证工程事件，不是复盘空泛口号。

## 五、交付优先与证据优先并存

计划优化目标不是 Review 数量最少，也不是没有 Reviewer；而是在现有正确性/权限/质量底线下减少等待、重复试验和无效治理。若一项 CI 证据已在同 SHA/同范围等价完成，除非存在 Provider Required Check 或独立环境要求，不应反复重跑；相反，未真实验证的外部 Effect 不能由理论推导代替。

**教学反例**：两个 Agent 之间没有实质依赖，却因候选三图协议被错误串行，最后用新增三个虚构 Task Status 记录工作，既延误交付又与 GitHub 原权限冲突。正确的专业判断首先核实当前 ADS 生效合同和真实工作因果。
