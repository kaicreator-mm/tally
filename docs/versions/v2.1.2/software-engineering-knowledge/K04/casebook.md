## 7. 端到端教学案例与故障反例

**情景：** 一个版本同时改 API 和 UI，并调整一个共享数据库模型。三个 Agent 希望并发推进。

**正确处理：**
1. 先确认真正的需求/设计是否清楚；若仅 API 字段合同未定，则形成一个小 L2 决策而非并行开工。
2. 定义明确的 API/状态合同和用户关键路径；把数据库模型迁移与 API 开发的真实依赖说明。
3. 若 UI 只需消费冻结的 Contract，可由第二 Agent 在不重叠写集上并行；共享迁移/生成物保留单 Writer。
4. 集成 Task 在两个实际分支成果都可用后验证真实组合与端到端行为。
5. 源头需求变化时只重新评估受影响接口、Task/测试，不为所有老证据重新审核。

**可以观察的正确性：** 每条真实 blocked-by 有必要的前置产物说明；并行无共享写冲突，集成行为可在当前源版本上验证。

**故意错误的候选：** 把“测试”“异常处理”“实现”“文档”各自开一个不能独立验收的 Task，要求十次 PR 合并；同时两个 Builder 写同一个迁移文件。

**变更条件后如何调整：** 若仅修改单一错误提示，不需要 P/A/I 各一个显式 DAG；直接 INLINE 并执行受影响检查。

## 反模式与错误后果

## 8. 常见反模式与止损条件

1. **False Serial**：只因喜欢顺序流程就让 API 任务等待无关文档 Task
2. **False Parallel**：写集不重叠就当作协议/集成完全可并行
3. **Nested Authority**：在 Tally 私有工作图生成第二套 Claim 与 native Task 状态
4. **Unbounded Graph**：把每个 agent 推理步骤都提升为 Issue
5. **Over-validation**：已验无影响旧证据被逐任务要求再次跑完整 CI

### C-K04-01 · API/UI/schema 三模块

**问题**：共享 Schema/接口先冻结，互不重叠写集并行，最后做真实集成。

**如何用本模块诊断/解决：** 先识别用户目标、确切源/版本与真实约束，按 [方法矩阵](engineering-methods.md) 选与此情况匹配的一条有界程序；不影响结果的假设不额外提高流程成本。

**反例**：若 Agent 未核对上述关键条件就直接断言相同方法普遍适用，必须以 UNKNOWN/REWORK 处置而不是 PASS。
