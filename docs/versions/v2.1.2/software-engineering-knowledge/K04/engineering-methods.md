## 知识正文与重要权衡

## 3. 知识正文：核心工程方法

### 3.1 一图三视图的边界

DAG-P 的节点可能是研究某种用户行为，DAG-A 的节点可能是试验接口持久化，DAG-I 才是实际编码/测试/合并任务。它们共同来自一个可追溯开发过程，但“研究所用证据已被消费”和“前置实施任务已完成”不是相同的边。只有真实独立执行工作才需要图结构；日常明确任务可 INLINE。

### 3.2 按可验收成果拆分

任务划分首先找用户可感知功能、真实子系统合同和可独立检查的行为。测试、实现、合同和错误处理通常属于同一原子结果；如果拆成多个 Issue 后无法单独验证或必须反复合并，意味着拆分过细。一个复杂工作也不能一概并行：共享单文件/生成产物，最好由一个有界 Writer 负责。

### 3.3 前置依赖的因果检验

为每条 BLOCKED_BY 回答“如果前任务未完成，后任务究竟缺少什么不可替代的事实/接口/输入？”如果说不清，不应建立硬边。跨阶段证据通常引用确切版本而非自动 native Issue Dependency。循环依赖需要重新审视合同或将多方共享的公共决策提升为单一前置节点。

### 3.4 阶段独立选择复杂度

INLINE 用于一人、有充分证据且无真实协调成本；BOUNDED_WORKLIST 用于几个问题或检查，无独立调度价值；EXPLICIT_DAG 用于真实依赖、不同角色/环境、共享写/合同与可并行研究。复杂 L1 不要求复杂 L2；简单 L1 仍可能触发复杂 Architecture Demo；小范围高风险任务也不能因 INLINE 取消必要验证。

### 3.5 并行的经济和安全边界

并行只在模块/Task 交付边界真正独立且合并总成本低于串行时有价值。读-only 分析可以较自由并行；同一工作树、锁文件、代码生成器、公共 index、数据库迁移需要明确 Owner 和合入顺序。写集无重叠并不证明接口稳定、实际可同时集成，也不自动满足原生 Claim/Host 限制。

### 3.6 进度、Closure 与变化重规划

DAG 节点数、PR 数或 Agent 数都不是交付成果。目标是在真实结果完成后收尾，禁止为证明努力而反复 Review/CI。上游需求改变时只查受影响的 Design/Task/测试证据，不重建整个 DAG；变更不得反向涂改已完成原始历史，当前版本需要新决议。

### 3.7 任务描述到执行 Pack

独立 Task 的可执行合同至少说明目标、source/current HEAD、已有 frozen requirement/architecture、允许写路径、真实依赖、受影响测试、完成证据、环境与禁止范围。任何 Agent 候选计划都不能自己生成有效 Claim 或强制 Tally 创建一套新的工作状态存储。

## 具体可执行方法与取舍

分解时先问‘用户最终得到什么成果’，再判断是否可以由单一 Writer 连同测试直接交付。若跨模块实现可以并行，应先对共享接口、Schema、生成物和测试环境划边界。对每条 blocked-by 做反事实检验：移除此边后，后续工作是否仍能合法完成？若可以则不是真正硬依赖。简单 Task 使用 INLINE/原有 fast path，研究节点只在真实前置存在时组织，不为形式完整强制三套图。

### 场景选择矩阵

| 真实条件 | 推荐分析/方法 | 需要记录的结果 | 禁止误推 |
| --- | --- | --- | --- |
| 单一模块小修复、可当天完整验收 | INLINE 单 Task + 真实必要测试 | 原子任务包 | 无显式三 DAG |
| 多模块但接口尚未确定 | 先完成共享契约，再拆合法并行写集 | 合同 Task 与后续依赖 | 不能假并行 |
| 多项相互依赖的 L1/L2 研究 | 按已发布 ADS 原 owner 做有界映射/研究 | 研究问题和停止条件 | 不是 L3 Native Task DAG |
| 上游仅一个接口发生变化 | 传播到受影响任务和测试 | 最小重规划 | 不重做全部旧研究/CI |

## 现有 Decision Procedures（输入、步骤、产物与停止）

## 4. 可执行的 Decision Procedures

决策程序定义可复用的方法及终止条件，不创建第二套运行时状态机、审批权威或 Agent 调度器。

**提案来源边界：** `TALLY_V212_PROPOSED_KNOWLEDGE / ADS_1100_HISTORICAL_DESIGN / ADS_1384_UNADOPTED`；`DAG-P/A/I` 统一命名和全阶段 `INLINE/BOUNDED_WORKLIST/EXPLICIT_DAG` 选择是候选知识，不可称 ADS v4.19 已采纳。现行 L1 是按需 Evidence DAG/研究映射，L2 走 Architecture/Research Demo，L3 使用合法 Task DAG 及 GitHub native dependencies。

### DP-K04-01 · 最小工作图选择

**输入：** 用户目标、Product/L2 不确定性、真实工作/人/环境依赖

**步骤：**
1. 先按真实结果列出需要交付的用户/工程成果。
2. 分辨问题属于 P/A/I 哪层，而非先创建 Issue。
3. 评估可由一人有界完成、几个检查还是确实独立可调度。
4. 为每层选择 INLINE/WORKLIST/DAG，并对真实阻塞说明必须等待什么。
5. 列止损条件及不必做的工作，复用现有规范与 CI 证据。

**产物：** 阶段计划/节点必要性和有界停止标准

**失败/停止：** 真实权威/来源不足则只形成提案，不写入 native Task 图。

### DP-K04-02 · Task 原子性与并行评估

**输入：** 候选模块边界、API/seam、可改路径、测试/集成成本

**步骤：**
1. 每个候选 Task 写明可独立验收的用户或工程结果。
2. 检查 Contract/Tests/Code 是否应该由同一个 Writer 完成。
3. 根据交叉文件/生成产物/接口依赖修正并行组和合入顺序。
4. 比较拆分后额外 Review、CI、冲突解决成本与预计节省时间。
5. 保留必要最小集成 Task 和实际 blocked-by，不增加“装饰性”依赖。

**产物：** 合法拆分方案、写集、关系及合并验证计划

**失败/停止：** 若拆分使一个任务无法独立通过最低验收，需合并或调整 seam。

### DP-K04-03 · 受影响范围重规划

**输入：** 变更的需求/ADR/合同及旧任务和证据版本

**步骤：**
1. 定位最早变化的有权语义层。
2. 列出直接消费该来源的设计与 Task，再按实际依赖传播。
3. 复核仅受影响测试、接口及合并证据的当前性。
4. 保留无关旧工作成果并记录新的版本修订理由。

**产物：** 受影响节点的有界增量计划与历史引用

**失败/停止：** 禁止把旧历史任务直接改写为新版本的 PASS 或全部重新开工。

## 抗过度流程原则

一次实际 Task 至多选择足以完成当前判断的 Procedure；除非已知缺口会改变业务、架构或正确性结果，否则不自动开新 Issue、实验或大量 CI。若缺少有权决策者、现行数据或真实 Host，保持 UNKNOWN 并说明最小下一项证据，不通过 Agent 自信度推定通过。
