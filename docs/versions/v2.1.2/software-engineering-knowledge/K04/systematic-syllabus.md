> `SYSTEMATIC_KNOWLEDGE_CANDIDATE / NOT_SOURCE_CLAIM_QUALIFIED / NOT_CONNECTED`。这是 **5 个学科群、15 个原创建模知识点**的系统性专业纲要，不是“任务已运行/业务规则已获权”的声明，不摘抄受限制国际标准全文。当前模块 Owner：**可交付工作单位、真实依赖、并行写集、计划适应与有限工程推进方法**。

## 一、知识对象与专业推理的原则

工程过程与任务规划 要从概念的明确语义延伸到工程机制、条件性取舍和可反驳的实际结果。学习一个技术名词不等于学会何时用它；能输出步骤不等于执行/验证通过。此处每个知识点包括**概念、因果/适用机制以及常见错误泛化**，作为 Agent 的系统学习和主题检索基础。只有实际工程问题需要深入时，才延伸到相关 Topic/DP/Skill/真实测试。所有业务效力仍由当时适用的 Product/ADS/GitHub/Host 事实决定。

## 1. 软件生命周期与方法选择

### K04.F1.1 — 生命周期过程

**专业知识/机制**：需求、设计、构造、验证、部署、维护可迭代交错，ISO 12207 不要求一种固定阶段/过程。

**错误外推及负例入口**：把每个小修复强制重走完整瀑布阶段。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K04.F1.2 — 迭代/增量与反馈

**专业知识/机制**：围绕真实用户价值划最小可集成增量，早期可证伪证据降低后续返工成本。

**错误外推及负例入口**：为增加 PR 数把同一完整业务行为切成多个无法独立验收任务。

### K04.F1.3 — 复杂度与风险驱动流程

**专业知识/机制**：简单任务可 INLINE、复杂度/真实依赖高时使用适量 Worklist/Task DAG；统一 DAG-P/A/I 仍是历史候选表达而非现行统一规范。

### K04.F2.1 — Work Unit/Task Outcome

**专业知识/机制**：每个 Task 有明确输入/可验结果、写集、测试和退出；不按文件数/Agent 数量机械划分。

**错误外推及负例入口**：仅输出“已经分析完成”却没有可检查成果。

### K04.F2.2 — 问题分解与组合

**专业知识/机制**：通过责任/用户垂直功能、平台、真实接口等分解可独立交付子成果；合并成本要入账。

**错误外推及负例入口**：把前端/后端/测试完全割裂又无合同交接。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K04.F2.3 — 验收与授权

**专业知识/机制**：Task 的完成由真实当前 Issue/Claim/必要 Review/Validation 决定，知识 Task 不另建状态权威。

**错误外推及负例入口**：某 Agent 自称 DONE 就把其它人的 Task 标 PASS。

## 4. 不确定性与研究计划

### K04.F4.1 — 事实缺口/研究目标

**专业知识/机制**：研究只解决实际会改变决策的问题，输出可区分候选方案的证据和停止条件。

**错误外推及负例入口**：无材料性未知仍不断扩展调查。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K04.F4.2 — 变更影响与重规划

**专业知识/机制**：来源/接口/资源变化时只重排受影响的节点和实际消费者，保留未变化的审查/CI 收据。

**错误外推及负例入口**：某一文档改动导致所有 Task 无条件重新开始。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K04.F4.3 — 计划中的风险预算

**专业知识/机制**：针对不可逆数据、权限、外部 Effect 和关键用户路径保留保证底线；风险低的任务少做重复流程。

## 六、完整专业知识如何映射到 Tally 可执行领域智能

**角色**：可交付工作单位、真实依赖、并行写集、计划适应与有限工程推进方法。K04 借 K11 判断成本/停止，借 K07 划分多 Agent 写集；K08 判断实际 CI/发布来源，不抢占真正 GitHub Task 权威。

**专业案例（教学情境）**：假依赖导致的串行阻塞。对 Release Note 文档 A 与 API 任务 B 做反事实移除；若 B 根本不消费 A，则不得构造 A→B 的 Native 阻塞。

**禁止的错误判断**：按文件列表顺序创建 20 个 BLOCKED_BY 使真正独立任务都等待。

**推理/证据链**：当前 Goal/事实/来源 → 选 K04 的相应学科群及 Concept → 明确 Rule/Model 是否具备有权业务前提 → 选择 [方法与 DP](engineering-methods.md)、[Agent Skill](agent-skills.md)、已有或未来 [Topic](README.md) → 给出正反 Oracle 与 STOP → 只有在合法消费者实际运行时才附真实 Host/CI/Review 收据。

## 七、知识深化的可观察标准和当前缺口

- **基础层**：这里的 15 个知识点已形成概念+机制+反模式的**原创系统知识纲要**，但不意味着该学科所有细目已经获得全文教材深度或来源 Claim 资格。
- **方法层**：真正要处理的任务应能从本群的术语/条件追溯到现有 DP/Skill/案例或形成新的具体 Topic，且至少能指出一个会使错误判断失败的负例。
- **选用层**：未来根据明确 Product/Task/Package 权限，只为真实使用的知识链补准确 Source/Clause、适用性、许可和消费者测试；没有实际执行仍保持 NOT_RUN。
- **维护层**：新增学科研究、反例或实测失败优先补本群的专业机制与出处，多个 Topic 仅链接到唯一概念解释。未被当前开发用到的理论不因缺运行时资格而从学科知识库删除。
