# K04 — 任务规划与分解 / Task Planning & Decomposition

> 版本：[v2.1.2 #521](https://github.com/kaicreator-mm/tally/issues/521) · 模块：[Tally #525](https://github.com/kaicreator-mm/tally/issues/525) · [总索引](README.md)。`DETAILED_CONTENT_CANDIDATE / NOT_QUALIFIED / NOT_ACTIVATED`。ADS 为 Agent 开发实践与版本化规范的来源，Tally 负责选择合格的知识并在具体开发任务中消费。文中案例为**可证伪教学情景**，除非另有精确来源，不声称已在真实 Host 上执行。

## 1. 模块定位与目标

将软件开发目标分解为**最少但可独立验收**的实际工作。既要识别真实前置关系、共享写冲突、关键路径，也要能在简单变更时停止分解，不制造任务与治理成本。三层图属于不同工程语义：L1 解决产品/需求的不确定性，L2 解决设计的不确定性，L3 才组织正式代码交付。

**适用触发：** 新版本任务分解、复杂需求/技术研究、并行 Agent 开发、共享源码文件、长期无法收尾的工作流与变更重规划。

**本模块最重要的边界：** 一套概念 Work Graph、三个条件式阶段视图；执行 Task 真正的 blocked-by 由已有 GitHub native Issue Dependencies 管理。Evidence 引用不会自动变 Task 阻塞、一个阶段的节点 PASS 不会替另一阶段授予 Freeze。本文不另建代码库逆向分析或软件安全/供应链两个专项；当前实际工程已经生效的权限、源代码和必要安全标准不会因专项暂缓而失效。

## 2. 术语与领域模型

| 概念 | 具体含义 | 易错判断 |
| --- | --- | --- |
| Work Outcome | 独立可验收的交付结果，能够说明用户/工程目标得到什么 | 只按代码文件或编辑动作数划分工作 |
| DAG-P | L1 需求/产品研究节点间实际前置依赖 | 把它当已经冻结的源码 Task DAG |
| DAG-A | L2 架构研究/合同/试验间实际前置依赖 | 一个架构讨论就创建正式 Task Claim |
| DAG-I | 既有实施 Task 与 GitHub native dependency 事实图 | 创建独立第二套实施 DAG 权威 |
| BLOCKED_BY | 前项未得到所需真实产物时后项不能合法完成 | 仅有关联/同一话题就标阻塞 |
| CONSUMES_EVIDENCE | 后项决策参考前项的来源、观察或结论 | 把引用自动当作 ready/PASS |
| Write Set / Owner | 某次 Builder 允许改哪些文件及共享资源谁持有写权 | 文件互不冲突便不需要接口和 Host 边界 |
| Work Shape | INLINE / BOUNDED_WORKLIST / EXPLICIT_DAG 按阶段单独决定 | 所有版本都使用同一种大 DAG |
| Critical Path | 由真实依赖制约最后交付的必要工作链 | 任务最多的路径或最复杂研究即关键路径 |

这些术语不是全局强制新增的 Tally Schema；仅当实际 Workflow/Business 的输入输出需要区分语义时，才形成有来源的可复用类型或术语。

## 3. 知识正文：核心工程方法

### 3.1 一图三视图的边界

DAG-P 的节点可能是研究某种用户行为，DAG-A 的节点可能是试验接口持久化，DAG-I 才是实际编码/测试/合并任务。它们共同来自一个可追溯开发过程，但“研究所用证据已被消费”和“前置实施任务已完成”不是相同的边。只有真实独立执行工作才需要图结构；日常明确任务可 INLINE。

### 3.2 按可验收成果拆分

任务划分首先找用户可感知功能、真实子系统合同和可独立检查的行为。测试、实现、合同和错误处理通常属于同一原子结果；如果拆成多个 Issue 后无法单独验证或必须反复合并，意味着拆分过细。一个复杂工作也不能一概并行：共享单文件/生成产物，最好由一个有界 Writer 负责。

### 3.3 前置依赖的因果检验

为每条 BLOCKED_BY 回答“如果前任务未完成，后任务究竟缺少什么不可替代的事实/接口/输入？”如果说不清，不应建立硬边。跨阶段证据通常引用确切版本而非自动 native Issue Dependency。循环依赖需要重新审视合同或将多方共享的公共决策提升为单一前置节点。

### 3.4 阶段独立选择复杂度

INLINE 用于一人、有充分证据且无真实协调成本；BOUNDED_WORKLIST 用于几个问题或检查，无独立调度价值；EXPLICIT_DAG 用于真实依赖、不同角色/环境、共享写/合同与可并行研究。复杂 L1 不要求复杂 L2；简单 L1 仍可能触发复杂 Architecture Demo；小范围高风险任务也不能因 INLINE 取消必要验证。

### 3.5 并行的经济和安全边界

并行只在模块/Task 交付边界真正独立且合并总成本低于串行时有价值。读-only 分析可以较自由并行；同一工作树、锁文件、代码生成器、公共 index、数据库迁移需要明确 Owner 和合入顺序。写集无重叠并不证明接口稳定、实际可同时集成，也不自动满足原生 Claim/Host 限制。

### 3.6 进度、Closure 与变化重规划

DAG 节点数、PR 数或 Agent 数都不是交付成果。目标是在真实结果完成后收尾，禁止为证明努力而反复 Review/CI。上游需求改变时只查受影响的 Design/Task/测试证据，不重建整个 DAG；变更不得反向涂改已完成原始历史，当前版本需要新决议。

### 3.7 任务描述到执行 Pack

独立 Task 的可执行合同至少说明目标、source/current HEAD、已有 frozen requirement/architecture、允许写路径、真实依赖、受影响测试、完成证据、环境与禁止范围。任何 Agent 候选计划都不能自己生成有效 Claim 或强制 Tally 创建一套新的工作状态存储。

## 4. 可执行的 Decision Procedures

决策程序定义可复用的方法及终止条件，不创建第二套运行时状态机、审批权威或 Agent 调度器。

### DP-K04-01 · 最小工作图选择

**输入：** 用户目标、Product/L2 不确定性、真实工作/人/环境依赖

**步骤：**
1. 先按真实结果列出需要交付的用户/工程成果。
2. 分辨问题属于 P/A/I 哪层，而非先创建 Issue。
3. 评估可由一人有界完成、几个检查还是确实独立可调度。
4. 为每层选择 INLINE/WORKLIST/DAG，并对真实阻塞说明必须等待什么。
5. 列止损条件及不必做的工作，复用现有规范与 CI 证据。

**产物：** 阶段计划/节点必要性和有界停止标准

**失败/停止：** 真实权威/来源不足则只形成提案，不写入 native Task 图。

### DP-K04-02 · Task 原子性与并行评估

**输入：** 候选模块边界、API/seam、可改路径、测试/集成成本

**步骤：**
1. 每个候选 Task 写明可独立验收的用户或工程结果。
2. 检查 Contract/Tests/Code 是否应该由同一个 Writer 完成。
3. 根据交叉文件/生成产物/接口依赖修正并行组和合入顺序。
4. 比较拆分后额外 Review、CI、冲突解决成本与预计节省时间。
5. 保留必要最小集成 Task 和实际 blocked-by，不增加“装饰性”依赖。

**产物：** 合法拆分方案、写集、关系及合并验证计划

**失败/停止：** 若拆分使一个任务无法独立通过最低验收，需合并或调整 seam。

### DP-K04-03 · 受影响范围重规划

**输入：** 变更的需求/ADR/合同及旧任务和证据版本

**步骤：**
1. 定位最早变化的有权语义层。
2. 列出直接消费该来源的设计与 Task，再按实际依赖传播。
3. 复核仅受影响测试、接口及合并证据的当前性。
4. 保留无关旧工作成果并记录新的版本修订理由。

**产物：** 受影响节点的有界增量计划与历史引用

**失败/停止：** 禁止把旧历史任务直接改写为新版本的 PASS 或全部重新开工。

## 5. Tally 消费路径与跨模块接口

**主要 Workflow：** 各阶段按需 DAG-P / DAG-A / Implementation DAG-I

| 工作环节 | 读取的当前事实 | 本模块的输出 | 原有权威/禁止推断 |
| --- | --- | --- | --- |
| L1 | User Need/冲突/研究 | DAG-P 或 INLINE/Worklist | 不冻结 Product |
| L2 | 被接受的需求、架构未知 | DAG-A/试验依赖 | 不冻结 Architecture |
| L3 | 已准入的实施目标 | DAG-I/真实 Native BLOCKED_BY | 不自动签 Claim |
| 交付 | 现有 Task/Review/Host 状态 | 最小关键路径与影响重规划 | 不自动完成 Release |

**跨模块组合：** K01 供给 Need/Requirement，K02 供给设计合同，K03/K05 形成原子实施与测试，K07 提供多 Agent 角色/写集准则，K11 用于估计拆分协调成本。K09 变更时调用重规划而非整图重做。

## 6. Agent Skills（输入、输出和验证）

### SK-K04-01 · Phase Planner

- **调用时机：** 存在阶段不确定性或多项研究任务
- **最低输入：** 来源绑定的 Product/Design/Task 事实与真实需求
- **产出与格式：** 每层工作形态+真实节点和停止准则
- **自查及异常路线：** 没有不可替代前置则不能造 blocked-by
- **不能做：** 独立决定 Product/Architecture Freeze

### SK-K04-02 · Task DAG Designer

- **调用时机：** 已确认实现范围且有多 Task
- **最低输入：** Task Pack 候选、版本/写集、接口 seam、验证义务
- **产出与格式：** 验收单位、Owner、真实依赖、并行/串行理由
- **自查及异常路线：** 检查循环/虚假边/共享写冲突
- **不能做：** 把研究节点复用成源码 Task PASS

## 7. 端到端教学案例与故障反例

**情景：** 一个版本同时改 API 和 UI，并调整一个共享数据库模型。三个 Agent 希望并发推进。

**正确处理：**
1. 先确认真正的需求/设计是否清楚；若仅 API 字段合同未定，则形成一个小 L2 决策而非并行开工。
2. 定义明确的 API/状态合同和用户关键路径；把数据库模型迁移与 API 开发的真实依赖说明。
3. 若 UI 只需消费冻结的 Contract，可由第二 Agent 在不重叠写集上并行；共享迁移/生成物保留单 Writer。
4. 集成 Task 在两个实际分支成果都可用后验证真实组合与端到端行为。
5. 源头需求变化时只重新评估受影响接口、Task/测试，不为所有老证据重新审核。

**可以观察的正确性：** 每条真实 blocked-by 有必要的前置产物说明；并行无共享写冲突，集成行为可在当前源版本上验证。

**故意错误的候选：** 把“测试”“异常处理”“实现”“文档”各自开一个不能独立验收的 Task，要求十次 PR 合并；同时两个 Builder 写同一个迁移文件。

**变更条件后如何调整：** 若仅修改单一错误提示，不需要 P/A/I 各一个显式 DAG；直接 INLINE 并执行受影响检查。

## 8. 常见反模式与止损条件

1. **False Serial**：只因喜欢顺序流程就让 API 任务等待无关文档 Task
2. **False Parallel**：写集不重叠就当作协议/集成完全可并行
3. **Nested Authority**：在 Tally 私有工作图生成第二套 Claim 与 native Task 状态
4. **Unbounded Graph**：把每个 agent 推理步骤都提升为 Issue
5. **Over-validation**：已验无影响旧证据被逐任务要求再次跑完整 CI

## 9. 训练与知识资格验证案例

以下是**未来**测试/案例设计，不代表测试或知识资格已经完成。

| 案例 | 期望推断或行为 | 需要拒绝的结论 | 验证依据 |
| --- | --- | --- | --- |
| 小错别字修复 | INLINE，不建显式 DAG | 强制 3 层全套 Issue | 明确 Product/变更范围 |
| 新增含复杂权限流程 | L1 真实研究有依赖时 DAG-P | 将研究 PASS 当 Task PASS | L1 来源与需要澄清的权限 |
| 架构试验依赖合同 | DAG-A 记录设计工作先后 | 研究节点自动完成 Release | Architecture Demo 收据 |
| UI/API 并发+共享生成物 | 独立任务并行，共享文件单 Writer | 两个合法并发 Writer 改同一产物 | 写集与接口合同 |
| L2 仅一个接口变化 | 只重规划受影响 I 子图 | 重跑所有无关模块 | 当前 ADR/受影响 Task 引用 |

真实测量时先固定任务、输入、预期标准及基线，再比较直接 Agent 与 Tally 选中知识后的实际质量/修复/成本。不得用文档样例或图谱问答成绩替代实际编码效果；没有结果就标明 `UNKNOWN/NOT_RUN`。

## 附录 A · Agent 直接调用的工作示例（非正式 Wire Schema）

**教学输入：** 新功能有 API、UI 和共享 Schema 三类变更；两个 Agent 希望并行。
- 使用知识：AtomicConcern、BlockedBy、WriteSet、DAG-P/A/I，执行 DP-K04-01/02。
- 期望产物：API/Schema 的唯一 Owner、UI 消费的稳定合同、真实集成 Task，以及各阶段 `INLINE/WORKLIST/DAG` 选择理由。
- 反例核对：如果删掉某条 `BLOCKED_BY` 仍可合法执行后项，就不应将它设为硬阻塞。
- 停止与交接：建议图不制造 GitHub Native Dependency/Claim；接入正式 Task DAG 需现有 Owner 路径。
