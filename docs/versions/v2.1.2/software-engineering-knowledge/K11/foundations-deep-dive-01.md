## 1. 最低 Token 并不等于最低交付成本

对同一可检验 Goal，工程总成本至少包含开发时间、研究时间、测试、Reviewer、CI/Host、集成、返工、未来维护、故障风险与可能的客户损失。某些成本缺实际价格，必须记录 UNKNOWN 而不能造出精确财务数值。机会成本是被该路线延误/放弃的合法替代收益。

高风险不可逆数据迁移只有三行代码，也可能比普通长篇 UI 修改有更高验证需求。质量保证下限先由当前有权 Task/ADS/Host 决定，再考虑如何减少重复验证；不能用预计节省的 Token 数否决硬性安全/权限条件。

## 2. 比较方案要固定输入和成功定义

“一个 Agent”对比“八 Agent 并行”时，应固定任务、源码初始 HEAD、工具权限、可用模型、测试 Oracle、运行环境和观察窗口。记录每个方案的真正**合格交付结果**，不只记录完成了几个 Issue 或生成了多少代码。并行的收益是关键路径缩短，但共享写集、冲突解决、上下文加载和审核成本会抵消部分优势。

如果处理任务的难度/预算显著不等，不能把观测结果解释成 Agent 数量的因果效果。若选用相似但不相同的任务，应进行难度分层、交叉任务分配或谨慎限定结论，不直接推广到所有软件项目。

## 3. 实验设计：先声明可证伪的假设

示例假设：加入选定软件工程知识后，相同版本、相同权限下，合格修复率提高，且总交付时间没有不可接受增长。实验最小设计：
1. 预定义任务集：需求/架构/实现/测试/修复/交付的不同类型，包含负例和会触发 ASK/UNKNOWN 的输入。
2. 对照组：不提供新知识、但保持当前模型能力/工具权限和有效 ADS 约束；实验组仅增加**明确版本**的知识切片。
3. 同一验收：独立业务 Oracle、受影响真实测试、必要 Host/用户路径、Review，并记录 false PASS 和不可用建议。
4. 记录执行事实：源 SHA、知识 ID/版本、选用理由、环境/工具调用、失败、返工和完成时间；不搜集私有模型 Chain-of-Thought。
5. 统计与解释：报告样本数、成功率及不确定性（必要时置信区间）、任务类型、不可比案例、负收益、未观测项和版本限制。

若仅在六条合成问答里表现良好，只能说教学选择流程符合预期，**不能声称真实软件工程生产率提高**。

## 4. 指标要对应决策而不是提供漂亮仪表盘

| 决策问题 | 可能的观测指标 | 典型误用 |
| --- | --- | --- |
| 代码能否正确交付？ | 独立 Oracle 通过率、缺陷与回归 | 用生成 LOC 替代正确性 |
| 开发是否更快？ | 合格完成的端到端墙钟、返工 | 只数 Agent 并行数量 |
| 维护是否改善？ | 后续变更成本、架构耦合/缺陷 | 用代码行少就称“维护性好” |
| 流程是否稳定？ | 实际交付/失败恢复分布 | 把跨组织 DORA 相关性当本地因果 |
| 知识是否适用？ | 选用正确率、UNKNOWN/误用率 | 来源链接数等于知识可信度 |
| 成本是否下降？ | 完成质量约束后的真实资源/人工/CI 总成本 | 只统计 Token 金额 |

SPACE 与 DORA 提供多维观察框架，并非允许从某个数字反推出每位开发者的价值，也不是 Tally 自动增加强制 KPI 的理由。

## 5. 真实效用反馈怎样回写系统知识

失败必须定位到：来源过期、概念解释错误、跨模块关系错误、策略选用条件缺失、执行实现问题，还是评估环境不一致。对应修补 Kxx 的原始知识与适用条件，再选择必要的受影响正反例；单次 Agent 自报不能变成强制 Rule。

**继续深化的投资原则**：保留完整的 165 点学科基础；对严重错误、跨模块复用、真实反例或基础理论缺口投入更深研究；选中生产 Consumer 的一小部分再进行精确 Clause/Source/Host 资格，不因未部署而删除其余专业知识。
