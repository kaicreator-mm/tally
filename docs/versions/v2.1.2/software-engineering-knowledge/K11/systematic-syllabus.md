## 一、知识本体、工程推理与能力归属

软件工程经济学、度量与实证决策 不仅是若干执行提示词。它必须提供专业原理与假设、对真实输入的条件性判断、可反证的错误做法、跨学科连接与明确资格。**当前唯一知识 Owner：价值/成本/风险/可逆性、工程过程度量、方案取舍和反馈效果的横向专业知识拥有者**。下面的主题是完整课程的骨架，实际深度 Topic 是对必要问题的解释与实践投影；现有 DP/Skill/Case/Source 仍为可被引用的专项资料，不强制复制 15 次。

## 1. 工程经济与价值目标

### K11.F1.1 — 目标、用户价值与效用

**专业知识及适用机制**：生产率必须以真实交付目标和质量结果为主；Token、代码行数和 PR 数只是活动量/成本，不能代理用户价值。

**错误外推/反例**：为了消耗剩余 Agent 配额新建一堆并行任务。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K11.F1.2 — 总成本与生命周期

**专业知识及适用机制**：项目成本包含需求/设计、代码、Build/CI、审查、集成、运行、维护、风险和债务利息，不能只比较初次实现价格。

**错误外推/反例**：开源库下载免费就认为未来维护成本为零。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K11.F1.3 — 机会成本与可逆性

**专业知识及适用机制**：考虑不实施、局部修复、渐进替换、自建框架的机会收益、失败后果和是否可撤销。

**错误外推/反例**：在需求不确定时先执行不可逆数据迁移。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 2. 工程估算与不确定性

### K11.F2.1 — 估算不是精确承诺

**专业知识及适用机制**：用范围、类比与真实历史样本估计工期/成本，区分 OBSERVED/ESTIMATED/UNKNOWN，避免虚构毫秒级准确性。

**错误外推/反例**：没有测量就承诺减少构建耗时 83%。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K11.F2.2 — 复杂度与依赖成本

**专业知识及适用机制**：不同任务可独立实现程度、共享依赖、Review/CI 排队和边界冲突是总周期的主要因素。

**错误外推/反例**：并行 Builder 数越多就必定越快。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K11.F2.3 — 研究价值与停止规则

**专业知识及适用机制**：一次 Demo/实验若能改变方案选择值得做，否则已有信息足够时及时停止，避免重复审核和无收益的 CI。

**错误外推/反例**：因追求完美治理文档持续阻止真正用户交付。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 3. 风险和工程保证底线

### K11.F3.1 — 风险识别与后果强度

**专业知识及适用机制**：失败概率、可检测性、用户/数据/权限影响和不可逆性一起决定测试与架构保证；修改行数小不等于风险小。

**错误外推/反例**：三行数据删除不测升级/恢复。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K11.F3.2 — 质量保证下限

**专业知识及适用机制**：沿用真实 Product/ADS/Task/独立 Review/Host 要求，已满足的可复用，必须特定平台证明的不能从 Mock 替换。

**错误外推/反例**：为了少跑一次 CI 直接豁免真实 Device Gate。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K11.F3.3 — 风险缓解选项

**专业知识及适用机制**：比较规避/减轻/转移/接受风险的可观察成本与退出条件，不把单一标准流程强加所有任务。

**错误外推/反例**：所有小型内部脚本都建立完整企业审计体系。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 4. 度量与实证软件工程

### K11.F4.1 — 信息需求驱动的度量

**专业知识及适用机制**：先明确要回答何种决策：用户正确性/维护性/交付稳定性/成本，再选真实可观察指标和适用时间窗。

**错误外推/反例**：只展示 PR 数和开发者完成行数。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K11.F4.2 — SPACE / DORA 的解释边界

**专业知识及适用机制**：多维评估体验、实际绩效、活动、协作和效率，交付效能研究是观察关系，不自动证明任何工具带来因果收益。

**错误外推/反例**：引用跨组织统计就宣称本 Agent 提效 200%。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K11.F4.3 — 实验和对照设计

**专业知识及适用机制**：同任务/同工具权限/预算与合格 Oracle 的基线和候选策略比较，保留失败、样本偏差、复现性与负收益。

**错误外推/反例**：给知识辅助组更强模型再比对另一组弱模型的成果。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 5. 治理简化和知识进化经济学

### K11.F5.1 — 最小必要流程

**专业知识及适用机制**：选择能真实降低风险/返工的检查，避免为绿色徽章重复运行等价 CI 或无材料性新证据的 Review。

**错误外推/反例**：一次 Markdown 注释变更重跑整个端到端部署矩阵。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K11.F5.2 — 多 Agent 协作经济学

**专业知识及适用机制**：比较并行减少的等待与额外上下文、合并、Review、重试成本；有真实独立任务时才扩大 Agent。

**错误外推/反例**：Agent 多输出文档便认为业务速度提升。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K11.F5.3 — 知识维护/经验化投资

**专业知识及适用机制**：研究/来源资格优先真实会被调用或能减少严重错误的知识，但系统学科基础也需要完整覆盖；两者不是互斥。

**错误外推/反例**：只维护被精选的四条 Claim，把其它软件工程基础从知识库删掉。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 六、知识复用、专业反例与跨模块推理

**所有权**：价值/成本/风险/可逆性、工程过程度量、方案取舍和反馈效果的横向专业知识拥有者。K11 与全部模块联动，但不拥有它们的业务或实现权威；K04 负责任务组织，K07 负责多 Agent 交接，K05/K08 提供实际质量和交付证据。

**专业教学情境**：单 Writer vs 八 Agent 并行的总价值。对同一个业务目标比较真正完成时间、问题正确性、合并冲突、审查、CI/Host 和返工成本；如果共享 Schema 主导关键路径就优先一个合法 Writer。

**必须识别的反模式**：用 Agent 数量和 Token 消耗衡量成功，却完全没有用户任务实际完成证据。

**最小推理闭包**：Goal 与真实事实 → 本课程序列中的 Concept/前提 → Applicable/Excluded/UNKNOWN 判定 → [Decision Procedure](engineering-methods.md)/[Skill](agent-skills.md)/[Case](casebook.md) → 可观察 Oracle 与 STOP → 未来只有合法 Agent/Host/CI 真实运行时才得到相应验证结果。单独的系统课程文章永远不授予生产执行权。

## 七、从完整知识库继续增长的原则

- **系统完整性**：现有 15 个知识点为 5 个专业知识群的概念基础，可继续增加算法、理论/实证研究、不同规模/环境反例和相邻领域关联，而不是等待生产任务才允许编写知识。
- **实际使用深度**：优先把多次遇到的误判、复杂取舍和关键质量问题深化成独立 Topic，既有 Topic 通过 [README](README.md) 选择，不强制为每点创建独立文件/Issue。
- **专业准确性**：当某项资料仅列于来源目录或不能取得精确原文时，保持 `SOURCE_CANDIDATE` 并标明不能外推；后续选定 Task 需要时只审实际用到的主张与负例。
- **服务边界**：Tally 的选定领域资产可被未来 DomainHarness selected Element Content/Function 消费，但编译/运行/授权/反馈仍归 [Harness 边界](../domain-harness-consumption.md) 及原有 GitHub/Host/Release Owner；不创设第二知识 Runtime。
