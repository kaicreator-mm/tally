# K11 深层专业知识：如何评价知识辅助 Agent 的真实工程价值

> [K11 系统课程](systematic-syllabus.md) · [第一卷：经济与合理对照](foundations-deep-dive-01.md) · [第二卷：实验设计与统计](foundations-deep-dive-02.md)
>
> **R5 STUDY_DESIGN_CANDIDATE / CONTROLLED_EXPERIMENT_NOT_RUN / KNOWLEDGE_SERVICE_NOT_CONNECTED。** 这份知识解释怎样识别因果、测量真实收益和报告负收益；不是新设置的 Release Gate，也未获得真实 Agent 系统改进的实验证据。

## 一、研究问题必须明确干预变量

宽泛的声称“软件工程知识库使 Agent 更强”没有可反驳的操作定义。首先定义单位：Task、修复的缺陷、受支持的 User Journey 或发布的 Artifact。然后定义干预：同一个 Agent/模型/工具权限/预算与任务输入下，**是否提供当前相关且版本正确的领域知识**。主要结局可以是材料正确性（受权 Rule + 独立 Oracle）、成功交付比例、返工量、真实端到端耗时与总资源成本。

对照应同时保护质量底线：一个更快但未阻止跨租户写入或重复付款的实现不能通过“省时 35%”获得合法替代资格。

若实验组同时更换模型、扩大预算、额外人工 Reviewer 或更换更简单的任务，那么观察到的成功率差异不能唯一归因于知识库。这是**混杂因素（confounder）**而不是“不够真实”；可以进行观察性研究，但要诚实标识因果推断的弱点。

## 二、三个与基础工程任务相符的评估单元

| 任务类别 | 精确输入 | 主要结果 | 反例要求 |
| --- | --- | --- | --- |
| 业务规则冲突 | 同一 Goal、两个作用域不同的政策、历史 FAQ | 是否识别同条件真假冲突与合法 Owner | 不能猜测未授权政策 |
| 测试假阳性 | 同一 Git SHA、测试 globs 缺失、错误 Golden | 是否发现材料 NOT_RUN 而非 CI 绿 | 不允许用旧 Mock 自报 E2E |
| 恢复性实现 | 同一初始状态、ACK 丢失的支付 Job | 是否识别 UNKNOWN_EFFECT 并提出安全边界 | 无远端幂等合同时不能直接重试 |

这三类覆盖了“知道原理”“在复杂输入中选择方法”和“承认缺少现实证据”三个不同能力；若模型只回答概念测验正确，尚不能声称能安全交付任务。评价应同时报告**拒绝做越权推断的能力**，而非只统计响应长度和最终代码量。

## 三、如何组织最小可信对照而不虚构统计结论

一种候选设计（需要以后有合法试验方能实施）：
1. 预先冻结同一组 Task 输入、真实项目来源 SHA、可供调用的工具与权限，确保评价 Oracle **不由同一 Agent 临时写出**。
2. 将任务按领域与难度分层，尽量随机或匹配分配有知识/无知识条件，避免先在一组任务试到会了再换条件。
3. 若允许重复实验，记录模型随机性、任务顺序、环境与任何中断、请求预算、失败/未运行状态；不能剔除困难任务后才报告“完成率”。
4. **预先指定对所有被分配任务（all assigned / intention-to-treat 风格）计算的主要结局**：独立 Oracle 的质量合格数/分母、按任务计的总墙钟（含失败/超时/人工接管）、模型/CI/审查/返工资源与成本、单位总体成本产出的质量合格交付；对失败、未完成、拒绝及 UNKNOWN 保留原分母与各类代价，不删去未通过任务。对于无法定义有意义完成时间的失败，预先选定观察窗口和删失/超时规则，不能事后只留成功任务的时长。
5. 对跨 Agent 编排，分别报告单任务成本与整体交付墙钟；并行 Worker 数增加但冲突/整合成本也会增加，不能只看第一个 Worker 的完成时间。

**重要因果陷阱：事后只看成功任务的延迟**。是否成功/达到质量底线本身可能受知识干预影响；如果实验组和对照组都删去失败任务，再比较剩余样本的平均时长，即使原先分配是随机的，也可能发生 post-treatment selection / collider bias。**成功任务条件下的时长只能作为描述性次要结果**，需同时报告成功条件、样本比例与每组分母，不能直接解释为面向全部任务的因果效率提升。对所有分配任务的整体质量-成本-时间分布与质量合格交付/总资源更能代表实际工程价值，但具体估计方法仍取决于预注册目标和任务时限。

**不应该把候选试验流程直接写成所有 GitHub PR 的新强制 Gate**。只有实际 Product/Task Owner 选定范围后，才有必要执行真正对照。

## 四、样本量与不确定性：直观例子

假设 10 个任务中知识组 8 个正确，对照组 6 个正确。样本观察成功率分别为 80% 和 60%，差异是**20 个百分点**；两组任务如果不一样、工具或预算不同，甚至不能称为受控比较。即使分组严格随机，这 10+10 的样本通常不足以得出稳定的普遍提效结论。不能把成功率“提高 33%”写成因果事实，也不能在没有估计不确定性的情况下声称将持续复制。

跨多个模块评价时，要注意同一个大型项目拆成多个 Task 会产生高度相关样本，不能把来自同一 Bug 的十个小 Task 当作十个独立实验复制。若只保留成功的任务，还会有幸存者偏差。应如实报告分母、成功定义、失败/UNKNOWN、抽样规则、结局分布和可用时的区间估计。

DORA/SPACE 可以提供组织层和开发者体验维度的研究背景，但把团队/组织调查相关性直接当作某个 Tally Agent 的个人性能因果结论，是典型的层级混淆。

## 五、成本模型应包含后续维护负担

定义候选 `TotalEngineeringCost = model/tool/CI cost + human review + integration + rework + defect recovery + knowledge maintenance`，其中变量若无法观测就应明确未知/区间。知识检索在某些任务上可能增加上下文和推断成本但没有提升正确性，负收益不应被删除；某些极低频高严重度错误的防止收益很大，却不能仅凭一轮没有事故就精确折算为货币。

举例：A 方案减少当前评审 10 分钟，却每次旧 HEAD 变化都要求重复全量复审；B 方案首次多花 5 分钟明确影响边界，使后续变更仅增量验证。若未观测未来改动次数和错误率，不能断言 B 的净现值必然更高；可给出不同次数/风险情景下的转折区间。

## 六、经验化的入选与退出

一个新经验建议从“观察到失败”开始，而不是从“在某个 LLM 回答中被提过”开始。最小科学闭包是：

`Symptom/Task context -> hypothesis -> differentiating observation -> corrected mechanism -> falsifying counterexample -> applicability -> candidate knowledge`。

只有足够可复现且跨任务可迁移的知识才值得固化为通用方法；若只是某仓库的配置值，保持为项目事实；若涉及正式政策/源资格，必须由有权 Owner 处理。经验过时或出现反例时，记录失效范围而非用“模型从现在起永远遵循”掩盖来源变化。

**停止规则**：现有正确性材料已充分且新研究不会改变交付决定时停止额外研究；新研究暴露关键错误时按真实项目缺陷范围恢复必要修正与验证。不能把每个定性新见解都转换成永续的后台 Agent 任务。
