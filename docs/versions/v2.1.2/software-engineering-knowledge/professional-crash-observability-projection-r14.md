## 1. 由真实实验到可检验的问题，不把关联升格为因果

R3 的 **A=ADS-only、B=7段 Bulk@S1、C=同7段 Staged@S2/S4** 三组各只运行一次，原始源码包/投放字节/隐藏 QA 已由不同会话 Reviewer 复算。H0 是失败的阴性对照，A/B/C 首次冻结版本全部 **12/12**；一次性总体 QA 指标完全饱和。R3 因而**不能证明**增加知识或改变时机改善首次 QA，亦不能由 B 的较低 Token 认定 Bulk 普遍经济。

独立源码轨迹同时证实：A 在 S2 提出 `COMMITTED|PREPARED|SWITCHED` 三阶段提交记录，其中 `SWITCHED` 在真实写入顺序下根本无法持久表示；S4 红色测试暴露这一错误，随后 A 以 `PENDING` + 源/目标摘要证据修改架构，并在首次 S5 冻结前通过测试。B、C 在首次 L2 方案中就使用摘要证据与保守的 `UNKNOWN` 处理。**这是具体文档/设计/修复轨迹的关联，是有价值的专业假说，不是实验已隔离出来的知识因果收益。** #539 的六项 P2（单次、单协调者、Token 独立计量不足、六个未测面、ADS pin 可恢复性、归因上限）必须原样保留。

此处的问题不是「在所有系统强制增加 Commit Record」，而是：**当需求包含可恢复持久写入时，如何在 L2 证明设计所描述的每个状态都能被真实介质表示，且崩溃后可以仅凭权威事实作出不越权的判定？**

## 2. 触发与不适用：先选择问题，再选择小知识片段

| 输入问题 | 应确认的事实 | 缺失时的结果 |
| --- | --- | --- |
| 有真实持久化状态变更吗？ | Owner、Scope、合法业务身份与数据来源、可观察提交语义 | 纯只读、无持久状态任务：本投影 `NOT_APPLICABLE` |
| 必须应对什么故障？ | 进程崩溃、并发、重启、ACK 丢失、掉电分别是否在合同内 | 不能把进程崩溃测试扩写为掉电保证 |
| 谁能判断已提交？ | 受权状态 Owner、事务/文件系统的原子性与耐久保证、结果查询能力 | 缺失可靠证据：`UNKNOWN`、STOP 或请求有权澄清 |
| 数据来源和目标能区分吗？ | 原始摘要、目标摘要、身份/版本，比较是否基于真实保存状态 | 不能仅凭“文件存在/rename 返回”宣称已提交 |
| 存在外部 Effect 吗？ | Provider 是否允许幂等、只读查询、补偿或确认失败 | 必须另引 [K10 UNKNOWN_EFFECT](K10/topics/UNKNOWN_EFFECT.md)，不得用本地事务冒充全局事务 |
| 涉及旧版本兼容/敏感配置迁移吗？ | 历史输入、语义保持、备份/回滚与密钥 Owner | 条件引用 [K09 演进](K09/advanced-configuration-migration-and-evidence-impact-closure.md)，不无条件注入其整章 |
| 是何种具体介质？ | 原生文件/SQLite/其他 DB；Windows/POSIX、本地/网络文件系统、sync 设置 | 不能默认 `wx`/rename/SQLite 对所有环境有同一保证 |

**停止**：无法指明有权需求、提交/ACK 语义或介质能力时，保留待确认问题；严禁 Agent 用知识卡替代用户或产品 Owner 授权。已发布 ADS v4.19.0 的准入与 QA 规则照常适用；本投影不增加必需 Gate。

## 3. L2 六个必须能回答的设计问题（候选决策程序，不是执行协议）

1. **不变量与范围**：什么必须保持，谁是状态 Owner？例如 `scope+project+version+logicalId` 唯一且失败不覆盖原始 bytes；不得由目标路径恰好相同推断合法身份。
2. **唯一可观察的提交合同**：对外 `success` 表示哪一步已被可靠证实？是逻辑 Commit、事务结束、持久落盘，还是只接受排队？明确 `UNKNOWN` 是否可出现和由谁解释。
3. **持久状态可实现性**：画出所选方案的**实际写入序列**（并非概念状态机），列每个命名阶段的持久介质证据。若 `SWITCHED` 仅能在数据切换之后写入 Commit 文件，那么切换与写 Commit 之间的崩溃无法观察到这个阶段；以一个“计划记录”命名它并不会让它耐久。
4. **按切点恢复**：在 Intent 保存前/后、数据发布前/后、Commit 事实保存前/后、ACK 发出前/后每处断开后，只依据持久 facts 判定已提交、未提交、`UNKNOWN`、损坏；不能把缺失事件猜成「没有发生」。
5. **竞争和资源**：多写入者如何获得权威顺序/Scope/Owner？EEXIST 只说明抢创建时目标存在，不证明记录完成；临时资源必须有 Owner 且只清理自身文件。特定存储原语需有其可验证的适用条件。
6. **最小反驳实验**：指定一个若设计错误就必定失败的负例，例如让提交记录声称已经 `SWITCHED`，但选定崩溃点只保留了前一状态。由 K05 定义可区分 Oracle、执行环境、测试发现/退出与尚未覆盖的故障模型。

### 示例：仅以持久事实分类的一张推理表

*下表是教学性质的假设模型，必须在真实选择的存储/事务/权限合同下重新论证，不是所有文件系统或产品通用的状态机。*

| 崩溃/观察切点 | 允许的持久观察 | 可以得出的结论 | 必须拒绝的捷径 |
| --- | --- | --- | --- |
| Intent 写入之前 | 有权来源仍完整、无本次有权 Intent/目标变更，且无并发未知写入 | 仅在独占和完整事实前提下可判 `NOT_STARTED` | 文件缺失 ⇒ “全局无副作用” |
| Intent 已存，目标未切换 | Intent 有身份/源摘要/目标摘要；live 仍匹配源摘要 | 可以识别本次尝试未到指定提交点，是否自动继续取决于合同 | Intent 存在 ⇒ `COMMITTED` |
| 目标可能已切换，但 Commit 证据未可确定 | live 可能匹配目标摘要，Intent 仍 `PENDING` | 需要本方案授权的 readback/recovery 规则；不能仅凭逻辑状态推断 ACK 成功，必要时 `UNKNOWN` | rename 成功 ⇒ 事务 Commit/掉电耐久 |
| 有可验证 Commit 事实但 ACK 丢失 | Commit 身份+版本+摘要与 live 在选定故障模型下吻合 | 仅在承诺的可靠持久范围内可回读为已提交 | 收到超时 ⇒ 重新制造相同外部 Effect |
| 摘要/身份不一致、半成品或多写入竞争 | 多个证据之间矛盾或不能解释 | `CORRUPT/CONFLICT/UNKNOWN` 按已授权合同区分；保留原始 bytes | 删除异常文件、无限重试直到绿色 |

如果使用 **SQLite/事务数据库**，可以将提交线性化点放到数据库事务（结合具体 journaling / durability 配置），但仍须验证事务外文件或外部 Effect；如果使用**多个普通文件**，必须单独设计及测试跨文件中断后的协议，不得称一个 `rename` 为跨文件事务。对于同步刷盘、目录写入、Windows 共享句柄与网络文件系统限制，必须验证目标环境，无法验证时不扩大保证。更多机制来源于 [K02 原理](K02/advanced-architecture-invariants-and-failure-tradeoffs.md) 与 [K03 R13 原理](K03/advanced-concurrent-local-file-write-convergence-r13.md)，而不是本表的推断。

## 4. K05 用反例验证 L2 决策，而非仅增加单元测试数

对于每个有权不变量 `I`，要同时冻结一个**故障假说/错误候选 M**，构造一个与合格设计可区分的最小输入 `X`，记录该 `X` 的真实执行与直接断言；避免从“测试命名叫 crash”推出已经发生真实 OS 进程 Kill。

| 设计错误形态（教学） | 最小会使错误暴露的 Oracle | 证据边界 |
| --- | --- | --- |
| 声称可持久的阶段并不能被写入 | 模拟切断实际写序列，重启只读检查持久事实/分类 | 模拟 crash≠真实 OS Kill/掉电 |
| Intent/Live/Commit 相互矛盾 | 精确前后文件摘要、合法状态及返回错误码，不只观察清理异常 | 不能由 cleanup ENOTEMPTY 推导业务失败原因 |
| EEXIST 被当成 Commit | 第二进程在第一个写了一半时回读，检查未完成数据不会被判成功 | Promise 并发≠跨进程独占 |
| 用迁移流程覆盖未验证来源 | 未知/损坏版本输入原始 bytes 不变，没有“成功”标志 | 明确真实旧版输入/升级窗口 |
| 断言未被 Runner 选中 | 输出真实 discovery/executed IDs/EXIT 和负例信号 | 12/12 不能推出未选中的风险已验证 |

复用 [K05 R13 验证学理与 Oracle 账本](K05/advanced-invariant-derived-discriminating-oracles-r13.md)，每个 Requirement 分开标记 `TESTED/PARTIAL/NOT_INDEPENDENTLY_VERIFIED`。R3 #539 的六个声明未测边界（真实 OS kill、typed API downgrade、已推进项目再导入、独立 v1→v2、具体 category 规则、idle/CLI recover）**继续未验证**，不是 R14 补一篇文档就转 PASS。

### 候选知识能给 Agent 带来什么？

输入：有权 Requirement/Scope、选定持久方案、目标环境、未知故障范围；输出：**一份可反驳的 L2 ADR**（每个关键持久状态的真实证据、写序列、切点分类、备选方案与停止点），再交给 K03 细化以及 K05 验证。观察指标可以是 **首次 L2 冻结的材料性状态错误**，但必须在 R4 *运行之前* 由独立 Reviewer 固定评分规则，不能依照 R3 的 A 组错误直接事后“定制获胜指标”。
