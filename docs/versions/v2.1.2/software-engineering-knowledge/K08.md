# K08 — 构建、集成与交付 / Build, Integration & Delivery

> [v2.1.2 #521](https://github.com/kaicreator-mm/tally/issues/521) · 本模块 [#529](https://github.com/kaicreator-mm/tally/issues/529) · [总目录](README.md)。`DETAILED_CONTENT_CANDIDATE / NOT_SOURCE_QUALIFIED / NO_RUNTIME_ACTIVATION`。ADS 是 Agent 软件开发实验/实践和已发布工程规范来源，Tally 在软件工程 Workflow 中消费选定、合格的知识。示例除有真实来源外均为教学情景，非真实测试结果。

## 1. 目标、适用条件、边界

教 Agent 把源码成果变成真正能被运行和验证的版本。理解安装依赖、构建、测试、CI Provider、合并、打包、环境/配置和交付的区别，用**一次最小充分的真实工程链路**证明结果，而不是靠 PR/CI 数量证明质量。实现阶段与打包/发布阶段的权威必须区分。

**触发条件：** 有可集成的源码候选、新公共接口/模块、构建配置或 CI 调整、真实应用/安装包的用户验收、发布及热修复。

**不承担：** 不构建通用 CI 平台、额外发布审批系统或软件供应链安全专项；已适用的项目发布质量、权限/保密规则仍有效。本版本暂不单独建设代码库逆向分析、软件安全与供应链知识专项；已有必要源码理解、权限和基本安全规范仍按实际 Task 生效。

## 2. 概念、语义及常见混淆

| 概念 | 工程语义 | 容易出现的错误 |
| --- | --- | --- |
| Build / Compile | 从当前源与工具链形成可运行/可验证的目标产物 | 安装依赖成功便声称构建成功 |
| Dependency/Lockfile | 项目声明的依赖来源/版本及工具链约束 | 用开发机上存在的 Node 版本强制所有项目升级 |
| CI Provider | 实际执行命令的 Woodpecker/GitHub 等环境及其日志/状态 | 本地测试 PASS 冒充 Provider CI SUCCESS |
| Selected Consumer Path | 生产/测试入口真正调用了变更后的公开能力 | 模块文件存在就认为功能已生效 |
| Integration | 多个模块与合同在同一真实版本下运行并通过必要验证 | 各分支单独成功就认为最终组合正确 |
| Artifact Identity | 制品摘要、源/测试 SHA、目标平台和配置版本 | 用可变 latest 标签证明不可变交付内容 |
| Install/Startup | 用户真实启动、安装、配置及失败行为 | 只看本机开发命令就声称首次运行可用 |
| Release Qualification | 发布证据和资格由现有所有者受控决定 | 合并 PR 就自动产生正式 Release |
| Pipeline Efficiency | 最小必要 clone/步骤/验证与缓存策略 | 每个 workflow 都重复完整 clone 而无真实需要 |

此处是领域知识概念，而非要求另外建立一套消息数据库、Task 状态机或通用 Schema；必要时可映射到现有 Tally Engineering Business/Domain Data 结构。

## 3. 知识正文：分析方法与工程权衡

### 3.1 区分安装、构建、测试和发布

依赖安装检验 package resolution，TypeScript/编译器检验语法/类型，测试检验行为，构建/packaging 检验产物，真实 Host/用户路径检验运行；各自回答不同问题。一个 pipeline 可能安装全部成功却在 tsc 阶段失败，说明该 CI 没有完成 Build。不要省略真实失败点，只报告总 exit code。

### 3.2 工具链与版本适配

Node/Python/Go 等版本依据项目当前 manifest、构建特性与实际已验证平台确定，不能以 Agent 主机的工具链当作产品硬要求。按现有锁文件、包管理器和目标平台复现依赖；若没有用到某个新 Runtime 特性，不能无故把版本下限抬高。可缓存第三方依赖，但必须区分缓存正确性与可复现证据。

### 3.3 CI 最小充分设计

将工作流拆成必要的语法/类型、受影响测试、真实接口/组合、制品发布等层，只有真实差异/风险要求才额外构建复杂矩阵。一次 clone/checkout exact SHA 在同一 pipeline 中尽量复用，在真正需要隔离的环境才单独获取源码。稀疏检出/部分 clone 要遵守相关文件和构建脚本的依赖闭包，不能因文档无关就误删测试必须的数据。

### 3.4 集成合同与真实入口

从已确认的模块 API/Schema/状态 Owner 检查新旧版本与真实消费者是否一致。合并多个 PR 时不应假定各自已通过单元测试即集成成功；当前集成 HEAD 的真实 UI/API/Service/DB/CLI/安装包所使用的入口必须调用新实现。对改变共享接口的任务，选择必要的合同回归和最小真实集成路径。

### 3.5 制品、安装与配置的实际行为

可交付目标可能是 desktop binary/installer、容器镜像、Web bundle 或 CLI 分发包，必须明确目标平台、版本及完整起步路径。适合交互的应用应允许启动后在应用中配置，CLI/后台服务/容器可能使用环境或启动参数；不能对所有产品机械要求同样初始化 UI。未获得真实安装/运行环境时保留对应资格 NOT_RUN。

### 3.6 变更/合并/发布的权威分离

代码候选有 Git SHA；执行 Build/Test 有对应 Tested SHA；CI Provider 对其真实命令负责；独立 Review 审核准确 Diff；Release Owner 根据适用证据选择发布。某项 PASS 不可自动提升其他层资格。发布后若发现失败，事件与修复、回滚和新 Candidate 都应可追溯，不能修改历史 PASS 的语义。

### 3.7 交付效率与失败归因

无关格式/文档变更不应强制重跑昂贵 Host/E2E，但真正受影响的行为和发布平台仍要验。失败需要记录首个实际异常步骤、命令、退出码、具体文件/行号及可操作诊断；区分 Provider 网络拉取、安装依赖、代码编译和用户安装错误，避免每次失败都完整重新 clone 并重做旧验证。

## 4. Decision Procedures（Agent 可执行的决策方法）

### DP-K08-01：最小有效构建/CI 路线

**输入：** 项目真实 package/build 配置、合法源码 SHA、目标环境和改动类型

**步骤：**
1. 确认 manifest/lock/toolchain 和实际构建入口，选择有效目标平台。
2. 判断受影响源文件、测试和公共合同的依赖闭包。
3. 先安排语法/类型/受影响测试，确有必要时执行集成/真实 Host/打包。
4. 审查 CI workflow 能否复用单次 checkout/缓存且不会漏依赖。
5. 对所选命令记录准确执行环境、SHA、exit code、首个失败点。

**输出：** 实际运行矩阵、跳过/复用理由与后续交付条件

**停机与边界：** 没有运行的 Provider/Host 证据保留 NOT_RUN，不因本地命令成功写 SUCCESS。

### DP-K08-02：多模块集成与变更收敛

**输入：** 目标 base/PR HEAD、合同/写集/依赖和原始测试收据

**步骤：**
1. 核对目标基础版本和最新候选，识别互相冲突的接口或生成产物。
2. 把正确已通过的相同源码/测试证据复用到受影响范围。
3. 对新组合必须测试的公共 seam 选择真正的 Consumer/Host。
4. 确认合并后当前源和生成产物版本与测试/安装版本一致。

**输出：** 集成版本、相应验证计划、缺口及需要修复的范围

**停机与边界：** 有实际兼容冲突/目标环境缺失时不合并为“已验证交付”。

### DP-K08-03：发布和首次启动验收

**输入：** 可打包的精确源码、目标平台、安装配置和授权 Release 规则

**步骤：**
1. 生成可定位的安装包/镜像/CLI 制品，绑定来源、平台与版本。
2. 按用户实际首次运行流程验证配置、异常和必要功能。
3. 核对所需 QA、审查、CI/Host 结果及发布元数据。
4. 交给正确 Release Owner 形成真实发行事实，追踪残余未验证范围。

**输出：** 交付资格清单与实际可用制品证据

**停机与边界：** Candidate 包存在不等于 GitHub Release 创建或用户安装成功。

这些步骤为可引用的决策方法，不是第二个调度器、权限授权或 Review/Release PASS。

## 6. Agent Skills：输入、输出、验证、失败路由

### SK-K08-01：Build & CI Planner

- **触发**：任务已有合法源候选和当前工具链
- **需要的事实输入**：manifest/lock/build scripts、changed paths、需要验证的合同
- **产生的工件或结论**：一次最小有效命令及平台矩阵、测试复用理由和执行输出要求
- **自我核对**：检查语法/测试确实选择目标源，真实 Provider/Host 条件可核实
- **拒绝/升级**：不得将 Agent 主机版本当作通用项目要求

### SK-K08-02：Integration & Artifact Verifier

- **触发**：多个模块合并或用户可运行制品需要证明
- **需要的事实输入**：当前集成 HEAD、真实调用入口、模块合同、制品摘要和目标平台
- **产生的工件或结论**：核心调用路径/安装/启动/失败的执行与回读收据
- **自我核对**：确认测试、运行和制品指向同一实际版本
- **拒绝/升级**：不能用 Mock 或源文件存在来说明用户功能生效

### SK-K08-03：Release Evidence Composer

- **触发**：有实际 Release Candidate 和资格材料
- **需要的事实输入**：目标版本、构建/测试/Host/Review/安装证据、残余 UNKNOWN
- **产生的工件或结论**：可审阅的 Release 证据和未完成条件列表
- **自我核对**：不将未知条件冒充满足，不代签发布
- **拒绝/升级**：不得自动发 Tag/Release 或把 PR Merge 当正式发行

## 7. 贯穿示例：正常路线、故意错误路线和适用差异

**情景（教学模拟）：** 一个 TypeScript 项目的 Woodpecker pipeline 含多个 workflow，每个都重新完整 clone；npm install 成功后某共享包 tsc 报错，最终用户还未收到构建好的桌面安装包。

**正确推进：**
1. 识别同一 pipeline 中能否复用一次 exact SHA checkout 及依赖闭包，在真实隔离条件不允许时才保留必要重复 clone。
2. 分清安装成功、tsc 失败、目标受影响测试未执行、桌面包未生成四种不同状态。
3. 依据编译失败文件/类型错误交 K06 局部根因修复，而不是更新所有锁文件。
4. 在新 HEAD 上执行所需类型检查、受影响测试和打包构建，记录真正的 Provider CI 结果。
5. 有权限和环境时运行安装包首次启动/配置与关键用户路径，否则清楚报 Host/Release 未完成。

**有效的验收证据：** 选定流程真实使用正确源 SHA、相关 TypeScript 构建和测试通过、可交付制品在目标平台运行且来源可追溯。

**错误实现/决策：** 流水线所有 clone 都执行成功就宣称优化完成；安装依赖绿灯直接合并 Release；没有发布包也报告正式 MVP 已可下载。

**条件变化如何影响选择：** 若每个 workflow 确实运行在相互隔离且不能安全共享工作区的远程 Host，重复 clone 的优化必须在提供者能力约束内实施，不能假设单个 Docker Volume 总是共享。

## 8. 反例库与适用性边界

1. **Clone Explosion**：默认每个工作流都重新完整拉无关源码而无必要
2. **Install=Build**：成功安装包依赖就跳过实际类型/源码构建
3. **Mock=Installed**：测试环境模拟启动成功就宣称真实安装包可用
4. **Stale Release**：打包与审查 SHA 不同仍当作同一 Candidate
5. **CI Overreach**：无影响改动触发昂贵完整矩阵，阻碍交付
6. **Silent Failure**：只提供流水线 exit code 不暴露首个可操作错误

## 9. 面向真实 Tally Consumer 的验证矩阵

以下均是后续可转换为 Validation 的**预设案例**，不是已跑通过的工具/Host 结果。

| 情景 | 正确行为 | 禁止结论 | 需要的实际证据 |
| --- | --- | --- | --- |
| npm install PASS / tsc FAIL | 保持 build FAIL 并定位实际类型错误 | 写 NPM_CI_RESULT=PASS 代表全 CI 成功 | 流水线具体 step/命令/exit code |
| 同一 pipeline 19 次完整 clone | 依据 provider 能力考虑一次 checkout 复用 | 没有能力证据就声称已省 95% 时间 | workflow 拓扑和网络耗时 |
| 代码进入了模块但没有导出消费 | 验证真实应用入口 | 仅 Build PASS 当功能生效 | selected path 的实际消费测试 |
| 桌面安装包未创建 | Release artifact NOT_FOUND | 在 Release 页面伪称存在可下载文件 | 实际 artifacts/Release 页面 |
| Node 22 项目无 Node24 专属特性 | 按项目合理下限选择工具链 | 全局强制 Node24 | 项目 package/功能与当前 CI |

验收应绑定当前 Source/Task/Attempt、实际消费者和适用环境；真实测试未执行时必须保留 `NOT_RUN/UNKNOWN`。不要以知识目录完整、算法讲解正确或一次模型问答得分代替真实开发任务的质量。

**模块交接边界：** K05 决定必要测试行为与 Oracle，K08 决定实际执行/集成/打包路径和 Provider 来源；CI GREEN 不证明 K05 的 Oracle 合格，也不授予 Release。
