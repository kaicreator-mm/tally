> `SYSTEMATIC_KNOWLEDGE_CANDIDATE / NOT_SOURCE_CLAIM_QUALIFIED / NOT_CONNECTED`。这是 **5 个学科群、15 个原创建模知识点**的系统性专业纲要，不是“任务已运行/业务规则已获权”的声明，不摘抄受限制国际标准全文。当前模块 Owner：**特定已观察故障的证据、竞争解释、根因实验与最小修复知识**。

## 一、知识对象与专业推理的原则

调试、根因定位与维护修复 要从概念的明确语义延伸到工程机制、条件性取舍和可反驳的实际结果。学习一个技术名词不等于学会何时用它；能输出步骤不等于执行/验证通过。此处每个知识点包括**概念、因果/适用机制以及常见错误泛化**，作为 Agent 的系统学习和主题检索基础。只有实际工程问题需要深入时，才延伸到相关 Topic/DP/Skill/真实测试。所有业务效力仍由当时适用的 Product/ADS/GitHub/Host 事实决定。

### K06.F1.1 — 现象与原因分离

**专业知识/机制**：Observed 日志/状态与 Hypothesis 因果解释分开，竞争假设在事实不足时保持并存。

**错误外推及负例入口**：看到 timeout 就断言数据库死锁。

### K06.F1.2 — 第一失败点与失败传播

**专业知识/机制**：按完整执行时序定位 earliest failed step；下游错误可能只是同一上游根因。

### K06.F1.3 — 环境/版本同一性

**专业知识/机制**：源 SHA、配置、Provider/OS、依赖和输入共同定义重现条件，旧事故根因不能直接覆盖新事件。

## 3. 错误类型与范围判定

### K06.F3.1 — 确定性 Bug 与基础设施缺陷

**专业知识/机制**：语法/类型/违反状态合同是源码问题；网络不稳定/配置错误/Host 权限可能是环境问题，需不同解决方式。

**错误外推及负例入口**：把所有红色 CI 均标成 Provider 故障。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K06.F3.2 — 超时/未知副作用

**专业知识/机制**：先判定调用是否可能已提交，必要时合法读回；不因网络 ACK 缺失重复不可逆动作。

**错误外推及负例入口**：重复支付操作以“测试重试是否恢复”名义执行。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K06.F3.3 — 跨模块/集成缺陷

**专业知识/机制**：真实错误可能出在公共接口、旧消费者或测试选择；应定位已选实际调用链而非只搜索相似符号。

**错误外推及负例入口**：只修被测试 Mock 的函数，真实应用仍调用旧函数。

## 4. 修复策略与验证

### K06.F4.1 — 最小合法改动

**专业知识/机制**：将修复限制在当前 Task 写集及真正因果根源，必要时联动授权的合同 Owner。

**错误外推及负例入口**：发现一个 bug 就全仓重写无关模块。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K06.F4.2 — 回归与反事实

**专业知识/机制**：构造会使原错误实现失败而新实现通过的反例，执行受影响测试并检查旧行为是否保留。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K06.F4.3 — 补丁当前性与复核

**专业知识/机制**：补丁、实际测试、Reviewer 分别绑定精确 HEAD；旧 review/CI 不因新提交继承为现行 PASS。

**专业知识/机制**：降级、绕行、回滚属于恢复策略，不表示根因已消除或回归已通过。

### K06.F5.2 — 事故时序与影响

## 六、完整专业知识如何映射到 Tally 可执行领域智能

**角色**：特定已观察故障的证据、竞争解释、根因实验与最小修复知识。K06 获取 K08 的当前执行和日志事实；K03 进行受权修复；K10 提供可靠性/恢复语义；K11 限制没有新证据的重复尝试。

**专业案例（教学情境）**：CI 前后不同失败根因。前次 npm ci 被锁文件版本阻断，本次 npm ci 通过但 TypeScript `class Error extends Error` 触发 TS2506；先判当前 tsconfig/源码符号而非复用旧锁文件结论。

**禁止的错误判断**：只看 pipeline exit 2 就不断重试部署/升级依赖，未诊断本次最早失败源码。

**推理/证据链**：当前 Goal/事实/来源 → 选 K06 的相应学科群及 Concept → 明确 Rule/Model 是否具备有权业务前提 → 选择 [方法与 DP](engineering-methods.md)、[Agent Skill](agent-skills.md)、已有或未来 [Topic](README.md) → 给出正反 Oracle 与 STOP → 只有在合法消费者实际运行时才附真实 Host/CI/Review 收据。

**关联专业资料**：[A01](../external-source-catalog.md)、[A14](../external-source-catalog.md)、[A28](../external-source-catalog.md)、[A31](../external-source-catalog.md)、[A41](../external-source-catalog.md)。这些是覆盖和方法的公开参考，**并不表示整套出版物已逐条核对/获得复制许可/成为已认证知识**；当前 ADS 精确规范条款的适用性仍以 [sources.md](sources.md) 为准。核心软件工程和工程基础跨领域关系见 [disciplinary-coverage.md](../disciplinary-coverage.md)。

## 七、知识深化的可观察标准和当前缺口

- **基础层**：这里的 15 个知识点已形成概念+机制+反模式的**原创系统知识纲要**，但不意味着该学科所有细目已经获得全文教材深度或来源 Claim 资格。
- **方法层**：真正要处理的任务应能从本群的术语/条件追溯到现有 DP/Skill/案例或形成新的具体 Topic，且至少能指出一个会使错误判断失败的负例。
- **选用层**：未来根据明确 Product/Task/Package 权限，只为真实使用的知识链补准确 Source/Clause、适用性、许可和消费者测试；没有实际执行仍保持 NOT_RUN。
- **维护层**：新增学科研究、反例或实测失败优先补本群的专业机制与出处，多个 Topic 仅链接到唯一概念解释。未被当前开发用到的理论不因缺运行时资格而从学科知识库删除。
