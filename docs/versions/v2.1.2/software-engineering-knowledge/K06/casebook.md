## 7. 端到端教学案例与故障反例

**情景：** Woodpecker 一条流水线的 npm install 成功，随后 TypeScript build 报 TS2506 和 TS2339；之前另一流水线曾失败于锁文件下载。

**正确处理：**
1. 从当前流水线读取实际 clone/source SHA、成功的安装命令和第一个失败 build 命令。
2. 将安装阶段失败的旧历史与当前编译失败分开；当前成功安装不能继续归因为锁文件。
3. 定位 TS2506 对应类继承声明是否遮蔽内置 Error，并检查 TS2339 与该根因是否相关。
4. 在合法写集内最小更正类命名/继承关系及必要的对应测试，不顺带更新所有依赖。
5. 运行项目实际 TypeScript build 与受影响测试，绑定新的源码 HEAD；仍未运行的真实 Host/CI 标 NOT_RUN。

**可以观察的正确性：** 同一编译错误不再出现；类型和构建检查真实执行，修复不影响既有公开错误合同。

**故意错误的候选：** 因为之前 npm install 失败过而立即删除/重建 lockfile、升级所有包、添加 clone 重试；当前真正错误完全没有被修复。

**变更条件后如何调整：** 如果当前首次失败确实是网络 fetch/registry，才把问题归入 Runner/外部环境并选择有界重试，不改动无关产品代码。

## 反模式与错误后果

## 8. 常见反模式与止损条件

1. **历史诊断套用**：旧流水线故障类别覆盖新流水线实际失败
2. **盲目重试**：源代码确定性编译错误靠增加 CI retry 解决
3. **多 Agent 补丁振荡**：相同错误不同 Agent 反复更改而不比较新旧事实
4. **无复现器**：只改源码注释或期望输出就称问题修好
5. **修复越界**：局部实现缺陷扩大为所有模块的大重构
