## 一、跨进程发生顺序不同于墙钟时间排序

不同机器的时钟可能有偏移，日志写入或采集也可能延迟；把三个服务的时间戳排序，不一定得到真实因果顺序。应尽量保留 Trace/Span、消息 ID、请求 ID、持久化 commit identity、Attempt/SourceSHA 与关键发送/接收关系。

**Happens-before** 是由同一执行序列与消息发送→接收等约束得到的部分顺序；无因果路径的事件可以并发，不能因为本地时钟差 100ms 就断定谁导致了谁。分布式 Trace 的父子边也不自动证明业务事件已经提交，仍需状态源读回。

## 二、采样日志缺失不是事件未发生的证明

诊断时记录两个维度：**观察到什么**，以及**未观察到的原因可能是什么**。如果异常发生在日志 flush 之前，或者观测采样率低，搜索不到记录不代表调用没有执行。日志中“开始扣款”也不是扣款提交证明。副作用未知时优先查询有权最终系统事实，不凭缺失 Trace 直接重试。

不应为了调试而全量打印秘密、请求 Token、个人数据或未授权的业务载荷。K10 拥有日志规范与隐私边界，K06 选择必要的低风险探针。

## 三、区分第一材料失败、传播与根因链

示例 CI：
1. checkout 成功，依赖缓存命中；
2. codegen 使用旧 Schema 生成接口；
3. 编译失败 “unknown field”；
4. 下游测试/打包未执行。

第 3 步是第一个**可观察失败**，第 2 步可能是上游原因，进一步根因可能是缓存输入漏掉 Schema 版本。诊断需要先证伪“代码真的有该字段”的相反解释；不能只把第 3 步编译器错误压成忽略警告，也不能将第 4 步标为已运行失败。

## 四、研究型探针需要控制混淆变量

| 竞争假设 | 区分性操作 | 结果的限定解释 |
| --- | --- | --- |
| H1 缓存键遗漏 codegen 输入 | 在同 SHA 下改变/清除受控缓存，检查生成物 hash | 受影响缓存候选，仍需核验输入因果 |
| H2 当前源文件导出错误 | 使用相同工具链干净构建相同 SourceSHA | 若持续失败，更支持源码合同问题 |
| H3 Runner 使用旧工作树 | 读回命令 cwd 和 checkout 的 SHA | 发现不一致可证明来源身份缺陷 |
| H4 故障发生于远端调用后 | 读回有权远端交易/Effect ID | 不可读回时保持 UNKNOWN_EFFECT |

一次探针最好只改变一个可控条件；不同环境的同时变动无法将成功归于单一因素。无法重现的问题也可以保留关联证据、可监控的预测和明确未确认的因果候选，不以不确定性制造虚假根因。

## 五、事故恢复与长期知识回流

临时缓解（限流、切换、停止错误重试）与永久修复（纠正缓存键、状态所有权、事务/重试合同）必须分开。复盘应记录范围、受影响用户、可见时间线、检测延迟、竞争假设、恢复步骤、成功与失败反例、以后何种环境会再次发生；避免把个人责备变成“根因”。

反事实问题：“如果修复 X 真的解决故障，那么在保持同样输入时错误是否消失，同时人为引入旧缺陷会不会重现？”这比“修复后本次测试绿色”有更强的因果解释力，但也仅证明已观察范围。
