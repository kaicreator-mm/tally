## 知识正文与重要权衡

## 3. 知识正文：核心工程方法

### 3.1 事实取证先于修复建议

读取目标 Task/SHA、真实 CI/Host/编译器的**首个失败命令**、行号、堆栈、标准错误及环境版本。后续“pipeline exit 2”可能只是包装层；早期成功的 npm install 并不能证明后续 build 没有源码缺陷。先观察再定义根因，避免凭旧版问题模板反射性生成新修复。

### 3.2 故障层级的划分

需求错误：接受标准或业务规则本身不清；设计错误：状态归属/契约不成立；源码错误：实现逻辑/类型/异常；测试错误：Oracle 假设错误、用例未被发现；工具/环境错误：依赖、网络、权限、Runner；Host/CI 问题：能力缺失或特定 Provider 故障。分类只是初步假说，必须用相应可观察事实进一步证伪。

### 3.3 因果假设与最小复现

针对最有可能的两个解释建立能区分它们的测试：比如锁文件下载失败应在 install 阶段报错，而 TypeScript 自继承会在编译时报特定诊断。用最小可复现输入/模块固定版本，必要时比较正确/错误代码路径与实际建构环境，不能用无限人工重试代替事实分析。

### 3.4 修复所在层级

局部编译错误应在相应源码和必要测试修；接口/状态所有权不成立需依设计变更进入 L2；用户范围矛盾需回 L1。CI 环境缺失工具不是代码缺陷，直接改产品依赖通常会扩大范围。修复应解释为何该处修改消除了机制、哪些相关失败仍未覆盖。

### 3.5 有界修复与重复失败止损

一次 Repair 应包含确认问题、明确假设、合法修改及最小必要验证。相同来源/环境重复失败时，应对比前一 Attempt 的新证据，不应仅换一个 Agent 重新执行同样命令。无改进、无新证据、碰到权限/外部 Host 限制时停止并上报缺失条件；不要给本地 Agent 无界“持续推进”使命。

### 3.6 错误信息与可恢复诊断

在产品代码中保留适当日志、上下文/相关 ID、故障分类与用户下一步行动；不要通过打印全部环境变量、token/请求内容解决可观察性问题。错误结果要区分业务拒绝、可重试的临时环境问题、内部缺陷和未知副作用；恢复事件不能抹掉真实失败历史。

### 3.7 回归与真实效果确认

用原复现器证明新 HEAD 不再故障，再用典型正向用例与最小边界负例保护已有行为；如果修复影响跨模块入口则增加必要真实消费者检查。Builder 运行测试与 Review、CI、Host 或 Release 是不同资格，不能从新的源码 Commit 直接推断生产修复已经部署。

## 具体可执行方法与取舍

先保留源 HEAD、Runner/Host 身份、命令实际执行顺序、第一条错误诊断和对应日志，再提出两个可能解释。选择能最少成本将解释区分开来的探针；例如 npm 安装已成功而 tsc 自继承报错时，优先查对应源码继承与符号遮蔽，不因旧流水线锁文件问题再次重建所有依赖。修复必须有合法写集，并用原复现器和受影响回归证明；相同错误无新证据时停止并升级，而非继续轮换 Agent。

### 场景选择矩阵

| 真实条件 | 推荐分析/方法 | 需要记录的结果 | 禁止误推 |
| --- | --- | --- | --- |
| 当前 install 成功，首次 build 出 TypeScript 错 | 定位编译器具体源码/合同问题 | root cause hypothesis + scope | 不要修改无关锁文件 |
| 网络超时但业务是否提交未知 | 先读回状态和 Provider 证据 | UNKNOWN/恢复路径 | 不盲重试不可逆副作用 |
| 测试用例根本没被发现 | 修复测试选择/布局，非业务逻辑 | test discovery 修复 | 不重构目标实现 |
| 多轮同类失败没有新证据 | 停止振荡，报告阻塞与最小新探针 | 有界升级记录 | 不能续跑直到 token 耗尽 |

## 现有 Decision Procedures（输入、步骤、产物与停止）

## 4. 可执行的 Decision Procedures

决策程序定义可复用的方法及终止条件，不创建第二套运行时状态机、审批权威或 Agent 调度器。

### DP-K06-01 · 首个失败点与竞争解释诊断

**输入：** Runner/Host/编译器日志、真实命令顺序、source/tested SHA、任务范围

**步骤：**
1. 确认实际运行过的步骤，标记最后成功与第一个失败命令。
2. 归纳症状、错误消息/堆栈与对应源码/环境边界。
3. 列最少两个可能解释并找能区分它们的一个最便宜检查。
4. 为最有可能原因建立可复现正/负差异或读回确切来源。
5. 选择代码/合同/环境/测试问题的真实责任层。

**产物：** 有来源的根因假设及最小下一步检查/修复范围

**失败/停止：** 日志不足则标 UNKNOWN，不能凭 exit code 猜修复位置。

### DP-K06-02 · 根因修复与回归验收

**输入：** 合法 Task 写集、可复现故障、当前源和最小修改方案

**步骤：**
1. 确保根因解释可以预测现有失败以及修复后的行为。
2. 只改允许源码/必要测试；不加入掩盖错误的无限重试。
3. 先运行失败复现器，再运行受影响正向回归和必要边界反例。
4. 记录新 SHA、执行环境、真实命令与结果，区分未测的 CI/Host。

**产物：** 可审查 Patch + 受影响回归收据/剩余风险

**失败/停止：** 影响其他层、需要越权或改变 Product 时 STOP 并请求原 Owner 修订。

### DP-K06-03 · 振荡止损与经验提炼

**输入：** 多次 Attempt/失败日志、修复方案差异、当前依赖/Provider 环境

**步骤：**
1. 按时间归并相同症状与首次变化，排除重复无价值检查。
2. 判断新尝试是否增加证据或只重现原错误。
3. 如果属于外部 Provider/权限不可用，保持 BLOCKED 并暂停无意义重试。
4. 有来源地提炼可复用 Case/Rule/Skill 候选，并保留失败适用条件。

**产物：** 有界停止/升级结果与经验候选

**失败/停止：** Agent 自报“学到了”不等于已证明跨项目通用性。

## 抗过度流程原则

一次实际 Task 至多选择足以完成当前判断的 Procedure；除非已知缺口会改变业务、架构或正确性结果，否则不自动开新 Issue、实验或大量 CI。若缺少有权决策者、现行数据或真实 Host，保持 UNKNOWN 并说明最小下一项证据，不通过 Agent 自信度推定通过。
