> `SYSTEMATIC_KNOWLEDGE_CANDIDATE / NOT_SOURCE_CLAIM_QUALIFIED / NOT_CONNECTED`。这是 **5 个学科群、15 个原创建模知识点**的系统性专业纲要，不是“任务已运行/业务规则已获权”的声明，不摘抄受限制国际标准全文。当前模块 Owner：**测试 Oracle、风险驱动测试设计、实际测试发现与证据充分性的唯一知识拥有者**。

## 一、知识对象与专业推理的原则

软件测试、验证与质量保证 要从概念的明确语义延伸到工程机制、条件性取舍和可反驳的实际结果。学习一个技术名词不等于学会何时用它；能输出步骤不等于执行/验证通过。此处每个知识点包括**概念、因果/适用机制以及常见错误泛化**，作为 Agent 的系统学习和主题检索基础。只有实际工程问题需要深入时，才延伸到相关 Topic/DP/Skill/真实测试。所有业务效力仍由当时适用的 Product/ADS/GitHub/Host 事实决定。

## 1. 测试知识论与 Oracle

### K05.F1.1 — 测试与证明的范围

**专业知识/机制**：测试只能针对声明的输入/环境/版本提供观察，不能证明无限输入域中的所有行为；依据风险选取负例。

**错误外推及负例入口**：用“所有 Unit PASS”代替整个系统的可靠性证明。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K05.F1.2 — 业务来源驱动 Oracle

**专业知识/机制**：从 Requirement/Rule/Invariant 定义期望、拒绝和副作用，没有受权政策的 Expected 应 UNKNOWN。

**错误外推及负例入口**：把当前实现的错误输出直接更新成 Golden。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K05.F1.3 — 验证与确认 V&V

**专业知识/机制**：区分实现对合同的符合性和真正用户目标的符合性，要求每层有独立可观察对象。

**错误外推及负例入口**：API Schema 正确就认定用户实际流程可用。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。


## 2. 测试设计与系统性选例

### K05.F2.1 — 等价类与边界值

**专业知识/机制**：按输入分区、上下界、空值、非法形式和极值选能发现不同错误的代表样本。

**错误外推及负例入口**：只用 10 个不同名称但相同 happy path。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K05.F2.2 — 决策表与状态转换

**专业知识/机制**：对角色、前置状态、事件、输出/副作用构造条件组合，重点覆盖不允许的迁移。

**错误外推及负例入口**：只验证 OPEN→CLOSED，不测重复 CLOSE 和非法状态。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K05.F2.3 — 性质/组合/变异测试

**专业知识/机制**：对排序、去重、幂等和不变量可设计性质/变形或适当变异检查，复杂度高时只用必要的最小集。

**错误外推及负例入口**：强制所有 UI 文案变更开展数千次 Property tests。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。


## 3. 测试层与真实集成

### K05.F3.1 — Unit/Contract/Integration/E2E

**专业知识/机制**：不同层验证本地逻辑、消费者合同、真实依赖、用户关键路径；不可用 Mock 证明真实环境副作用。

**错误外推及负例入口**：Pact/DB Integration 通过就推断安装版 UI 自动正常。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K05.F3.2 — 依赖环境与隔离

**专业知识/机制**：根据真实资源选择内存 fixture、Testcontainers、外部 Host 和稳定清理；测试独立于运行顺序与其他租户。

**错误外推及负例入口**：测试在单机偶尔绿就跳过并发污染。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K05.F3.3 — Build/Package 与平台

**专业知识/机制**：类型编译、打包、依赖解析及支持平台的安装路径有不同失败模式；与 K08 合作选择真实受影响范围。

## 4. 测试质量与假阳性

### K05.F4.1 — 实际发现/执行

**专业知识/机制**：Runner exit 0 不能证明需要的 suite 被发现；针对材料性覆盖检查实际执行清单和 Source SHA。

**错误外推及负例入口**：0 tests collected 仍报告目标接口 PASS。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K05.F4.2 — Snapshot/Golden 和过期证据

**专业知识/机制**：Golden 应绑定有权行为来源；旧 HEAD/BASE 或未选中实现的测试不能提升为当前候选结果。

**错误外推及负例入口**：修复回归时直接改 Snapshot 使错误变绿。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K05.F4.3 — Flaky 测试与诊断

**专业知识/机制**：识别时钟、调度、外部资源、隔离问题；隔离/quarantine 需要有界退出，不把无界重试当作修复。

**错误外推及负例入口**：为偶发失败设置 retry=99 然后宣称根因解决。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。


## 5. 质量分析与测试策略

### K05.F5.1 — 风险驱动优先级

**专业知识/机制**：基于真实失效后果、变更范围、运行条件、可逆性选必要测试，不要求每次全量 CI。

**错误外推及负例入口**：修改 README 就跑全部集成数据库迁移套件。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K05.F5.2 — 覆盖与变异有效性

**专业知识/机制**：覆盖率只是代码执行指标，不证明 Oracle 有效；选故意错误的实现来检查测试能否发现。

**错误外推及负例入口**：100% 行覆盖便宣布需求不变量一定满足。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

### K05.F5.3 — 测试结果与权威

**专业知识/机制**：CI、真实 Host、Reviewer/Release 是不同证据主体，PASS 必须有实际执行、当时完整输入和合法 Owner。

**错误外推及负例入口**：用 mock PASS 自动标独立 Release READY。

**判断产物**：选择当前真实任务下适用的解释、已知事实、缺失条件和不能被默认成立的反例；不借此生成现行任务的权限/验证 PASS。

## 六、完整专业知识如何映射到 Tally 可执行领域智能

**角色**：测试 Oracle、风险驱动测试设计、实际测试发现与证据充分性的唯一知识拥有者。K01 决定业务 Rule 与验收，K02 提供架构合同，K08 记录真实 Runner/Host/Artifact，K06 专注异常诊断。

**专业案例（教学情境）**：测试命令绿但目标 suite 完全未发现。在保留其他 Unit PASS 的同时，发现受影响 Contract Test 被 Runner glob 排除，明确该合同仍 NOT_RUN，修正选择后只重验目标范围。

**禁止的错误判断**：借 CI 绿色徽章覆盖旧测试找不到的缺陷，属于 False PASS。

**推理/证据链**：当前 Goal/事实/来源 → 选 K05 的相应学科群及 Concept → 明确 Rule/Model 是否具备有权业务前提 → 选择 [方法与 DP](engineering-methods.md)、[Agent Skill](agent-skills.md)、已有或未来 [Topic](README.md) → 给出正反 Oracle 与 STOP → 只有在合法消费者实际运行时才附真实 Host/CI/Review 收据。

## 七、知识深化的可观察标准和当前缺口

- **基础层**：这里的 15 个知识点已形成概念+机制+反模式的**原创系统知识纲要**，但不意味着该学科所有细目已经获得全文教材深度或来源 Claim 资格。
- **方法层**：真正要处理的任务应能从本群的术语/条件追溯到现有 DP/Skill/案例或形成新的具体 Topic，且至少能指出一个会使错误判断失败的负例。
- **选用层**：未来根据明确 Product/Task/Package 权限，只为真实使用的知识链补准确 Source/Clause、适用性、许可和消费者测试；没有实际执行仍保持 NOT_RUN。
- **维护层**：新增学科研究、反例或实测失败优先补本群的专业机制与出处，多个 Topic 仅链接到唯一概念解释。未被当前开发用到的理论不因缺运行时资格而从学科知识库删除。
