# K09 — 软件演进与重构 / Software Evolution & Refactoring

> [v2.1.2 #521](https://github.com/kaicreator-mm/tally/issues/521) · 本模块 [#530](https://github.com/kaicreator-mm/tally/issues/530) · [总目录](README.md)。`DETAILED_CONTENT_CANDIDATE / NOT_SOURCE_QUALIFIED / NO_RUNTIME_ACTIVATION`。ADS 是 Agent 软件开发实验/实践和已发布工程规范来源，Tally 在软件工程 Workflow 中消费选定、合格的知识。示例除有真实来源外均为教学情景，非真实测试结果。

## 1. 目标、适用条件、边界

指导 Agent 在不破坏真实已接受行为的前提下演进软件：区分 Bug 修复、重构、新功能、架构迁移、数据迁移和技术债消除；知道何时选择局部变更、何时需要兼容层、何时必须在受控版本中协调 Product/L2 变更。不是以“代码更漂亮”为目标的大规模改写。

**触发条件：** 已有软件持续迭代、跨版本接口/数据结构变化、旧功能回归、技术债有真实维护成本、维护事件和必要的兼容/迁移工作。

**不承担：** 不把每次小改动变成强制完整迁移设计，也不建设通用技术债自动评分或源代码逆向分析系统。本版本暂不单独建设代码库逆向分析、软件安全与供应链知识专项；已有必要源码理解、权限和基本安全规范仍按实际 Task 生效。

## 2. 概念、语义及常见混淆

| 概念 | 工程语义 | 容易出现的错误 |
| --- | --- | --- |
| Refactoring | 外部观察行为预期保持的内部结构改进 | 换了 API 语义却叫重构 |
| Compatibility Contract | 被真实消费者依赖的接口/版本/配置/数据格式和错误语义 | 只检查新客户端正常便认为兼容 |
| Breaking Change | 破坏已有承诺或消费者可观察行为的改变 | 没有声明就静默删除旧接口 |
| Migration | 现有数据/状态/配置逐步变成新格式和新行为的过程 | 仅定义最终 schema 而不考虑老数据 |
| Expand/Contract | 先扩展兼容范围、迁移消费者，再收紧旧合同的演进路线 | 直接发布不可回滚的高风险切换 |
| Technical Debt | 当前权衡导致未来真实维护/测试成本的负担 | 任何旧代码都称技术债 |
| Preserved Behavior Oracle | 已接受的既有行为及其对应测试/消费者证据 | 只把新需求的测试当完整回归 |
| Rollback/Compensation | 变更失败时返回可接受状态的方式，可能是补偿而非直接反转 | 假设所有数据库迁移都能简单逆转 |

此处是领域知识概念，而非要求另外建立一套消息数据库、Task 状态机或通用 Schema；必要时可映射到现有 Tally Engineering Business/Domain Data 结构。

## 3. 知识正文：分析方法与工程权衡

### 3.1 先确定变化的性质

问目标是修 Bug、增加功能、改良结构、改变行为还是迁移数据；不同类别决定是否需要 L1 新需求或 L2 设计修订。重构以外部可观察行为尽量不变为约束，新增功能则需明确新 Acceptance，行为改变必须有有效的业务来源和兼容处置；不能把所有类型混称“清理代码”。

### 3.2 识别真正的消费者合同

考虑公开 API、CLI 参数/退出码、JSON/事件、持久化格式、配置默认值、错误消息是否被其他组件依赖。只检查编译可通过不足以证明真实消费者没有破坏。必要时明确支持版本、降级策略和真实迁移期限；不能无限保留未经要求的所有历史兼容，但也不应擅自删除已承诺行为。

### 3.3 重构的安全小步

确定变更前后必须保持的不变量，先建立覆盖实际公共入口的行为测试。将移动代码、拆函数、调整依赖方向与改变业务规则分离，保持每一步可审查/可回退；若需要大结构改动则明确接口和 Owner、单 Writer 的共享文件/生成物边界。避免“新架构自然更好”且缺乏可测问题的无用重写。

### 3.4 Schema 与持久化迁移知识

迁移不只是改表结构：现有数据值、版本标记、读写兼容、运行中旧进程、事务/中途崩溃、不可逆清理、可重试执行都可能影响结果。根据项目实际需要选择 expand-contract、分阶段回填、读旧写新或受控停机迁移；不能假定单个成功测试意味着所有历史数据安全。

### 3.5 兼容失败与修复/回退

设计中至少包含旧版读写、新版读写、迁移中断/重试、部分完成和回滚/补偿的适用情况。发现兼容性冲突时先定位是 L2 合同、L1 需求、实现或环境的影响，再提出有界修正；不能用修改旧测试期望掩盖产品回归。旧版产品冻结的事实仍在原有来源中有效。

### 3.6 技术债的真实优先级

整理触发变更频率、缺陷复发、构建/测试耗时、性能或发布阻碍作为技术债的价值证据。若只是美观偏好且没有业务收益、当前维护成本不高，可能应暂缓。对高成本债务也要比较“局部修复/抽象”“替换”“暂时保留”的总成本，不因有空闲 Agent 就自动全仓重构。

### 3.7 演进中的文档/知识反馈

把项目中成功/失败的变更案例保留为相应 Case、适用架构条件和反例，并将可泛化的程序反馈 ADS。Tally 后续选用要绑定知识版本/受影响的消费者和任务，不能静默更换已进行中的工作协议。

## 4. Decision Procedures（Agent 可执行的决策方法）

### DP-K09-01：行为变化与兼容影响分类

**输入：** 变更目标、当前有效 Product/L2、公开入口/消费者和版本事实

**步骤：**
1. 先判定 Bug/Refactor/Feature/Migration/Deprecation 中的实际类型。
2. 列可观察保留行为与允许改变行为，标明来源/支持期。
3. 识别受到影响的消费者、配置/数据格式及合同约束。
4. 比较维持兼容、新增层或正式破坏升级的成本。
5. 输出最小需要的业务/架构决议和回归范围。

**输出：** 受影响合同/责任层级/有源风险与迁移候选

**停机与边界：** 业务决策未批准时不得擅自废弃既有行为。

### DP-K09-02：分阶段重构与迁移设计

**输入：** 真实当前数据/接口、失败语义、版本消费者和回滚能力

**步骤：**
1. 先建立公共入口保留行为 Oracle 和变更前基线。
2. 把结构清理与业务修改分成可核对的小步。
3. 若有持久化变化，设计旧/新读写兼容和部分失败恢复。
4. 按可逆性和目标平台选择滚动/停机/分阶段策略。
5. 准备最小执行和真实数据验证/回退条件。

**输出：** 有界实现/迁移序列、版本约束、正反测试方案

**停机与边界：** 没有数据迁移就不要生成空迁移工件；不可逆操作需要真实 Owner。

### DP-K09-03：技术债优先级选择

**输入：** 真实维护/缺陷/交付成本与可以替代的方案

**步骤：**
1. 确认技术债是否造成可量化或可观察的项目问题。
2. 评估局部修复、重构、替换或延后的机会成本。
3. 识别会否扩大当前核心任务与是否可独立交付。
4. 优先执行能改变真实用户/工程结果的最小改进。

**输出：** 选择理由、目标行为和停止点

**停机与边界：** 不以“重构完成多少行”或 Agent 工作数量衡量质量。

这些步骤为可引用的决策方法，不是第二个调度器、权限授权或 Review/Release PASS。

## 5. Tally Workflow 与其他知识模块的组合

**消费方（条件性拟议）：** `PROPOSED_NOT_CONNECTED`；Tally Engineering Business Maintenance/Change-intake 读者仅在兼容、数据迁移或重构需求真实发生时选用。输入：旧新版本、当前消费者合同、变更目标/数据；产出：保留行为清单、兼容决策和增量迁移/回归方案；L1/L2 与实际升级/Release 仍由原 Owner 授权。

| 环节 | 既有事实输入 | 使用该知识获得的输出 | 不能推断 |
| --- | --- | --- | --- |
| 维护受理 | 实际缺陷/新需求和版本记录 | 变更类别、范围和兼容性需求 | 不能直接改写历史 L1/L2 |
| 设计与任务规划 | 消费者/合同/迁移前提 | 有界迁移与重构计划 | 不是所有修复都重新冻结 |
| 实现验证 | 当前 Task/数据样本/旧行为 | 旧/新路径、失败/回退结果 | 新测试 PASS 不等于旧消费兼容 |
| 交付和经验 | 合格版本/真实回归与发布 | 知识案例及后续维护处置 | 不能自行生成 Release |

**与 K01–K11 的交叉关系：** K01/K02 负责真正的需求与结构变更，K03/K05 提供小步实现与保留行为测试，K06 区分修复与根因，K08 用于版本/制品兼容交付，K10 的运行恢复义务与 K11 的技术债经济决策按需求选用。

## 6. Agent Skills：输入、输出、验证、失败路由

### SK-K09-01：Compatibility Impact Analyst

- **触发**：公开接口/数据/配置可能变化
- **需要的事实输入**：旧新合同、使用者、支持范围、已存在测试/版本
- **产生的工件或结论**：变更影响矩阵/破坏点/应保留行为与待授权决定
- **自我核对**：每一条“兼容”有真实消费者和测试覆盖
- **拒绝/升级**：不能只靠新版本编译证明兼容

### SK-K09-02：Refactoring & Migration Planner

- **触发**：结构改良或真实数据迁移有价值
- **需要的事实输入**：明确目标/数据事实、允许写集、旧用户基线
- **产生的工件或结论**：小步方案、验证/回退路径和失败停点
- **自我核对**：每一步能区分行为改变与纯结构整理
- **拒绝/升级**：不能凭口号强迫全部项目做 expand-contract

### SK-K09-03：Legacy Behaviour Verifier

- **触发**：修改老功能或关键公开合同
- **需要的事实输入**：被接受的旧版行为、当前新实现/测试
- **产生的工件或结论**：当前旧/新客户端/数据案例及残余 UNKNOWN
- **自我核对**：检测破坏后的旧调用和真实失败
- **拒绝/升级**：不应通过修改旧 Golden 掩盖非预期回归

## 7. 贯穿示例：正常路线、故意错误路线和适用差异

**情景（教学模拟）：** 产品想给订单查询 API 增加分页字段并重构内部查询模块，仍有旧客户端只认识原来的数组结果。

**正确推进：**
1. 确认“增加分页”是新功能而“拆查询模块”是重构，分别列出允许变化与必须保留行为。
2. 识别真实旧客户端对响应 JSON 的依赖，判断是否能通过新端点/可选字段/版本参数保留旧合同。
3. 为旧版响应、分页新路径、非法页大小、空结果和错误处理形成可观察测试。
4. 先在可接受的接口合同下做小步重构，再实现分页；集成测试证明两个消费者实际调用。
5. 若将来停用旧合同，应有正式版本/业务决策、通知或迁移方案，不得在本次小改动私自移除。

**有效的验收证据：** 新客户端分页行为合格，旧客户端受支持的调用仍有正确可读的旧结果，重构没有引入额外副作用。

**错误实现/决策：** 重构后统一返回 {items, nextPage}，却直接删除旧数组接口，然后把旧测试修改成新 JSON 并宣称重构无回归。

**条件变化如何影响选择：** 若上游已明确声明是全新 major 版本且无兼容承诺，可正式设计破坏性变更；需要清楚限定支持目标，不必无限兼容所有历史客户端。

## 8. 反例库与适用性边界

1. **Feature-as-Refactor**：改变用户行为却宣称只是内部清理
2. **Snapshot Laundering**：直接更新所有 Golden，使不兼容结果变成 PASS
3. **Universal Migration**：没有持久化数据变化也生成复杂迁移与恢复流程
4. **No Consumer Evidence**：公开接口改变只验证内部单元函数
5. **Debt Vanity**：为抽象优雅进行全仓重构而没有实际问题

## 9. 面向真实 Tally Consumer 的验证矩阵

以下均是后续可转换为 Validation 的**预设案例**，不是已跑通过的工具/Host 结果。

| 情景 | 正确行为 | 禁止结论 | 需要的实际证据 |
| --- | --- | --- | --- |
| 新字段加入旧 JSON | 明确旧客户端合同仍满足 | 编译通过即兼容 | 旧客户端消费/Schema |
| 数据迁移中途断电 | 部分失败后有恢复或阻断策略 | 仅一次成功迁移 PASS | 真实样本和失败注入 |
| 只拆函数不改行为 | 保留行为和公共测试 | 把大量代码变化视为用户价值 | 旧新入口结果 |
| 技术债未实际导致问题 | 记录待观察并按价值延后 | Agent 有时间就重构 | 缺陷/工时/维护来源 |
| 版本明确破坏性升级 | 按合法 Product/Release 边界处理 | 一律强制无限旧兼容 | 明确版本/支持/用户决定 |

验收应绑定当前 Source/Task/Attempt、实际消费者和适用环境；真实测试未执行时必须保留 `NOT_RUN/UNKNOWN`。不要以知识目录完整、算法讲解正确或一次模型问答得分代替真实开发任务的质量。
