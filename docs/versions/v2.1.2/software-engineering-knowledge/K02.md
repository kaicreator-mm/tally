# K02 — 架构与系统设计（Architecture & System Design）

> **内容阶段**：DETAILED_KNOWLEDGE_DESIGN / SOURCE_CANDIDATE / NOT_QUALIFIED。版本 [v2.1.2 #521](https://github.com/kaicreator-mm/tally/issues/521)，模块 [#523](https://github.com/kaicreator-mm/tally/issues/523)；[总索引](README.md)。**ADS 是真实 Agent 开发实验和规范来源，Tally 是选用这些知识的软件工程 Domain App**。本文是解释、方法与案例候选，不因写成文档而成为已批准的规则、真实测试结论或生产 Domain Package。

## 1. 能力目标、适用范围与非目标

教会 Agent 根据已确认需求、质量目标及实际约束做架构取舍：为何选择某种模块边界、接口与状态所有权，何时应进行小型架构实验，何时已有设计足以复用。重心是可实施、可证伪、可维护的工程决策，而非罗列设计模式名词。

**典型触发**：新增关键模块、状态一致性/持久化/并发条件变化、对外接口或部署拓扑变化、实际架构 UNKNOWN；普通局部改动可直接引用现有 L2。

**输出的工程价值**：在编码前消除会造成大规模返工的职责和接口不确定性，让独立 Task 在同一契约下集成。

**不包含**：不强制 DDD/微服务/事件驱动，不把研究 Demo 当生产验证，不额外建设安全与供应链专项。另外，本版本不设“代码库理解与逆向分析”和“安全与供应链”两个独立知识专项；实际任务中原本适用的源代码定位、权限、敏感信息与安全底线不因之被豁免。

## 2. 领域概念与边界

| 概念 | 精确定义及判断要点 | 常见误用 |
| --- | --- | --- |
| **Architectural Driver** | 有来源的功能/质量/部署/成本约束，足以影响结构决策 | 拿某个技术潮流当作驱动 |
| **Boundary / Component** | 具有清晰责任和依赖方向的模块或子系统边界 | 按代码目录名称机械划分服务 |
| **Interface Contract** | 调用者与实现共同遵循的输入输出、错误、版本和行为语义 | 仅列函数签名而忽略失败情况 |
| **Data/State Ownership** | 谁具有状态变更权、事务范围与最终真相 | 两个模块可各自任意修改同一份状态 |
| **Quality Attribute** | 可靠性、性能、演进、可测试性等项目真正关心的系统属性 | 不带目标/场景就宣称“高性能” |
| **ADR / Trade-off** | 决策原因、备选方案、代价、限制与适用期的持久记录 | 只有结论，没有候选和权衡 |
| **Research Demo** | 针对关键未知假设设计的有界可证伪试验 | Demo PASS 等同 Host/Release PASS |
| **Architecture Freeze** | 经现有 L2 Authority 确认的设计基线 | Agent 写了 ADR 就默认冻结 |

不同概念之间通过具体的来源/适用性/决策/消费者连接，不必为每一个词建立全新的数据库表。只有在真实 Tally 任务中被调用且能够改善工程判断时，才有必要形成可选的结构化资产。

## 3. 专业知识：方法、权衡与失败模式

### 3.1 从需求抽取架构驱动

从 L1 Requirement 与验收出发，问哪些因素实质影响系统结构：并发量、数据保留/一致性、部署网络、延迟、离线要求、团队维护能力。将“速度快”转成可观察的性能场景（操作、负载、边界、目标/阈值如已有来源）。未获确认的数字只能标为假设，不得写进系统级硬规范。

### 3.2 选择边界而非追逐模式

首选能解释职责、依赖方向和所有权的最小结构。模块化单体通常比为少量团队引入多服务协调成本更可控，但并非普遍结论；存在独立伸缩、隔离或组织边界时服务拆分可能合理。DDD 的 Bounded Context 用来处理真实业务语义边界，不是每个类都强制标 Aggregate。

### 3.3 合同先于并行实现

多个 Agent 并行实现接口、UI 和适配器之前，应先确认公开合同、错误响应、数据版本和最小集成 seam。设计接口不仅要定义成功数据，还需定义超时、取消、重试、部分失败、权限不符与 UNKNOWN 的表现；否则不同 Agent 会实现不兼容的“成功”。

### 3.4 状态一致性与故障语义

判断谁发起状态转换、持久化点和失败后可恢复的事实；对事务内原子性和跨进程最终一致性做明确区分。对异步任务考虑重复消息、幂等键、过期请求、补偿或重复执行；不要将网络消息送达当业务完成，也不要以单机内存状态代替持久确认。

### 3.5 方案比较的证据结构

ADR 至少回答：要解决什么问题、现实可行的候选、每个候选的收益和额外复杂度、选定理由、被拒绝方案为何不合适、未来退出或演进路线。复用成熟组件前确认实际合同/版本/维护与集成成本。缺少关键条件时先有界研究，不要为了写完整文档臆造优势。

### 3.6 Architecture Demo 的真正用途

只针对会改变结构的未知项设计最小 Demo：设置基线、可证伪结果、测量条件、未覆盖的真实系统部分。Demo 的某段读取延迟达到目标只说明那段实验条件成立，不意味着数据损坏/升级/权限/真实 Host 都合格。被证伪后缩小或调整 L2 决策，而不是无限强化实验工具。

### 3.7 架构演进与可追溯性

记录设计决定与来源版本、受影响需求、关键不变量、实现 Task seam 和必要测试。新事实反驳旧设计时通过合法 L2 Amendment 更新受影响的 Design/Task，不自动重写整个 L1 与既有历史事实。

## 4. 可复用 Decision Procedures（决策程序）

每个程序是能由 Agent 实行的**有界决策步骤**，不是另一个 Workflow Engine。任何输出必须保留实际证据与 UNKNOWN，不得自行授予 Product/L2 Freeze、Task Claim、Review 或 Release。

### DP-K02-01 · 架构驱动与方案比较

**输入：** Frozen L1 需求/验收、已存在架构决策、部署/数据约束和未知点

**执行：**
1. 提取真正会影响结构的驱动，并注明来源、重要性和可验证属性。
2. 列出至少两种实际可行方案；简单任务若唯一合理方案明显则说明复用依据即可。
3. 对模块边界、接口、数据所有权、故障/演进和总成本作相同维度比较。
4. 对会改变决策的未知项安排最小 Demo/文献/既有代码事实验证。
5. 生成 ADR 候选，列反例和仍需 L2 Authority 的确认点。

**输出：** 决策候选矩阵、选定方案及其限制、ADR、受影响 Requirement/Task/Validation

**停止与升级：** 没有可靠关键事实时不声称已经证明方案最优；与 Product 要求冲突时回到有权来源。

### DP-K02-02 · 接口与状态边界设计

**输入：** 已批准目标、预期使用者/调用者、状态与外部依赖

**执行：**
1. 列清楚读写拥有者与不变量，明确单一事实源。
2. 设计公开 API/消息、错误语义和版本兼容边界。
3. 覆盖重复调用、超时、取消、部分成功、交付确认。
4. 提出真实集成测试的 seam 和便于独立任务实施的合同。

**输出：** 契约草案+状态流+正反例+允许并行模块

**停止与升级：** 若状态所有权未定且影响一致性，不能下发彼此冲突的实现任务。

**提案来源边界：** `TALLY_V212_PROPOSED_KNOWLEDGE / ADS_1100_HISTORICAL_DESIGN / ADS_1384_UNADOPTED`；`DAG-A` 与跨阶段统一形态只是可选设计候选。已发布 ADS 的 L2 应走 Architecture/Research Demo 原 Owner 的有界研究，不创建新 native DAG 权威。

### DP-K02-03 · L2 研究深度选择

**输入：** 设计不确定性、当前证据、真实实验/依赖、Owner/Host 环境

**执行：**
1. 有充分当前证据且方案明确：INLINE。
2. 几个独立问题可用工作列表解决：BOUNDED_WORKLIST。
3. 有前置设计研究或多个独立试验：建立 DAG-A 节点、真实依赖、停止条件。
4. 研究产物回填 ADR，沿用现有 L2 Freeze 权威。

**输出：** 有界架构研究计划及其决策消费者

**停止与升级：** 不能因为生成了显式 DAG-A 就让系统默认进入实施状态。

## 5. Tally Workflow 消费契约

**消费阶段：** L2 Solution Design / DAG-A；使用 Tally 已有 Engineering Business、Task/Attempt 与 Agent/Host 事实源，新增的仅是领域知识与程序的调用关系。

| 环节 | 需要从上游获得 | 该模块实际提供 | 必须保留的判断 |
| --- | --- | --- | --- |
| 输入 | 被确认的 L1 要求与有效版本 | 驱动/质量属性/约束表 | L2 不能擅改 Product Scope |

| 冻结/移交 | 原有 L2 Authority | ADR/契约/Task seam/验证义务 | 设计文档完成不等于 L2 Freeze |

## 6. Agent Skills 与任务输入输出

### SK-K02-01 · Architecture Decision Writer

- **何时调用**：多个实现方案会导致显著不同的长期成本或质量
- **最小输入**：准确 Product 需求、系统约束、已有方案及来源
- **输出结构**：ADR 的背景、备选方案、驱动矩阵、选定理由、风险/未知、验证和退出路线
- **自检**：结论可从驱动证据推导，未选方案有实质反例
- **禁止的捷径**：只列软件行业流行词或无数据编造 SLO/吞吐数字

### SK-K02-02 · Interface/State Designer

- **何时调用**：数据所有权、接口或异步状态是关键设计变量
- **最小输入**：当前系统权限/状态/事务与外部调用边界
- **输出结构**：责任图、接口 schema/示例、状态转移/重复与故障语义、合同测试种子
- **自检**：读写权、正常与异常的同一事实源一致
- **禁止的捷径**：在同一字段上赋予两个相互竞争的变更 Owner

### SK-K02-03 · Architecture Experiment Planner

- **何时调用**：至少一个可测技术未知会改变架构
- **最小输入**：反事实假设、候选方案、环境/成本和可用工具
- **输出结构**：最小实验、证伪阈值、输入版本、真实测量、明确外推限制
- **自检**：Demo 只说明它实际测试的事实
- **禁止的捷径**：把实验型 Mock PASS 写成部署生产资格

## 7. 贯穿案例：正例、变体与反例

以下为**教学/设计情景**，不是宣称 ADS/Tally 已经执行或验证过的真实项目记录。实际资格认证必须替换为来源可核查的真实 Issue、源码版本、测试/Review/Host 收据。

**场景**：业务要新增大文件异步导入，要求用户可以查看进度并在失败后重试；原系统仅同步处理小请求。

**正确处理路径：**
1. 从 L1 提取进度可见、失败重试与已确认数据一致性等驱动；具体 SLA 如未批准保持 UNKNOWN。
2. 比较直接同步请求、进程内队列、持久化工作队列，分析部署实例数、重启、重复消息与存储成本。
3. 确认导入作业状态由一个持久化服务拥有；Worker 只能通过受控接口更新状态，UI 仅查询。
4. 定义作业状态 PENDING/RUNNING/SUCCEEDED/FAILED 等候选状态及可复验的转移、重复提交和取消策略。
5. 对队列持久性这一关键未知设计单一有界可证伪测试；依据结果记录 ADR 和接口/集成测试。

**成功的可观察标准：** 重启后任务状态可正确恢复，重复投递不造成重复不可接受的业务副作用，接口和数据合同可供独立 Agent 实施。

**错误处理路径与后果：** 直接引入多个微服务却没有持久化状态 Owner；Worker 和 UI 都更新同一作业表；Demo 表明单线程队列最快便宣称生产系统已经安全可靠。

**情景变体与边界：** 若项目只有单用户桌面应用且可靠性要求很低，简单本地队列或串行处理可能比远程消息服务更合理，方案选择受实际需求约束。

## 8. 反例库：哪些情况不能据此推断成功

1. **模式优先**：不看部署与业务需求先认定微服务、CQRS、DDD 必须采用
2. **伪架构证据**：PoC/局部 Demo 覆盖一个性能点就宣布全生产目标满足
3. **无失败合同**：API 只说明成功 JSON，不定义错误、超时、重试或状态一致性
4. **接口晚于并行实现**：几个 Agent 在不同分支里各自发明同一公开结构
5. **职责重复**：两个模块都被设计为状态来源，后续并发冲突不可控

## 9. 训练题与验证矩阵（后续可转换为 Cases / Validation）

| 任务/情景 | Agent 期望判断 | 错误或危险结果 | 最小证据 |
| --- | --- | --- | --- |
| 仅需一个简单同步读接口 | 保留已有模块结构，INLINE L2 | 因为有 L2 就强制多服务 | 现行 L1/已验证 L2 |
| 异步作业需要重启恢复 | 设计持久状态和明确写入 Owner | 仅用进程内 Map 宣称 durable | 具体恢复/失败要求 |
| 多个 Agent 并行 API/UI | 合同和异常码先明确 | 各自定义不同字段且无集成 seam | 冻结接口/Task 契约 |
| 队列 Demo 只测吞吐 | 限定结论适用面 | Demo PASS → 正式 Release PASS | 实验输入/指标/未测场景 |
| L2 与 Product 范围冲突 | 交 Product Authority 修订 | 擅自删除用户验收要求 | 来源版本和影响报告 |

**不完整证据的表示**：缺少用户业务决定、来源版本、真实调用结果或正式环境时，记录 `UNKNOWN / NOT_RUN / BLOCKED`，并写明下一项最小可验证事实。案例/模拟结果不能冒充真实 Agent 开发效果。

## 附录 A · Agent 直接调用的工作示例（非正式 Wire Schema）

**教学输入：** 用户需要导入较大文件，并能观察进度及重试；系统当前仅同步处理请求。
- 使用知识：ArchitectureDriver、StateOwnership、InterfaceContract、ADR，执行 DP-K02-01。
- 比较：同步、进程内队列、持久化队列；显式讨论重启恢复、重复提交、部署复杂度和成本。
- 期望产物：驱动→候选→选定理由→失败合同→Owner/接口→验证点的 ADR 及未证 UNKNOWN。
