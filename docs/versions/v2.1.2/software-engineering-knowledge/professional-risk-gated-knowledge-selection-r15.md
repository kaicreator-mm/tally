## 1. 问题：什么时候选知识、选多少、交给谁？

完整 K01–K11 是**系统专业知识**，不是每次 Agent 都要读取的上下文包。任务中的授权需求、已有代码、合同、平台和可观察风险优先于通用知识数量。按三个问题决定是否消耗一段知识：

1. **具体错误会造成什么后果？** 例如竞态下重复发布、持久状态错判、外部 Effect 重复、非法数据删除；是否存在真实失败/未决风险的证据？纯格式调整、简单类型纠正通常不需要持久化专题。
2. **在当前阶段谁有权做这个决定？** K01 确认 Requirement/Scope，K02 决定架构/State Owner/提交语义，K03 负责具体实现和实际可用原语，K05 负责独立 Oracle；K04/K07/K08/K11 在其真实权责范围帮助 Task/执行/取证/成本。课程编号**不代表强制顺序**。
3. **知识输入能改变哪个可观察决策？** 仅因关键词匹配而贴长篇教材没有价值。应该指出被选择的候选机理、适用性、要否证的错误与缺少什么；无法形成区分性决策，则不注入新段落。

## 2. 首轮路由决策（用于人和 Agent 阅读，不新增运行时规则）

| 已有任务事实/触发 | 此时最小推荐阅读 | 实际应交付 | 不应做的推断 |
| --- | --- | --- | --- |
| 无持久状态、无异步副作用，仅局部确定性函数变更 | 受影响模块的已知合同；需要时 K03 基础与 K05 对应单测 | 受影响入口/类型和合同用例 | 不必因为 R4 用过提交知识就强制提供 K02/K03/K05 全包 |
| **并发写入、可恢复的本地持久状态** | L2：K02 状态 Owner / 崩溃切点；选定方案后 L3：K03 文件/DB 原语；验证：K05 不变量负例 | 实际可持久观察的状态序列、提交点、竞争处理、真实 OS/FS 前提和独立测试 | 条件创建 `wx` ≠ 业务事务；`rename` ≠ 一切介质上的掉电耐久保证 |
| **外部 Effect / 发送成功但 ACK 丢失** | K02 业务与外部 Effect 的提交边界；K03 有条件回读/恢复；K05 作用数、冲突/UNKNOWN 的反例；需要时 K10 | 明确“权威状态读回”的所有者和事务外副作用表；不能确定的记 UNKNOWN | 本地存储 Commit 不能代表外部接收方 Effect 已提交；超时不能直接报告未发生 |
| **版本前置条件、跨 Writer 冲突** | K01 真正错误合同 → K02 原子性范围 → K03 并发/回读实现 → K05 顺序旧版本 + 竞争者两类独立 Oracle | `CONFLICT`、`CORRUPT`、`UNKNOWN` 的有权判别和不可变事实 | 文件已存在或被锁占用 ≠ 一定损坏；竞态冲突测试不能替代顺序 `--expect` 测试 |
| **测试绿但性质可能没被验证** | K05 [测试夹具/Oracle 有效性](K05/advanced-test-fixture-and-oracle-validity-r15.md)，K08 实际 Runner/环境 | 测试 SHA/发现执行、有效时间窗、正向/阴性/变异、NOT_TESTED | 事后 QA 全绿不能回写旧冻结评分；等待进程退出后稳定 ≠ 回复后的整个时间窗稳定 |

**选择规则是可撤销的建议，不是隐含的强制 Gate**：若任务已有足够有效证据，可以直接用当前已选知识并停止；若 Owner、行为合同或环境未知，先 ASK/UNKNOWN/STOP，不能靠更长知识包弥补缺少的授权。仅当有真正版次迁移才追加 K09；仅当外部 Effect/运行时恢复/容量或可靠性条件命中才追加 K10。保持知识**最小但充分**，不是一律越短越好。

## 3. R3/R4 到底给出了什么证据？

### R3：同一个知识包的阶段变化，没有产生质量优胜证据

R3 对照原始知识投放策略，独立来源/候选/QA 复验确认三组首次冻结实现均 12/12。由于成功率端点**饱和**且每组只有一次，既不能证明增加知识改善了通过率，也不能推出“把所有知识放在 S1”或“分阶段给出”更优。合理收获是：**把 L2 首次设计的可区分决策和独立负例列为未来评价重点**，而不是直接向 ADS 增加固定强制流程。

### R4：同一 S2 阶段，内容选择的可观察差异

R4 两种任务（快照发布与恢复 T1、外部 Effect 账本恢复 T2），A 仅 ADS、B 原 R3 完整七切片、C R14 3168B 最小 L2 卡。原始首次 S2 记录及后置**非盲、定点源码核对**支持：

| Task | A：ADS-only | B：完整切片 | C：最小知识卡 |
| --- | --- | --- | --- |
| T1 首次 L2 | 0 个报告缺陷 | 0 个报告缺陷 | **2 个有文本依据的非关键缺口** |
| T2 首次 L2 | **1 个有合同依据的关键误分类 +1 个非关键缺口** | 0 个报告缺陷 | 0 个报告缺陷 |

T2-A 的真实 L2 错误是：不同内容的竞争者命中 EEXIST 时过早归类 `CORRUPT`，绕过有权 Claim 的重读，导致本应允许的 `CONFLICT` 分支不可达；首次 S5 代码后来采用了不同的处理，不应据此**回写早先 L2 评分**。T1-C 的两处缺口是长时间暂存者与非匹配管理对象的观察/清理前提。其余 CLEAN 是原始评分记录，不是这次对所有 D1–D6 的独立盲重评。

**边界必须显式保留**：

- n=1/任务/组、预注册资源降级到六次、组顺序非完全平衡、原始 QA 的四项异步测试曾由夹具产生假失败；因此实验**没有证明 B 优于 C**，也没有证明“知识导致 A 的失误”。C 并非产品级充分知识的通用基线。
- 原冻结 QA T1 8/10、T2 6/8 **共同主要终点部分无效**；#547 的 Windows v2 10/10、8/8 是**事后诊断补充**，且仍存在状态稳定性和 `--expect` 的未检出变异，不能把 R4 改写成“所有候选满足全部风险”。
- 原 Builder/Reviewer 共用 OS 账户与私有 Release 权限，评审时间戳主要来自协调者记录；没有观察到泄漏，但也不能宣称技术上已经实现严格隔离。今后的真实 A/B 必须实施不同凭据/隔离上下文，而不是只在文件名加 reviewer-only。
- 原始实验结果没有赋予 K01–K11 新的生产 Source Claim、正式 Domain Package、Tally/DomainHarness Runtime 能力或 ADS 强制 Gate。

## 4. 可执行的最小知识交接（候选模板）

在合法 Task 的**决策时刻**生成以下有限、可追溯的阅读建议，而不是一次发送整库：

| 字段 | 含义 |
| --- | --- |
| `TASK_FACTS` | 有权的需求/Scope、Exact Source/Owner/公开接口 |
| `RISK_TRIGGER` | 具体并发、崩溃、持久化、版本或外部 Effect 风险及其证据 |
| `STAGE_AND_OWNER` | 当前 L1/L2/L3/QA 决定由哪个已有职能承担 |
| `SELECTED_KXX` | 不超过任务需要的 Concept/Topic/DP/Source 切片及引用版次 |
| `WHY_NOT_MORE` | 未命中的 K09/K10 等何以不需要；若证据不足写 UNKNOWN |
| `DECISION_TO_TEST` | 被选择的知识应影响哪项具体设计决策、哪条反例可以推翻 |
| `EVIDENCE_LIMITS` | 原始/诊断、Host/OS、未测时间面、身份、成本和独立性 |
| `STOP_OR_HANDOFF` | 必须澄清的问题、合法下一阶段或有证据的结束判断 |

**示意（非真实运行记录）**：任务要求在单节点文件系统下原子发布版本快照，并明确只保证进程崩溃恢复。L2 先读取 K02 状态/提交 Owner 与 R14 卡的崩溃切点，写明哪个元数据和字节构成可恢复的权威版本；L3 由 K03 按选定文件系统和错误合同决定持久化与竞争回读；K05 要求一个“另一 writer 已提交不同摘要仍报告 EMPTY/CORRUPT”必须失败的反例，再检查真实测试发现和影响范围。没有外部 Effect 就不主动发送 K10 外部 Effect 章节。

### 候选算法的停止与反例

1. 如果只有应用错误栈但没有需求/状态 Owner，不得把 K02 的一般原理转成真实批准的架构决议；应返回缺少合同/Source。
2. 如果当前任务是小范围纯静态改动，持续注入七份持久化/竞争文档是**潜在负迁移**而不是知识完整性。
3. 如果首次 S2 设计本身存在重大反例，后续 S4 代码修对了，也只能分别记录“首次设计错误”和“后续实现自修复”，不能在评估时抹去过程事实。
4. 如果测试未观察必要时段或独立对照，返回 `NOT_INDEPENDENTLY_VERIFIED`，不因 CI/诊断绿灯报告更高资格。

## 5. 当前状态、学科完整性与下一道真正的门

本篇只是跨 K02/K03/K05 的**专业知识投影/选择指南**；保留 11 模块、165 个学科课程点、既有来源与先前完整专业正文，既不新增专业知识点 ID，也不删除未命中主题。未来真正由 Tally Domain App/DomainHarness 消费时，仍需要 #286 和 0.11.x 的独立 Consumer/SDK/Package 合同设计、真实权限、BUILD 约束、测试和发布，**本文不是运行时实现计划或已获权的 Domain Harness API**。

具体可应用性必须由新任务的合同、来源和有权 Owner 判定。任何后继多任务统计研究，必须另行预注册样本、随机化/配额、盲评与测试夹具正负/变异控制；R3/R4 不支持现在晋升“最小卡是最优”或“完整包必胜”的现行规则。
