# K01 — 需求工程与业务建模（Requirements Engineering & Business Modeling）

> **内容阶段**：DETAILED_KNOWLEDGE_DESIGN / SOURCE_CANDIDATE / NOT_QUALIFIED。版本 [v2.1.2 #521](https://github.com/kaicreator-mm/tally/issues/521)，模块 [#522](https://github.com/kaicreator-mm/tally/issues/522)；[总索引](README.md)。**ADS 是真实 Agent 开发实验和规范来源，Tally 是选用这些知识的软件工程 Domain App**。本文是解释、方法与案例候选，不因写成文档而成为已批准的规则、真实测试结论或生产 Domain Package。

## 1. 能力目标、适用范围与非目标

让 Agent 从用户说法、既有业务证据和受约束的目标中确定**究竟要解决什么问题**，并把含糊表述变成可确认、可设计、可检验的需求。明确区分真实用户意图、Agent 的解释、待证假设和获得 Product Authority 采纳的要求。对复杂需求能够形成最小需求工作图 DAG-P，但不强制所有请求走长流程。

**典型触发**：新功能、业务流程调整、需求变更、跨角色权限与状态规则发生歧义；简单明确的补丁仍可采用 INLINE。

**输出的工程价值**：减少错误需求驱动的返工；让下游 L2 知道哪些不变量必须满足，L3 能推导有效的行为测试。

**不包含**：不替用户做未授权的业务决策，不编写整个行业业务百科，不把研究结论等同 Product Freeze。另外，本版本不设“代码库理解与逆向分析”和“安全与供应链”两个独立知识专项；实际任务中原本适用的源代码定位、权限、敏感信息与安全底线不因之被豁免。

## 2. 领域概念与边界

| 概念 | 精确定义及判断要点 | 常见误用 |
| --- | --- | --- |
| **Need / Goal** | 用户或业务追求的结果；可以源于明确的真实请求或正式业务来源 | 把某个按钮/表单当成最终业务目标 |
| **Stakeholder / Actor** | 具有不同目标、约束和权限的用户或系统角色 | 只考虑直接点击 UI 的用户 |
| **Requirement** | 对系统可观察行为或属性的约束，具备来源、范围、状态和优先级 | 把 Agent 提议当作用户批准的要求 |
| **Business Rule** | 在明确场景下决定允许、拒绝或计算的业务规则 | 将某个演示数据的偶然值写成通用规则 |
| **Invariant** | 在受约束过程或状态中必须持续成立的性质 | 把理想结果当成已由系统保证的事实 |
| **Acceptance Criterion** | 某个要求是否实现的可测试判据，含输入、前提、预期结果和边界 | 以“体验好”“看起来正确”代替判据 |
| **Assumption / UNKNOWN** | 已说明但尚无足够证据的假设，或未知的必要事实 | 补写一个默认业务决策掩盖 UNKNOWN |
| **Traceability** | Need→Requirement→Rule→Design→Task→Test 的证据链接 | 只列文档标题而无法说明来源和当前性 |

不同概念之间通过具体的来源/适用性/决策/消费者连接，不必为每一个词建立全新的数据库表。只有在真实 Tally 任务中被调用且能够改善工程判断时，才有必要形成可选的结构化资产。

## 3. 专业知识：方法、权衡与失败模式

### 3.1 需求获取不是一味询问用户

先从当前用户请求、已采纳的业务约束、现有合法文档和产品行为提取能确认的事实。针对会实质影响范围或验收的缺口提问：谁可以做、在什么状态做、失败如何表现、是否有例外。若缺口可以通过已有权威资料解决则直接研究；若需要业务授权，不得靠 Agent 猜测。对不影响当前工作的低风险细节可做明确、可推翻的临时假设。

### 3.2 需求分解与质量属性

将目标转成场景与交互：触发事件、前置条件、主要路径、异常路径、数据约束、状态改变及可观测结果。功能要求定义系统做什么；质量属性描述可接受的延迟、可靠性、可维护性、可访问性等，只有与当前产品相关且有来源或决策依据的属性才形成强约束。避免对简单 CLI 文档修改强制设计大型质量矩阵。

### 3.3 业务模型的最小闭环

用领域对象、标识、属性、角色、状态与事件表达规则。区别对象之间的关系、聚合需要保护的一致性边界和跨边界最终一致性；不要因为概念上关联就把所有对象做成单一聚合。每项关键不变量都应能写成正常与禁止的行为示例，并指向验收条件。

### 3.4 歧义与冲突的证据处置

主动检查同词异义、同一动作不同角色、不同来源版本冲突、配置默认值与运行时行为矛盾。先列事实来源与谁有权裁定；若冲突可以在现有授权方案中进行版本/适用范围分解，则解释分解；若是业务选择，明确给 Product Owner 的选项、成本和待回答问题。审查 PASS 不是 Product Freeze。

### 3.5 规格与验收质量

优先用角色-前提-动作-结果或 Given/When/Then 格式写验收，配上错误路径及禁止行为；测试应能在实际用户/接口边界观察，不要仅检验内部私有函数被调用。规格应足够让新加入的 Builder 实现，让 Reviewer 独立判断，避免要求自然语言文档自证实现正确。

### 3.6 范围控制和变更传播

需求增加、删除、修改时识别受影响的状态/规则/验收、L2 设计节点和 L3 Task/测试，保留原版本历史而非覆盖历史。只有真正受影响的证据需要更新；已确认的不受影响条目应被复用。真实需要多个独立研究工作时生成 DAG-P，否则一个有界需求清单足够。

## 4. 可复用 Decision Procedures（决策程序）

每个程序是能由 Agent 实行的**有界决策步骤**，不是另一个 Workflow Engine。任何输出必须保留实际证据与 UNKNOWN，不得自行授予 Product/L2 Freeze、Task Claim、Review 或 Release。

### DP-K01-01 · 从 User Job 到可验收需求

**输入：** 用户原文、当前 Product 版本、已有受权业务来源、有关约束

**执行：**
1. 逐句区分用户已说的事实、Agent 理解与待证假设；为不确定条目标注来源和影响。
2. 列角色、触发场景、正常和禁止行为，识别至少一条关键业务规则。
3. 为每条主要需求补可验证的接受条件，明确数据与状态边界。
4. 对未获授权的业务选择创建有界问题而不默认采用。
5. 检查与现有要求重复、冲突或欠缺的事项，形成最小 L1 交接。

**输出：** 来源约束的 Requirement/Rule/Acceptance 表，以及 UNKNOWN 清单和 Product 决策点

**停止与升级：** 若重要业务规则无法证实则 HOLD 相应决定；不影响的部分可先闭环，研究成果不能代签 Product Freeze。

### DP-K01-02 · 需求冲突分析

**输入：** 两个及以上互相冲突的要求/来源，准确版本与角色

**执行：**
1. 检查是否只是名称不同、时间或角色适用范围不同。
2. 如果确属同范围冲突，提出可选择的业务策略与可观察后果。
3. 用真实源和已有接受条件比较，不根据模型偏好擅自挑选。
4. 交付最小决策问题及影响面，等待有权者确认。

**输出：** 冲突证据表、范围归属、影响范围、备选方案和责任决策人

**停止与升级：** 无 Product 决策时保持 UNKNOWN，不把其中一方抹掉。

### DP-K01-03 · L1 深度选择

**输入：** 当前需求可确定程度、真实独立研究、影响范围和决策成本

**执行：**
1. 需求已完整并有可信来源时使用 INLINE。
2. 仅有几个小问题且无前置依赖时使用 BOUNDED_WORKLIST。
3. 相互依赖或多 Owner 研究、权限/真实用户验证阶段存在时使用 EXPLICIT_DAG-P。
4. 为每个实际节点标注预期产物、阻塞原因和停止条件，复用既有证据。

**输出：** 阶段工作形态及可执行的最小计划

**停止与升级：** 禁止为形式完整而创建空的 DAG 和审批环节。

## 5. Tally Workflow 消费契约

**消费阶段：** L1 Requirements / DAG-P；使用 Tally 已有 Engineering Business、Task/Attempt 与 Agent/Host 事实源，新增的仅是领域知识与程序的调用关系。

| 环节 | 需要从上游获得 | 该模块实际提供 | 必须保留的判断 |
| --- | --- | --- | --- |
| 受理 | 用户原始描述和 Product 当前版本 | 目标/角色/范围及原文来源 | 用户意图不等于已冻结需求 |
| 分析 | 相关合法规则/证据 | 场景、规则、不变量和冲突/未知 | 证据不足时不能默认业务结果 |
| 规划 | 复杂度/依赖/权威 | INLINE/WORKLIST/DAG-P 选择 | DAG-P 不自动创建 L3 Task |
| 确认与交接 | Product Owner 的采纳/处置 | 准确版本的 Requirement/Acceptance | 研究审查成功不等于 Product Freeze |

**跨层交接/复用：** L2 消费被采纳的要求及适用的 UNKNOWN；L3 的测试 Oracle 追溯到 Requirement/Business Rule。K02/K05 共享同一需求语义，不能各自再解释并修改用户原意。

## 6. Agent Skills 与任务输入输出

### SK-K01-01 · Requirements Clarifier

- **何时调用**：用户说法存在多个合理解释
- **最小输入**：原文与已确认 Product、目标场景和适用约束
- **输出结构**：澄清问题（按影响排序）、不确定项、建议选择与后果、现有证据
- **自检**：每个问题影响真实验收/设计；无须询问的事实已从允许的来源获得
- **禁止的捷径**：借澄清机会扩大功能和强行转成长访谈流程

### SK-K01-02 · Business Rule Modeler

- **何时调用**：新功能影响状态、角色或业务对象
- **最小输入**：可追溯的需求、场景、规则及已有对象
- **输出结构**：对象/关系/状态/约束矩阵、正常/非法转换、Acceptance 和仍未知条件
- **自检**：每条业务不变量都至少能找到一个正例和禁止行为
- **禁止的捷径**：未得业务授权就断言复杂聚合/权限策略是正式需求

## 7. 贯穿案例：正例、变体与反例

以下为**教学/设计情景**，不是宣称 ADS/Tally 已经执行或验证过的真实项目记录。实际资格认证必须替换为来源可核查的真实 Issue、源码版本、测试/Review/Host 收据。

**场景**：产品新增“取消订单”能力。用户只说“订单页面加入取消按钮”，未说明已发货、退款及重试时的行为。

**正确处理路径：**
1. 从原请求确认用户希望取消，但不假设任何状态都可取消；列出订单状态与角色权限的待确认点。
2. 生成候选规则：仅在被明确批准的状态允许取消；其余状态返回可行动的业务错误，并保持订单不变。
3. 将退款、物流撤回、撤销窗口列为需要业务决策的 UNKNOWN，而非 Agent 直接选择。
4. 以可测试的 Given/When/Then 形式给出未发货订单取消、已发货拒绝、重复取消、权限不足四条候选验收。
5. 把已确定规则/验收交 L2 的状态和接口设计，后续测试覆盖正常/失败和重复请求。

**成功的可观察标准：** 不同状态产生受业务规则约束的结果；未确定退款政策绝不自动标记已实现。

**错误处理路径与后果：** 直接写“任何订单都可取消并自动退款”，因为它看似用户友好；后续代码即使通过全部自编测试，也违反真实业务约束。

**情景变体与边界：** 若用户明确批准“取消只影响未履约订单”，则将已拒绝状态作为负例；若现有版本以前允许取消某类已履约订单，必须按实际版本和来源单独处理。

## 8. 反例库：哪些情况不能据此推断成功

1. **伪澄清**：重复询问已经在有效文档中确定的事实，增加用户负担而不提高准确性
2. **无来源的规则**：Agent 按自己熟悉的行业惯例填入退款/权限政策
3. **测试无法观测**：接受标准只写“符合业务逻辑”，独立测试者无法判断
4. **研究即冻结**：L1 Evidence/DAG-P 完成即宣称 Product 已批准
5. **无限需求扩张**：发现未知项后不区分影响大小，阻止所有无关实施

## 9. 训练题与验证矩阵（后续可转换为 Cases / Validation）

| 任务/情景 | Agent 期望判断 | 错误或危险结果 | 最小证据 |
| --- | --- | --- | --- |
| 模糊“可批量撤销”需求 | 识别角色/适用状态/部分失败策略未知 | 假设全部记录可删且永久成功 | 用户原话+具体状态与操作源 |
| 两角色对取消权限不同 | 将角色条件映射为规则和负例 | 无条件向所有角色展示/允许取消 | 批准的角色/权限规范 |
| 旧版本规则冲突 | 标注版本差异及权威裁决 | 覆盖旧决定不留痕 | 两版本来源与有效区间 |
| 简单文案修改 | L1 INLINE，少量验收即可 | 创建 6 个研究 Issue | 当前任务范围及明确需求 |
| 研究完成但无 Product 批准 | 提交待裁决项而非 Freeze | 以 Reviewer PASS 代 Product Freeze | 真实 Product Authority 收据 |

**不完整证据的表示**：缺少用户业务决定、来源版本、真实调用结果或正式环境时，记录 `UNKNOWN / NOT_RUN / BLOCKED`，并写明下一项最小可验证事实。案例/模拟结果不能冒充真实 Agent 开发效果。
