# K11 — 工程经济学与工程决策 / Engineering Economics & Decision-making

> [v2.1.2 #521](https://github.com/kaicreator-mm/tally/issues/521) · 模块 Issue [#532](https://github.com/kaicreator-mm/tally/issues/532) · [总目录](README.md)。`DETAILED_KNOWLEDGE_CANDIDATE / NOT_SOURCE_QUALIFIED / NO_RUNTIME_ADOPTION`。ADS 负责 Agent 真实软件工程实验、实践及现行工程规范，Tally 负责把合格知识接入软件工程领域工作流。案例为可供未来验收的教学情景，不表示已经实测通过。

## 1. 本模块能让 Agent 解决什么

让 Agent 优先解决真正影响用户交付与工程质量的问题，按实际复杂度选择**最小充分**的设计、Task 拆分、验证和协作深度，同时不以“省钱”作为跳过必要质量底线的理由。知识应帮助 Tally 在方案、工作计划、质量风险和重复修复之间作有来源的取舍，而不是建立额外复杂成本优化系统。

**适用与触发：** 多个技术/交付方案需比较、复杂度驱动 Task DAG、重复 CI/Review/Agent 重试浪费、长期阻塞或实际技术债收益不明确；小而确定的工作不要求独立经济评估报告。

**明确不做：** 不要求每次任务都估算 Token 单价和 ROI，不新建通用 Agent 成本优化器或把主观评分当作真实用户交付。现阶段不新增独立的代码库逆向分析和软件安全/供应链知识专项；已生效的权限、基本安全和实际工程质量约束仍应执行。

## 2. 术语表、关系与边界误区

| 概念 | 可使用的工程定义 | 必须避免的推断 |
| --- | --- | --- |
| **Value / Outcome** | 交付后用户/业务/工程系统真实获得的结果 | 以 commit、PR、Issue 数量替代交付收益 |
| **Opportunity Cost** | 资源用在此任务时无法用于其他更重要任务的代价 | 只考虑直接 Token 成本 |
| **Total Engineering Cost** | 研究、Agent 运行、Review、CI、集成、故障修复与维护的总成本 | 把某个阶段最便宜当全生命周期最便宜 |
| **Marginal Value** | 额外研究/审查/工具给当前目标增加的实际收益 | 所有检查做得越多越好 |
| **Risk / Assurance Floor** | 失败后果和现行权限/测试最低要求 | “小改动”就省去高风险必须验证 |
| **Reversibility** | 错误决策修复/回滚的难易和后果 | 所有方案都能无代价回退 |
| **Evidence vs Estimate** | 实测资源/时间与基于假设的成本模型 | 把未经测量的估算写成 observed |
| **Work Shape Choice** | INLINE/BOUNDED_WORKLIST/EXPLICIT_DAG 以实际依赖和不确定性选择 | 所有版本一律用大型 DAG |
| **Outcome Evaluation** | 真实任务完成、缺陷、返工、延迟、资源的可比观察 | 单个 LLM answer 得分证明软件工程普遍改善 |

这些概念可以作为 Domain Concepts/Knowledge 与 Tally Workflow 的语义输入，但**不是**新增通用数据中心或自建 Task/Claim/Release 权限状态机的理由。

## 3. 专业知识正文：原理、应用、代价和限制

### 3.1 评价单元应是工程结果

开发效率不能简单用完成 Issue 数、行数、模型对话轮次、PR 数或者 AI Token 消耗衡量。对于 Tally 软件工程的重点是：用户需求是否真实实现、错误是否泄漏到发布、测试是否有效、方案是否可维护、是否有重复修复/过量验证以及实际耗时。一个有用的工程决策应事先说明要改善哪个真实结果，而不是只追求活动更丰富。

### 3.2 选择技术方案的总成本

从现有成熟实现复用、引入依赖、局部自研、建立框架、升级旧系统中比较初始集成、部署/兼容、测试、Review、Agent 能力要求与未来变更成本。复用并不永远更便宜：复杂授权、API 限制、维护风险也可能让小范围自研更合理；但新方案必须基于证据，而不是喜欢某个工具或模式。

### 3.3 适应性工程深度与质量下限

小且明确的需求可 INLINE；几个问题以 BOUNDED_WORKLIST 组织；真实独立研究与实施才使用显式 DAG。探索性和高保证并不互斥：前者说明不确定，后者由后果与适用权威决定。即使只改三行代码，若可能破坏资金/权限/不可逆状态，也必须保留相应质量验证，而不是 Fast Path 全部豁免。

### 3.4 多 Agent 并行是否值得

先确定可以合法分离的工作产物和稳定合同，再比较并行节约的时间与额外交接、重复读上下文、写集冲突、合并、重复 Review/CI 成本。多个 Agent 都空闲不代表应拆分同一个原子修复；相反，对于真正独立的只读研究或互不交叉的模块合同，合理并行可以缩短关键路径。不能将总 token 支出等同于交付耗时。

### 3.5 研究与验证的边际收益

额外调查是否能影响某个材料性决策？多跑一遍 CI 能否覆盖新的代码/环境/独立性要求？如果答案是否，重复步骤可能是浪费。已确认 source/exact SHA 的成功证据可在适用范围内复用，但缺少真实 Host/授权/独立 Provider 的必须验证不能因为本地测试通过就跳过。区分“检查数量多”和“真实错误被识别”。

### 3.6 工程经济学中的不确定性

成本估计可能没有工时、云账单、Agent 调用时长和真实 CI 网络时间等数据。必须把 observed、estimated、unknown 分开；在不知道外部工具收费或耗时时不造数字。比较方案时宜给成本分类、重大风险与范围假设，不强制所有任务都带严谨财务模型。对不可逆或高不确定方案，先进行可证伪的小实验更有价值。

### 3.7 经验对照与学习闭环

ADS 提供真实 Agent 工程实验与失败反例，Tally 采用选定领域方法。评估是否有益要选择可对比的真实编码任务，事先确定验收/Review 规则、独立评分、用户路径和预算，再比较直接 Agent 与知识辅助。历史 v2.1.1 小模型 7 对问答即使得分改善，也不能代表大型项目开发质量普遍改善；负效果、遗漏回归和成本也须报告。

### 3.8 何时停止与收敛

当核心功能已真实满足要求、剩余风险被允许的权威处置并且没有高价值未完成工作时应停止持续研究/新增治理/无界修复。出现同根因重复失败应检查是否真的增添了新证据，转换为 K06 的有界根因调查；不得通过继续创建 Issue 逃避已有工作收尾。

## 4. Agent Decision Procedures（决策方法）

### DP-K11-01 · 工程方案成本与价值比较

**输入：** 同一目标下两个及以上可行方案、实际任务/环境、质量与业务权威

**操作步骤：**
1. 明确用户/工程希望达成的可观察结果及不得降低的质量底线。
2. 列可行方案与必要依赖，排除明显越权或不能集成的候选。
3. 对各方案分别考察实现、Review/CI、集成、维护、恢复和机会成本。
4. 记录已观察成本、估计假设和未知风险，避免伪精确报价。
5. 选可交付质量目标下边际价值最大且合理有界的方案，并给出停止点。

**输出：** 权衡表、选择理由、风险/成本来源、后续需要的证据

**停止与例外：** 不能为了看起来便宜而覆盖不可降低的权限/验证底线。

### DP-K11-02 · 选择是否研究/并行/重复验证

**输入：** 当前阶段的实际未知、真实依赖、已有合格收据和执行成本

**操作步骤：**
1. 识别新的工作是否真正影响当前决策、当前 HEAD 或质量要求。
2. 根据材料性和依赖判断 INLINE/WORKLIST/DAG，而非凭习惯。
3. 比较单 Agent 完成与多 Agent/CI 的交接、冲突和产出收益。
4. 必要情况下安排小型研究/验证，并在没有新收益时停止。

**输出：** 阶段工作形态和需要验证的最小问题清单

**停止与例外：** 高后果/保护性约束不能被时间成本替代。

### DP-K11-03 · 受控 Agent 效用评估

**输入：** 若干真实任务、固定验收标准、基线 Agent、选定知识版本/实际用例

**操作步骤：**
1. 预先固定任务范围、验收与质量指标、评估预算和独立 Reviewer 条件。
2. 执行直接 Agent 和 Tally 选择知识辅助两种可比路径，保持公平环境。
3. 收集实际需求正确性、缺陷/回归、测试覆盖有效性、返工/重复修复和成本。
4. 呈现有效改进与负面结果、样本局限与未知外推范围。
5. 只有证据真正支持时才扩大某知识模块的资格/消费范围。

**输出：** 可追溯局部效用报告和下一轮 ADS 实验建议

**停止与例外：** 不能用单次问答或非独立评分宣布全领域性能提升。

决策方法的输出是候选依据和建议；不自动获得产品采纳、Architecture Freeze、Agent 执行权限或 Release 状态。

## 6. Agent Skills 与输入输出契约

### SK-K11-01 · Engineering Trade-off Analyst

- **调用条件**：至少两种可行路线且区别会影响工程质量/总成本
- **输入**：真实目标、可行候选、现行保证、环境与资源证据
- **输出**：同一维度的方案矩阵、推荐与替代方案、适用范围/待测变量
- **核验要点**：估计与实测分开，无法核实数字不写为事实
- **拒绝或升级条件**：不能把单一 Token 成本压到最低作为唯一准则

### SK-K11-02 · Adaptive Work Stop Planner

- **调用条件**：任务过度拆分、重复研究/CI 或版本久未收尾
- **输入**：当前真正未完成结果、真实依赖、已合格/缺失证据和价值
- **输出**：最小下一步或应当停止的条件、受影响验证范围
- **核验要点**：没有额外研究收益时明确结束准备工作
- **拒绝或升级条件**：不允许反向规避高风险真实 Host/独立审查

### SK-K11-03 · Task Outcome Evaluator

- **调用条件**：ADS 实践或 Tally 已收集足够真实工程结果
- **输入**：固定任务集/验收标准、实际源/Review/CI/Agent 消耗
- **输出**：对照正确性、返工、缺陷、时间、成本和局限的效用报告
- **核验要点**：如样本数少、不是公平对照就明确不可外推
- **拒绝或升级条件**：不能修改原始收据或自评成果取代独立验证

## 7. 完整教学案例：正确实施、错误做法及边界

**任务情景：** 一个现有 Web 产品要新增导出字段并修复一处错误处理；管理者提议同时创建 8 个 Agent、5 层 Review 和整仓测试以确保万无一失。

**合理的工程路线：**
1. 首先确认用户真正要的新字段与失败行为，判断 L1/L2 是否已有明确依据。
2. 如果没有新架构风险，则 L1/L2 INLINE，实施保持一个可独立验收 Task；如真实涉及公开合同变化再调用适用 L2 设计。
3. 把相关字段构造、错误处理与受影响测试交同一 Builder 完成，避免将互相依赖的细节拆成八个 Issue。
4. 执行有效语法/类型/受影响合同/集成测试；仅在需要时执行真实 Host/Release 的适用检查。
5. 通过实际任务完成、缺陷与返工证据评价这一方案，相比多 Agent/多 CI 有无真实时间或质量收益。

**可观察的正确性：** 用户请求和现有行为被真实验证，额外协作/验证没有掩盖质量缺口，总工程成本可以解释且未知处未编造数字。

**反向/失败方案：** 因为 Agent Token 即将到期就让八个 Agent 同时修改重叠文件，重复二十次 CI；最后 PR 很多却没有真实用户功能验收。

**适用条件变动：** 若改动实际涉及不可逆数据迁移或重大接口/高后果功能，即使代码只有三行也必须保留适用的设计与独立保证，不以 INLINE 省去必要验证。

## 8. 反模式及不该泛化的教训

1. **Proxy Metric**：用任务/PR/代码行/Token 消耗代替工程结果
2. **False Cheapness**：最便宜的单个步骤导致更高集成/修复成本
3. **Unbounded Parallelism**：用 Agent 数量提升“进度”而大量共享写冲突
4. **Excessive CI**：相同来源同范围旧证据无变化仍反复执行
5. **Fake ROI**：把估算或主观评分写成实际 ROI
6. **Fast Waiver**：以小改动名义跳过真正的质量/权限保护
7. **Research Forever**：不断开研究 Issue 推迟真正交付/收敛

## 9. 有界训练与未来验证场景

这是一组供知识审查与后续消费者验证的**设计案例**，没有被标为实际 Host/Agent/CI PASS。

| 情境 | 期望工程行为 | 被禁止的判断 | 真正需要的证据 |
| --- | --- | --- | --- |
| 普通局部错误提示 | INLINE 与受影响测试 | 强制三层显式 DAG/全量 CI | 当前范围/测试合同 |
| 重大不可逆迁移 | 保留受影响设计/风险保证 | 只按代码行数判断风险低 | 业务/持久化恢复要求 |
| 两组 Agent 总费用不同 | 比较真正完成质量、集成/返工成本 | Token 少就自动最好 | 实际 Task/CI/Review/修复时序 |
| 已有相同 SHA 合格 CI | 可在合法范围复用并停止无谓重跑 | 所有 PR 必须再跑全部测试 | 证据当前性/实际强制校验 |
| 小模型 7 问答局部改善 | 仅报告受限样本观察 | 宣称所有编码工作必然提升 | 冻结题目与真实评估记录 |
| 两轮同源失败且无新证据 | 及时收敛或切换根因验证 | 持续新增同类补丁任务 | 历史 Attempt 与失败因果 |

实际效用评估应先冻结测试任务、预算和验收标准，再比较直接 Agent 与选用本知识后的 Tally Agent 在真实软件开发中的需求实现、回归、修复、返工、耗时及成本。不允许以题库问答效果代替实际源码和用户行为，也不得虚构定量提升。

## 附录 A · Agent 直接调用的工作示例（非正式 Wire Schema）

**教学输入：** 一项小幅 UI 变更，有人建议为其派多个 Builder、建立复杂 DAG 并重复全量 CI。
- 使用知识：Outcome、TotalCost、MarginalValue、AssuranceFloor，执行 DP-K11-01/02。
- 期望产物：单 Agent INLINE 与多 Agent EXPLICIT_DAG 两方案的真实依赖、交接、Review/CI、返工成本和质量要求对比。
- 判断：无新风险或真实独立工作时优先最小有效流程；有高后果/真正 Host 验证要求时保留其不可省略部分。
- 停止与交接：未测量的成本记 `ESTIMATED/UNKNOWN`；不能仅凭模型问答评分或 token 消耗声称质量提升。
