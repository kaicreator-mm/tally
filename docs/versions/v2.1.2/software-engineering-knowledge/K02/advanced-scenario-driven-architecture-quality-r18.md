# K02 · R18 进阶：以质量属性场景评价架构，而不是评价图画得是否漂亮

> `DOCUMENT_CANDIDATE / QUALITY_EVALUATION_METHOD / NOT_A_PRODUCT_RULE` · [K02](README.md) · [既有架构决策方法](engineering-methods.md) · [跨模块质量知识选择](../professional-quality-risk-knowledge-selection-r18.md) · [#551](https://github.com/kaicreator-mm/tally/issues/551)。
>
> 学科背景：[ISO/IEC 25010:2023 产品质量模型（官方九大特性）](https://www.iso.org/standard/78176.html)；[SEI ATAM 评价方法集合](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/)；[SEI 架构可扩展性分析](https://www.sei.cmu.edu/library/extensibility/)。以下是基于这些专业方法**自行推导的限定工程审查方法**，不是对受版权保护标准全文的复制，也不证明任何特定架构合格。

## 1. 质量不是图或模式的数量，而是特定环境下可达成的行为

一种架构可以有正确的模块图、ADR 和项目结构，却在并发、故障、数据升级或新增需求时表现不合理。评价必须首先记录：

| 场景字段 | 实际追问 | 缺失时 |
| --- | --- | --- |
| `SOURCE` | 谁或哪个事件触发？是用户、其他系统、并发 Worker，还是故障？ | 不凭空补业务 Actor |
| `STIMULUS` | 引起什么变化，例如重试相同请求、停机后恢复、添加新的输出格式？ | 避免“高可用/可扩展”空词 |
| `ARTIFACT` | 哪个 Package/状态存储/公共接口受影响？ | 不把界面图等同实际依赖 |
| `ENVIRONMENT` | 正常、竞争写入、版本迁移、异常网络或进程重启？ | 不默认单机行为能代表掉电 |
| `RESPONSE` | 系统必须如何决策、失败或保持不变量？ | 不由架构评审者擅造业务规则 |
| `RESPONSE_MEASURE` | 什么可观测事实能说明要求达到，例如修改受限的模块、恢复一致、没有跨租户访问？ | 没有已授权阈值写 `UNKNOWN`，不编造数字 |

六字段用作**审查推理框架**。不要求每个普通 Task 填六格；只有对关键结构权衡有区分价值时才采用完整场景。ISO 25010 的质量特性不能代替实际项目中的明确阈值或真实需求授权。

## 2. 从有权要求推导能推翻方案的最小场景

**步骤 A：识别驱动和状态 Owner。** 记录真正有权的需求/不变量、写者、读者、外部 Effect 和持久事实。避免把“API 调用了另一个模块”误当“拥有该模块状态”。判断数据 Owner 时要看写入职责和故障恢复依据。

**步骤 B：画出现有代码的真实依赖图。** 分开 Package 的编译时直接依赖、运行时调用、共享数据模型、外部协议、跨进程通信；逐一找出循环、越界访问、共享可变状态和缺失的接口契约。依赖方向好看但要改一个状态仍要同时改五个地方时，依然可能是坏边界。

**步骤 C：比较至少两个实际可行方案。** 简单模块化单体 vs 分出独立 Service；显式状态拥有者 vs 各层写公共状态；按需接口 vs 无需求的多层抽象。比较当前需求、变更传播、错误/恢复、集成、观测、维护成本，不机械将“更多层、更高可配置性”打高分。

**步骤 D：为候选写一个反例。** 例如“引入新输出格式时，是否要改核心持久化和每个消费者？”；“Worker A 先提交，B 读取 EEXIST 能否分清同值/异值冲突？”；“新增一个 Provider 是否破坏既有 API 的错误语义？”；反例可来自已授权质量场景，不得偷看隐藏评估需求。

**步骤 E：独立记录权衡。** 给每个决定说明证据、假设、被拒方案、适用范围、可能推翻方案的事件、剩余 `UNKNOWN` 和何时需要复评。ADR 自述 `PASS` 不构成架构独立合格。

## 3. 错误分类：比主观 1–5 分更有可复核性

| 发现 | 证据门槛 | 如何处理 |
| --- | --- | --- |
| `MATERIAL_ARCH_DEFECT` | 从现有有权质量场景可构造可执行或可论证的失败路径；违反状态 Owner、约束、隔离、故障行为或强制兼容性 | 记录真实触发/具体职责冲突/可反驳事实；不靠审美 |
| `NONMATERIAL_DESIGN_RISK` | 设计有实质可维护/复杂度代价或依赖风险，但当前要求未必失败 | 提供替代方案及其真实成本，不能直接判不合格 |
| `OVERDESIGN` | 增加模式/Adapter/层级/配置使当前合法场景变难、重复协议或未带来可观测收益 | 说明冗余路径/删除后仍保留的合同，不只数接口 |
| `UNKNOWN_OR_NOT_TESTED` | 缺少实际部署环境、真实数据/消费者、Owner 决议、可观察恢复边界 | 明确下一个合法最小探针，不能补假设当证据 |

一个模块承担多职责并不自动失格；若状态边界紧密且将它们拆开反而使交易一致性更难证明，保留单模块可能更合理。反之“接口稳定”不能为循环依赖或越权共享状态开脱。

## 4. 简单例子及反证

**原创教学例（非 R18 隐藏任务）**：某工具读取配置，把不同设备的公开记录格式化为文本。设计 A 含五层抽象和可插拔 Registry；设计 B 用单一解析入口与两个格式化函数。若当前没有运行时插件/多部署需求，B 可能更易理解和演进。若后来有被授权的第三方动态插件、隔离版本和支持合同，A 的额外结构可能具实益。**“B 更少行”不是理由；必须引用真实可观察改变和未来已知场景。**

**反例 1**：一项独立部署要求强制不同 Provider 的权限隔离，仅凭“模块化单体更简单”拒绝隔离是错误的。

**反例 2**：同一持久事务跨两个包协作，拆成两套独立写者以达到“单一职责”却制造半提交，架构质量降低。

**反例 3**：候选首次 L2 把状态写在不能持久表达的提交阶段，S4 后来改正；应记录 `FIRST_L2_DEFECT` 与 `S4_REPAIR` 两个事实，不能事后改写原始 L2 评分。这是 R3/R4 研究的一般方法边界，不提供未来隐藏题答案。

## 5. 与其它模块及未来评价的接口

- K01 提供有权需求、Actor 与不可擅定的质量阈值；K02 只判断结构决策及不同设计方案。
- K03 证明实施后的真实依赖/调用语义；K09 判断后续修改传播、回归成本；K05 独立审查质量场景与可证伪测试；K11 比较总成本和不确定性。
- 一个真实评价单位至少保存：`Task/Source_SHA`、`FIRST_L2_SHA`、`QualityScenario_ID`、`Boundary/Owner`、`Finding/Class`、`Falsifier`、`Alternative`、`Reviewer_ID/Blindness`、`NOT_TESTED`。
- **停止条件**：已提出的分歧只涉及样式偏好/题目没有有权质量驱动/继续深挖无法改变决定，则复用已接受架构与轻量记录，不创建无谓复杂度治理。

**资格边界**：本篇只完善专业领域知识，不添加 ISO 正式证书、Tally 架构评分 API、DomainHarness 消费 ABI、ADS 必经 ATAM Gate，也没有运行新的 Agent/实验。
