## 一、架构视图是有目的的投影

Context 视图看系统与环境；组件视图看职责与调用依赖；数据/状态视图看真实提交与持久化；部署/运行视图看故障域、容量和可恢复性。若所有问题都画在一张“万能类图”上，可能既看不见客户流程，也看不见关键失效点。

同一个“订单已处理”有三层事实：业务上何时允许宣告完成（K01）、哪一个状态 Owner 对结果负责（K02）、具体事务何时提交（K03）。在架构评审里，这三层不一致时不能用新框架命名消除矛盾。

## 二、模块划分是控制变化传播

比较两种结构：`UI -> DatabaseClient` 直接调用与 `UI -> ApplicationPort <- PersistenceAdapter`。后者通过稳定合同隔离技术选型，但新增间接层也增加接口、测试和调试复杂度。只有多个消费者、数据库可能更替、测试边界或能力授权确实需要隔离时，抽象的收益才可验证。

依赖倒置不等于“每个函数都必须有 interface”；开放扩展点也不等于允许 Package 隐式调用未声明依赖。BUILD/运行时的实际 Extension 规则应以对应 DomainHarness 版本的已确认合同为准，不能由本章发明新的 Package 解析/许可协议。

**违反边界的反例**：一个插件直接 import 宿主内部事务连接，并写入宿主独占的状态表；即使所有 TypeScript 类型正确，资源和状态 Owner 仍被破坏。

## 三、分布式状态的正确性要写成安全性与活性

- **Safety（坏事永不发生）**：例如同一有权交易 ID 不得重复产生不可撤销的结算副作用。若缺少真正的幂等合同，这一不变量只是候选。
- **Liveness（好事终会发生）**：例如合法 Job 最终完成或给出明确可恢复失败；必须补充公平性、外部依赖可用性、重试预算等必要假设。
- **Fault Model**：进程崩溃、重复消息、网络分区、超时后响应丢失、时钟漂移可能导致不同后果。

仅证明 safety 不能证明作业有进展；仅证明队列最终清空不能证明没有双重副作用。将关键状态压缩为枚举（NEW、CLAIMED、APPLIED、ACKED）可用有限状态探索辨别重放/中断错误；如果枚举抽象遗漏数据库/远端效果，模型检验结果只覆盖该抽象。

**状态序列教学反例**：写入远端后、写本地 ACK 前崩溃；重启根据旧状态重新执行。必须检查幂等 ID、Effect 查询和合法恢复策略；“执行成功一次”不足以保证 crash/replay 安全。

## 四、数据库隔离不是一个可随意替换的标签

在 PostgreSQL 18，Read Committed、Repeatable Read 与 Serializable 提供不同并发可见性/异常约束；不是所有 SQL 引擎都完全相同。业务“只有一个 Owner 可以更新当前 Task”的要求还需明确冲突检测与失败重试，而不是因为事务用了 Repeatable Read 就推断任意跨服务状态串行化。即使 DB 的 Serializable 提供强保证，也不自动覆盖第三方 HTTP Effect。

给定两个交易并发读取余额、再各自扣款的教学场景，检查是否存在不能同时成立的最终状态，必要时用**真实目标数据库与所选隔离级别**反证，不能把理论表格冒充实际运行 PASS。

## 五、架构演化与重新评价条件

一份 ADR 要同时记录有效情景和失效阈值：原来仅单机操作→新增多实例；原来没有旧客户端→开始滚动升级；原来允许丢作业→改为可恢复。出现前提变更时才触发受影响架构复核，而不是每次微小重构重新冻结全系统。

**可观察教学任务**：要求比较内存 Job 与持久 Job 两种图，明确真实 Owner、提交点、外部 Effect、可运行的中断/重放反例、选定方案要牺牲的质量属性。禁止从模型检验工具可用性推断已形式证明。

**未知与停止条件**：真实业务提交条件、目标数据库隔离级别或外部 Effect 的权威来源缺失时，输出 `UNKNOWN/STOP_FOR_AFFECTED_DECISION`；可以提出形式模型与失败注入候选，但不能将未运行的 TLC/DB 测试写成 PASS。独立技术探索不因此阻塞不受影响的实现。
