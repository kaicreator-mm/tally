## 1. 架构决策是对约束的选择，而不是选框架名称

架构关注组件责任、依赖方向、状态所有者、部署形态与系统重要质量属性；详细函数/语法属于 K03。先从 Stakeholder 的 Concern 写出**可测的质量场景**：刺激来源、刺激、环境、受影响构件、期望响应、可观察度量。比如“运行中断后允许恢复”必须确定：什么作业、如何恢复、是否允许重复、容忍的丢失和耗时、受支持的运行平台。

“高性能”“可扩展”不是可用于选型的测量合同。架构 ADR 的最小记录为：问题事实、约束、可行备选、为何选此项、牺牲项、失败时回退/重新评估条件。不要把候选设计当成生产已通过的 L2 Freeze。

## 2. 模块边界与数据所有权

一个组件的公共合同包含输入、可观察输出、拒绝/错误和时序约束，不能只提供 TypeScript interface 就断言消费者兼容。数据所有权要能回答：谁允许改变状态、哪项事实为源、提交点在哪里、哪个系统只能读取投影。

对持久批处理：
- 内存 Queue 可能实现低延迟，但进程退出后未提交任务可能丢失。
- 持久 Job Store 能跨重启保留工作，但需声明 Job ID、提交事务、租约/接管、重复执行策略及观察一致性。
- 分布式队列并非默认最佳；复杂度、部署和运维成本是选择条件。

对于跨服务“先写数据库，再调用支付网关”，本地数据库事务不能使远端副作用一起原子提交。若超时后远端是否已提交未知，必须区分 `UNKNOWN_EFFECT` 与 `FAILED`，后续由 K10 定义安全恢复策略，K03 做具体实现。

## 3. 一致性选择中的具体失败模式

| 设计因素 | 需要的问题 | 错误推断 |
| --- | --- | --- |
| 单写者/多写者 | 并发更新时如何拒绝旧版本写入？ | 锁住一个进程变量就保证分布式一致 |
| 消息投递 | 至少一次投递时有无稳定业务请求 ID？ | ACK 代表业务副作用只执行一次 |
| 事务边界 | 本地提交与外部调用发生在什么顺序？ | DB rollback 同时撤销外部 API 调用 |
| 可恢复性 | 崩溃后怎样读回进度并安全接管？ | 重启后队列为空就说明工作完成 |
| API 兼容 | 旧消费者可能如何解释新增状态/字段？ | 新 Schema 能编译就能滚动升级 |

“恰好一次”通常必须限定在特定存储/协议/副作用范围，不能笼统承诺所有外部系统全局 exactly-once。若条件不足，保留 ASK/UNKNOWN，而不是自动引入事务协调器。

## 4. 有界架构实验：用最小事实区分两种设计

**教学 Demo 目标**：判断内存 Queue 是否满足“重启可恢复”。准备 5 个 Job，在处理第 3 个时强制中断，再启动同一服务；记录提交/未提交 Job、外部副作用次数、恢复结果和耗时。对照持久 Job 候选在相同输入和崩溃点的表现。

可证伪条件：若丢失尚未完成的 Job，内存候选违反该恢复需求；若持久候选重复执行造成不可接受副作用，不能因为数据仍在就宣布已达成质量目标。Demo 只是研究证据，必须由现行合法 L2/Task/Host 机制评价，不直接晋升 Release 资格。

## 5. 有界专业判断

优先研究会真正改变选择且当前未知的关键假设。小型单进程工具未要求持久恢复时，不应因教材示例默认部署多副本数据库/消息中间件；真实业务需要跨重启一致性时，也不能因为内存实现简单就忽略故障。跨模块：K01 给质量目标，K03 实现条件写与 ID，K05 提供失败注入 Oracle，K09 负责滚动升级兼容，K10 提供生产观测，K11 比较全生命周期成本。
