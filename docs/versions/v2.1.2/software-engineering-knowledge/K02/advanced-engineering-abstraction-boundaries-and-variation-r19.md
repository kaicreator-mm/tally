## 一、抽象的目标是封装真正的变化，不是把步骤分成更多文件

工程抽象回答三种不同的问题：

- **概念抽象**：哪些操作依赖同一个*稳定业务不变量*？同名、同语法、同数据结构并不必然是同一个领域概念。相同概念如果错误行为和授权条件不同，可能需要分开表达。
- **机制抽象**：哪些算法/状态变化/资源操作具备相同前置条件、后置条件、故障语义与资源生命周期？只有共享这些约束，才有资格抽取公共机制。
- **模块/边界抽象**：哪个真实 Owner 拥有哪一份权威事实，哪些可能变化的实现决策应该在内部隐藏，哪些稳定行为必须作为公共契约？文件、类和包不是天然的权威边界。

**模块划分依据不是所有用户操作流程，也不是某种框架惯例。** 如果两种流程在数据持久化、错误优先级、隔离权限或生命期上不同，合并为一个仅按操作名称切换分支的巨大 `Manager` 未必是抽象，反而可能是职责纠缠。反过来，为每个输入参数建立一套工厂也不会自动提升扩展性。

## 二、抽象候选的“六问”决策程序（DP-K02-R19-01）

| 顺序 | 必须知道的事实 | 操作与可证伪产物 | 缺失时 |
| --- | --- | --- | --- |
| 1. 来源 | 当前有权的 FR、质量属性、用户/消费者和数据来源 | 列出当前必须成立的*不变量*以及支持它的 Source，不补编需求 | `ASK/UNKNOWN`，不创建猜测的领域类型 |
| 2. 变动 | 哪些行为已经不同，哪些将被授权独立变化 | 对每个变化列出触发、Owner、可能影响的消费者；未来猜测标 `SPECULATIVE` | 未知未来不以“以后可能变”创建公共 API |
| 3. 共性 | 候选操作是否有相同输入/输出、授权、错误、事务、幂等和清理语义 | 逐项寻找反例；若存在一个不相容的稳定差异，就不强行并入单一公共行为 | `WRONG_ABSTRACTION_RISK` |
| 4. 隐藏 | 让何种内部选择变化时消费者无需了解/同步修改 | 指定模块 Owner 与允许/禁止的直接依赖；明示要隐藏的内部决策 | 若没有确定的“要隐藏什么”，不要凭模式增加接口 |
| 5. 备选 | 不抽象 / 局部 helper / 专属模块 / 稳定边界接口 / 可替换策略 | 比较至少两个*实际可行*方案的真实依赖、调试、故障、变更传播和学习成本 | 不以多层架构天然优于简单实现 |
| 6. 反证与停止 | 下一项已知变化、故障、阅读者问题能否推翻决定 | 写下会迫使改边界的具体观测；明确 STOP 与重新评估触发 | 只有风格偏好则保持现有实现 |

六问是一种**按风险选择的思考方法**，不是每个小改动都必须填写六个模板字段。来自项目真实权限的质量场景优先于所谓“最优架构模式”。

## 三、对不同边界选择的比较（原创教学材料，非实验案例）

某 CLI 需要将两种不同来源的传感器测量显示成相同的终端表格。**显示格式**确实可以复用，但**采集**可能具有不同超时、重试和错误语义。选用同一个格式化函数不等于可以合并两个设备的采集生命周期；不应为了行数更少把故障处理藏到统一的 `catch { return [] }`。反过来，如果只支持一个静态格式和一个终端，不必建立插件发现、工厂注册和配置 DSL 才能输出表格。

可以独立改变的是显示样式和设备接口；不能轻易混同的是设备错误、已采集/未采集状态与数据质量。真正的决定依赖现有 Source、消费者和故障模型；若未来新增动态插件是未获授权的猜测，不应为了它现在强制建立框架。

### 结构性坏味道与必要证据

| 观察 | 可能错误 | 什么才算证据 |
| --- | --- | --- |
| 相同逻辑在三个文件出现 | `UNDER_ABSTRACTION` 候选 | 真正相同的前后条件，且已观测到修复/改动必须重复进行 |
| 某公共函数出现越来越多的 `mode` 分支 | `WRONG_ABSTRACTION` 候选 | 某些分支有不同 Owner/权限/错误/事务语义被混同 |
| 一个公共 API 修改迫使许多不相关模块改动 | 边界泄漏候选 | 逐一列出必要与非必要修改；不能只数 touched files |
| 引入多个 Provider 接口和注册表 | `OVER_ABSTRACTION` 候选 | 无真实动态替换/扩展合同，且确有跨层阅读/调试/测试开销 |
| 只有一个不变的简单实现 | `NO_ABSTRACTION_NEEDED` | 未受权独立变化、没有复用/隔离收益，直接实现满足全部现行合同 |
| 为保证原子性将两个职责合并到一个事务边界 | 可能是正确组合 | 若拆分制造不可恢复半提交，不可为了单一职责教条拆分 |

**同一个设计特征可能在不同合同下分别正确或错误**。评审必须附需求场景和具体代码/决策出处，不因类数、深度、函数长度给机械分。

## R19-F2 反馈候选：权威状态 Owner 与输入对象引用所有权需分开判定

[R19-F2 研究反馈](../professional-abstraction-empirical-feedback-r19f2.md) 提示：模块是某份内部状态的唯一写入 Owner，**并不自动意味着构造器/方法接收的可变入参已经被复制、冻结或取得排他所有权**。调用者仍持有原对象引用时，其后续写入可能影响保存该对象的模块。应按现行授权合同确认 `COPY_SNAPSHOT`、`SHARED_MUTABLE` 或 `IMMUTABLE_BORROW` 等交接语义，再找可执行反例；**不能默认所有入参都必须深拷贝**。若 Source 未规定，标 `SOURCE_UNSPECIFIED`，不可用隐藏 QA 或审核者个人偏好替 Owner 创造需求。

这只是根据真实执行收据提出的知识修订候选；原队列不能反推「额外知识改善或伤害代码抽象」。

## 四、K02 的退出条件和跨模块交接

- 完成当前范围的稳定边界、Owner、可公开的错误/状态合同后，将实现细节交 K03 判断可理解性与具体抽象粒度，交 K09 在后续真实变更中验证边界的变化隔离，交 K05 验证违约反例，交 K11 比较总成本。
- 无受权未来变更时只保留假设和可以触发复评的条件；不提前规定要做 Clean Architecture、DDD、SOLID 的某个固定层级。
- 出现具体状态混写、权限泄漏、错误合并、未声明依赖时，以原项目规范/源合同处理，不以“抽象美学”否决真实保证。
- **STOP**：如果进一步提炼增加了跳转、间接性、跨包合同而没有可观察的隔离收益，选择最简单满足源合同的方案。若 Source 不足，`UNKNOWN`，不伪造抽象正确的证据。
