## 一、需求发现首先要识别观察偏差

访谈提供涉众的**陈述**，现场观察提供在特定环境下的**行为**，日志提供经采样和仪表化后可见的**事件**，正式政策提供适用条件下的**授权规则**；四者对象、误差、权威不同，不能取最新者直接覆盖其他来源。

- 抽样偏差：只访谈高活跃用户会遗漏初次配置、离线环境和低频失败者；样本数多不必然具有代表性。
- 回忆/社会期许偏差：用户可能把想要的流程描述成已经发生的流程。
- 仪表化偏差：页面埋点成功不代表服务器提交成功，缺失日志不等于失败没有发生。
- 权威偏差：需求提出者不一定有权限改变收费、合规或权限合同。

**三角验证**并非简单多数投票。面对“售后退款当天到账”的两份口头说法和一份正式政策，应分别保留 Source/Actor/Scope/Time；政策不完整时明确哪一条件 UNKNOWN，不能把三条观察做平均后生成 Rule。

## 二、把模糊非功能词语转成可证伪质量场景

“快、稳定、简单”都缺刺激与上下文。一个质量场景最少包含：

| 字段 | 例：批量导入任务 | 缺失时的风险 |
| --- | --- | --- |
| 刺激源/刺激 | 用户触发 20,000 条导入 | 无法定义真实工作负载 |
| 环境 | 低配置单实例，网络波动，可进程重启 | 只在开发机表现良好 |
| 系统对象 | 导入请求、队列、持久进度、用户结果页 | 不知道测哪个边界 |
| 响应 | 返回已受理的作业标识，恢复后继续 | 只测 200 OK |
| 度量 | 由业务 Owner 批准的响应分位数与最大数据丢失界限 | Agent 自造 SLA |
| 排除/限制 | 不保证第三方 API 绝对可用 | 把外部系统故障归于单节点设计 |

具体阈值**必须来自实际项目决策**；教学情境只能使用假定值，不能将其提升为正式合同。K01 描述可观察的业务需求，K02/K10 才选择满足它的机制并核实成本。

## 三、质量属性并不总是独立可最大化

当要求更强可用性、成本约束、数据一致性和较低延迟同时出现，可能产生 Pareto 权衡。首先识别哪些是不可妥协的业务/安全边界，哪些是可谈判的目标，再由 K02 提供方案空间和测量方法。对尚无实测的技术方案，不应把“应该更快”填入已批准需求。

**教学反例**：客户说“必须全局实时同步”，但其实只要求库存页面几秒内可见。若没有澄清“读取延迟、丢失容忍与付款提交”间的不同，就可能为一个 UI 目标投入错误的跨地区事务系统。

## 四、可追溯性是有条件的影响图，而非每次全量审查

建立概念关系：Goal → Requirement → 适用 Rule/Assumption → Acceptance/Quality Scenario → 测试候选。每个边都有来源/版本和适用区域，并非 GitHub Native Task BLOCKED_BY。规则更新时只传播到**真正依赖该条规则的**架构、方法、Oracle 和旧消费者；文案、测试清理等不受影响资产不必重建。

例如修改“CLOSED 状态允许主管重开”的业务规则：
1. 指定新 Rule 的主体、事件、权限、生效时间。
2. 找出原状态机是否禁止此边，确认由 K02/K03/K05/K09 实际使用的关系。
3. 更新相应正反行为表，检查旧客户端错误响应合同。
4. 不自动重开全体项目的发布、运营指标与无关模块任务。

**反事实**：一个旧 FAQ 被删除不代表唯一权威政策失效；如果当前正式 Rule 另有来源，需更新的是陈述源/说明，而不是整个退款状态机。

## 五、可复用的知识输出与验证练习

给定两个角色、两类用户访问环境、一个模糊质量声明，要求 Agent 输出：事实表、源与版本、样本局限、待问的关键问题、两个可测质量场景、哪条要求会改变架构选择、哪项尚不可验证。正确答案可能是 ASK/UNKNOWN，不是“已完成需求冻结”。

**停止条件**：受影响的政策权威或质量阈值没有明确所有者时，停止将候选变成硬约束；其他可独立交付工作可继续。实际 Product/L1 Freeze 仍服从现行授权机制。
