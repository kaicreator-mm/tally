## 一、需求不是命令，而是受上下文限定的知识命题

完整的需求知识对象至少应区分 `ObservedFact`（谁在何处观察到何事）、`StakeholderClaim`（某角色说了什么）、`AuthorizedRule`（谁有权规定何种条件）、`Assumption`（暂时假定）、`Unknown`（缺必要来源）。它们不是可信度从低到高的线性阶梯：一个现场观察可以反驳“现在流程确实如此”，但不能自行修改批准的付款政策；一份最新 FAQ 也不能覆盖仍有效且适用范围更精确的正式合同。

**范围化原则**：每个政策候选至少带 `actor, objectState, event, contextualCondition, effectiveTime, governingScope, owner`。对同一个命题，先比较上述范围是否重叠，再检查是否真正矛盾，而不是按 URL 更新时间或主张频次投票。

教学公式：`Allowed(a,s,e,c,t) := PolicyVersion(t,c).Permits(a,s,e)`。这只是带条件的形式化**说明**；当 `PolicyVersion` 不明或不同来源权威冲突时，该函数不应由 Agent 猜出 true/false，而应保持 UNKNOWN。缺少事实的情况与事实确认为 false 不同。

## 二、规则冲突的三个专业层次

设两份材料：
- `R1`：对于普通用户、已发货订单、取消请求，拒绝取消。
- `R2`：对于所有用户、任何状态，付款后允许取消。
- `F`：用户界面存在“取消”按钮。

如果 R2 是过期 FAQ，则 `F` 说明 UI 可能有错误入口，不说明 R1 失效。若 R2 是新正式政策而生效时间未确认，则相同 Actor/State/Event 下可出现**真正规范冲突**，这时受影响状态转换应等待有权政策裁定。若 R2 只适用于未发货订单，两个规则可能毫不矛盾。

因此需要分别进行：(1) source/authorship 与权利，(2) scope overlap，(3) predicate conflict，(4) policy precedence/authorized change，(5) affected behavior 的影响传播。避免把“存在不同意见”一概标冲突，也不能通过实现者任选一种规则解决正式政策争议。

## 三、业务状态机与并发正确性如何互相约束

考虑 `PAID -> PACKING -> SHIPPED`，普通用户仅能在 `PACKING` 之前请求取消。系统有两个线程：

1. Thread A 读取订单状态 `PACKING`，准备同意取消。
2. Thread B 读取状态 `PACKING`，完成发货并提交 `SHIPPED`。
3. Thread A 使用旧读取结果把订单设为 `CANCELED`。

如果政策禁止已发货后的取消，则仅有业务 Rule 和前端按钮校验**不足以维持不变量**。K01 负责给出允许转换的角色/版本/条件与“不准已发货再取消”的业务 Oracle；K02 决定状态所有权及提交边界；K03 选用条件更新/事务并通过失败重试处理冲突；K05 设计并发负例。K01 不能从业务说明替 K03 承诺某一种数据库隔离级别。

教学合法结果之一：在有权提交点比较版本或当前状态；若 Thread B 已提交，Thread A 返回有明确错误语义的拒绝，而不是先宣告业务成功再覆盖状态。该选择仍取决于真实政策是否允许强制取消/补偿流程。

## 四、可验收性：从事实假说导出独立 Oracle

业务验收的独立性指 **Expected 不应仅来自受测代码当前返回值**。对于上述政策，至少设计：
- 正向：未发货且有权用户在政策适用期可按合法结果取消。
- 反向：已发货、缺权限、越过生效时间范围、旧客户端错误参数均不能产生非法状态。
- 竞争反例：发货与取消交错不得同时宣告两个不可兼容业务后果。
- 恢复反例：若取消外部退款发生但 ACK 丢失，状态不能靠本地超时猜测为“未退款”后再执行一次。

每个 Oracle 都需保留对应的批准政策与 Scope。如果原政策未获权，**可以给出验证候选，但不得将这些建议标为通过的真实验收**。若测试发现为零，应明确 NOT_RUN，不用用例列表充当真实结果。

## 五、质量需求与决策经济的边界

质量需求可以写为“在预期导入量、有限网络、允许一次进程重启的环境下，用户可恢复批次进度”，但要进一步明确真正的成功率/延迟与丢失容忍阈值。对于“导入不能慢”这一陈述，架构、队列与缓存设计必须先拿到量化的 Source/Owner 决议。没有预算/负载数据，不能凭技术经验决定 Kafka/多活/分布式事务“必须存在”。

对 Tally 的知识应用，优先输出**影响决策的最少未知**（例如真实政策效力、State Owner、是否允许补偿），而不是在每个任务里展开完整需求百科。

## 六、可证伪演习与边界

输入一份“旧客服 FAQ + 新正式政策缺批准日期 + 一个会触发并发的状态转换”材料，要求写出：
1. 两份命题精确适用范围与信息来源；
2. 一种成立的冲突序列、以及一种其实不冲突的反例；
3. 两条业务不变量与有权 Oracle 来源；
4. 所需的最小并发验证，不把 Mock 当真实；
5. 最终可能的 `ALLOW / DENY / ASK / UNKNOWN` 如何跟随授权前提变化。

**STOP**：权威政策来源未定时，只暂停受该政策影响的行为决策；其他独立知识检索可继续。本文不是对任何实际订单系统的政策批准、Host 验证或真实用户研究。
