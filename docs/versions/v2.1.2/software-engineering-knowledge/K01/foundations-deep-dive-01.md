## 1. 业务问题不等于预设技术解法

用户说“增加取消按钮”可能指误操作恢复、退款、履约中止或客户体验。建模应先区分 **Need（可观察价值）**、**Goal（目标状态）**、**Rule（合法行为约束）**、**Feature（候选实现）**。同一个 Need 可以通过 UI、API 或人工授权流程满足；不同解决方案的成本与风险须由 K02/K11 评估。

业务词汇必须标注 Bounded Context：支付侧“已完成”不等于物流侧“已发货”。同名字段只有在主体、时刻、所有者与转换语义相同时才可复用。跨上下文同步的延迟是可能的事实，不应直接称为数据库缺陷。

## 2. 将可审核业务规则写为条件性谓词

对一个命令定义候选函数：

`Decision(actor, objectState, action, context, policyVersion) -> ALLOW | DENY | UNKNOWN`

- `ALLOW`：当前适用、有权政策允许该状态转换；`DENY`：明示禁止且来源有效。
- `UNKNOWN`：关键角色、当前状态、来源权利、版本或优先级缺失/矛盾；不能以 LLM 的“常见规则”补写为允许。
- 不同角色的不同结果未必构成冲突。只有 **相同 Actor/State/Action/Context/有效期** 且结果不兼容时，才需要规则冲突仲裁（K01.F5.1）。
- 命令表达意图，事件表达已观察发生的事实；“RequestCancel”不可直接等同“OrderCancelled”。

例如“发货后不得自助取消”并不自动意味着“客服有权限退款”。两个 Actor/Action 不同，必须各自找真实来源。系统应能输出未决政策的必要澄清项，而非写出貌似完整的状态机。

## 3. 状态机、不变量和事务范围

以工单为例：`OPEN -> RESOLVED -> CLOSED`，`CLOSED -> OPEN` 是否允许必须来自明确业务决议。状态模型包括动作、前置角色/前置状态、允许的后继状态、禁止路径以及失败后的可见结果。**不变量**是所有合法状态及转换前后均应保持的性质，如“已关闭工单不可再次产生结算副作用”；但这个例子只有在业务授权后才可成为真实产品 Oracle。

K01 负责定义业务聚合的一致性边界；K02 负责技术持久化与提交点；K03 负责事务/条件写；K05 负责从批准规则推导正反 Oracle。聚合不是“数据库一张表”，事务也不保证外部 HTTP 副作用的原子性。

**教学情境（未获业务批准）**：三个工单，输入是 `[OPEN,OPEN,CLOSED]`，请求全部 CLOSE。有两个可行而互斥的政策：
- **全有或全无**：出现已 CLOSED 就拒绝整体，无任何副作用。
- **部分成功**：前两个变 CLOSED，第三个报告跳过/拒绝，返回逐项结果及副作用。
两者都可被实现成测试全绿，却不能同时满足同一明确业务合同。K01 必须先标 `POLICY_UNKNOWN` 并请求决策。

## 4. 如何从来源产生验收而不循环自证

| 维度 | 有效输入 | 反例/边界 | 不可提前声称 |
| --- | --- | --- | --- |
| 角色 | 业务授权 Actor | 只读角色、跨租户角色 | 开发者猜测的角色授权 |
| 状态 | 生效状态机 | 重复操作、过期状态 | 实现代码当前分支等于政策 |
| 操作 | 指定命令与副作用 | 失败、取消、重复投递 | Mock 调用过就是成功 |
| 来源 | 有效版本、Owner、适用范围 | FAQ 旧版本/权限不明 | 较新链接天然优先 |
| 验收 | 输入→期望状态/拒绝/可见副作用 | 非法路径无隐形副作用 | 仅 Snapshot 随实现更新就是真 Oracle |

最小可反驳闭包：**政策版本 + 角色×状态×命令矩阵 + 一个正例 + 一个同条件反例 + 未知项列表**。业务 Expected 必须独立于当前实现；没有有权规则时只输出候选验收和待定项，不能向 K05 传递“已经批准”。

## 5. 何时使用、何时停止与专业边界

适用于需求来源相斥、状态转换、批量操作、跨上下文实体语义。仅改文案且不影响行为时不必全量建模。若目标依赖未解决政策、关键 Actor 或版本，应停止受影响的实现选择；其他已授权部分可继续。跨模块选择：K01→K02 状态/质量合同，K01→K05 Oracle，K01→K09 旧客户行为影响。
