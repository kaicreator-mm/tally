## 既有核心方法

## 3. 专业知识正文：原理、应用、代价和限制

### 3.1 错误信息必须面向真实使用者

错误可能显示在 UI、CLI、日志或 API response，所需粒度不同。用户应该知道请求是否已被处理、哪些部分失败、是否可重试、该检查配置还是联系管理员；开发者可以在受限日志看到原始技术错误与相关 ID。禁止泄露密钥、用户隐私或全环境变量。仅捕获所有异常并返回“失败，请重试”会导致用户无法判断实际状态。

### 3.2 日志不是越多越好

按业务结果、错误原因、关键状态转换和真实需要的关联信息规划日志级别。高频成功路径不必每步输出数十条 INFO；严重失败应带操作名称、可追溯的安全 ID、失败阶段、已执行副作用/是否未知。日志要能与版本、Host/环境、Attempt/Task 的证据关联，但不得凭日志存在就认定结果被验证。

### 3.3 首次启动与配置策略

桌面/Web 本地交互产品可以启动后引导设置、存储与校验配置，再开放需授权的业务能力；命令行、容器和后台服务可能更适合通过参数/环境变量/配置接口初始化。这是根据应用形态选择的策略，不是“不能出现任何配置文件”或“所有业务必须先显示配置 UI”。敏感配置需遵守已有项目权限和保密规范。

### 3.4 重试、超时、取消与幂等性

将确定性的非法输入/代码缺陷与临时网络/外部 Provider 错误分开。只有存在合理恢复可能且副作用安全时才重试，需指定次数/退避/总超时；重试对多次提交的业务影响应有幂等键或状态回读。超时只代表当前观察者没在期限内得到确认，不一定意味着服务端没有提交。取消需要理解是“停止后续工作”还是“回滚全部已生效副作用”。

### 3.5 状态与恢复保障

为实际项目的最重要业务状态定义恢复条件：持久化点、重复或部分执行、重启后能否恢复、外部系统是否承诺交付/确认。恢复事件不应抹除历史已观察的失败和补救；未知副作用应通过合法状态查询确认，而不是直接标成功或失败。没有业务持续性要求的单文件工具没必要引入分布式恢复框架。

### 3.6 性能调查应以可复现证据为基础

分析性能前先定义请求/数据规模、目标用户感知的指标、运行平台及负载。利用真实 profiling、指标和差异基准选择瓶颈，而非只看源码复杂就猜测热点。优化不仅要测延迟和吞吐，还需看内存、资源/CPU、长期维护成本及业务正确性是否退化。不同主机/输入/缓存条件的结果不能直接得出因果结论。

### 3.7 故障经验和运行生命周期

一份有效运行事故记录应区分 DETECTED、MITIGATED、RECOVERED、VERIFIED、FOLLOW_UP，保留确切时间/来源和客户影响。可以从可复现案例提炼 DecisionProcedure/Skill 候选，但单次事件中的“当时增加了重试就好了”可能不适用于其他确定性错误。Tally 在维护/反馈流程使用知识时不能自行改变既有 Release 和事件事实。

## 方法论进一步细化

日志设计按 UI/CLI/API/后台服务区分用户可见错误与技术诊断；应说明安全原因、影响范围、相关 ID 和恢复指引，不在日志泄漏密钥。对外部故障先识别可重试/确定性类型与真实提交点，再设计有限重试、指数退避、取消/状态回读及幂等语义。交互桌面工具可启动后配置，容器/CLI 应保持合适的无头配置合同。性能优化前必须通过真实代表性负载收集基线，并在同条件重跑正确性及延迟/资源。

## 操作决策表

| 任务/环境条件 | 选择或调查路径 | 应交付证据 | 需要排除的错误 |
| --- | --- | --- | --- |
| 交互桌面工具尚未设置仓库 | 允许启动配置 UI，禁止未授权业务操作 | 首次启动正负场景 | 不能要求启动前必须人工设所有 env |
| CLI/后台服务配置错误 | 按无头形态输出明确的配置诊断 | 退出码/日志或管理 API | 不机械强制弹窗设置 |
| 超时后状态未知 | 先查询结果并选择有界安全重试 | UNKNOWN/幂等/恢复合同 | 不直接重复不可逆操作 |
| 没有固定负载基线 | 先定义测量方法；否则 NOT_MEASURED | 性能测试计划 | 不得虚报 3 倍改进 |

## 原始 Decision Procedures：输入、步骤、输出、停止

## 4. Agent Decision Procedures（决策方法）

### DP-K10-01 · 用户可操作错误与日志设计

**输入：** 产品运行形态、业务错误分类、用户操作、必要日志/隐私约束

**操作步骤：**
1. 识别用户/运维/开发人员各自需要的错误信息和行动。
2. 为业务拒绝、配置缺失、暂时故障和内部异常定义不同状态与输出。
3. 选择必要关联 ID、稳定错误码/原因/恢复建议与日志级别。
4. 排查高风险信息泄露和日志量过大/频率过高的问题。
5. 在实际 UI/CLI/API 入口验证用户能找到相关错误。

**输出：** 错误/日志契约、正反例及用户可执行下一步

**停止与例外：** 若没有足够权限说明细节，应输出安全摘要与相关 ID 而不是敏感上下文。

### DP-K10-02 · 超时/重试/恢复规则选择

**输入：** 业务操作是否幂等、外部状态读回能力、容忍重复副作用和超时要求

**操作步骤：**
1. 区分确定性与可能恢复的故障。
2. 确认操作的提交点及重复执行能否安全。
3. 定义有界超时/重试/指数退避/取消/回读行为。
4. 针对重复请求、迟到结果、部分成功和重启做最小测试。
5. 结果无法确认时保留 UNKNOWN 并要求合法状态回读。

**输出：** 有条件的恢复策略及对业务副作用的保证

**停止与例外：** 不把所有超时解释为失败，不能用无限重试恢复代码缺陷。

### DP-K10-03 · 性能优化证据判断

**输入：** 实际工作负载/平台、基线与目标、可重复测量方法

**操作步骤：**
1. 明确对用户有影响的指标和输入分布。
2. 在固定环境和真实代表性数据上获得基线。
3. 定位最可能瓶颈，明确其他竞争解释/缓存影响。
4. 进行最小改动，重复测量正确性和性能。
5. 报告统计/条件及已知偏差，不推断跨平台普遍效果。

**输出：** 同条件前后测量、功能回归、成本/不确定性报告

**停止与例外：** 基线不可得则 NOT_MEASURED，不能声称实测提升。

决策方法的输出是候选依据和建议；不自动获得产品采纳、Architecture Freeze、Agent 执行权限或 Release 状态。

## 方法适用性限制

这些 Decision Procedures 是可解释的候选工程知识，不自动创建新增 Runtime Workflow；遇到无权 Product/L2/Task/Host/Release 决策时应输出上游 Owner、缺失原始证据与最小下一步。已有真实证据可复用，不因模型上下文长或文档多而重复重审。
