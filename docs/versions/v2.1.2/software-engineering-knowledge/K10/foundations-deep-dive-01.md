## 1. 可靠性是用户能观察到的行为

可靠性设计先说明服务边界、关键用户动作、时间窗口、错误后果与恢复承诺。SLI 是实际观察指标，SLO 是在指定条件下的目标，Error Budget 是对不满足目标的可接受范围的决策工具，不自动成为所有项目的部署强制要求。单次成功或“有重试代码”都不能证明可用性。

区分 Fault（内部缺陷/不良条件）、Error（内部错误状态）、Failure（对外服务偏离合同）：错误可能被内部隔离而没有用户可见失效；告警数量和事故数量不能互相代替。

## 2. Timeout 并不告诉你远端是否已经执行

考虑一次付款 API 请求：客户端超时，可能发生了三种事实——请求未到达、远端已提交但响应丢失、远端尚在处理。单个 timeout 本身不能区分它们，因此输出应该允许 `UNKNOWN_EFFECT`，不可以直接把它写成 `FAILED` 然后立刻重试。

安全重试需同时判断：操作能否幂等、稳定请求 ID 是否由远端接受、是否有可查询的提交身份、重试预算与延迟、是否可能造成放大的负载。即使读取状态可用，也要确认读取的时效/一致性边界。无法消除未知且动作不可逆时，保持 STOP/人工核实。

## 3. 减少故障传播需要具体约束

| 机制 | 能解决什么 | 可能制造的新问题 |
| --- | --- | --- |
| Deadline/Timeout | 限制单次等待上限 | 远端 Effect 仍可能完成 |
| 有界重试与退避 | 应对部分暂态失败 | 重试风暴、重复副作用 |
| 幂等请求身份 | 针对某个明确定义 Effect 去重 | ID 使用错误导致误合并或去重缺失 |
| 熔断/隔离 | 避免故障跨边界扩散 | 对正常流量形成额外拒绝 |
| 背压/有界队列 | 控制内存/资源增长 | 需要明确丢弃、拒绝与排队政策 |
| 持久恢复记录 | 进程中断后可重建状态 | 仍需保证提交点、接管和读回 |

“不设置 timeout 就永远等待”和“所有错误都重试”都是不正确的通用策略。K02 负责失败域和状态 Owner，K03 负责资源生命周期实现，K05 负责注入故障并检验合同，K11 比较收益/成本。

## 4. 日志需要让人能够行动，且不能泄露数据

最小诊断事实包括时间、可关联的操作 ID、发生位置、失败类别、相关实体的非敏感标识、具体可执行的下一步。Log/Metrics/Traces 各有侧重，是否引入 OpenTelemetry 取决于项目部署能力；不应为了“可观测性”强制安装新平台。错误消息的用户版与开发/运维版应按安全边界区分，绝不回显密钥、Token、敏感请求体。

“异常已被 catch”不等于错误可恢复：异常后是否释放锁/文件句柄、是否留下半提交状态、是否给出可追踪状态仍须实际验证。一次 HTTP 200 也不能证明异步 Job 后续已完成。

## 5. 性能与可靠性必须有可比较基线

比较性能前需定义负载分布、预热、CPU/IO/内存限制、指标（如用户请求的尾延迟）、真实生产路径和对照时段。Profiling 的热点是候选因果解释，不意味着调整后端到端一定更快。未收集足够样本时输出 `NOT_MEASURED`；不从复杂度或局部 microbenchmark 自动推导整体加速。

教学负例：请求第一次超时后自动重发付款，产生两次收费；后续 Agent 宣称第二次请求成功因此故障恢复 PASS。正确判断应保留首次请求的未知副作用，通过有权支付记录核实再考虑补偿。
