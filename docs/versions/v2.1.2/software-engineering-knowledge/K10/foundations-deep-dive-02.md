## 一、吞吐与响应时间不是同一个指标

系统性能至少区分：
- 吞吐率：单位时间完成的合法操作数，不包括仅“开始处理”的请求。
- 等待：队列与调度带来的延迟，与实际服务时间分开。
- 响应延迟：由用户可见起止点定义，受尾部慢请求影响。
- 利用率与饱和：服务资源忙碌程度，单看 CPU 低并不排除锁/IO/网络瓶颈。
- 错误/超时：超时操作可能仍在服务器内部执行，不能仅从 HTTP 408/504 推出没有 Effect。

若结果只报告平均值，极少数超慢请求可能对用户不可接受，P95/P99 要与样本量、流量类型、采集窗口和实际 SLA 一起解释；低样本的 P99 可能高度不稳定。

## 二、Little 定律与容量判断的限定条件

在处于长期稳定状态并采用一致观察边界的系统中，Little 定律可写为 **L = λW**：平均系统内工作数 L = 平均到达/完成率 λ × 平均停留时间 W。它不要求服务时间服从指数分布，但需要明确稳定、守恒的对象和时间窗口。不能从一次高峰截图直接将队列长度除以进程数推得“必需扩容十倍”。

**教学数例**：长期稳定完成率 10 个请求/秒，平均端到端停留 0.2 秒，则对应观察边界内的平均请求数约为 2。若真实系统因为失败重试形成重复工作，先明确计数对象是请求、任务还是唯一业务操作，否则这个数学关系即使数值正确，也不能给出产品容量结论。

## 三、资源利用率与尾延迟之间没有简单线性关系

当平均到达速度接近可持续服务能力时，即使长期平均仍可完成，等待时间也可能明显增大；服务时间长尾、流量突发、串行临界区和资源竞争会放大尾延迟。增加 Worker 数不一定改善，可能转为 DB 连接池、锁或远端速率限制瓶颈。

容量选型顺序：
1. 选择与业务对应的真实端到端观察指标、工作负载与峰值条件。
2. 采集资源利用、队列等待、服务时间、网络/DB/GC、重试与错误数据。
3. 根据实际瓶颈提出至少两种候选（查询优化、批处理、缓存、并发限制、扩容），记录新风险。
4. 在同等输入、相同正确性 Oracle、可比较环境中测量前后；失败/不可比项保留 UNKNOWN。

## 四、Profiling 发现热点不代表改它就能提高最终吞吐

火焰图显示的宽度常关联 CPU 样本消耗比例，不等于该函数对用户所有延迟的直接因果贡献。CPU profiler 可能看不到外部网络等待，锁争用可表现为等待而非热点；优化某段代码还可能增加内存、GC 或缓存失效。

**Amdahl 思路**：若某段可优化工作仅占总执行时间比例 p，即便该段完全消失，整体理论加速上界约为 1/(1-p)，前提是固定工作负载、其他时间不变。它只给上界，不证明实际速度。比如 p=0.2，理论上限为 1.25 倍，不得宣传“函数提速 10 倍→系统提速 10 倍”。

## 五、实验与工程停止条件

| 证据 | 可说明 | 不可说明 |
| --- | --- | --- |
| 代表性负载/基线 | 当前路径的观测时间分布 | 任意流量下仍如此 |
| Profiling 热点 | 候选资源消耗位置 | 必然是业务延迟根因 |
| 局部 Benchmark | 受控函数的速度变化 | 整机端到端可用性 |
| 实际用户路径对照 | 指定版本/负载下的收益 | 未覆盖部署与未来版本 |
| 同 SHA 独立复跑 | 一定范围内重复性 | 所有外部 Provider 结果等价 |

如果没有可信基线或实验改变了模型/缓存/任务规模，结果须标不可比较；必要安全修复可以先做，但不能伪造性能收益。K03 提供算法正确性，K05 提供不回归 Oracle，K08 提供构建与 Provider 身份，K11 负责实证成本决策。
