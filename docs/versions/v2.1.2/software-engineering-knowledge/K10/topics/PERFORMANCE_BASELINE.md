## 1. 工程问题和适用前提

开发者把一个函数从 O(n²) 改为 Map 实现后就宣称“整个系统快了 300%”，但没有相同环境的性能基线。

**开始前必须确认：**
1. 真实投诉或已批准的性能质量目标
2. 代表性的输入量/负载/平台/工具链/缓存状态
3. Baseline SHA、Candidate SHA、正确性测试/运行时间/内存指标

**学科知识与因果机制：** 性能判断涉及业务目标、运行平台、输入数据分布、缓存、并发、I/O、测量稳定性和正确性，不能仅由大 O 推导实际端到端加速。质量模型提供可选择的性能指标框架，但不为每个项目自动设 SLO。度量必须说明能回答哪一个用户问题，并区分观测数据与开发者估算。

## 2. 可执行的有界判断过程

1. 先确定真实关切：用户交互响应、单任务吞吐、延迟分位数、内存压力还是网络/磁盘成本。
2. 在固定或说明差异的环境中测 Baseline 与候选，记录至少多次样本、异常值、缓存状态、目标负载与版本。
3. 在性能实验后执行必要行为回归，确保排序、去重、并发和失败语义未退化。
4. 报告所观察到的局部指标变化和不确定范围；不能把局部微基准推断为整个系统或其他设备的改进。

## 3. 场景分支、替代方案和不适用范围

| 条件 | 推荐的判断及范围 |
| --- | --- |
| 无 Baseline/负载 | 设计测量计划，结果 NOT_MEASURED。 |
| 有可比基线且行为回归 PASS | 允许报告该条件下的测量差异。 |
| 优化提升局部速度但出现业务错误 | 不能以性能收益掩盖正确性退化。 |

## 4. 真实可证伪的教学情景

**受限教学输入及正确路线：** 百万个 ID 查找由双循环换为 Map 后在固定负载下减少局部延迟，但总用户任务中网络占绝大多数时间，端到端改善可能有限。

**失败路线/反模式：** 在两个不同平台、不同缓存、不同数据集比较单次调用时间，随后对所有用户宣传 3 倍性能提升。

**最低可证伪 Oracle：** 当 baseline 记录缺失时，Agent 必须输出 NOT_MEASURED；在同环境测量但业务不变量 FAIL 时不能报告优化完成。

## 5. 最小交接与明确的 STOP

**Agent 输出契约**：当前已观察事实/证据身份、选择的知识与前提、备选方案取舍、正反 Oracle、未得来源或环境、最小下一步。凡 Source Claim 未获得正式资格、Host/CI 未运行、Product/Task 未授权的内容，必须与可证实事实区分。

**跨模块交接**：K03 做实际算法调整，K05 验证行为，K11 对收益与维护成本作整体取舍。

**停止规则**：需要越过合法写集、缺少有权业务决定、结果可能有不可逆副作用、外部状态不可确认或没有真实执行来源时，仅提出最小受控检查并保持 UNKNOWN/NOT_RUN，不通过重复调用或虚构状态推进。
