## 7. 完整教学案例：正确实施、错误做法及边界

**任务情景：** 一款桌面管理工具第一次启动需配置仓库与工作目录；业务操作偶发请求超时，用户再次点击可能导致重复执行。

**合理的工程路线：**
1. 依据交互式应用场景提供启动后的配置入口，未配置完成时禁止需要授权的业务动作并给出明确错误。
2. 对 CLI/后台同类应用允许符合其启动环境的参数或服务配置，不机械复制桌面配置 UI。
3. 将请求 ID、当前版本、操作和失败类型记录为可行动日志，避免输出令牌/完整敏感请求。
4. 确认请求可能已提交但 ACK 丢失时的重试/状态回读和幂等性合同。
5. 用未配置、非法配置、超时、重复点击、服务端已完成但客户端超时等场景验证用户实际体验。

**可观察的正确性：** 用户可在首次启动后完成配置；未知结果不会被悄悄重复执行；错误提示能支持恢复且不会泄漏敏感配置。

**反向/失败方案：** 启动前必须手动设置大量环境变量，否则崩溃；超时后自动无限重试并重复执行业务；日志打印整个仓库 token。

**适用条件变动：** 如果是无交互后台服务，要求启动后弹 UI 反而不合适；应以清晰配置校验和运维日志为主要体验。

## 既有反模式和失效机制

## 8. 反模式及不该泛化的教训

1. **Trace Flood**：无关键作用的每行日志掩盖真实失败
2. **Retry Everything**：确定性缺陷/拒绝也被无限重试
3. **Timeout Means No Effect**：一次超时就确信服务端没有操作
4. **Metrics Without Baseline**：未测量就宣传性能改进
5. **Config Absolutism**：所有产品都必须使用相同启动后配置 UI
6. **Incident Rewrite**：系统恢复后删除此前失效历史和不确定性
