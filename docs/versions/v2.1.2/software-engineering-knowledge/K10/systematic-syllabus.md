## 一、知识本体、工程推理与能力归属

可靠性、可运维性、观测与性能工程 不仅是若干执行提示词。它必须提供专业原理与假设、对真实输入的条件性判断、可反证的错误做法、跨学科连接与明确资格。**当前唯一知识 Owner：通用运行时质量特征、诊断日志、恢复策略、性能量化与用户操作可恢复性的知识拥有者**。下面的主题是完整课程的骨架，实际深度 Topic 是对必要问题的解释与实践投影；现有 DP/Skill/Case/Source 仍为可被引用的专项资料，不强制复制 15 次。

## 1. 软件质量和可靠性基础

### K10.F1.1 — 质量特征与业务场景

**专业知识及适用机制**：可靠性、性能、可恢复性、安全/可用性应依据当前产品风险、用户结果和环境选取，不必为所有 CLI 设全部 SLO。

**错误外推/反例**：开发者随手设定 99.999% 可用性作为强制合同。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K10.F1.2 — 故障/缺陷/失效区分

**专业知识及适用机制**：缺陷是潜在实现问题，故障事件与用户可见 Failure 不必一一对应；可观察性提供区分证据。

**错误外推/反例**：看见错误日志就判断用户每个操作都已失败。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K10.F1.3 — SLO/SLI 与错误预算

**专业知识及适用机制**：只有真实服务及有权业务目标才采用可解释的 SLI/SLO、窗口和观测；小型离线工具不需要强制部署统一监控平台。

**错误外推/反例**：为了引入 SRE 流程让所有工具运行 Prometheus。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 2. 可行动错误和可观测性

### K10.F2.1 — 结构化诊断与关联 ID

**专业知识及适用机制**：用户错误消息应说明失败/是否完成/下一步；内部日志保留时间、阶段、关联 ID、错误码和可访问上下文。

**错误外推/反例**：向用户只输出 stack trace；向 GitHub Issue 暴露完整 Token。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K10.F2.2 — Logs/Metrics/Traces

**专业知识及适用机制**：日志解释特定事件、指标观察聚合、链路辅助定位分布式调用；每种信号的保留/成本和权限不同。

**错误外推/反例**：接入 OpenTelemetry 自动证明所有缺陷根因可定位。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K10.F2.3 — 监控与告警噪声

**专业知识及适用机制**：从用户后果/可行动阈值选指标和告警，区分症状监测与原因调查、报警可恢复性。

**错误外推/反例**：所有 DEBUG 消息都触发高优先级事故。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 3. 弹性与错误恢复

### K10.F3.1 — Timeout/重试/退避

**专业知识及适用机制**：超时只是调用方未得回应，重试要看幂等、副作用、截止、资源预算和状态回读合同。

**错误外推/反例**：网络超时即重复发送出库/支付写入。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K10.F3.2 — 幂等与恢复一致性

**专业知识及适用机制**：同一请求标识/业务参数、已提交结果、重复/乱序处理决定可安全恢复的范围，不等于任意分布式事务都有 exactly-once。

**错误外推/反例**：用新的幂等 key 重试导致重复持久订单。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K10.F3.3 — 隔离/熔断/背压

**专业知识及适用机制**：根据真实依赖和容量风险限制队列、失败级联和并发；熔断/缓存可能牺牲可用功能或新鲜度，需明确降级策略。

**错误外推/反例**：将所有错误自动重试到外部服务完全过载。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 4. 性能测量与优化

### K10.F4.1 — 用户指标与分层定位

**专业知识及适用机制**：区分用户端到端延迟、吞吐、峰值资源、尾延迟、成本；选具体瓶颈和可代表负载。

**错误外推/反例**：单个函数微基准快 10 倍就宣传整页快 10 倍。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K10.F4.2 — 火焰图/Profiling 和瓶颈

**专业知识及适用机制**：依据真实采样环境、热点调用链和数据分布判断 CPU/IO/内存/锁争用，选择能改变用户结果的局部优化。

**错误外推/反例**：只凭代码长度推测性能热点。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K10.F4.3 — 实验对照和误差

**专业知识及适用机制**：Baseline/Candidate 同平台同负载比较，记录冷暖缓存、并发、测量噪声和业务回归；无基线则 NOT_MEASURED。

**错误外推/反例**：两个不同设备的不同数据集结果直接相除得提升比。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 5. 运行管理与反馈

### K10.F5.1 — 首次运行和配置形态

**专业知识及适用机制**：桌面应用首次可以先启动并设置，未配置或未授权时阻止业务效果；CLI/headless 有明确参数和错误出口。

**错误外推/反例**：要求所有服务/CLI 必须通过 GUI 初始化。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K10.F5.2 — 事故响应与恢复验证

**专业知识及适用机制**：分离检测、缓解、真正修复和用户业务验收；恢复运行并不能倒填过去 Task 的 PASS。

**错误外推/反例**：重启服务后把历史失败流水线改为成功。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K10.F5.3 — 运行质量经验回流

**专业知识及适用机制**：将失败信息、影响与恢复条件归属相应专业知识，不发送未经授权的敏感内容或自动晋升规则。

**错误外推/反例**：从一次匿名用户错误日志推断整个产品必须改架构。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 六、知识复用、专业反例与跨模块推理

**所有权**：通用运行时质量特征、诊断日志、恢复策略、性能量化与用户操作可恢复性的知识拥有者。K10 的通用运行原则供 K02 架构、K03 实现、K06 真实故障诊断及 K08 平台执行复用；K11 决定性能/运维成本价值；不抢占正式 Host/Release 事实。

**专业教学情境**：请求已提交却超时，重复执行会有副作用。客户端收到 timeout 后依据有权幂等 key 查询服务端当前订单结果，已提交则不再重复创建，无法查询则保留 UNKNOWN。

**必须识别的反模式**：一律重发写请求，导致用户有重复订单而 CI 只测 Mock 仍显示绿色。

**最小推理闭包**：Goal 与真实事实 → 本课程序列中的 Concept/前提 → Applicable/Excluded/UNKNOWN 判定 → [Decision Procedure](engineering-methods.md)/[Skill](agent-skills.md)/[Case](casebook.md) → 可观察 Oracle 与 STOP → 未来只有合法 Agent/Host/CI 真实运行时才得到相应验证结果。单独的系统课程文章永远不授予生产执行权。

## 七、从完整知识库继续增长的原则

- **系统完整性**：现有 15 个知识点为 5 个专业知识群的概念基础，可继续增加算法、理论/实证研究、不同规模/环境反例和相邻领域关联，而不是等待生产任务才允许编写知识。
- **实际使用深度**：优先把多次遇到的误判、复杂取舍和关键质量问题深化成独立 Topic，既有 Topic 通过 [README](README.md) 选择，不强制为每点创建独立文件/Issue。
- **专业准确性**：当某项资料仅列于来源目录或不能取得精确原文时，保持 `SOURCE_CANDIDATE` 并标明不能外推；后续选定 Task 需要时只审实际用到的主张与负例。
- **服务边界**：Tally 的选定领域资产可被未来 DomainHarness selected Element Content/Function 消费，但编译/运行/授权/反馈仍归 [Harness 边界](../domain-harness-consumption.md) 及原有 GitHub/Host/Release Owner；不创设第二知识 Runtime。
