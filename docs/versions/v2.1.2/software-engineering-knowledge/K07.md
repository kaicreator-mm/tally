# K07 — 多 Agent 工程协作 / Multi-Agent Engineering Collaboration

> [v2.1.2 #521](https://github.com/kaicreator-mm/tally/issues/521) · 本模块 [#528](https://github.com/kaicreator-mm/tally/issues/528) · [总目录](README.md)。`DETAILED_CONTENT_CANDIDATE / NOT_SOURCE_QUALIFIED / NO_RUNTIME_ACTIVATION`。ADS 是 Agent 软件开发实验/实践和已发布工程规范来源，Tally 在软件工程 Workflow 中消费选定、合格的知识。示例除有真实来源外均为教学情景，非真实测试结果。

## 1. 目标、适用条件、边界

在保持软件工程任务与 Review 真实权威的前提下，让多个 Agent 高效协同：选对是否需要多 Agent、明确每个 Agent 的任务角色/环境、使用适合的消息通道、管理写集与集成合同、在失败和消息重复时维持可恢复状态。最重要的原则是**交互方式与工程权限分离**：Git/GitHub 优先但不是唯一。

**触发条件：** 任务真的可以拆为独立的需求/设计/实现/验证工作，或不同执行环境/模型能够解决不同问题；单 Agent 足够时不因多 Provider 可用而强制并行。

**不承担：** 不建立新的 Agent 调度引擎，不把 GitHub 评论当作唯一通信介质，不要求立即实现所有 IPC/HTTP/队列/A2A 适配器。本版本暂不单独建设代码库逆向分析、软件安全与供应链知识专项；已有必要源码理解、权限和基本安全规范仍按实际 Task 生效。

## 2. 概念、语义及常见混淆

| 概念 | 工程语义 | 容易出现的错误 |
| --- | --- | --- |
| Logical Agent Identity | 同一执行单元/Session/Attempt 的逻辑身份和角色标识 | 用 GitHub 登录名等同模型身份或审核独立性 |
| Role / Responsibility | Planner、Builder、Reviewer、Verifier、Repairer 的实际工作职责 | 同一 Writer 给自己签独立审核 |
| AgentExecutor | 真正调用 Agent 和运行其工具/环境的现有能力 | 将消息发送成功当作 Agent 已运行 |
| AgentInteractionPort | 消息/请求/观察/确认/工件引用的抽象边界 | 将它与 AgentExecutor 和权威状态存储做成同一接口 |
| Git / GitHub | Git 版本化源码/工件；GitHub 当前正式 Task/PR/Issue/依赖事实 | Git 是唯一可行的 Agent 即时消息传输 |
| Message / ACK | 传输中的指令、通知、确认与相关 ID | ACK 自动表示代码已通过验收 |
| Artifact Ref | 源代码、测试、日志和审查产物的可校验位置与版本 | 引用可变 latest 作为 Exact SHA |
| Write Set / Fencing | 并发 Worker 能合法改的文件/共享产物及写锁/租约边界 | 不重叠文件便默认没有逻辑合同冲突 |
| Review Independence | 来源/时间/写者与审查证据可区别的技术审核过程 | 同账号不同会话就自动认定所有条件都满足 |
| Late/Retry Message | 重复、迟到、丢失或乱序传输需要对账/幂等判断 | 队列至少一次投递被当作 exactly-once 的工程事实 |

此处是领域知识概念，而非要求另外建立一套消息数据库、Task 状态机或通用 Schema；必要时可映射到现有 Tally Engineering Business/Domain Data 结构。

## 3. 知识正文：分析方法与工程权衡

### 3.1 应不应该采用多个 Agent

从真实交付结果拆分出相互独立的分析/实现部分，再评估额外 Agent 的协同成本。单一 Task 内只读分析可多 Agent 并行；共享核心模块写入通常由一个 Writer 负责。多模型提供交叉意见不必等同多份代码分支；将多 Agent 使用建立在需求、质量或实际时间收益上，而非 Token 剩余量。

### 3.2 角色与独立性需要证据

Planner 划范围、Builder 实施、Reviewer 查设计/代码/测试、Verifier 在最新候选上核验、Repairer 在合法写集修复。身份需要区分账号、会话、Attempt、工作区和实际是否写过目标源码。审核独立性是**来源绑定的过程事实**；同账号不同对话可以独立，但不能仅凭账号相同/不同决定。Reviewer 不应冒充 Product/Release Owner。

### 3.3 交接合同要能重建工作现场

一次有用交接包含 Repo/Task、精确 source HEAD、已接受上游 Product/L2/Task Pack、允许/禁止范围、实际依赖、运行环境/工具、需验证的行为、消息相关 ID 和失败停止条件。没有这些，Agent 只能靠猜测重复调查，且旧源码的“PASS”容易漂移。信息优先引用准确 Git 源/证据，避免把整个日志/知识库塞给 Worker。

### 3.4 交互端口和传输适配器

AgentInteractionPort 概念可支持 send/request、receive/observe、ack/reconcile、ArtifactRef；GitHub event 和 Git PR 是默认耐久绑定，同主机 IPC 可快速协调子 Agent，HTTP/RPC 可用于远程服务，queue 可用于异步通知，A2A 可作为有实际 Provider 时的协议适配。定义抽象不等于一次安装全部协议；MCP 工具访问与 Agent-to-Agent 交互职责不同。

### 3.5 Task 事实源与传输成功分离

GitHub native Issue Dependencies、Claim/FSW、Review 与 Release 的既有权限不会因 IPC/HTTP/A2A 消息到达而改变。Host 执行、Artifact 写入、消息 ACK、构建测试、正式审查是不同事实。只有选定的合法权限路径才可以申请工作状态变更；不能新增 Agent 私有状态库覆盖 GitHub 中已存在的 canonical Task。

### 3.6 安全并行与冲突处理

写集不重叠是必要条件之一，不足以保证合同稳定：两个 Agent 即使改不同模块，也可能假设互斥的 Schema/状态语义。先冻结真实必要接口，再让模块独立写作；任何共享生成物、lockfile、根 index 或迁移需单 Writer/显式串行。完成时以同一真实集成基础合并，验证当前 HEAD 的完整功能。

### 3.7 失败、迟到与重复消息

消息可能重复发送、超时未确认、Worker 实际完成但 ACK 丢失、迟到响应已过期。用 Task/Attempt/correlation/idempotency 与准确 Source Ref 对账；不知道执行是否发生时保留 UNKNOWN 并读回事实，禁止无条件重做不可重复副作用。离线子 Agent 的报告不能在未接纳的情况下写入正式 Release 状态。

## 4. Decision Procedures（Agent 可执行的决策方法）

### DP-K07-01：协作形态和 Agent 数量选择

**输入：** 目标任务、独立交付/读写范围、能力/环境约束、集成成本

**步骤：**
1. 划分真实可独立验收的结果，不按 Agent 名称拆任务。
2. 将只读、合同、核心写入、集成/审核角色分开，识别共享写集。
3. 比较单 Agent、并行子 Agent、远程专用 Agent 的真实协同成本。
4. 只对有确切可行性和收益的部分派多 Agent。
5. 定义候选合法执行环境和等待/停止条件。

**输出：** 最小角色/并行计划、写集和任务交接

**停机与边界：** 没有合法 Task/权限或无法验证效果时停在规划而非派发。

### DP-K07-02：Agent 交互选择与合同

**输入：** 消息用途、双方位置、Git/source 状态和权限

**步骤：**
1. 决定消息是需求澄清、只读分析、实现工作、结果通知还是权威请求。
2. 选择 GitHub/PR 持久交接、同机 IPC 或真实提供的其他适配器。
3. 传送 Task/Attempt/correlation、身份、精确 source/artifact ref、期待结果和期限。
4. ACK 后读取合法事实权威并对账；只在真实允许时进行状态改变。

**输出：** 通道选择、消息语义、对账和幂等约定

**停机与边界：** Agent 的 HTTP 成功响应不能直接授予 Task PASS。

### DP-K07-03：独立审核与并发集成

**输入：** 候选 Git SHA、真实 Diff、Builder/Reviewer 会话与目标接口

**步骤：**
1. 检查实际写者、审查者/会话的来源绑定，避免原 Writer 自称独审。
2. 独立读取精确候选与用户/设计/测试要求；记录可执行 P0/P1/P2。
3. 若需修复，由合法当前 Writer 处理并生成新 SHA；对新 SHA 做必要增量审核。
4. 集成前检查共享代码和接口冲突，整合后验证真实选定路径。

**输出：** 独立审查候选/真实集成收据/遗留阻塞

**停机与边界：** 缺少独立 Reviewer 的证据时不得自造 ACCEPT。

这些步骤为可引用的决策方法，不是第二个调度器、权限授权或 Review/Release PASS。

## 5. Tally Workflow 与其他知识模块的组合

**消费方（拟议，不代表已接线）：** `PROPOSED_NOT_CONNECTED`；Tally 既有 Engineering Business 的 L3 Task/Attempt、Agent Handoff 与 Review 入口在有合法任务时选择 DP-K07-01/02/03。输入：当前 Issue/Task、角色、源 HEAD、允许写集及消息/Artifact 事实；产出：受约束的角色/通道选择、独立审查交接、迟到消息对账建议；最终 Task Claim、Review 和执行授权仍由既有 GitHub/Host 权威决定。

| 环节 | 既有事实输入 | 使用该知识获得的输出 | 不能推断 |
| --- | --- | --- | --- |
| Planner | 用户/任务/分层 DAG | 角色和可并行界面 | 不自动批准任务 |
| Builder/子 Agent | 合法执行环境/写集 | 源码和可验证工件 | 消息完成不等于 Task 完成 |
| Reviewer/Verifier | 精确 HEAD/独立身份与测试 | 有边界的结论/返工要求 | 不代签 Product/Release |
| 集成与回读 | 当前 native Task/Host/CI 事实 | 合法状态与真实消费者证据 | IPC/HTTP ACK 无权限效力 |

**与 K01–K11 的交叉关系：** K04 判断任务是否真正能拆分，K02 先定义接口/状态合同，K03 完成受控实现，K05/K06 分别为验证和修复服务，K08 负责整合与实际 Build；K11 估算并行真实成本。

## 6. Agent Skills：输入、输出、验证、失败路由

### SK-K07-01：Bounded Agent Handoff

- **触发**：需要跨 Agent/Host 交付独立工作
- **需要的事实输入**：Repo/Issue/PR/Exact HEAD/Task Pack/Role/写集/环境
- **产生的工件或结论**：结构化交接、输出工件和可停止的单次任务
- **自我核对**：信息足以让接收者复原状态并知道哪些决策无权改变
- **拒绝/升级**：不得生成无界“持续推进直到完成”的本地 Agent 指令

### SK-K07-02：Independent Source Reviewer

- **触发**：已有候选源码和真正独立复核需求
- **需要的事实输入**：候选 HEAD/Base、真实 Diff、有效要求、测试收据和逻辑身份
- **产生的工件或结论**：ACCEPT_SCOPED/REWORK、P0/P1/P2、准确来源和最小修复
- **自我核对**：Reviewer 与 Writer 在实际工作上分离，并说明检查了什么
- **拒绝/升级**：不能靠同一 Writer 自报 PASS 取代独审

### SK-K07-03：Interaction Adapter Designer

- **触发**：接入非 GitHub Agent 消息系统时
- **需要的事实输入**：现行 Host/Task 权威、发送/确认/错误/重放语义
- **产生的工件或结论**：端口契约、发送/观察/对账、失败及幂等行为
- **自我核对**：ACK 不写 Task 状态，重试不产生重复外部 Effect
- **拒绝/升级**：不把任意 Agent 协议消息当作 Release 许可

## 7. 贯穿示例：正常路线、故意错误路线和适用差异

**情景（教学模拟）：** Tally 使用两个 Agent：Builder 修改一个 API，Reviewer 在独立会话审核；同机第三个 Agent 通过 IPC 提供只读测试建议。

**正确推进：**
1. Planner 从合法 Task 中提取准确 Repo/HEAD、允许写集和用户验收，并确认 API 已有 L2 合同。
2. Builder 在自己受控工作区实施并通过 Git 持久化源码与测试，产出 Exact SHA 及实际受影响测试结果。
3. IPC 子 Agent 只传递测试建议和工件引用，不持有直接发布 Task 或修改共享写集权限。
4. 独立 Reviewer 从 GitHub 读取当前确切候选和真实 Diff，结合需求/测试给出局部结论。
5. 只有合法 Task/Host/CI/Review 路径确定适用结果后，才更新对应工程事实；消息 ACK 不触发此动作。

**有效的验收证据：** 实际源码候选/审查者/最终组合都绑定相应准确 HEAD；并行无共享写冲突且 IPC 消息不授予工程权威。

**错误实现/决策：** Builder 给 Reviewer 发“已通过”聊天消息后 Tally 自动把 Task/Release 标成功；两个 Builder 同时更新 lockfile 并互相覆盖。

**条件变化如何影响选择：** 如果没有适合的独立工作，单 Agent 直接完成是更好的选择；远程 Agent 可用 HTTP/A2A 只替换消息通道而保持同样的 Task 权威限制。

## 8. 反例库与适用性边界

1. **GitHub-only 假定**：把消息语义与特定平台评论 API 绑定，阻碍本地高效协作
2. **ACK-as-PASS**：通信成功自动变成正式工程资格
3. **Identity Shortcut**：以账号相同/不同代替真实独立审核证据
4. **Shared Writer**：多个 Agent 改同一个生成产物而无租约/集成规则
5. **Late Effect**：新 Task 已换 HEAD，迟到 Worker 仍尝试执行旧版指令
6. **Token Parallelism**：因资源闲置强行拆分本来原子的 Task

## 9. 面向真实 Tally Consumer 的验证矩阵

以下均是后续可转换为 Validation 的**预设案例**，不是已跑通过的工具/Host 结果。

| 情景 | 正确行为 | 禁止结论 | 需要的实际证据 |
| --- | --- | --- | --- |
| 同机 IPC 结果成功返回 | 只认消息成功和工件引用 | 自动 Task PASS | IPC 消息/Task 事实对照 |
| Builder 和 Reviewer 同账号不同会话 | 核查实际工作/审查独立证据 | 仅凭账号相同拒绝或批准 | 两方审查来源和候选 SHA |
| 两个 Agent 写同一 generated file | 单 Writer/真实串行 | 无冲突直接并行 | 写集和实际文件控制 |
| HTTP 任务重复投递 | 幂等对账当前 Task/Attempt | 重复执行不可逆 Effect | 相关 ID、Host 状态回读 |
| 旧 HEAD 工件迟到 | 拒绝或重绑定并验证 | 用旧结果覆盖新任务 | source/attempt/current HEAD |

验收应绑定当前 Source/Task/Attempt、实际消费者和适用环境；真实测试未执行时必须保留 `NOT_RUN/UNKNOWN`。不要以知识目录完整、算法讲解正确或一次模型问答得分代替真实开发任务的质量。

## 附录 A · Agent 直接调用的工作示例（非正式 Wire Schema）

**教学输入：** Builder 已推送一个 PR HEAD；Reviewer 在独立会话审核，同机子 Agent 通过 IPC 提供只读分析。
- 使用知识：LogicalAgentIdentity、Attempt、AgentInteractionPort、ArtifactRef，执行 DP-K07-01/02/03。
- 期望产物：`repo/task/role/session/attempt/exact_head` 的交接，允许写集，消息相关 ID，候选与独立审核来源。

- 停止与交接：迟到/重复消息在当前 HEAD 对账失败则标 STALE/UNKNOWN，不应用旧结果覆盖正式事实。
