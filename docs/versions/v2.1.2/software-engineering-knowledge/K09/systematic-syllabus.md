## 一、知识本体、工程推理与能力归属

软件维护、演进与重构 不仅是若干执行提示词。它必须提供专业原理与假设、对真实输入的条件性判断、可反证的错误做法、跨学科连接与明确资格。**当前唯一知识 Owner：已有行为与消费者的兼容演进、数据版本迁移、技术债及退役决策的专业知识**。下面的主题是完整课程的骨架，实际深度 Topic 是对必要问题的解释与实践投影；现有 DP/Skill/Case/Source 仍为可被引用的专项资料，不强制复制 15 次。

## 1. 维护的分类与生命周期

### K09.F1.1 — 修复/增强/重构/适配

**专业知识及适用机制**：故障修复改变错误行为，新能力改变受权需求，纯重构应保留公共行为，平台适配涉及环境合同。

**错误外推/反例**：公开接口行为变更却在 PR 中标“仅内部重构”。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K09.F1.2 — 维护优先级与长期成本

**专业知识及适用机制**：由用户影响、故障复发、变化频率、支持期限与预算决定维护工作，不由代码风格主观评分唯一决定。

**错误外推/反例**：因为一个长函数不好看就重写整个产品。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K09.F1.3 — 系统生命期和退役

**专业知识及适用机制**：考虑客户版本、数据保留、配置迁移、运维支持和合法通知；停止支持旧能力不能由新代码测试独自裁定。

**错误外推/反例**：宣称所有旧版本都可以无限期自动支持。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 2. 重构及遗留代码治理

### K09.F2.1 — 行为保留的重构 Oracle

**专业知识及适用机制**：重构前明确哪部分对外输入输出、异常和状态不允许变化，变更必须有真实受影响回归。

**错误外推/反例**：更新 Golden 为新结果掩盖旧用户破坏。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K09.F2.2 — 逐步替换与 Strangler 模式

**专业知识及适用机制**：旧新组件可通过已有入口逐步切换，关键是有真实运行路径、状态源和可安全终止的过渡；不要求每次都加代理。

**错误外推/反例**：部署临时路由后永不删除并产生双权威状态。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K09.F2.3 — 可测试性与依赖切割

**专业知识及适用机制**：通过稳定合同和最小 seam 降低维护成本；不要在没有真实变化的地方提前建设庞大抽象层。

**错误外推/反例**：为一个静态工具创建可热插拔全栈框架。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 3. 接口/数据演进

### K09.F3.1 — API 兼容版本

**专业知识及适用机制**：定义受支持旧客户端/协议窗口、类型/错误/语义变化，必要时新端点或 opt-in 版本。

**错误外推/反例**：数组返回改成对象，却因新客户端通过就关闭旧测试。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K09.F3.2 — 演进式数据库设计

**专业知识及适用机制**：按真实部署决定 Expand/Backfill/Contract 或停机原子迁移；旧新读写/中断/重跑各有不变量。

**错误外推/反例**：新建空库 CREATE TABLE PASS 即宣布所有旧数据升级成功。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K09.F3.3 — 配置和数据语义迁移

**专业知识及适用机制**：配置默认值、字段弃用、数据缺省/非法值需要有来源决定如何处理；不可逆清理需风险与恢复决议。

**错误外推/反例**：未映射旧状态全部默认为 CLOSED。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 4. 稳定性、版本与变更控制

### K09.F4.1 — 受支持消费者及契约

**专业知识及适用机制**：区分真实已部署用户与历史测试文件，维护资格由当前产品/发布边界定义。

**错误外推/反例**：仅因 git blame 很旧就删除仍被使用的端点。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K09.F4.2 — 渐进部署与回滚

**专业知识及适用机制**：新旧实例并存时维护协议/数据兼容；回滚可回代码不一定可回业务副作用。

**错误外推/反例**：系统返回旧二进制便认为已删除字段回来了。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K09.F4.3 — 回归传播和证据复用

**专业知识及适用机制**：只对受影响客户、合同、数据/Host 重新验证，旧版完全不同结果不继承到新 SHA。

**错误外推/反例**：修改 Migration 后复用旧 build/Host PASS 证明数据没坏。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 5. 技术债与进化决策

### K09.F5.1 — 技术债成因与利息

**专业知识及适用机制**：缺陷复发、变更难度、构建耗时、耦合是可观察债务成本；区别审美与实际瓶颈。

**错误外推/反例**：以重构代码行数证明生产率提升。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K09.F5.2 — 替换与保留的经济评估

**专业知识及适用机制**：比较修复/局部重构/迁移/替换的初始与长期成本、不可逆风险、用户价值和团队能力。

**错误外推/反例**：开源框架更流行就立即重写整个系统。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

### K09.F5.3 — 受证据驱动的停止条件

**专业知识及适用机制**：当原问题在有权范围内已修复且回归足够，应停止扩大重构；新发现问题另有独立范围判断。

**错误外推/反例**：修一个 bug 延伸成未截止的架构翻新。

**对 Agent 的可检验要求**：面对具体问题时指出真实输入、可以使用本知识的前置条件、未选择替代方案的理由和关键缺失项；缺必要事实时输出 UNKNOWN 或停止而不是自报 Rule/Host PASS。

## 七、从完整知识库继续增长的原则

- **系统完整性**：现有 15 个知识点为 5 个专业知识群的概念基础，可继续增加算法、理论/实证研究、不同规模/环境反例和相邻领域关联，而不是等待生产任务才允许编写知识。
- **实际使用深度**：优先把多次遇到的误判、复杂取舍和关键质量问题深化成独立 Topic，既有 Topic 通过 [README](README.md) 选择，不强制为每点创建独立文件/Issue。
- **专业准确性**：当某项资料仅列于来源目录或不能取得精确原文时，保持 `SOURCE_CANDIDATE` 并标明不能外推；后续选定 Task 需要时只审实际用到的主张与负例。
- **服务边界**：Tally 的选定领域资产可被未来 DomainHarness selected Element Content/Function 消费，但编译/运行/授权/反馈仍归 [Harness 边界](../domain-harness-consumption.md) 及原有 GitHub/Host/Release Owner；不创设第二知识 Runtime。
