# K09 · R18 进阶：陌生维护者增量修改，作为可维护性的可证伪证据

> 学科背景：[ISO/IEC 25010:2023 产品质量模型](https://www.iso.org/standard/78176.html)、[SEI 架构可扩展性分析](https://www.sei.cmu.edu/library/extensibility/)、[Google 代码审查标准](https://google.github.io/eng-practices/review/reviewer/looking-for.html)。质量模型/方法是专业参考，以下是原创工程评价方法，**不是**某个标准授权的统一“可维护性分数”。

## 1. 可维护性不同于“当前代码看起来整齐”

维护成本是代码、业务合同、变更类型、团队能力和环境共同作用的结果。没有观察过后续变更，最多提出 `MAINTAINABILITY_HYPOTHESIS`，不能宣称此实现的长期维护成本更低。合理的评价对象不仅包含首次实现，还包含维护者能否以正确、局部、可追溯的方式完成新要求，且没有破坏旧用户行为。

| 概念 | 真正评价的事实 | 常见伪证明 |
| --- | --- | --- |
| `ANALYSABILITY` 可分析性 | 新维护者能定位某个行为、识别风险和修改约束 | 代码短、注释多、类名专业 |
| `MODULARITY` 模块性 | 一个有权局部变更是否被正确 Owner 限定；共享状态不泄漏 | 文件数多、接口数多、改动行数少 |
| `MODIFIABILITY` 易修改性 | 新需求正确实现且未产生真实回归、变化范围合理 | 单次编译成功、仅新增测试通过 |
| `TESTABILITY` 可测试性 | 旧与新行为各有真实 Oracle、可复现失败及独立发现 | 新增 100 个只断言 mock 的测试 |
| `COMPATIBILITY` 兼容性 | 实际在支持窗口内的消费者/数据格式仍符合有权合同 | 直接改写 Golden，再声称通过 |

这些是质量维度的使用性解释，不能从数量型指标直接推导产品等级。

## 2. “陌生维护者”实验的因果边界

**第一步，冻结原始实现。** 明确 `H0`、每组首次 L2 与首次 S5 提交、实现可用的业务说明、依赖和测试版本。原 Builder 不准见到未来维护变更内容。S5 以后原始候选不准修写；另建维护分支保留原始 HEAD。

**第二步，先冻结可用的维护题目和 Oracle。** 由独立编题者在任何候选结果出现之前，选一个与原范围相邻、真实工程可能发生的变更（例如新增一类合法状态、一个受约束的输入策略或小范围接口兼容行为），指定原行为保留集合和新增行为接受准则。避免仅适配作者预想的内部结构；要求外部可观察合同，不提供要求候选采用的具体类/接口数量或设计答案。

**第三步，安排实际陌生维护者。** 维护者不可是原 Builder；知识条件应单独登记，不能不经控制给某组更强维护者、更多工具或额外缺陷提示。最好对不同候选平衡维护者/顺序，并记录 Reader 是否知道原始 A/B、是否看到原始评价。若不可盲，标记 `NOT_BLIND` 及可能的学习效应。

**第四步，要求真实修改与完整回归。** 新需求成功、旧支持行为保持、跨租户/状态边界不破、真实 Test Discovery+Execution、旧/新合同正反例、在维护分支上实际版本一致；若有不可逆写入或未授权远端 Effect，不能用真实危险操作造测试。必要时通过模拟但明确模拟覆盖范围。

**第五步，保留所有成本和失败。** 初次阅读直到正确定位、修改、测试、报错、返工、独立审查、提示、失败终止均计入实际成本；不得只统计最终成功路径，也不因某组代码更长就自动判更难维护。

## 3. 变更传播的结构性判断，不等于文件越少越好

记录 `TOUCHED_OWNER_MODULES`、`PUBLIC_CONTRACT_CHANGED`、`NECESSARY_VS_INCIDENTAL_TOUCHES`、`UNEXPECTED_SIDE_EFFECT`、`OLD_BEHAVIOR_REGRESSION`、`CHANGE_RISK`。**必须先确定应该修改的职责边界**：一个大文件里完成十种职责并不是有界影响；一个真正需要同步升级三个消费者的接口，修改三个文件也不必然是坏设计。

比较**反事实选择**：如果只修改某一个 Owner 却错误地绕过校验、破坏旧版数据，这种“低改动范围”应判失败；如果新增一个小而明确的边界适配器使旧消费者不变，这种“多一个文件”可能更容易维护。对于兼容窗口和数据迁移，先问真实支持的版本和 Owner，不能给不存在的旧客户端制造永久兼容债务。

## 4. 一次维护工作的可复算记录

| 字段 | 可核验的数据和不可混淆的判断 |
| --- | --- |
| `ORIGINAL_S5` / `MAINTENANCE_HEAD` | 两个精确提交；原始候选保持不变 |
| `CHANGE_SPEC_SHA` / `ORACLE_SHA` | 在看原始结果前版本冻结的需求与原行为保留范围 |
| `MAINTAINER_CONTEXT` | 新 Agent/人类维护者的 Provider/经验、可用文件、权限和盲性 |
| `LOCATE` | 从第一次看代码到正确解释目标行为的实际耗时和必要的提示 |
| `CHANGE_SET` | 真实修改的职责模块、公共 API、数据变更，以及新旧路径与失败行为 |
| `VALIDATION` | 目标测试真实发现/运行、旧行为回归、变异与未测面 |
| `TOTAL_EFFORT` | 阅读+修改+测试+审查+修复+人工接管、失败与超时 |
| `LIMITATIONS` | 维护者熟练度、工具缓存、样本规模、任务难度/顺序、是否真正盲评 |

同一个失败可由题目歧义、原有架构、维护者误解、工具/环境、Oracle 不成立引起；必须先独立归因，再决定是否回补 K02/K03/K09。不能“知识组结果不好”就改写专业理论或隐藏任务。

## 5. 最小负例及停止条件

**原创负例 A**：为了让后续变化只改一个函数，将所有租户持久逻辑集中到一个 `util.ts`，引起隐式共享状态；修改行数变少，但跨租户隔离破坏——不是可维护性改善。

**原创负例 B**：为了“抽象稳定”，给只有一个实际消费者的内部函数加 Builder/Registry/Adapter 三层，后续维护者必须跨五文件定位错误；没有新增真实可替换边界则属于可讨论的设计负担。

**原创反向例**：另一个实现多改一个适配模块，保护了已批准的公开协议与旧数据兼容，虽然改动文件更多，仍可能更易维护。

若无批准的后续变更目标或没有真正可评价的原行为 Oracle，则保留 `NOT_TESTED`，不假造一次维护通过。如果只是 README 错别字，不要求设计陌生维护者复杂实验。

**边界**：本篇用于知识库研究，不产生正式 K09 规则、迁移程序、Runtime Consumer 或下次 R18 隐藏维护题的具体答案。
