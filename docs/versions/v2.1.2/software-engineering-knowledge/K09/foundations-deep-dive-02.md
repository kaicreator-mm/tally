## 一、维护类型不同，判断对象也不同

Corrective 修复可观察错误；Adaptive 适配变化的平台/外部合同；Perfective 改善可维护性/性能；Preventive 降低未来故障风险。这些分类可用于判断适用知识，但不代表每次改动只可能属于一个类型。重构通常以支持范围内的行为保持为合同，改变对外行为的增强必须回到有权需求/产品来源。

反例：把返回空数组改成 HTTP 404 虽只有一行代码，但真实消费者可能依赖旧响应，它不天然是“安全重构”。

## 二、技术债应有可观察的成本假设

技术债不是“开发者不喜欢的代码风格”，而是当前某种设计取舍造成将来修改/运维成本更高的可观察机制。可按**额外维护工时、缺陷发生机会、接口变化传播范围、故障恢复困难程度**分析。某个抽象暂时冗余不一定值得立即消除；未来不再被使用的服务也不一定应该花费大量资金“完全重构”。

假设方案 A 立即重构需 20 单位成本，方案 B 保留每次变更多花 3 单位，未来可能修改次数未知。不能直接由 20/3≈6.7 推出“一定在第七次变更时投资回本”，因为实际变更概率、失效后果、折现/机会成本和并行迁移风险都未知。这个简单阈值只是情景分析，不是预测。

## 三、兼容必须按受支持消费者构成

| 演进情境 | 需要的证据 | 禁止的推论 |
| --- | --- | --- |
| API 字段弃用 | 哪些旧客户端仍读取、过渡期 | 新客户端能编译即全体可用 |
| 旧 DB 状态映射 | 当前数据分布、合法规则、恢复入口 | 旧非法值随意置默认值 |
| 生成协议改版 | 上游源/下游生成消费者 | 单仓单元测试已证明全兼容 |
| 渐进替换 | 双路由行为/数据对齐/切流 | Strangler 必须用于所有重构 |
| 退役系统 | 实际调用/存储/保留期/权限 Owner | 零最近日志就代表永无用户 |

动态消费者发现可能不完整：日志采样/离线批处理和长期停用客户都可能让“零访问”失真。因此 EOL 不能只看过去 24 小时内没有请求；需要相应业务、服务承诺和保留期决议。

## 四、演进设计的恢复路径

Expand–Migrate–Contract 只是可用模式之一。不可逆删除、历史数据清理和外部接口切换应明确：谁有权决定，哪些旧客户端仍在运行，写入双路期间怎样保持一致，失败时具体可以停止或恢复到哪里。恢复不是“执行 rollback 命令成功”而是业务可观察状态确实返回合规范围。

对不会进行滚动升级的内部一次性工具，过度建设多阶段双写可能增加风险；K11 要比较实际总成本，K05/K08 要保留真实迁移验证，K10 负责运行中告警/恢复。

## 五、知识与系统同时演进

源条款或 API 版本变化时，把实际语义变化传播到受影响 K01 规则、K02 合同、K03 实现、K05 Oracle、K08 制品和 K10 运行假设。不是任何一个新版本出现就重新执行全量 11 模块审查。还应保留淘汰知识的历史适用范围，避免旧 Agent 在历史任务回溯时将较新事实强行赋值给旧场景。

**练习**：给定支持两个客户端版本的数据服务、旧字段未迁移以及用户要求停用接口，输出可执行的最小兼容计划、真实未知和一条反例；不能凭当前测试全绿自动批准退役。
