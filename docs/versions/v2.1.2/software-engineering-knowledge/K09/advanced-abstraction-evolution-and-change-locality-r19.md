## 一、抽象的“好坏”必须经历真实变化，而非仅由作者解释

一次通过测试的原始实现，可以看起来架构整齐，却在未来很小的新需求下要求跨 Owner 修改多个组件、删除兼容保护或重复修改同一不变量。因此**抽象质量的可观察主张**至少区分：

- **FIRST_DESIGN**：初次 L2 中声明了哪个变化轴、被隐藏的实现决策、哪些消费者依赖这个合同；
- **ACTUAL_STRUCTURE**：初次 S5 中真正的接口/模块/状态 Owner/依赖方向，而不是纯文档图；
- **FUTURE_CHANGE**：在见到初始方案输出之前冻结的真实增量需求，要求保留哪些旧行为、增加什么新行为；
- **READER_AND_MAINTAINER**：陌生维护者怎样定位实际边界、能否安全修改、多少返工与错误、是否有外部兼容损坏。

后续变更并不是用来奖励“修改的文件越少越好”。如果状态与实现职责全部塞入一个巨型文件，真实修改虽然只触及一个文件，也可能更难理解、测试和回归。反过来改动两个必要的界面/适配模块以保持旧消费者稳定，可能是合理的局部传播。

## 二、抽象失效的三种纠正策略（DP-K09-R19-01）

| 判定 | 具体错误迹象（需要源代码/需求证据） | 合理修正方案 | 危险做法 |
| --- | --- | --- | --- |
| `UNDER_ABSTRACTION` | 同一真实业务不变量在多个 Owner 之外重复维护，合法修复多处漂移；无正确状态边界 | 找唯一语义 Owner、提炼最小共享机制，保持原公共行为 | 将不同权限/错误语义仅因语法相似一并折叠 |
| `WRONG_ABSTRACTION` | 公共 API 用 flag/模式隐藏不同的契约或写入责任，新增一种行为使已有消费者行为被改变 | 重新划分不变量，拆开不相容行为，在受权的兼容窗口迁移消费者 | 继续加 flag、catch-all 与全局状态以勉强维持通用接口 |
| `OVER_ABSTRACTION` | 为未经授权的扩展建工厂、注册表、泛化配置，使真正阅读/修改更困难且无真实收益 | 缩减到最小合法边界，优先替换无价值间接层并维持外部 API | 不顾真实多实现、插件协议就一律删掉接口 |
| `JUST_ENOUGH_ABSTRACTION` | 必要变化限定在正确 Owner，旧合同不受破坏，Reader 能找到行为，成本可接受 | 不需要重构，记录观察与未来复评触发 | 为追求更高“抽象程度”再次改写代码 |
| `NOT_ESTABLISHED` | 没有观察实际维护变更、没有有效 Oracle/未知合法变化 | 坦诚保留假设，必要时有界验证 | 用作者自评、测试全绿或文件数代替维护证据 |

## 三、跟随一项真实变化的六个观察点

1. **确定变化属于谁**：从有权新需求，定位哪个领域不变量、状态 Owner、消费者合同应该变化。若源不明确，`UNKNOWN`，不得以 Reviewer 自己的偏好定义答案。
2. **预期影响**：在看到候选实现之前由独立方写出最小必须涉及的*职责集合*和旧/新行为 Oracle；不规定文件/类名/框架架构。
3. **执行影响**：比对真实 Git Diff，分别标 `REQUIRED_OWNER_TOUCH`、`INCIDENTAL_CROSS_OWNER_TOUCH`、`PUBLIC_CONTRACT_CHANGE`、`HIDDEN_STATE_LEAK`；命中数不足以独立决定优劣。
4. **保留旧行为**：测试发现和实际执行保留了哪些原合同、异常/拒绝/兼容性，不能只展示新功能成功。若历史数据未知，不能猜支持窗口。
5. **陌生维护者理解**：由未写原代码的 Agent/人类在同样工具/时间下定位原入口、数据 Owner、失败路径，记录误读、提示、真实跳转与时间。
6. **全成本与反证**：包括初始、独立 Reviewer/QA、后续阅读、修复、测试、返工与失败；如果简单重写更合理，说明为什么。无证据时保留 `NOT_TESTED`，不编造小时节省率。

## 四、原创教学反例与边界

某园艺程序的两种浇水方式具有相似的每日计数算法，但一方要求离线确认，另一方必须在用户撤销时异步取消。将两者合成一个 `schedule(mode)`，在重构时只保留单一 `success` 状态，看起来实现短了、旧正例仍通过，但新取消场景暴露了错误抽象。相反，纯计算每日统计量若源合同相同，复用可能减少修复漂移。这个例子不能搬入 R19 的隐藏任务或独立 Oracle。

另一个反例：新增一个合法输出格式需要修改五个消费者，因为内部格式化枚举被跨模块读写。这是潜在的封装泄漏；但若五个模块都是被批准的实际输出消费者，改动五处可能不可避免。必须检查**修改是否由谁应该负责**，不能把五这个数字本身定义为缺陷。

## 五、结论的效力边界

- K02 的模块信息隐藏是一种设计假设；K03 的恰当抽象粒度是一种实施选择；**K09 只在真实后续变化和有效回归测试中才可能支持“维护收益”的经验性结论**。
- 真实经验只能提示要补什么知识；如果发现某结果的根因是 LLM Tool/Provider、受测任务泄漏或 Oracle 不稳定，优先修实验方法而不是根据偏好重写学理。
- 不能让候选 Builder 知道已冻结的增量维护题；否则它会通过提前优化答案造成伪收益。
- 若未实际跑过维护、Reader 或回归，必须标 `NOT_TESTED`；不能把新知识文档独立审核通过等同 LLM 工程抽象能力已提升。
