# K09 进阶软件演进：消费者合同、渐进迁移与明确的不兼容重写

> [K09 课程](systematic-syllabus.md) · [数据/接口迁移第一卷](foundations-deep-dive-01.md) · [技术债/退役第二卷](foundations-deep-dive-02.md)
>
> **R6 ORIGINAL_SOFTWARE_EVOLUTION_KNOWLEDGE_CANDIDATE / NO_ACTUAL_MIGRATION_EXECUTED。** 映射 K09.F1.1、F2.1、F2.2、F3.1、F3.2、F4.1、F4.2、F5.2。迁移策略取决于真实产品版本原则，不强制所有重构保留旧接口。尤其不能对已明确宣告“完整重写且不要求旧版兼容”的系列强推 Compatibility Shim。

## 一、“兼容”必须指定消费者、方向和时期

“兼容性通过”是不完整命题，至少要描述 `Consumer identity, API/schema version, expected behavior, deployment overlap, data history, rollback target`。向后兼容可能意味着旧客户端可读新服务，向前兼容可能意味着新客户端能容忍旧服务；业务语义兼容又不等于二进制/API 兼容。一个字段从 optional 变 required，在当前单一构建中 TypeScript 编译通过，也可能破坏仍在运行的旧 Consumer。

**重要例外**：有权架构明确将某版本系列设计为**完全重写、整体更换接口、各子版本逐步实现，且明确不兼容原接口**时，工程任务应验证新目标版本的自洽合同，而非添加旧版兼容层把不一致推迟到下一子版本。历史能力是否保留，也由新的有权需求决定，不能由重构一词自行推导“必须复用所有旧实现”。

## 二、扩展—迁移—收缩：只在确有重叠消费者时采用

一个假想 SaaS 在发布期间存在同时运行的 v1/v2 Reader，数据库字段 `full_name` 将改为 `first_name,last_name`。可比较几种策略：
1. 强制一次停机升级：如果有权迁移窗口/停机容忍，并能在目标端验证所有消费者，可能最简单；
2. Expand–Migrate–Contract：先增加新列并让新旧消费者可读；逐步回填；在已验证全部消费者迁移后删除旧列；
3. 新数据库/新产品边界双轨：只有当真实业务迁移要求并能承担同步/双写风险时才采用。

**展开/收缩不是无代价的万能方案**：若拆分包含不可逆的姓名解析，`full_name="Prince"` 无法可靠拆出 firstname/lastname；旧数据若含不同文化命名，不能凭空生成已核实的字段。应保留 `MIGRATION_UNKNOWN` 和业务规则 Owner，而非强制执行一个会静默丢失信息的转换。

更多风险：双写中一个成功一个失败、回填过程中并发更新、新旧代码对 NULL 的语义不同、回滚后旧 schema 已无法容纳新数据。Rollback 程序存在不等于业务真实可逆。

## 三、状态机/业务合同的演化比字段重命名复杂

例子：旧 `Order.status = paid/canceled`，新系统引入 `cancel_pending/refund_unknown/refunded`。若把历史 `canceled` 直接映射为 `refunded`，可能错误宣告外部退款已发生。这不是技术类型转换，而是改变**业务事实/有权 Oracle**。K01 必须给出这些状态的业务语义/适用时间；K03 执行转换；K05 用旧数据、边界例与外部事实证明迁移；K10 在真实 Effect Unknown 时保留风险。

合格迁移的正向测试不能仅看 schema 新列已创建，还要看旧 Consumer 在批准的重叠窗口是否能正确读，新 Consumer 真实业务路径是否运行，以及新旧数据 round-trip 是否有信息损失。若 Consumer 完全不要求旧版支持，则不必为“通用最佳实践”建立双读/兼容层。

## 四、演进的六个关键决策点

| 问题 | 决策需要的证据 | 不应做的推断 |
| --- | --- | --- |
| 是否需要旧兼容？ | 有权版本策略、实际正在运行的 Consumer | “重构必然要兼容” |
| 能否自动迁移？ | 历史数据分布、业务保真要求 | 所有旧值都有唯一新映射 |
| 是否滚动发布？ | 同时存活版本与部署控制 | 单仓源码同步=运行 Consumer 同步 |
| 变更是否可撤回？ | 持久数据/外部 Effect 是否可逆 | 回滚代码就能回滚账务 |
| 回归范围多大？ | 受影响消费者/版本/输入集 | 所有项目全量测试或完全不测 |
| 何时能删旧路径？ | 真实消费者迁出与旧数据可读证据 | 版本号加一=全部客户端已升级 |

对于显式完全重写的 DomainHarness 0.11.x 一类工程（如相关项目有权规则所述），不能以“推荐的 Expand/Contract”干涉已澄清概念的版本归属；如果发现问题，在对应目标版本解决，而非借旧版 Shim 隐藏冲突。这里是知识适用性的**条件说明**，不是确认任何运行时代码已变更。

## 五、技术债与学习价值

技术债既包括有意换取短期收益的权衡，也包括无意形成的脆弱性；“有债”不说明“必须立即全量重写”。评估需考虑故障风险、改动频率、持续维护成本、可证伪边界及替换后回退能力。若一段遗留代码有稳定合同、受支持消费者，盲目重写可能增加缺陷率；反之，继续实现旧兼容也可能违背新版本的整体重写目标。

## 六、反事实练习

给出：v1/v2 两个实际存活消费者、不能无损拆分的 `full_name`、一个已付款但退款未知的历史订单，以及新的完整重写产品分支。正确答案必须分别决定：
- 针对已有重叠 Consumer 的数据迁移怎样保障读/写与回填条件；
- 何处无法自动转换，必须留下业务 UNKNOWN；
- 哪些新版本明确无需兼容旧行为；
- 用哪个独立 Oracle 证明实际数据迁移而不凭程序自检；
- 什么时候可以停止维护旧版本，依据是有权退役决议和实际消费者状况。
