# K06 — 调试与根因修复 / Debugging & Root-cause Repair

> 版本：[v2.1.2 #521](https://github.com/kaicreator-mm/tally/issues/521) · 模块：[Tally #527](https://github.com/kaicreator-mm/tally/issues/527) · [总索引](README.md)。`DETAILED_CONTENT_CANDIDATE / NOT_QUALIFIED / NOT_ACTIVATED`。ADS 为 Agent 开发实践与版本化规范的来源，Tally 负责选择合格的知识并在具体开发任务中消费。文中案例为**可证伪教学情景**，除非另有精确来源，不声称已在真实 Host 上执行。

## 1. 模块定位与目标

让 Agent 从实际失败证据定位最早失效的环节，区分症状、真正根因和错误所在的工程层级，采用小而正确的修复并通过有针对性的测试验证。特别避免出现“CI 红→修改依赖→CI 又红→继续改无关文件”的无限循环。

**适用触发：** 真实构建/测试失败、用户关键路径故障、Provider/Host 环境故障、重复超时、旧问题回归，或一个 Task 多轮同类修复没有收敛。

**本模块最重要的边界：** 诊断不直接授予编辑/环境权限；只有合法 Task/写集与真实执行条件满足才能实施，不能以一条失败日志代替有证据的根因确定。本文不另建代码库逆向分析或软件安全/供应链两个专项；当前实际工程已经生效的权限、源代码和必要安全标准不会因专项暂缓而失效。

## 2. 术语与领域模型

| 概念 | 具体含义 | 易错判断 |
| --- | --- | --- |
| Symptom | 用户或 Runner 实际观察到的错误表现 | 以 exit code 直接当作根因 |
| First Failing Step | 按真实执行时序第一个失败且有实际输出的命令/检查 | 只看 pipeline 最终总结消息 |
| Root Cause | 能够解释症状并可用反事实/修复证据验证的机制 | 出现频率高的猜测就等同确定因果 |
| Reproducer | 在受控输入/版本下可重复触发相同缺陷的最小执行 | 用不相关 Mock 演示替代真实触发 |
| Competing Hypothesis | 仍可能解释同一症状的其他原因 | 用一个猜想排除所有其他环境问题 |
| Repair Scope | 最小合法变更路径及应保持不变的业务/工程行为 | 故障排查时擅自重写整个项目 |
| Regression Oracle | 证明修复问题并保持已有行为的正负测试 | 仅旧错误消失但引入新的缺陷 |
| Attempt/UNKNOWN | 记录哪次 Agent/Host 检查实际运行，哪些结果未取得 | 工具未执行或权限缺失却写 FIXED |
| Oscillation | 不同修复在相同缺陷上反复回滚、补丁互相抵消 | 将多轮无进展当成持续推进 |

这些术语不是全局强制新增的 Tally Schema；仅当实际 Workflow/Business 的输入输出需要区分语义时，才形成有来源的可复用类型或术语。

## 3. 知识正文：核心工程方法

### 3.1 事实取证先于修复建议

读取目标 Task/SHA、真实 CI/Host/编译器的**首个失败命令**、行号、堆栈、标准错误及环境版本。后续“pipeline exit 2”可能只是包装层；早期成功的 npm install 并不能证明后续 build 没有源码缺陷。先观察再定义根因，避免凭旧版问题模板反射性生成新修复。

### 3.2 故障层级的划分

需求错误：接受标准或业务规则本身不清；设计错误：状态归属/契约不成立；源码错误：实现逻辑/类型/异常；测试错误：Oracle 假设错误、用例未被发现；工具/环境错误：依赖、网络、权限、Runner；Host/CI 问题：能力缺失或特定 Provider 故障。分类只是初步假说，必须用相应可观察事实进一步证伪。

### 3.3 因果假设与最小复现

针对最有可能的两个解释建立能区分它们的测试：比如锁文件下载失败应在 install 阶段报错，而 TypeScript 自继承会在编译时报特定诊断。用最小可复现输入/模块固定版本，必要时比较正确/错误代码路径与实际建构环境，不能用无限人工重试代替事实分析。

### 3.4 修复所在层级

局部编译错误应在相应源码和必要测试修；接口/状态所有权不成立需依设计变更进入 L2；用户范围矛盾需回 L1。CI 环境缺失工具不是代码缺陷，直接改产品依赖通常会扩大范围。修复应解释为何该处修改消除了机制、哪些相关失败仍未覆盖。

### 3.5 有界修复与重复失败止损

一次 Repair 应包含确认问题、明确假设、合法修改及最小必要验证。相同来源/环境重复失败时，应对比前一 Attempt 的新证据，不应仅换一个 Agent 重新执行同样命令。无改进、无新证据、碰到权限/外部 Host 限制时停止并上报缺失条件；不要给本地 Agent 无界“持续推进”使命。

### 3.6 错误信息与可恢复诊断

在产品代码中保留适当日志、上下文/相关 ID、故障分类与用户下一步行动；不要通过打印全部环境变量、token/请求内容解决可观察性问题。错误结果要区分业务拒绝、可重试的临时环境问题、内部缺陷和未知副作用；恢复事件不能抹掉真实失败历史。

### 3.7 回归与真实效果确认

用原复现器证明新 HEAD 不再故障，再用典型正向用例与最小边界负例保护已有行为；如果修复影响跨模块入口则增加必要真实消费者检查。Builder 运行测试与 Review、CI、Host 或 Release 是不同资格，不能从新的源码 Commit 直接推断生产修复已经部署。

## 4. 可执行的 Decision Procedures

决策程序定义可复用的方法及终止条件，不创建第二套运行时状态机、审批权威或 Agent 调度器。

### DP-K06-01 · 首个失败点与竞争解释诊断

**输入：** Runner/Host/编译器日志、真实命令顺序、source/tested SHA、任务范围

**步骤：**
1. 确认实际运行过的步骤，标记最后成功与第一个失败命令。
2. 归纳症状、错误消息/堆栈与对应源码/环境边界。
3. 列最少两个可能解释并找能区分它们的一个最便宜检查。
4. 为最有可能原因建立可复现正/负差异或读回确切来源。
5. 选择代码/合同/环境/测试问题的真实责任层。

**产物：** 有来源的根因假设及最小下一步检查/修复范围

**失败/停止：** 日志不足则标 UNKNOWN，不能凭 exit code 猜修复位置。

### DP-K06-02 · 根因修复与回归验收

**输入：** 合法 Task 写集、可复现故障、当前源和最小修改方案

**步骤：**
1. 确保根因解释可以预测现有失败以及修复后的行为。
2. 只改允许源码/必要测试；不加入掩盖错误的无限重试。
3. 先运行失败复现器，再运行受影响正向回归和必要边界反例。
4. 记录新 SHA、执行环境、真实命令与结果，区分未测的 CI/Host。

**产物：** 可审查 Patch + 受影响回归收据/剩余风险

**失败/停止：** 影响其他层、需要越权或改变 Product 时 STOP 并请求原 Owner 修订。

### DP-K06-03 · 振荡止损与经验提炼

**输入：** 多次 Attempt/失败日志、修复方案差异、当前依赖/Provider 环境

**步骤：**
1. 按时间归并相同症状与首次变化，排除重复无价值检查。
2. 判断新尝试是否增加证据或只重现原错误。
3. 如果属于外部 Provider/权限不可用，保持 BLOCKED 并暂停无意义重试。
4. 有来源地提炼可复用 Case/Rule/Skill 候选，并保留失败适用条件。

**产物：** 有界停止/升级结果与经验候选

**失败/停止：** Agent 自报“学到了”不等于已证明跨项目通用性。

## 6. Agent Skills（输入、输出和验证）

### SK-K06-01 · Failure Triage

- **调用时机：** 收到 CI/TypeScript/测试/Host 错误
- **最低输入：** 实际日志、命令/阶段、SHA、上下文与已成功的步骤
- **产出与格式：** 症状、最早失效位置、竞争解释和最小验证建议
- **自查及异常路线：** 写清直接观察 vs 推断 vs UNKNOWN
- **不能做：** 从最终 exit code 自动生成代码修改

### SK-K06-02 · Bounded Repairer

- **调用时机：** 已确认可在当前合法 Task 修改范围内修复
- **最低输入：** 失败复现、Task 写集/当前 HEAD、相关测试
- **产出与格式：** 最小 diff/修复理由/新 HEAD/受影响测试收据
- **自查及异常路线：** 比较新旧失败行为并保护旧功能
- **不能做：** 无界运行直到发布或编辑越权文件

### SK-K06-03 · Incident Learning Extractor

- **调用时机：** 一次真实故障已得到可信结果或保持阻塞
- **最低输入：** 确切问题、修复/测试、环境/前置条件
- **产出与格式：** 经验 Case 的原因链、适用条件、反例和未知
- **自查及异常路线：** 判断是否真的跨任务可复用并避免泛化
- **不能做：** 将一次失败的个别修复当作全局 MUST 规则

## 7. 端到端教学案例与故障反例

**情景：** Woodpecker 一条流水线的 npm install 成功，随后 TypeScript build 报 TS2506 和 TS2339；之前另一流水线曾失败于锁文件下载。

**正确处理：**
1. 从当前流水线读取实际 clone/source SHA、成功的安装命令和第一个失败 build 命令。
2. 将安装阶段失败的旧历史与当前编译失败分开；当前成功安装不能继续归因为锁文件。
3. 定位 TS2506 对应类继承声明是否遮蔽内置 Error，并检查 TS2339 与该根因是否相关。
4. 在合法写集内最小更正类命名/继承关系及必要的对应测试，不顺带更新所有依赖。
5. 运行项目实际 TypeScript build 与受影响测试，绑定新的源码 HEAD；仍未运行的真实 Host/CI 标 NOT_RUN。

**可以观察的正确性：** 同一编译错误不再出现；类型和构建检查真实执行，修复不影响既有公开错误合同。

**故意错误的候选：** 因为之前 npm install 失败过而立即删除/重建 lockfile、升级所有包、添加 clone 重试；当前真正错误完全没有被修复。

**变更条件后如何调整：** 如果当前首次失败确实是网络 fetch/registry，才把问题归入 Runner/外部环境并选择有界重试，不改动无关产品代码。

## 8. 常见反模式与止损条件

1. **历史诊断套用**：旧流水线故障类别覆盖新流水线实际失败
2. **盲目重试**：源代码确定性编译错误靠增加 CI retry 解决
3. **多 Agent 补丁振荡**：相同错误不同 Agent 反复更改而不比较新旧事实
4. **无复现器**：只改源码注释或期望输出就称问题修好
5. **修复越界**：局部实现缺陷扩大为所有模块的大重构

以下是**未来**测试/案例设计，不代表测试或知识资格已经完成。

| 案例 | 期望推断或行为 | 需要拒绝的结论 | 验证依据 |
| --- | --- | --- | --- |
| install 成功、build TS2506 | 将源码/类型问题定位到首次失败 build | 继续归因 npm lock | 实际执行日志+编译器行号 |

**模块交接边界：** K06 消费 K03 的实现错误契约和 K10 的运行可靠性模式，对实际失败做根因调查/修复；不得改写 K10 的通用重试规则或重复声明 K05 的测试资格。
