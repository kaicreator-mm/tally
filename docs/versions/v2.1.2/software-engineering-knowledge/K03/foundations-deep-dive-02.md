## 一、让非法状态难以表达，但不能误认类型为业务真相

将一个任务结果建模为互斥变体，例如 `Pending | Running(jobId) | Succeeded(result) | Failed(error)`，通常比一个包含 `isDone, isFailed, result?` 的对象减少不一致组合。但静态联合类型仅限制类型检查时的某些代码路径；网络 JSON、持久化旧行、外部 SDK 或不可信 Getter 仍需要运行时边界验证。

静态类型不自动证明业务不变量、资源关闭或外部副作用。合法状态转换必须由 K01 有权业务规则和 K02 的提交点共同限定；类型模型可以阻止“有 result 却仍 PENDING”等内部结构矛盾，但不能自行决定用户是否有权关闭订单。

## 二、并发问题至少有三种不同失败模型

1. **丢失更新**：两个 Worker 读同一 revision，各写后值，后者覆盖前者；条件写 `WHERE version=expected` 可在支持的原子存储路径上检测冲突。
2. **顺序依赖**：两次合法操作次序影响结果，单线程事件循环也可能因 await 交错而观察旧状态。
3. **事务异常**：读写集合跨多个行/条件时仅保护一个 version 字段可能不足以维护跨记录不变量；隔离语义应看实际数据库文档与具体语句。

PostgreSQL 18 的 Repeatable Read 在具体实现中避免部分标准允许的异常，但并不自动排除所有序列化异常；Serializable 事务可能需要处理冲突后重新运行整个事务。远端效果不能因本地重试而重复计费。知识图标注“需要事务”不足以选对实现。

## 三、取消和资源清理不是只抛一个异常

异步执行中至少区分：
- **Cancellation request**：调用者希望终止，不能证明后台已结束。
- **Cancellation acknowledgement/settled**：受控任务已经观察到取消并完成约定清理。
- **Effect outcome**：外部服务可能在取消之前已经提交不可逆操作，不能凭 AbortSignal 就撤销。

资源生命周期需覆盖 acquire/use/release，特别是失败分支：文件句柄、锁、临时目录、网络连接、子进程和定时器。若多个依赖同时失败，保留首个材料错误和清理错误；不能吞掉原始失败，也不能在错误打印中泄露密钥。K10 提供一般可行动日志政策，K03 负责当前任务中落实和测试。

## 四、背压是队列增长的数学问题

假设平均到达率为 `λ`、稳定服务率为 `μ`。在长期平均且简单单服务者条件下，若 `λ >= μ`，无界排队将持续增长或无法稳定，调大内存并不能从根本上解决容量缺口。即使 `λ < μ`，流量突发、服务时间分布和下游慢调用仍可能导致尾延迟过高。

备选包含有限队列 + 拒绝、限流、批次、削峰、更多消费者或持久作业；必须根据需求明确是允许丢弃、阻塞生产者，还是记录为可恢复工作。不能把“无限重试直到成功”当背压策略。

教学反例：批量导入 API 返回 200 后，把所有工作放进未持久化无限内存队列；高峰时进程耗尽内存并丢失任务。错误不在“队列实现语法”，而在容量/持久性合同遗漏。

## 五、证伪正确性的最小测试闭包

给定一个支持重试/取消的 Job，独立设计：
- 重复请求 ID、并发旧版本写、取消与提交竞争的正反输入；
- 出错后的文件/连接释放与可观察状态；
- 有界队列溢出后的合法拒绝/恢复；
- 源码、依赖和真实受测路径是否一致。

缺目标数据库版本、外部 Effect 语义或 Queue 策略时输出 UNKNOWN，并在 K02/K10/K05 路径解决；不能因为单元测试或代码类型检查通过宣称已达完整工作流正确性。
