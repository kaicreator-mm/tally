## 7. 贯穿案例：正例、变体与反例

以下为**教学/设计情景**，不是宣称 ADS/Tally 已经执行或验证过的真实项目记录。实际资格认证必须替换为来源可核查的真实 Issue、源码版本、测试/Review/Host 收据。

**场景**：实现“批量处理工作项”，允许用户取消其中部分操作；同一请求可能因客户端超时被重试。

**正确处理路径：**
1. 根据批准合同确认每项工作可独立成功/失败，明确定义整个批次的部分成功表示与状态变更条件。
2. 选择批次大小限制、结果列表/错误格式与原子性边界，考虑一次性数据库事务与逐项更新的成本差异。
3. 为重复请求标出请求 ID 或可重试语义，防止重复造成额外副作用；明确 UNKNOWN 如何回读。
4. 在合法写集内实现状态检查、持久化、异常处理和资源释放，并记录可行动日志。
5. 编写成功、失败、取消、超时和重复请求测试，运行项目真实受影响命令并绑定当前 HEAD。

**成功的可观察标准：** 相同请求重复不会额外改变合法已处理业务状态；部分失败/超时有明确可观察语义；实际测试覆盖被执行的入口。

**错误处理路径与后果：** 使用全局可变数组表示批次进度，网络出错后无条件重做所有工作；错误仅输出“processing failed”；没有执行测试就声称完成。

**情景变体与边界：** 若业务要求整批原子性，必须调整状态/事务合同；如果已有接口不能表达部分成功，应由 L2 确认兼容性方案。

## 8. 反例库：哪些情况不能据此推断成功

1. **写代码替代设计**：重要状态与错误合同未清楚就直接开始多个 Agent 并发编码
2. **无限框架化**：简单同步逻辑导入抽象调度、重试、事件总线三套基础设施
3. **不可观测错误**：吞掉异常导致用户和维护者无法识别原因
4. **伪验证**：本地命令未实际运行、测试未发现或使用旧 SHA 便宣称完成
5. **跨写集修复**：发现上游接口不够就修改其他任务的冻结源码，无合法接纳

## 扩展场景：用不同条件检验知识的泛化边界

### C-K03-01 · 批处理重复请求

**问题**：同一请求 ID 的合法状态转移不可重复产生副作用；结果为 UNKNOWN 时查询。

**如何用本模块诊断/解决：** 先识别用户目标、确切源/版本与真实约束，按 [方法矩阵](engineering-methods.md) 选与此情况匹配的一条有界程序；不影响结果的假设不额外提高流程成本。

**反例**：若 Agent 未核对上述关键条件就直接断言相同方法普遍适用，必须以 UNKNOWN/REWORK 处置而不是 PASS。
