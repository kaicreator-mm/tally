## 一、不能从代码重复或长函数直接推出“必须抽象”

真正决定是否共用的不是语法相似，而是**语义相同且随未来变化的方向一致**。需要逐项核对：

`PRECONDITION`（谁能调用/何时可用）、`POSTCONDITION`、`INVARIANT`、`ERROR_SET`、`SIDE_EFFECT`、`STATE_OWNER`、`CLEANUP`、`VERSIONED_CONSUMER`、`CHANGE_AXIS`。

一个操作从 `false` 返回改为抛错，对两个消费者可能有完全不同的可观察后果。把它们合并，只因函数主体一样，却用可选参数隐藏这些差异，是**错误抽象**。也不等于“所有重复必须保留”：若机制不变量和变化轴真正相同，则重复实现会导致修改漂移，应逐步统一。

## 二、抽象粒度选择矩阵（DP-K03-R19-01）

| 候选 | 适用条件 | 主要收益 | 失败风险/反例 |
| --- | --- | --- | --- |
| **保持内联** | 逻辑局部、短且无真实复用或独立变化，额外接口不降低认知负担 | 最短行为路径，无隐藏 indirection | 大量散落的同一行为导致修改遗漏 |
| **局部 private helper** | 同一个 Owner 内多个点共享已证明相同机制，不需要跨包消费者 | 统一算法/校验，保留局部阅读 | 把不同错误/权限隐藏成一个布尔开关 |
| **领域模块/文件内聚** | 一组不变量、状态/资源生命周期和变化原因由同一 Owner 管理 | 隔离变化，把责任、测试和失败收口 | 仅按动词拆模块导致共享状态失控 |
| **窄公共接口/契约** | 存在真实异构消费者、稳定替换边界或独立发布/兼容要求 | 隐藏实现细节、减少非必要传播 | 因为一个调用者就引入接口、Adapter、Registry 或额外版本承诺 |
| **Strategy/可插拔 Provider** | 被授权的动态扩展/替换、多个实现共享同等合同而非只是同名 | 显式合法变化轴，可受控替换 | 两种实现有根本不同的错误/事务/信任语义，被强行统一 |

对于稳定单体或一次性实现，最正确的决定可能是**不引入公共抽象**。不能把“使用接口比具体类型多”当设计质量。对于跨 Package 共性，也必须先满足项目实际编译/依赖/权限规范，不能因为有抽象需求就非法调用未声明依赖。

## 三、八步有限推理与可复核产物

1. **列输入合同**：有权业务要求、消费角色、现有版本支持、共享状态/资源和真正不变量。
2. **找重复的类型**：区分相同符号、相同算法但不同语义、相同不变量与相同未来变化三个层次；至少找一个可推翻“相同”的失败场景。
3. **确认谁负责错误/状态**：在不同 Owner、不同清理或异步完成时，不能用公共函数吞掉差异来制造复用。
4. **列两个最小可行候选**：例如 helper vs 模块；也可直接比较 inline vs helper；不强制五种都实现。
5. **选变更隔离收益**：假设一个已获权的变更发生，会修改哪些职责模块/公共接口/测试？不要求猜测不存在的需求。
6. **计算间接性成本**：是否增加跳转层、隐式注册、难追踪错误或额外版本维护？能否保持调用者只理解必要的公共语义？
7. **最小实现 + 对等测试**：先保证受影响已有行为、错误与资源边界，再用真正覆盖行为差异的 Oracle 排除错误共性。静态指标是辅证而非通过证书。
8. **停止/反驳**：若抽象不能隔离真实变化，或不同机制被合并导致失去语义区分，应保留差异；若真实重复在多处导致同一 bug 多次修，才有明确重用动机。

**记录建议**：`SOURCE / INVARIANT / CHANGE_AXIS / ALTERNATIVE_A/B / OWNER / CHOSEN_SCOPE / REJECTED_AS_OVERDESIGN / FALSIFIER / STOP`。可用一段 ADR/设计注释表示，不要求每个工具函数开一个 Issue。

## 四、三个原创负例

**负例 A：仅复制了两行字符串处理。** 两个不同领域的标签处理流程，虽然用了相同正则表达式，但一个要求保留原始空格，另一个允许规范化。将两者复用为一个 `format(input, mode)` 如果误删空格，是**错误共性**；优先保持语义各自明确，再考虑独立共用底层纯函数。

**负例 B：为了多层抽象而增加调用间接性。** 只有一个固定本地文件写入实现，却添加统一 Provider Registry、远端加载、可配置注入三层，导致错误路径难读，而无实际插件/多平台要求。多一层不自动是架构专业化。

**反向例 C：同一个不变量真的被多处维护。** 三个 API 入口都要调用同一来源的无状态校验，且 Source 明确要求相同错误分类。统一私有 helper 可以避免修复一处时遗漏另两处；如果公共接口稳定并被外部复用，再讨论更高层次的契约。

上述只用于教学，**不得作为未来 #554 隐藏测试的题目或默认正确方案**。

## R19-F2 反馈候选：精确数值是行为合同，不是模式选择题

[R19-F2 研究反馈](../professional-abstraction-empirical-feedback-r19f2.md) 记录了一个跨多个实现的 JS 时间边界反例：输入均为安全整数，并不保证窗口端点计算、下一周期、重试倒计时的**中间运算**不会产生舍入误差。对有明确高精度合法域的任务，应设计接近整数/时间边界的可证伪测试，核对完整表达式范围；根据现行合同选择安全的差值/余数推导、范围限制或 BigInt。缺少精度要求时先向 Source Owner 确认，而不是机械要求更复杂的架构。

这一条属于**行为正确性/输入语义**，不因出现数字 bug 就自动计成 UNDER、WRONG 或 OVER 抽象；若要判为抽象错误，Reviewer 应证明失效与具体抽象决策（例如领域表示、语义合并、共享机制、Owner 边界或抽象粒度）的因果联系。例如局部领域类型把精确整数与近似测量值统一成舍入表示，导致合法精确值不可表达，即使没有跨模块共享也可能是 WRONG；若只是公式或实现 bug，则记录行为缺陷，不自动贴抽象标签。

## 五、避免让 LLM 假装做抽象

- **不要**让 Agent 只罗列 SOLID/DDD/Strategy/Factory 然后声称符合。必须指出当前代码的实际行为、变化驱动、每种候选可违反的具体合同。
- **不要**把所有重复强制 DRY；只有同语义/同维护变化方向才适合共用，否则属于 `WRONG_ABSTRACTION`。
- **不要**为了满足文件长度阈值把状态拆到无 Owner 的工具类或多重单例；也不要因“只有 1 文件”就默认坏。
- **不要**为了评分写更多架构文档。对小改动只需局部代码及真实回归。
- **确实存在必要多实现时**，要让消费者通过相同、有权的协议获得一致行为，但不能隐瞒原协议不同的完成/错误/授权语义。

**STOP**：没有共享不变量、合法变化点或具体重复维护成本时，保留最小直接实现；业务源不明时 `ASK/UNKNOWN`，不让工程抽象越权替 Owner 创造新需求或规范。
