# K03 · R18 进阶：代码可理解性、抽象成本与可读性的可观察评价

> 来源线索：[Google Engineering Practices — What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html) 将设计、复杂度、测试、命名和文档分别审查；[ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html) 是产品质量框架，不直接给“行数少=维护性高”的数学公式。以下是本知识库独立推导的代码理解实验方法，而非 Google 的官方评分制度。

## 1. “别人容易读懂”必须以实际任务表现证明

代码风格整齐、注释丰富、函数短不一定可理解。真正的观察对象是**不认识作者的维护者**能否在合理上下文中正确定位行为、预测输出、找出隐藏副作用、解释修改影响。阅读与运行验证要分开，避免单靠 Reader 自称“看懂”。

| 评价维度 | 可观察任务 | 可能的误判 |
| --- | --- | --- |
| 局部推理 | 给指定 public API 输入，正确指出返回值/错误/状态变更来源 | 函数短但需要跨六层查注册表 |
| 导航成本 | 从公开入口找到决定合法状态/权限/持久化的真正实现路径 | 单文件很长≠一定导航困难，自动跳转也会改变耗时 |
| 命名和概念一致性 | 区分业务键/数据库主键、请求成功/外部 Effect 已完成、异常类和状态类 | 名字看似详细却与实际生命周期不符 |
| 抽象成本 | 解释新增接口、继承层、Factory、Adapter 带来的一个实际收益和一种间接性 | 不是所有抽象都坏，跨多消费者变化可使抽象必要 |
| 修改影响理解 | 预测添加一种已知合法行为要改哪些职责模块 | “只改 1 文件”可能是将全部职责塞进巨型模块 |
| 测试可理解性 | 从用例读出断言的有权事实、输入与真实执行入口 | 断言多/覆盖率高不等于验证了关键不变量 |

在每个维度记录实际证据和 `NOT_TESTED`。避免为了评比而要求不必要的文档、Class 或测试；源码上下文和语言工具对不同人有不同帮助。

## 2. 有界代码审查决策顺序

1. **从合同与真实入口开始**：查 `Package`、公开 API、参数及失败路径，禁止凭目录名假定状态拥有者。
2. **画最短事实链**：请求 → 验证 → 持久状态/外部 Effect → 回复，标出隐藏 I/O、隐式单例、共享可变状态和可能的事件队列；有异步回调/Promise 的地方明确 settle 与资源清理。
3. **比较抽象收益**：新增接口是否隔离了真实变化轴？是否使一个修改只落在有权 Owner？是否有两个以上实际异构消费者、稳定版本合同或运行时替换要求？没有这些条件，“未来可能有用”的抽象只能是候选而非必要。
4. **对照两个损失方向**：重复导致分叉漂移和巨大函数造成局部认知过载；过早通用化造成跳转链长、可见错误状态被抽象隐藏。优先做**满足当前合同的最小可读设计**，而不是最小行数。
5. **审查控制流和错误**：错误信息是否提供安全、可行动的上下文？失败时资源是否必然释放？能否分辨业务冲突、无权、损坏、未知外部结果？异常是由真正 Owner 处理还是层层吞掉？
6. **给可反驳的例子**：指出精确文件/符号/事实路径；如果被审作者提供相同功能下更清晰的可观察解释，应允许反驳。无实际理由的个人喜好标 `STYLE_ONLY`。

## 3. 用陌生 Reader 的盲测衡量理解

对同一阶段冻结的不同候选，Reviewer 先把组别、知识来源、作者简介隐藏，分配**相同难度、相同背景和相同工具约束**的行为解释与代码定位任务。不要通过文件命名习惯或文档量暗示 A/B；若实现不同，需要在预冻结规范下为每份实现映射为相同职责目标，不能事后把某一份设为更难的题。

**原始测量建议**（研究方法，不是强制产品 Gate）：`CORRECT_COMPREHENSION`（明确裁定题的核心事实是否正确）、`TIME_TO_CORRECT_EXPLANATION`、`FILES_OR_SYMBOLS_INSPECTED`、`WRONG_INFERENCE`（具体误解）、`REQUIRES_HUMAN_HINT`、`REVIEWER_BLINDNESS`、`STATIC_ANALYSIS_OBSERVATION`。重试/提示成本纳入分母；超时不排除。

**不要直接归一化**各种指标形成“可读性 97 分”。时间受 Reader 熟练度/IDE/上下文缓存影响；文件数会奖励巨型文件；函数行数会奖励无谓跳转；注释数量会奖励重复陈述；lint pass 主要证明符合选定 lint，而非复杂业务逻辑可理解。以上指标应与具体错误解释、案例可读路径共同报告。

### 原创教学例（不含未来隐藏维护题）

`resolveOutcome()` 调用 `getResult()`，后者再次通过动态表调用 `query()`，而 `query()` 隐式刷新远端状态。变量名可很短、测试可全绿，但直接阅读函数无法判断是否产生远端副作用。比增加更多注释更有价值的改善，可能是明确副作用类型/调用入口和状态读取责任；**如果已有固定 Provider API，重新命名所有公开接口可能反而造成兼容损害**。

反例：把三个真的存在不同故障语义的操作合并为统一 `process()` 以减少重复，若由此丢失失败区分性，该“重构”降低质量。反向反例：为一个简单线性流程新建五个抽象层，将正常路径拆成五文件，也并不更专业。

## 4. K03→K05/K09 的实际交接

- K03 提供**具来源的符号行为/代码路径**，不自己评分自己的实现；
- K05 用独立 Reader、已冻结理解问题和阳性/阴性校准审查指标，覆盖实际未测路径；
- K09 在后续真实维护变更中验证“容易理解”是否转化为更安全、更低成本的修改；
- K11 计算新增抽象的构建/理解/运行/回归总成本，而非首次代码 Token。

**STOP**：简单 bug 定位已有完整合同与清楚代码路径，或实际 Reviewer 无法获得可访问的正确源码时，不生成大量伪度量。无法盲评标 `NOT_BLIND`；合同行为不明则 `EXPECTED_UNKNOWN`；读者没跑代码不能宣称功能合格。本文没有授权任何新 Code Review Rule、CLI/Linter、评分器或 Runtime Consumer。
