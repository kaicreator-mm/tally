## 1. 问题与应用触发

本地数组去重、百万条记录统计以及服务端分页能否复用同一种实现？性能和代码复杂度如何权衡？

**适用前置输入：**
1. 真实或能代表业务的数据量/负载、输入分布
2. 内存、磁盘/网络、数据一致性与平台约束
3. 当前项目已有库、实际工具链和可测试正确性要求

**学科原理与为什么这样决策：** 算法复杂度是对某个输入规模及操作分布的增长描述，不自动代表真实设备上的延迟。必须同时考虑数据规模、数据是否有序、操作次数、内存上界、I/O/网络瓶颈和业务正确性。小样本 O(n²) 可能简单可接受，频繁大规模检索可能更适合 Map/索引/数据库查询；不要基于理论阶数而忽视外部 API 和持久化成本。

## 2. 实际决策程序（按现有权限执行）

1. 定义必须保持的结果语义：稳定顺序、重复处理、大小写/空值、溢出、边界与错误处理。
2. 列最简单与一两个实际候选，例如嵌套查找 vs 哈希映射、全量载入 vs 流式迭代、扫描 vs 已有 DB 索引。
3. 分别分析渐近增长、常数、缓存/对象分配、内存和工程维护成本，不把粗略复杂度当真实毫秒。
4. 先用真实或代表性负载做基线，必要时局部优化，比较正确性、延迟和资源消耗；不改动合同的其他部分。

## 3. 按条件选择，而不是背诵一种答案

| 场景条件 | 当前应作的判断 |
| --- | --- |
| 输入几十条/不常调用 | 可选择清晰直接实现，避免过度抽象。 |
| 百万条大对象且内存受限 | 考虑游标/流式/有界批处理及背压。 |
| 数据库查询受索引选择影响 | 用实际 query plan/代表性数据确认，不能仅靠源代码循环复杂度判断。 |

## 4. 可复用的教学案例与负例

**合成正例：** 一万条订单按 ID 找用户，嵌套循环可能成为热点；Map 将查找改为平均常数时间，但会增加内存并要求唯一 ID/覆盖策略。真实规模只有 20 条时无需为了复杂度上界重构。

**失败/反模式：** 为了理论最快给一个每日调用一次的小函数部署全局缓存与共享存储，导致陈旧读和额外同步故障。

**可证伪的结果 Oracle：** 实际受影响行为测试保留原顺序/去重等语义；没有同环境基线时只能给算法选型理由，不能声称实测提升 10 倍。
