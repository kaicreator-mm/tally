## 1. 三个不同的“成功”，不可合并

- **标识唯一**：同一个逻辑提交键只能拥有一个稳定的逻辑记录身份；前提是使用明确的作用域（租户、项目、记录键、版本或内容摘要），不能把「文件名恰好相同」当身份约束。
- **持久状态一致**：存在可判定的原子提交边界；在并发和故障之后，调用者能凭本地持久化事实判定已提交、未提交或 UNKNOWN。不能仅以「写入函数返回」替代盘上提交的证明。
- **API 返回后的可观察静止性**：如果公开合同承诺 resolve 后不再有未等待的临时写/清理/发布操作，那么调用方之后观察数据目录时不应出现对本次提交的后台副作用。这个性质必须被**明示**；有意设计为异步最终一致的 API 不自动满足它。

**提交前写入临时文件、文件 rename 成功、事务落盘同步完成、向上层发送 ACK** 是可能彼此分离的事件。文件系统的 rename、独占创建和同步保证依赖 OS、文件系统、设备、进程故障模型。`fs.rename` **不是跨平台、跨故障类型的万能事务**，尤其不能由「进程崩溃可恢复」推出「掉电后已 ACK 数据一定持久」。SQLite 通过日志/事务/同步条件建立另一套可审查的保证，但也受配置和底层文件系统条件约束。

## 2. 并发创建：竞争者必须收敛，而不是在同一目标反复改名

对于「同一 scope+key 只能首次创建」的场景，可采用**原子 exclusive-create + 后续只读回读**的候选设计：

1. 先定义标准化 key 的作用域、值域及 expected digest；并为目标记录确定唯一的不可变身份。
2. 尝试以本地文件系统可提供的 `open(path, 'wx')`（或等价的、经平台验证的原子条件插入）取得**独占创建权**。成功者（CREATED）完成预定义可恢复提交协议；失败为 EEXIST 的竞争者不能盲目覆盖或不断 rename，须**从已提交事实回读**，比较 scope、key、digest 并给出等价结果或有权冲突。
3. **EEXIST 不等于目标已完整提交**：另一个创建者可能仍在写入、已崩溃或留下半成品。设计必须区别 `PREPARING`/已提交/损坏，设定有界观察、租约/恢复/拒绝策略，避免把尚未提交内容当成功。某些文件系统/NFS 与操作系统语义不适用，此时必须更换提交原语或存储技术。
4. 错误（EACCES/EPERM/IO/损坏/重试耗尽）保留为实际错误/UNKNOWN；不能将一切失败映射成「记录已存在」，也不能对持久状态做无界重试。
5. 临时文件采用唯一名字与显式 Owner；每次尝试清理自己创建的临时资源；对崩溃留下的孤儿使用**受界且可解释的恢复/GC**，不得删除其他活动写入者的文件。

这些步骤**不是普遍可直接复制的正确实现**。独占创建获得的是特定 path 的创建原语，不是多文件原子事务，不保证客户端永不重复收到外部 effect，也不意味着读者可以跳过提交状态判断。

## 3. 不同方案与前提

| 方案 | 适用条件与机制 | 主要失败边界 |
| --- | --- | --- |
| 单进程互斥/队列 | 同一进程持有唯一写入者，已验证进程内入口 | 多进程、重启和不共享内存的 Worker 不受保护 |
| `wx` / 条件创建 + 状态回读 | 目标文件路径和创建操作在实际文件系统中有适当独占语义，允许设计完整提交状态 | 已创建未提交、部分写入、重启、目录 fsync、外部效应及远端文件系统 |
| 临时写入+原子替换 | 单个数据文件整体替换，读者需要旧或新完整快照；平台条件经验证 | 多个文件事务、同目标并发创建者冲突、Windows 句柄/权限、掉电持久性 |
| SQLite 事务/唯一约束 | 有真正多条记录/并发事务/恢复需要，愿意引入数据库与配置成本 | busy/lock、sync 配置、迁移/维护、不能自动覆盖外部副作用 |
| 事件日志+投影 | 需要审计/补偿/恢复且已为独立持久标识分配 Owner | 重放可能重复投影或对外副作用；需要幂等消费者和顺序保证 |

如已选择支持目标故障模型的事务数据库，就不应因「一个实验 Agent 曾用 `wx`」而强制改为文件级账本。技术选型是 L2 Decision，R13 只是专业原理与反例。

## 4. 推导可反驳的验证需求

教学场景：两个进程对**同一用户范围内**同一逻辑条目同时保存；记录附加可观测递增次数（非真实付款/外部操作）。

- **T1 创建收敛**：二十次并发创建只可观察到**一个**合法记录身份；拒绝或等价返回必须按公开合同处理；记录所有执行路径，不因吞掉异常而记 PASS。
- **T2 交错/退出**：在拿到创建权后、数据写完前、已提交而 ACK 前分别终止写入者；重启后不得把半成品当作有效已提交结果。
- **T3 静止性**：若 API 保证 resolve 后完成清理，响应前后快照文件集合/目录与打开句柄；异步允许的场景不能误判成缺陷。
- **T4 竞争者回读**：竞争者观察到「存在但未提交」时，限时重试、恢复或明确 UNKNOWN；不可仅凭 EEXIST 立即报成功。
- **T5 平台失效分类**：在已声明的 Windows/Linux/文件系统上观测 EPERM/EACCES/EEXIST/错误注入，确认失败分类和资源清理；只在一个系统上通过不能宣称跨平台结论。
- **T6 幂等与资源**：重复提交的可见记录数与身份不变，临时资源无泄漏；存在外部操作时还要独立验证 Effect ledger/回读路径。

## 5. 反例、边界和来源

**反例 1**：两个 Worker 各自有 JS Mutex，仍同时试图 rename 同一个目标。两个锁都「正常」，但跨进程根本不共享；根因不是重试次数不够而是同步范围错误。

**反例 2**：`wx` 返回成功后尚未完成写入便崩溃，另一个 Worker 得到 EEXIST 立即返回 OK。磁盘上只有半个 JSON；这里 exclusive-create 阻止双创建，却**没有**达成 durable valid record。

**反例 3**：一个程序在 Linux 测过 rename 就宣称 Windows 上持久状态切换等价。这没有覆盖 Windows 路径/句柄共享与权限约束，也不能替代实际 Host 证据。

**原始技术来源（独立于 R2 报告，引用其适用机制，不视为 Tally 资格）：**
- [Node.js v22 File System API](https://nodejs.org/download/release/v22.3.0/docs/api/fs.html)：`wx` / exclusive flag、Windows 文件访问语义；应按当前选用的具体 Node22 release 文档复核。
- [SQLite Atomic Commit](https://www.sqlite.org/atomiccommit.html)：持久化、同步和故障模型；不是对任意自写 `fs.rename` 文件协议的背书。
- [SQLite Transactions](https://www.sqlite.org/lang_transaction.html)：并发写、busy、事务范围与支持条件。

**停机条件**：缺少目标文件系统保证、无法界定 ACK/commit 边界、未声明 effect 的幂等范围、无独立 crash Oracle，就保留 `UNKNOWN / NOT_VERIFIED` 而不把本章的方案当生产合格。
