# K10 — 可运维性、可靠性与性能 / Operability, Reliability & Performance

> [v2.1.2 #521](https://github.com/kaicreator-mm/tally/issues/521) · 模块 Issue [#531](https://github.com/kaicreator-mm/tally/issues/531) · [总目录](README.md)。`DETAILED_KNOWLEDGE_CANDIDATE / NOT_SOURCE_QUALIFIED / NO_RUNTIME_ADOPTION`。ADS 负责 Agent 真实软件工程实验、实践及现行工程规范，Tally 负责把合格知识接入软件工程领域工作流。案例为可供未来验收的教学情景，不表示已经实测通过。

## 1. 本模块能让 Agent 解决什么

让 Agent 在实现业务功能的同时，能够为用户与维护者提供**可操作的错误、合适的日志、可恢复的失败语义和可信的性能判断**。这部分不是要求每个小项目部署大型 Observability 平台，而是把运行质量与具体应用类型、真实故障及经过确认的质量要求绑定。

**适用与触发：** 用户首次运行/配置、后台服务故障、连接/依赖超时、任务重试/取消、错误排查、业务连续性或性能 NFR 真实受到影响时；普通小型纯函数变更可仅复用 K03 的基础错误处理。

**明确不做：** 不统一要求所有项目安装 APM/Tracing Server，不将重试作为通用解决办法，不制造未测量的吞吐/延迟提升报告。现阶段不新增独立的代码库逆向分析和软件安全/供应链知识专项；已生效的权限、基本安全和实际工程质量约束仍应执行。

## 2. 术语表、关系与边界误区

| 概念 | 可使用的工程定义 | 必须避免的推断 |
| --- | --- | --- |
| **Actionable Error** | 用户或操作人员能据此判断发生什么、影响是什么、怎么处理的错误 | 只返回未知异常堆栈或一串无解释 exit code |
| **Structured Log** | 适量、结构化、与来源/操作相关的运行记录 | 多打印调试输出即表示可观测 |
| **Correlation ID** | 将一次业务操作在多个模块/调用之间关联的标识 | 把用户秘密或敏感请求全文当相关 ID |
| **Transient vs Permanent** | 可因条件变化而恢复的临时问题，与确定性业务/代码错误 | 将所有异常一律无限重试 |
| **Retry/Idempotency** | 有条件重复请求时保证目标副作用语义不会错乱的机制 | 重复发送就认为 exactly-once 已经实现 |
| **Timeout/Cancellation** | 等待与取消的边界，包括超时之后业务结果仍未知的可能 | 超时=操作没有发生或一定失败 |
| **Reliability Scenario** | 故障模式、恢复方式、用户可见结果与保证条件 | 平均情况成功便宣称所有故障可恢复 |
| **SLO/Performance Baseline** | 明确真实负载、目标和测量环境的延迟/吞吐/资源评估 | 没有测量就说优化了 3 倍 |
| **Startup Configuration** | 首次启动/初始化与配置生效/失败的用户体验和后台例外 | 所有 CLI/容器都要同桌面 App 的交互设置 |
| **Incident Evidence** | 故障、缓解、恢复、验证和后续修复的可关联历史 | 恢复后删除/重写之前失败证据 |

这些概念可以作为 Domain Concepts/Knowledge 与 Tally Workflow 的语义输入，但**不是**新增通用数据中心或自建 Task/Claim/Release 权限状态机的理由。

## 3. 专业知识正文：原理、应用、代价和限制

### 3.1 错误信息必须面向真实使用者

错误可能显示在 UI、CLI、日志或 API response，所需粒度不同。用户应该知道请求是否已被处理、哪些部分失败、是否可重试、该检查配置还是联系管理员；开发者可以在受限日志看到原始技术错误与相关 ID。禁止泄露密钥、用户隐私或全环境变量。仅捕获所有异常并返回“失败，请重试”会导致用户无法判断实际状态。

### 3.2 日志不是越多越好

按业务结果、错误原因、关键状态转换和真实需要的关联信息规划日志级别。高频成功路径不必每步输出数十条 INFO；严重失败应带操作名称、可追溯的安全 ID、失败阶段、已执行副作用/是否未知。日志要能与版本、Host/环境、Attempt/Task 的证据关联，但不得凭日志存在就认定结果被验证。

### 3.3 首次启动与配置策略

桌面/Web 本地交互产品可以启动后引导设置、存储与校验配置，再开放需授权的业务能力；命令行、容器和后台服务可能更适合通过参数/环境变量/配置接口初始化。这是根据应用形态选择的策略，不是“不能出现任何配置文件”或“所有业务必须先显示配置 UI”。敏感配置需遵守已有项目权限和保密规范。

### 3.4 重试、超时、取消与幂等性

将确定性的非法输入/代码缺陷与临时网络/外部 Provider 错误分开。只有存在合理恢复可能且副作用安全时才重试，需指定次数/退避/总超时；重试对多次提交的业务影响应有幂等键或状态回读。超时只代表当前观察者没在期限内得到确认，不一定意味着服务端没有提交。取消需要理解是“停止后续工作”还是“回滚全部已生效副作用”。

### 3.5 状态与恢复保障

为实际项目的最重要业务状态定义恢复条件：持久化点、重复或部分执行、重启后能否恢复、外部系统是否承诺交付/确认。恢复事件不应抹除历史已观察的失败和补救；未知副作用应通过合法状态查询确认，而不是直接标成功或失败。没有业务持续性要求的单文件工具没必要引入分布式恢复框架。

### 3.6 性能调查应以可复现证据为基础

分析性能前先定义请求/数据规模、目标用户感知的指标、运行平台及负载。利用真实 profiling、指标和差异基准选择瓶颈，而非只看源码复杂就猜测热点。优化不仅要测延迟和吞吐，还需看内存、资源/CPU、长期维护成本及业务正确性是否退化。不同主机/输入/缓存条件的结果不能直接得出因果结论。

### 3.7 故障经验和运行生命周期

一份有效运行事故记录应区分 DETECTED、MITIGATED、RECOVERED、VERIFIED、FOLLOW_UP，保留确切时间/来源和客户影响。可以从可复现案例提炼 DecisionProcedure/Skill 候选，但单次事件中的“当时增加了重试就好了”可能不适用于其他确定性错误。Tally 在维护/反馈流程使用知识时不能自行改变既有 Release 和事件事实。

## 4. Agent Decision Procedures（决策方法）

### DP-K10-01 · 用户可操作错误与日志设计

**输入：** 产品运行形态、业务错误分类、用户操作、必要日志/隐私约束

**操作步骤：**
1. 识别用户/运维/开发人员各自需要的错误信息和行动。
2. 为业务拒绝、配置缺失、暂时故障和内部异常定义不同状态与输出。
3. 选择必要关联 ID、稳定错误码/原因/恢复建议与日志级别。
4. 排查高风险信息泄露和日志量过大/频率过高的问题。
5. 在实际 UI/CLI/API 入口验证用户能找到相关错误。

**输出：** 错误/日志契约、正反例及用户可执行下一步

**停止与例外：** 若没有足够权限说明细节，应输出安全摘要与相关 ID 而不是敏感上下文。

### DP-K10-02 · 超时/重试/恢复规则选择

**输入：** 业务操作是否幂等、外部状态读回能力、容忍重复副作用和超时要求

**操作步骤：**
1. 区分确定性与可能恢复的故障。
2. 确认操作的提交点及重复执行能否安全。
3. 定义有界超时/重试/指数退避/取消/回读行为。
4. 针对重复请求、迟到结果、部分成功和重启做最小测试。
5. 结果无法确认时保留 UNKNOWN 并要求合法状态回读。

**输出：** 有条件的恢复策略及对业务副作用的保证

**停止与例外：** 不把所有超时解释为失败，不能用无限重试恢复代码缺陷。

### DP-K10-03 · 性能优化证据判断

**输入：** 实际工作负载/平台、基线与目标、可重复测量方法

**操作步骤：**
1. 明确对用户有影响的指标和输入分布。
2. 在固定环境和真实代表性数据上获得基线。
3. 定位最可能瓶颈，明确其他竞争解释/缓存影响。
4. 进行最小改动，重复测量正确性和性能。
5. 报告统计/条件及已知偏差，不推断跨平台普遍效果。

**输出：** 同条件前后测量、功能回归、成本/不确定性报告

**停止与例外：** 基线不可得则 NOT_MEASURED，不能声称实测提升。

决策方法的输出是候选依据和建议；不自动获得产品采纳、Architecture Freeze、Agent 执行权限或 Release 状态。

## 6. Agent Skills 与输入输出契约

### SK-K10-01 · Error and Log Contract Designer

- **调用条件**：UI/CLI/后台服务需改善诊断体验
- **输入**：真实用户角色、错误类型、应用形态与数据保护规范
- **输出**：错误码/原因/行动/日志字段/示例及最小测试
- **核验要点**：用户无需查看源码就能理解下一步，不泄露敏感信息
- **拒绝或升级条件**：不能对所有产品输出完整堆栈/环境变量

### SK-K10-02 · Reliability Scenario Builder

- **调用条件**：超时、取消、重试或恢复是实际产品要求
- **输入**：当前提交点/存储/外部 Provider、状态机/异常语义
- **输出**：正常、重复、超时、部分成功、迟到、恢复的可证伪案例
- **核验要点**：UNKNOWN 与已提交结果被准确区分，重试有限
- **拒绝或升级条件**：不得“重试直到成功”或保证没证实的 exactly-once

### SK-K10-03 · Performance Evaluation Planner

- **调用条件**：性能要求/投诉有具体来源
- **输入**：目标指标、输入数据、设备/平台和可重复基线
- **输出**：profiling/对照/正确性回归和测量报告
- **核验要点**：测量可复验且可说明条件差异
- **拒绝或升级条件**：没有基线不得在文档里写数字改善百分比

## 7. 完整教学案例：正确实施、错误做法及边界

**任务情景：** 一款桌面管理工具第一次启动需配置仓库与工作目录；业务操作偶发请求超时，用户再次点击可能导致重复执行。

**合理的工程路线：**
1. 依据交互式应用场景提供启动后的配置入口，未配置完成时禁止需要授权的业务动作并给出明确错误。
2. 对 CLI/后台同类应用允许符合其启动环境的参数或服务配置，不机械复制桌面配置 UI。
3. 将请求 ID、当前版本、操作和失败类型记录为可行动日志，避免输出令牌/完整敏感请求。
4. 确认请求可能已提交但 ACK 丢失时的重试/状态回读和幂等性合同。
5. 用未配置、非法配置、超时、重复点击、服务端已完成但客户端超时等场景验证用户实际体验。

**可观察的正确性：** 用户可在首次启动后完成配置；未知结果不会被悄悄重复执行；错误提示能支持恢复且不会泄漏敏感配置。

**反向/失败方案：** 启动前必须手动设置大量环境变量，否则崩溃；超时后自动无限重试并重复执行业务；日志打印整个仓库 token。

**适用条件变动：** 如果是无交互后台服务，要求启动后弹 UI 反而不合适；应以清晰配置校验和运维日志为主要体验。

## 8. 反模式及不该泛化的教训

1. **Trace Flood**：无关键作用的每行日志掩盖真实失败
2. **Retry Everything**：确定性缺陷/拒绝也被无限重试
3. **Timeout Means No Effect**：一次超时就确信服务端没有操作
4. **Metrics Without Baseline**：未测量就宣传性能改进
5. **Config Absolutism**：所有产品都必须使用相同启动后配置 UI
6. **Incident Rewrite**：系统恢复后删除此前失效历史和不确定性

## 9. 有界训练与未来验证场景

这是一组供知识审查与后续消费者验证的**设计案例**，没有被标为实际 Host/Agent/CI PASS。

| 情境 | 期望工程行为 | 被禁止的判断 | 真正需要的证据 |
| --- | --- | --- | --- |
| 桌面应用首次启动无配置 | 可以访问安全配置入口，业务动作被阻止 | 系统直接崩溃或进行未授权操作 | 真实首次运行流程 |
| 后台服务配置错误 | 清晰日志和可诊断错误 | 必须弹 UI 才可启动 | 服务模式与错误输出 |
| 请求超时但可能已提交 | 保留 UNKNOWN/查询并有界重试 | 重新执行不可逆副作用 | Host 状态/幂等性试验 |
| 一次性能优化无基线 | 标 NOT_MEASURED | 报告 3 倍提升 | 真实 profiling/对照数据 |
| 恢复后影响仍未验证 | 记录 RECOVERED ≠ VERIFIED | 把先前故障覆盖为 PASS | 事件时间线和验证收据 |

实际效用评估应先冻结测试任务、预算和验收标准，再比较直接 Agent 与选用本知识后的 Tally Agent 在真实软件开发中的需求实现、回归、修复、返工、耗时及成本。不允许以题库问答效果代替实际源码和用户行为，也不得虚构定量提升。

**模块交接边界：** K10 仅提供适用的运行错误/恢复/性能知识，K03 负责 Task 内的代码实现，K06 负责真实故障根因；这三层不建立相互竞争的硬性 Rule。

## 附录 A · Agent 直接调用的工作示例（非正式 Wire Schema）

**教学输入：** 一个桌面工具首次启动尚未配置仓库，随后某远程操作超时且结果未知。
- 使用知识：ActionableError、StartupConfiguration、Idempotency、Timeout、IncidentEvidence，执行 DP-K10-01/02。
- 期望产物：允许进入配置流程但阻止未授权业务动作；超时返回可操作的安全错误与查询状态/有界重试策略。
- 验证：测试无配置、错误配置、超时但服务端已提交、重复点击和故障恢复后实际状态。
- 停止与交接：后台/CLI 配置策略另行按形态选择；没有真实性能基线写 `NOT_MEASURED`，不可虚报倍数。
