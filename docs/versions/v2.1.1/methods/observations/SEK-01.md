# SEK-01 — Method Observation

**Task:** #301  
**Date:** 2026-11-04  
**Status:** OBSERVED / DRAFT

## Observations

1. The official SWEBOK Guide v4.0a PDF is directly accessible and provides a verifiable 18-KA list, related-discipline list, taxonomy limitations and printed-page locators. This is stronger evidence for the initial discipline map than the ten-category hypothesis.
2. The original ten categories collapse distinct areas: Architecture and Design; Construction and Maintenance; Management and Quality; CI/CD and Operations. They omit Software Configuration Management, Software Engineering Process, Models and Methods, Professional Practice and Engineering Economics.
3. SWEBOK's discipline hierarchy does not answer the same question as a lifecycle process standard, product quality model or architecture-description standard. The multi-view approach is therefore a response to different classification questions, not a preference for graph complexity.
4. CS2023 is a useful comparator because it places Software Engineering inside a wider CS curriculum; it is not a substitute for a professional Software Engineering body-of-knowledge taxonomy. Its nine SE KUs include Teamwork, Tools and Environments, Product Requirements, Software Design, Software Construction, Software Verification and Validation, Refactoring and Code Evolution, Software Reliability and Formal Methods. The SE-Tools unit explicitly covers SCM/version control, release management, testing tools and CI/process automation.
5. Official ISO pages expose AI/ML-use restrictions. The discovery report and registry retain bibliographic metadata only; no normative clauses or ISO-derived paraphrase are stored.

## Corrections and unresolved points

- Do not infer that each SWEBOK KA is mutually exclusive or has exactly one parent.
- Do not use SWEBOK as an exhaustive ontology or universal process prescription.
- The boundaries of AI Engineering, Data Engineering, HCI and safety-critical engineering remain hypotheses.
- The exact taxonomy should be challenged with vertical-slice records before freeze.

## Method adjustment

Use one primary discipline reference spine, then explicitly model lifecycle, quality, architecture, testing, security and application context as separate views with typed cross-links. Record source limitations and alternative taxonomies alongside the proposed model.
