## 3. 执行顺序与停止条件

建议先做 R4-A/B/C 的定向原文/案例查找；R4-D/E 可在各自所需合同确定后并行；R4-F 与 R4-G 按实际变化/协议知识的依赖选择。若 B/C 的结果改变 G 的前提，则 G 相关组合待其明确，否则可引用已充分机制。所有包开始前确定准确范围、已有充分部分、真实缺口、源版本、Owner 与独立审核条件，单次增量只针对有限目标。发现旧资料已足够就记录复用，不增加章节。高风险机制未解决保留 D/UNKNOWN；不可为了“全部变绿”缩小原问题却不明示。专项 U 只有实际需求触发才扩展。R3 的分类本身须独审，不自动触发 A–G 写作或运行。

## 4. T36 及 LLM 消费的设计前置（候选，不是实现）

知识正文与消费索引不是同一层。先在 T36 中保留 K01–K11 原语义归属和历史身份，明确引用与拆分是否改变语义。设计消费单元时至少研究：稳定指向的概念/机制/方法/决策；真实适用条件、必要前置与反例；跨域关系类型、权威来源与版本；项目 Profile/业务规则隔离；独立 Oracle 及真实案例证据。不得把候选语义单元、教学案例自动变为可执行业务 Rule。可以先设计结构，不必待无限知识补全，但冻结可消费结构前须确认本次接受范围、关键未决与明确引用。

建议验证的有限问题（尚未执行）：给同一工程目标的不同阶段输入，让 LLM 找出必须的最小知识、为何采用/不采用、UNKNOWN 和反例；交换业务 Owner/原始版本/故障约束，检查选择是否正确变化；删除关键证据或添加相关性弱的材料，检验遗漏和干扰。候选输出区分知识存在、可检索、选用正确、真实工程行为、独立验证以及维护成本；这六项不是同一通过状态。只评价知识组织，不以纯问答正确或向量相似度证明真实交付提升。后续独立设计并冻结隐藏评价（不得使用已公开 G1/G2/B1/B2 充任未见题），再以 T34b 的全分配与维护联合结果验证实际效用。所有新机制、SDK/Runtime、Agent、实验或发布另行有权任务；本轮均未实施。
