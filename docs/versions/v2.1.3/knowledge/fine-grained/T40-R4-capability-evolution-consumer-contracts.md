# T40-R4 · 从消费者功能变化推导公共能力及抽象演化

#650 / #563；K02 公共边界及消费者、K03 抽象选择、K09 演进、K01 业务差异、K05 评价。基线 42332eeb00bc0c1869172a667944e9c02abbc0a7。复用 R19 粒度矩阵、T27a 合同、T32a-1 重构/迁移、T20 三项真实历史与 T37-R2 的条件引用。本章补以获权变化序列推导公共能力的最小合同、分裂/合并及替代，而不是重复“避免过度抽象”。以下新演练全部 NOT_RUN。

## 1. 从需求变化中识别稳定的合同交集

对每个真实消费者记录操作范围、合法输入、必要观察（结果、错误、顺序、身份、完成点）、允许修改、权限与独立演进责任。不能把交集理解成简单的共同方法名或返回字段：相同形状可能有不同语义，较宽的输入/较弱的输出也可能破坏原调用者。共享机制必须给每个获准消费者提供它实际需要且合法的行为；若在某一层只能承诺更窄能力，则保持消费者专属外层合同，以明确转换/追加检查弥合差异。需要共享的是同一变化原因及不可漂移的机制，不是所有实现都同一个接口。

教学：同一资料系统有界面预览、交互式下载、审计批量导出。三者都要选择记录，但预览仅展示当前允许的标题，支持截断及分页；下载要求完整指定对象的当前获权字节；审计导出要求固定快照、获权字段、完整范围和实际交付许可（复用 T35-4）。共用 parseFilter 或稳定的资源标识值，须先确认语义一致；不能提供 search(filter,mode,includeAll,ignorePermission) 来合并三种承诺。共用查询核心若仅支持“给已获权范围内按固定查询合同读取记录”，必须由真实权威保护读取及交付边界，不允许调用者自行扩大范围；外层仍独立定义范围、快照、字段、完整性、交付与错误。预览结果不能被导出直接当完整集合。若三个需求只有同一种短查询且无权限/快照差异，直接一个模块内函数可能足够。

## 2. 逐次变化说明何时升级抽象

| 获权变化（教学） | 可保留与实际需要改变的责任 | 最小候选 |
|---|---|---|
| V1 单预览、固定列表，标题筛选 | 只有一个真实消费者，局部解析和查询 | 直接函数或私有 helper |
| V2 新增同语义的另一预览入口，过滤语法同一权威 | 两入口必须同一过滤解释与错误域，展示不同 | 共用窄解析/筛选机制，局部展示各自保持 |
| V3 新增固定快照的审计导出 | 复用已同义的表示及谓词；导出独立权限、完整性、持久任务/交付 | 分操作合同，若真实复用再抽只读核心；不把预览 API 变通用导出 |
| V4 新增第二种数据源，仅能当前读且无一致快照 | 预览可能合法；不能实现强导出合同 | 明确能力子集或独立合同，拒绝无支持组合；若另有获权物化快照机制才评估 |
| V5 新增外部长期支持消费者，要求稳定可替换读取 | 公共版本、错误、取消/资源及兼容责任成为真实约束 | 窄公共接口+真实能力协商；不自动暴露内部全部操作 |
| V6 废弃旧预览入口且无获准保留消费者 | 解除旧入口责任，保留共同机制及合法历史 | 按真实支持合同迁移/删除；无消费者时可缩回私有边界 |

V3/V4 的反例说明共享能力不等于全功能统一：假设预览只返回前10条，而合法导出有12条；若使用其结果生成报告则丢2条。假设源 S1 支持固定版本，S2 只支持实时查询；两者都实现 getRows 并不证明多页报告满足快照约束。为 S2 定义明确不支持的强合同、采用已证明的获权快照替代或限制适用消费者，三者依真实需求选择。若后续获权导出允许实时逐页且明确报告不同版本，则原强快照不再必需，但这是政策变化，不是无损兼容。不要通过 flags 跳过许可或用默认空值伪装不支持的能力。

## 3. 公共能力的变更影响与最小合同

建立“消费者→实际操作合同→共享机制→资源/效果权威”的有向关系，仅用于真实影响分析，不必强制每个 helper 建图。变更语法解析只影响实际依赖其语义的消费者；变更授权或快照会影响所有共享相应权威的路径，即使未直接 import。影响边包括持久格式、生成/配置、动态调用和运维义务，不能只看源码引用。若共用函数新增一个默认选项导致旧调用者合法输出改变，必须分合同、保留兼容或取得有权迁移；仅编译通过不能证明。若两个消费者同一政策必须同时更新，分别复制造成漂移时应优先收敛真实规则；独立政策改变不能通过共享函数偷偷改变另一方。

最小公共能力可按调用者只需要的操作、权限及生命周期裁定，而非方法全集。例：管理任务队列的 owner 需要 clear，普通提交者只有 submit；两者共享队列不等于 submitter 可清其他人的任务。若包装对象真正拥有自己队列且消费者有权清未获准待办，可显式提供对应受限方法，不能把“清队列”扩展成取消已获准执行或所有全局工作。契约扩张应与类型/文档/运行路径及真实消费者一致。

## 4. 用已登记真实历史区分三种演化理由

T20-C01 pytest 维护者删除用于异常控制流的局部 helper，实际变化是更直接条件判断；支持“没有独立责任时缩减层次”，不证明所有 helper 坏。T20-C02 HTTPX 将 app 便捷入口逐步迁到已有 transport 选择；这是公共入口收敛及消费者迁移，不是增加另一层工厂的必要证据。T20-C03 p-limit 包装对象缺失 clearQueue，历史修复直接委托已有队列能力并同步类型/文档/测试；实际范围为仍排队未获许可工作，不能由方法名推出取消已获准工作。该三例可分别解释删除、合并公共选择、补足必要能力；不从一次历史推导普遍收益。本章不重新读取上游或运行案例，使用 T20 已接受的局部历史观察；未测实际维护代价。

## 5. 评价及停止（NOT_RUN）

对每个实际获权变化独立列旧/新消费者及合法观察，先核必要行为与共同机制，再比较候选维护范围、间接性与版本代价。正反例：预览截断10/导出12；S2无一致快照；撤权后新导出拒绝；普通提交者无法清他人任务；同一政策修正后两个入口一致而独立政策不被改变；旧支持版本迁移前不得删除公共入口。反向：单入口没有稳定外部消费者/变化，无需公共 registry；真正独立异构替换且合同可成立时才建立明确 port。若找不到具体受益的真实变化或无法证明共同语义，则停止抽取；不是用文件数、接口数或未来猜测评分。所有目标、消费者运行及收益 NOT_RUN。
