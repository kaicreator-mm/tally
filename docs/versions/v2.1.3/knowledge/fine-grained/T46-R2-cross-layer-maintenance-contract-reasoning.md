## 1. 从跨层事实确定哪些抽象应当共享

真实路径有多个不同入口（全量、feed/category、单条），S09 复用 findEntries 或 getEntryFromBuilder，S12 共同 query builder 负责组合用户范围、条件、排序和分页；S09/10/11 承担 API 输入语义，S13 共同 SetEntriesStatus 负责特定写操作。T19 同项目另有直接及 worker 共用 RefreshFeed，说明“共享业务能力”不等于“所有任务共用一套执行方式”。实际观察不到一般化 CRUD 引擎或纯领域层，故不可从结构外观判断更抽象必然更好。

可提取的稳定语义：真实 user/entry identity、状态合法域、请求条件与观察结果、共享 SQL 限定。不可随意合并的差异：列表、详情、总数和更新分别拥有不同输出/完整性/失败合同；更新不是查询条件加一条副作用，批量204也不是查询 count。公共 builder 能组合相同条件，不足以证明列表、count、单条具有相同连接基数及快照。反事实：若未来需要 count 与 entries 同一快照，应保护观察合同，而不是仅抽取更大的 SQL helper；现有不同入口复用可保留。真正需要复杂独立替换才增加窄接口，不由现有 Go package 层数或代码量推导强制 Repository/微服务。

## 2. 维护问题 A：从“至少更新一条”到“全部请求身份成功”

假设新获权需求严格定义：请求中每个不同 ID 必须属于当前用户且存在；全部获准时一次原子设置状态；有任一失败则不改变任何条目；返回不泄露其它用户存在性的错误。现有非空列表、合法状态校验和 RowsAffected>0 不满足新合同的必要条件；混合 [11,21,99] 是 R1 的区别性输入。这个变化是新合同，不是对旧版定责。

候选先明确重复 ID 政策（拒绝或获权去重），设 D 为请求去重身份集合，P 为提交时有权且存在的身份集合；合法前置是 D⊆P 且所有其它真实业务约束成立。若只比较受影响行数，至少需证明每个请求身份至多一行、更新语句匹配与实际合法域一致、没有额外过滤/触发改变计数合同，并把验证/修改置于共同事务/版本保护内。不能先独立 SELECT count 再无条件 UPDATE（删除/权限/状态可变化）；也不能先 autocommit 更新再发现 count≠|D| 返回错误，因为部分写已提交。一个条件候选为在同一获权事务内以实际 UPDATE ... RETURNING 身份核返回集合= D，未满足即回滚，且实际锁/隔离/权限机制满足提交合同；若还有跨资源约束或触发器外部效果，则另核，不将 SQL rollback 推广到外部系统。候选不要求使用此具体 SQL，也未在上游实施。

变化影响图：产品/接口错误合同 → client UpdateEntries 返回/错误映射与其它真实消费者 → model/validator 重复及形状政策 → handler/Storage 事务、身份回执 → 数据库约束/授权 → 独立读取验证。旧客户端仍以 nil/error 判断；若增强现有 endpoint 语义可能破坏原有容忍缺失 ID 的调用方，不能仅依据响应结构未改认定兼容。选择新操作/版本、明确迁移或获权破坏性变更；实际消费者清单未全查，保留未知。验证混合、全非法、重复、并发删除/撤权、提交回执丢失以及既有合法请求；独立核逐 ID before/after，而不是仅 HTTP code/总数。

## 3. 维护问题 B：重复操作、时间与真实变化

假设消费者用 changed_at 查询变更，S12 Before/AfterChangedDate 和 S09 configureFilters 已有时间范围条件。旧 SetEntriesStatus 每次合法匹配都写 changed_at，即使 status 相同；是否可改为“仅当 status 不同才写”取决于真实契约：时间代表最后尝试、最近赋值还是实际状态变化？若为实际状态变化，候选按明确 NULL/状态语义与共同事务条件跳过相同值，需重新区分 already-in-state 和不存在/无权。若当前成功要求至少一行 matched，而新过滤令相同状态产生零 changed rows，原 count==0 就误报；不能只修改 SQL 一行就宣布行为保持。若业务需要保留每次操作审计，独立操作事实/身份与 changed_at 可分离；若需可靠重放、查证原操作结果，则根据 T27c-3/T40-R2 选择稳定 identity 和持久 receipt，而不是把时间戳当 operationId。实际旧版不证明有此审计、严格去重或版本合同。

纸面：t1 A11 unread→read，t2 再读命令 read。旧候选在 t2 写 changed_at=t2；新实际变化合同希望 t1；第三种授权审计政策还记录 t2 命令但不改变业务状态时间。若 t1 后另一合法操作将 11 改 unread，盲重放旧 read 会改变当前状态；仅“赋相同常量幂等”不覆盖交错历史。独立检查时间条件、变更消费者、重复、交错、响应和历史事实。是否需要 CAS/序列、强制最新或 last-writer 由获权要求决定，不能从现有缺少条件版本直接判缺陷。

## 4. 维护问题 C：查询完整性、稳定排序和容量

现有 list 与 count 先后读取、builder 允许 offset、单个排序表达式可并列、limit=0 不附 LIMIT；GetEntries 逐行读取附属内容并可能有额外查询。若真实新合同需要一次完整扫描或稳定分页，先分开：授权集合、固定快照/可接受陈旧、完整排序键、游标边界、总数口径、结果大小及取消/失败。对一页固定 snapshot 的列表与 count 可考虑合适的共同数据库观察边界；但跨 HTTP 页的快照、权限再核、快照生命周期/成本另需合同，不因一次事务就推出跨页保证。若只是更新后刷新当前未读页面，允许变化且重新从头，则不必引入长快照；只读固定 id ascending、after_entry_id 可作为键范围的候选，但 S09/S12 真实 before/after 只是独立 ID 条件，不自动与其它排序构成 seek cursor。按 published_at 时必须核相同时间并列次键及游标适配；不能直接拿 ID 不等式当所有排序的分页。

R1 的 offset 删除反例及列表-count 交错证明更强观察目标需要新机制；并非真实 UI 当前错误。真实容量要求若新增上限，需定义 limit=0 和默认值语义、最大响应及附属查询成本、在途请求/资源限制，兼容原 client Filter 编码；不要以默认100或数据库索引代替预算。S14 实际有以用户、状态、发布时间等组成的迁移索引，只提示访问模式与维护成本，实际查询计划、行基数、统计、数据库版本和性能均未运行。若要求完整查询，S12 loop 结束还需检查实际迭代错误，不能仅保证 SQL 正确；在 count 另读成功时也不应以总数掩盖部分列表。修订的具体优先级由真实合同、资源和影响决定。

## 5. 将专业知识组合成实际工程判断，而非固定检查表

| 阶段 | 直接复用的知识和实际作用 | 当前独立证据边界 |
|---|---|---|
| 需求/约束 | T24c/T40-R1：目标、错误、状态变化及实际可观察义务；区分旧/新合同 | 真实源码功能；用户研究、获权新政策未建立 |
| 架构/抽象 | T26a-2/T40-R1/T40-R4：共同机制、消费边界和真正变化轴 | 实际 client/API/validator/storage 依赖；非全产品架构 |
| 表示/算法 | T27b-1/T42-R1/T43-R2：用户/ID、条件、集合、事务、分页和版本 | 实际 SQL/model/migration；假设数据和调度为纸面 |
| 实施/失败 | T27c-1/T27c-3/T25b-2：准入、重试、UNKNOWN 和时间 | 真实同步请求/返回点；未运行 |
| 验证/诊断 | T28a-1/T34b-2/T35-7：独立事实、负向与日志边界 | 现有 validator 测试源码，不是运行证据 |
| 维护/兼容 | T32a-1/T25c-3/T40-R4：真实消费者、版本影响与替代条件 | 假设变化；实际消费者总表及迁移验证未知 |

最小验证设计：固定两个用户的独立初态，分别检查读范围、混合写集、重复与错误；固定两个请求的可控交错，分别核列表/总数与时间版本；选择真实目标需要的负向断言，区别“没收到结果”和“没有发生写入”。已有测试的实际断言范围只可用作证据起点，不宣称覆盖所有产品层；若只是验证数学/知识正确性，纸面推理与最小独立反例足够，不要求启动 Miniflux、部署 DB 或新建 SDK。若未来产品实施，则需真实环境/消费者及已获权合同的额外验证，本阶段不调度。

## 6. 收敛边界（NOT_RUN）

本批以实际版本的有限 API 用户路径作为综合专业知识例，既不将它当产品架构审计，也不覆盖所有 HCI、移动、实时、图形、嵌入式等专项。反事实维护不是上游真实历史事件，无新增 qualified Case/Claim/Rule；正式知识关系与索引后续 T47 单独收敛。未发现新机制需要再建立独立知识 Owner：优先引用原正文、条件及反例；只保留该跨层组合带来的真实专业增量。所有目标、实际故障、DB/网络/客户端运行、性能、用户或模型收益 NOT_RUN；无产品/Package/DH/SDK/CI/Agent/LLM。
