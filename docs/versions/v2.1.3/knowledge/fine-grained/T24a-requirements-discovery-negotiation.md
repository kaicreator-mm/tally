# T24a · 需求获取、协商与系统责任分配

归属 K01（K02 系统边界、K05 验收、K11 决策为关联），#586；T23 SY02/03/04、SY05 接口部分。复用原 [Stakeholder 权威与三角核验](../../../v2.1.2/software-engineering-knowledge/K01/advanced-stakeholder-authority-and-triangulated-evidence.md)、[双向追溯](../../../v2.1.2/software-engineering-knowledge/K01/advanced-requirements-traceability-and-change-propagation.md)。不再定义相同追溯关系。以下是原创教学方法与推理，非实际产品需求；例与 Oracle 均 NOT_RUN。

## 1. 从调查问题到需求

需求发现不是收集功能愿望。先确定目标用户、其实际要完成的工作、当前环境、失败后果与未知；调查输出应区分事实、推断、候选方案、获权规则。用户可能知道痛点却不知道可行解法；实施者知道技术约束但不因此获得业务裁决权。调研对象也包括非典型用户、支持人员、外部系统维护者与受影响的非使用者。

| 调查技术 | 适合回答的具体问题 | 容易误判的地方 | 交叉验证 |
|---|---|---|---|
| 半结构化访谈 | 目标、例外、意义、约束 | 诱导式问题、回忆偏差、用理想流程替代实际 | 询问最近具体实例、核实际操作 |
| 现场观察 | 手工交接、隐性步骤、设备与环境 | 观察者影响行为，少数样本不代表全体 | 多种环境、经许可记录及事后解释 |
| 文档/接口分析 | 正式政策、现有能力、版本 | 草稿过期、示例不是完整合同 | 核作者、状态、有效区间及真实接口 |
| 数据/工单分析 | 常见失败类型及可能影响面 | 日志只覆盖被记录群体，不能代表未使用者 | 核分母、漏报、权限、时间窗口 |
| 工作坊 | 跨角色术语、系统边界、冲突及候选方案 | 强势参与者主导，沉默不是同意 | 会前独立收集、分角色确认记录 |
| 原型 | 交互理解、工作流可行性与未知 | 原型能演示不等于实际权限/规模/可靠性 | 明确哪些是模拟、哪些需真实验证 |

方法可组合，不要求每项目使用全部。对于危险、不可逆或昂贵操作，优先调查合同和失败后果，再用低风险原型验证操作理解；没有许可不得复制生产数据。访谈以“上一次你怎样确认这项业务已完成”为起点，不以“是否需要按钮”收尾。对无法直接观察的例外，保留未验证假设并问其出现条件。

## 2. 分析、分类和边界

从一个含混陈述提取：目标对象、参与者、触发事件、合法条件、预期状态、失败输出、依赖与质量约束。区分四种需求：功能（可观察行为）、质量（指定情境下的表现）、约束（限制方案空间）、数据/接口合同（系统间可见意义及责任，可能同时属于前两种）。分类是为了发现遗漏，不是要求每句只贴一类。

案例：某仓库要求“扫描后立即显示库存”。候选问题：
- 扫描指识别条码，还是一次实际收货确认？是否允许手工替代？
- “库存”是现存、可售、已预留、还是设备上最后同步值？哪一方持有权威事实？
- 离线时能显示最近快照，但是否允许产生出库？显示的时效与数据来源是什么？
- 网络差时用户要知道什么：请求已受理、已写本地，还是中央已提交？
- 质量要求应指定工作负载、计时起止、网络、用户群与阈值来源。未确认阈值只能写候选，不编造“200ms 即通过”。

## 3. 协商而非投票

冲突分类：术语误解（库存定义）、范围冲突（某租户或地区规则）、目标冲突（速度与核对）、资源限制（人时/设备）、证据不足（远端效果）。同一对象、相同适用时段、相同条件下的互斥陈述才是真正逻辑矛盾。不同主体的局部规则可并存，不先强行统一。

处理流程：分别复述真实目标→定位具体不兼容条件→区分谁有决定权、谁承担后果→列出最小候选及其损失→记录条件性决定、未决事项与复议触发。允许议而未决；不能因会议结束就将未批准内容晋升为 Rule。

教学冲突：A 要离线直接出库，B 要中央无超卖；若不同设备各凭旧库存执行，两个设备各读 1 都出库，可能超额。备选为 (a) 离线仅记录申请待中央确认；(b) 预分配互斥离线额度且规定过期/恢复；(c) 联网方可执行。三者影响不同工作；只有业务责任人可选择可接受的丢失、拒绝和待确认语义。技术原型只验证候选机制。

## 4. 优先级、可行性、最小验证

必要性、商业价值、风险、时间敏感性、依赖、实施成本、可逆性应分别记录。Must/Should/Could 是一种协商标签，不是数学真理。强制法规/已获权安全底线不能因加权得分低被取消。对于同一排序范围，先过滤不可接受方案，再比较价值、风险与实施代价；数据不足可作情景比较，不造精确分数。例：A 简化搜索需要 2 人日、B 解决不可逆错出库需 8 人日，工时只是一个因素；若 B 是获权必要保证，不能因 A 更容易就延后到未授权的生产状态。

可行性不是“可以写代码”：技术（环境、接口、容量）、运营（人员、维护、培训）、经济（全生命周期成本）、时间（真实依赖与约束）、合法使用（数据/许可及有权裁决）。将未知变成具体调查：外部 API 是否支持按版本条件更新？查正式接口版本或受控原型；若无则改变方案而非假定。原型需明确模拟边界、可丢弃性、数据保护和不进入生产的条件。K11 已有风险/信息价值，不重复模型。

## 5. 分配系统责任与验收

| 责任对象（假定） | 需求分配 | 接口/验收边界 |
|---|---|---|
| 终端 | 采集标识、显示待确认与错误、离线保留合法申请 | 输入/重启/断网/恢复；不自报中央完成 |
| 中央服务 | 在权威库存约束下接受或拒绝申请 | 标识、版本、结果查询与失败合同 |
| 设备/外部服务 | 提供受约定格式与质量的观测 | 明确单位、时间、版本、错误、超时和责任 |
| 业务人员 | 确认实物事实及异常处理 | 有权处理范围、审计、用户可观察结果 |
| 系统验收者 | 检验整条用户旅程与跨边界效果 | 独立预期、目标环境、验收责任；非单个模块绿 |

需求分配是用系统目标推导各子系统可承担的责任，不是把一句需求复制到每个模块。若外部提供方能力未知，接口合同待确认，不宣称端到端可实现。验收条件应写输入、前置状态、触发、可观察预期、负例及适用范围。例如“断网请求已入本地待办，不显示中央已提交；恢复后如中央拒绝，显示具体可行动错误”。这是方案 (a) 的假定合同，若选 (b)/(c) 必须修改。独立测试不能自行选择业务规则。需求变更要核受影响消费者、状态模型、测试、数据和外部责任，不将全量重审作为默认。

## 6. 使用与反例练习

1. 客户说“支持全部导出”，数据 Owner 说普通角色仅可导出自己的记录。先确认角色、资源和约束，再定义用户可见成功及拒绝；不是导出模块自动读取所有数据。
2. 只在访谈里询问“是否满意”可能不能发现工作人员反复复制粘贴、绕开工具；观察完整任务，再用可比较的原型验证假设。
3. 需求写“支持所有设备”，没有实际支持集合、系统环境或验收主体；保留未知，不能用一个浏览器 PASS 替代。
4. 规格“异步提交成功”必须区分受理和完成；测试明确受理后终止、外部 ACK 丢失、部分失败。Oracle 依据获权合同，NOT_RUN。
