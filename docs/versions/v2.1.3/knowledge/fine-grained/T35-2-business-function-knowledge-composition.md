## 2. 组合演练 B1：订单预留及取消的最小语义模型

教学场景：两个租户各自有 SKU（同名亦不同身份），一个 DB 是订单与预留的共同权威。已获权的购买者可为自己租户的订单预留库存，取消者权限另核。只讨论未发货订单，无预付款的订单取消不创建退款；已确认付款的订单在符合取消资格后需登记退款意图，外部退款不是本地事务。实际付款事实若未知则暂停依赖该事实的自动取消/退款，送有权核实。禁止负可用量和跨租户修改。政策变化须另获权。库存模型为无补货/发货的有限教学范围，不是完整库存账务。

教学权威合同：
- Stock(t,s): 固定 total≥0，reserved∈[0,total]，available=total−reserved。每个活动预留关联同一租户、SKU、订单及正整数 q；Stock.reserved 等于该租户/SKU 全部活动预留 q 之和。数据身份至少含 tenant，不能只靠外部传入的 sku/orderId。
- 订单状态 OPEN（已存在的未预留草稿）、RESERVED（活动预留存在）、CANCELED（无活动预留）；每订单在本例只有一个 SKU、一份活动预留。发货不在范围内，若出现已发货或其它状态按真实支持合同拒绝/澄清，不重写历史。付款状态另有 NONE/CONFIRMED/UNKNOWN，退款意图另有 PENDING/CONFIRMED/UNKNOWN/REJECTED（REJECTED 仅有权证明未成功；恢复策略需获权）。
- reserve：基于权威身份/权限、当前 OPEN、请求q、当前库存及稳定操作ID，在同一 DB 事务核条件、建立预留、增加 reserved、改订单 RESERVED 并记录该操作结果。唯一性、并发与提交约束须真实实现，非只加类型。重复同作用域同操作ID且同规范输入，返回原操作的已知结果并按当前授权允许查询；同 ID 不同输入拒绝冲突，不再修改库存。
- cancel：在有权提交边界核 RESERVED、未发货、当前付款事实、活动预留与操作ID。取消时释放该订单实际预留 q、置 CANCELED、撤销活动预留；若付款已确认且满足本例明确的全额退款政策，在同一本地事务登记唯一退款意图，金额/币种取权威付款记录并绑定付款身份（本例假定无先前退款）；NONE 不登记。付款 UNKNOWN 不提交自动取消。重复同操作同输入只查询原结果，不能再次释放；其它取消操作对已取消订单按本例拒绝，不新增效果。

纸面初始：租户 A 的 X 总量5，reserved=0；租户 B 的同名 X 总量8。A 两个订单 O1/O2 都 OPEN，分别尝试预留3和4。若两者同时读取 available=5，独立均可预检查，但合法提交历史至多一个成功：O1先成功则 A reserved=3/available=2，O2拒绝；O2先成功则 reserved=4/available=1，O1拒绝。B始终不变。若设计允许先检查后无条件写，两个均成功会产生活动量7>5（即使最后覆盖值显示4仍违背预留和式）。必须通过适合单 DB 的条件更新/锁与实际事务组合维护联合不变量，或受权独立额度方案；不能把无并发测试称证明。取消成功的 O1（q=3）应恢复 A reserved=0、O1 CANCELED，B仍不变；若 O1 未成功则不得凭取消命令扣减3。

## 3. 从业务不变量推导结构，而非按表/动词建框架

| 候选 | 本教学合同的判断 |
|---|---|
| A：一个业务模块内 reserve/cancel，各自明确规则；共用确有同义的身份/金额/事务基础机制 | 当前最小可行，两个动作保留不同资格、写集和错误；事务保护订单与库存联合状态 |
| B：通用 changeStatus(entity,next,flags)，由调用方另行 releaseInventory/refund | 可产生 CANCELED 但未释放预留；把两个不同的权限和副作用藏在 flags。除非另有不可绕过的业务提交机制及实际复用合同，否则拒绝 |
| C：订单与库存独立微服务，各自保存状态再发消息 | 不由本例规模或表数推出；跨库时原子不变量需重新论证，若真实独立部署才考虑合法额度/协议/补偿及可接受的暂态 |
| D：将相同的金额/币种精确值和规范输入校验做为窄共享值/纯函数 | 仅共享同语义表示，不共享付款、退款的授权及业务状态；货币政策独立时重新审视 |

示意合同（非可执行代码）：
```text
reserve(verifiedActor, tenant, orderId, sku, q, operationId)
    -> Reserved(receipt) | Denied(reason) | Unknown(reconcileRef)
cancel(verifiedActor, tenant, orderId, operationId)
    -> Canceled(localReceipt, refundIntent? ) | Denied(reason) | Unknown(reconcileRef)
```
输入的 verifiedActor 表示受权边界已经验证的身份上下文，不是任意请求字段；当前授权/状态仍由实际执行边界核验。Canceled 只证明本地取消及必要意图登记，不证明退款完成。Unknown 表示所需权威事实或提交结果尚无法确认，应有可行动查询/升级信息；它不是同一动作的确定拒绝。两个操作可在同模块但不强行统一返回内部状态结构；是否需公共接口取决于真实消费者。若将来新增获权审批规则，只修改相应政策与必要执行路径，不能因同名 canCancel 把退款许可一起改。历史 T17-C02 的 can_cancel 与 cancel_order 分离、实际调用链未全核；本例不能从该片段推导真实 Saleor 权限或事务保证。

## 4. 外部退款、重放和审计的组合边界

按已授权场景，取消本地事务只创建稳定身份 R=该次获权退款意图（绑定租户、付款ID、币种、精确金额，唯一约束）；Worker 在获权外部执行边界按实际 Provider 合同请求退款。若 Provider 返回权威成功收据，核对应身份/金额/币种与适用状态后记录确认；若网络超时而可能已提交，状态 UNKNOWN，依据实际 Provider 查询/幂等合同确认或有权接管。只有 Provider 明确支持该稳定身份的安全重试且时窗/输入一致、权限与预算仍有效，才可按合同重放；无此证据不得重复退款。明确失败也不自动改回订单/预留，因为本地取消可能已经提交且库存已被其他订单占用。

合成时序：
1. O1 预留3成功，已确认付款30单位（指定币种，整数最小单位）；独立授权取消后本地事务释放3、标 CANCELED 并创建 R1，提交。
2. Worker 发请求，远端可能已退30但 ACK 丢失；本地 R1 UNKNOWN。不能把订单 CANCELED 映射为 REFUNDED；也不能将UNKNOWN当作退款失败再次生成 R2。
3. 若权威查询证实 R1 已退30，确认 R1；如果远端只提供不能关联的总余额变化，不能当该意图收据。若未知保留，用户得到确认的本地取消与退款待核结果，而非假成功。
4. 迟到或重复 webhook 即使签名合法，仍须核当前租户/付款/意图/币种金额、权威状态及事件重复；不得因签名通过改变别的订单。状态变化、事件接收、审计事实和通知发送不同，不能把日志/消息当支付权威。

对照 [T33a-1](T33a-1-reliability-fault-analysis-recovery.md) 恢复和未知外部效果；T07-C04 的签名验证只证接收机制，T07-C05 差额/账务更新及取消入口只证登记局部行为，不证明幂等或全流程合规。支付政策、实际 Provider 协议和财务账务属于具体域 Owner，不由本章制定。

## 5. 变体 B2：审批与报表不是同一个业务操作

教学变体：租户内一份费用申请需有权审批者批准，申请人与审批人不同（本例规定）；报表仅汇总获权可见范围内已批准记录，显示 as-of 版本；报表允许明确标示的陈旧快照，但审批时必须核当前申请状态、身份与权限。申请/审批/报表可以复用 tenant scope 值、精确货币类型、分页基础机制；不能共用“已批准 = 当前用户可批准”的谓词。单一固定审批直接函数足够；若后来获权新增两级审批，按真实审批序列与互斥职责重评状态合同，而不是一开始引入通用工作流引擎。若后来报表要求实时，则重新评估读取权威源、成本与一致性，不把旧报表缓存作为审批依据。

独立例：租户A两条已批准金额10、20（同币种），B同名申请金额40。A合法报告在指定一致快照应汇总30，不能算70；若存在不同币种，不得未经获权换算合计。若A某记录在快照后撤销，应显示快照身份/陈旧性，当前审批仍查权威；不能用30证明当前业务状态。本人审批自己的申请、过期权限、直接 API 越权及报表缓存跨租户分别拒绝。历史 T07-C07/C08 仅为表单分层与报表入口的观察，未证完整行级权限。这里未创建真正审批政策、报表实现或预约行业规范；预约可类比资源容量/时段身份/并发，但有实际时区、取消及重叠政策后才写独立组合例。
