# T26a-1 · 架构场景、视图、质量权衡与产品线可变性

#596；K02 主责系统架构，K01 目标/权威，K11 经济决策，K05 验证。复用 [K02 基础卷一](../../../v2.1.2/software-engineering-knowledge/K02/foundations-deep-dive-01.md) 的六字段质量场景与 ADR、[卷二](../../../v2.1.2/software-engineering-knowledge/K02/foundations-deep-dive-02.md) 的视图与变化传播、[四类独立边界](../../../v2.1.2/software-engineering-knowledge/K02/advanced-extension-authority-state-and-consumer-boundaries.md)、[K11 决策风险](../../../v2.1.2/software-engineering-knowledge/K11/advanced-decision-risk-value-of-information-and-process-cost.md)。本章不是新的平行架构定义，而是场景评价的具体演练、视图对应与产品线治理。SY05/06、FM04、RE01。例为原创教学 NOT_RUN，数值不是实际需求或性能证据。

## 1. 从模糊质量要求到可比较的结构

架构应解决跨构件且影响系统重要属性的决定，详细设计处理构件内部表示与实现（见 [T27a](T27a-detailed-design-representation.md)）。用同一套获权需求比较候选；先过滤违反必需条件的设计，再讨论相对收益。架构图不是以图中方框数量决定优劣。以下教学系统：有多个网点的批量货物登记，终端提交批次后允许查询结果，持久受理的任务必须跨服务进程重启保留；有权主体尚未决定吞吐和时间指标，以下阈值仅为假设。

| 场景（教学） | 来源/刺激/环境/构件 | 期望响应与度量 |
|---|---|---|
| Q1 正常受理 | 网点/提交100条/稳定网络、并发10批/入口与Job Store | 在假定2s内返回可核对的持久受理身份；不等于100条完成 |
| Q2 故障恢复 | 运维/worker进程中断/受理后未完成/Job Store与worker | 重启后受理记录可查；合法恢复；不重复非法业务Effect；假定60s内开始处理可恢复任务 |
| Q3 权限隔离 | 普通网点/查询其他网点批次/正常运行/查询端与权威存储 | 拒绝且不泄露别方数据；不能靠 UI 隐藏 |
| Q4 可修改性 | 开发者/增加一种合法输入格式/旧消费者仍存在/解析与登记合同 | 变更隔离于输入适配及必要验证，旧格式语义保持；用实际影响范围/独立回归判定，不以修改行数单独判断 |
| Q5 限定资源 | 多终端/持续超过处理能力/下游变慢/入口、队列、worker | 有界资源、获权拒绝或延后、已受理者可查询；假定队列容量及工作量预算单独获权 |

质量场景的响应必须描述可观察事实而非指定框架。Q1 的2s不意味着业务完成，Q2 不能用进程自动重启代替实际任务恢复，Q4 没有实际团队测量就不能报维护时间降低。场景排序可从重要性与实现不确定性两维开始（不是精确概率）；业务方选择重要性、工程方说明难度，未知标 UNKNOWN。安全、合法性和其他不可妥协的合同不能仅因投票低而忽略。

## 2. 视图之间必须可追溯，而非一张万能图

SEI Views and Beyond 的实践是选择能服务不同关注者的视图，并记录跨视图信息。以下视图分类是教学用法，不宣称完整 ISO/IEC 42010 合规。相同领域名在不同视图中不一定是相同粒度。

| 视图 | 批量登记示意 | 用于回答 |
|---|---|---|
| Context | 网点、管理员、批量登记系统、外部库存 | 系统边界、外部责任和权限 |
| Module | Ingress、ImportParser、Registration、JobStoreAdapter、WorkerHost | 源码责任、允许依赖、变化传播 |
| Component & Connector | API进程→DB；worker进程→DB→外部库存接口 | 运行时实例、调用/消息/数据通路、并发/失败顺序 |
| Allocation | API及worker分别部署于何处、共享DB位于何故障域 | 部署约束、资源、故障隔离 |
| 数据与行为补充 | Job 与 Item 的Owner、提交点及恢复状态图 | 持久事实、合法转移、UNKNOWN及恢复 |

模块 WorkerHost 可对应多个运行实例，不是多个源码模块；一个进程可承载多个模块。API 与 worker 分开部署仍共享数据库故障域，不能从两个方框推出独立可用性。给每项关键场景列出所涉视图元素、连接关系、真实状态 Owner、提交/拒绝点；例如 Q2 的受理先由 JobStore 成功提交，再返回身份，worker 的租约和外部 Effect 另有约束，不能把运行箭头当已经完成证据。缺少跨图映射时优先补关键事实，非所有项目都需五份大图。变更后核实际代码依赖、启动拓扑和接口/数据合同，不将旧图当现状。

## 3. ATAM 启发的实际分析而非认证清单

SEI ATAM 将业务驱动、架构方法和质量场景结合，识别风险、非风险、敏感点与权衡点。此处只借鉴有限评价步骤，不声称正式执行完整 ATAM 或取得其认证。先确认关键业务驱动，列高重要/高不确定场景；对每个候选指出满足场景所依赖的机制、参数及未知，邀请受影响者提出反例，再记录证据和决定。风险是有理由担心某方案不能满足场景；非风险是具体场景与假设下已有充分理由认为可满足，而不是全部产品 PASS。敏感点是某架构决定/参数的变化显著影响一个质量响应；同一点影响多个属性时可形成 tradeoff，需指出方向和条件，不是把任意两个缺点列成权衡。

| 候选 | Q1/Q2/Q5 的具体判断 | 代价及边界 |
|---|---|---|
| A 单进程同步处理 | 完成后响应简单；受理阶段需等待批次处理；若无持久任务记录不满足Q2前提 | 对小有界且无需早受理的业务可能合适 |
| B 单部署的API+持久任务执行模块 | 受理提交与执行解耦；共享进程崩溃影响双方，但持久任务可恢复 | 需要恢复状态、容量与租约合同 |
| C API与worker独立部署、共享JobStore | 可独立配置执行资源和隔离部分崩溃；仍依赖共享DB | 增加网络/进程协调、部署和观测成本 |
| D 多服务并引入独立消息基础设施 | 在已有明确独立扩缩容或跨组织需求时有价值 | Broker受理不自动等于业务JobStore提交；双写/重放/权限更复杂 |

假定业务接受 B 或 C 的实际持久受理合同，A 若不改设计就不满足必需Q2。B/C 需对实际负载及恢复测试，不因 C 比 B 更多进程就选择 C。队列容量是 Q5 的敏感点，过小可能增加拒绝，过大可能扩大等待时间及占用；持久存储和批量大小可能同时影响 Q1 延迟、Q2恢复范围及吞吐。数值仅教学：并发上限4、每任务独占执行假设下，若每任务处理需10s且无其它约束，理想服务率0.4任务/s；持续1任务/s会形成积压或拒绝，而扩大队列不增加理想服务率。真实服务时间分布、DB共享负载/失败及调度会改变结果，NOT_MEASURED。

例 ADR：暂选 B 作为教学候选（不是已批准决定），依据是同一持久权威、现有单部署可运维且还无独立扩缩容证据；牺牲部分进程隔离和独立伸缩。若 Q2 恢复时间或 Q5 在相同实际环境达不到获权门槛，比较 C 的有限原型；若共享数据库是瓶颈，仅拆 worker 不保证改善。记录谁能决定接受风险、何时复议、所需证据（受理读回、崩溃恢复、队列限额、合法并发、端到端尾延迟）；不强制构建新基础设施作为架构评审本身。

## 4. 产品线、共性与可变性

产品线不是复制代码仓库或泛用工具库。面向一组明确市场/任务，共同资产包括架构、实现、规格、测试、配置及生产说明；差异应有计划地建模。SEI Variability 报告摘要提醒过度/重复/不兼容的 variation mechanism 也有成本，不能把所有差异硬编码为配置。教学：三个登记产品共用登记不变量和状态查询，但格式、审批方式与部署连接器可能不同。先识别真实变化轴：业务差异、集成环境差异、运营容量/部署差异、法规/权限差异。共性是可验证的稳定合同，不是代码长得像。对需要独立演进的不同业务状态不可强行共享策略。

| 变化点 | 绑定时机/备选 | 约束与失败反例 |
|---|---|---|
| 输入格式 CSV/JSON | 组合/安装时选适配器，或运行时按协议类型选择 | 统一规范化后的合法记录；不可把无效输入静默修正为合法 |
| 审批：无需/人工 | 产品组合时选择有权流程 | 需要人工审批的产品不得仅靠可随意修改 flag 绕过 |
| 存储与部署 | 发布组合时选择受支持 adapter/profile | 本地文件若不支持要求的事务/恢复合同，则不属于合法组合 |
| 容量参数 | 启动/运行时按有权配置 | 限额不能解除权限和持久受理承诺 |

定义 feature 约束（requires/excludes）、默认值、决策来源、组合时机和适用版本。教学三变量：格式 {CSV,JSON}、审批 {manual,none}、存储 {DB,file}；若 manual 要求 DB 且 file 仅支持 CSV，则 8 个理论组合中合法的是 (CSV,manual,DB),(JSON,manual,DB),(CSV,none,DB),(JSON,none,DB),(CSV,none,file)，共5个。此为假定约束的纸面枚举，非真实产品政策。配置验证应拒绝其它3个非法组合；测试覆盖获准产品、共同资产及变化点交互，不能凭 pairwise 或一个默认产品绿推断所有消费者兼容。每次新增核心资产变化必须评估已支持消费者及版本，不让变化层访问核心私有状态或越权（原 K02 四类边界负责定义）。

核心资产建设成本与长期维护收益需实际评估：如果只有单一使用者且未来差异未经证实，可先保留清晰局部边界；如果多产品共享稳定能力且变化频繁，可考虑明确扩展点、生成组合清单和对应验证。产品生产说明明确从哪份资产、哪些版本/变体产生何种产品、配置约束、支持范围及独立验收。共享资产Owner与产品Owner协商变更优先级、发布支持/退役及风险承担，不由共同代码自动赋予各产品权限。具体 SCM/构建、消费者迁移、采购合同留相应专题。

## 5. 验证与材料边界

教学 Oracle NOT_RUN：同一 Q1/Q2/Q5 负载与故障条件对比 A/B/C，核持久受理而非 HTTP 成功；重启或外部回执丢失后读权威事实，不能通过删记录恢复“正常”；视图核真实模块依赖/部署资源/状态Owner而非图名；5个合法/3个非法组合的独立枚举，核心资产变更对所有声明支持变体检查；候选成本未测则不宣称收益。证据要支持实际选择，不以文档量作为质量指标。
