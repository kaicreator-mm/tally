## 1. B3：多 SKU 预留、部分履约、部分退款与对账

### 1.1 同一权威下的多资源不变量

教学租户 A 的订单 O1 两行，SKU X 订3件每件1000最小货币单位、SKU Y 订2件每件500；总价4000，已确认实际 capture 4000（无税费/折扣/汇率），目标库存初始 X=5、Y=4（在手数量），无其它预留。状态分开：订单/行的预留、已发货、已取消、支付 capture/refund 意图及实际外部结果、账务分录；不以一个 enum 编码所有维度，也不以订单取消推断远端退款。原 B1 的单资源原子性保持。

本例有权政策：订单首次预留全部行要么成功要么不发生；支持部分发货及未发货数量取消，不允许取消已发货部分；已支付、合法取消部分应建立相应退款意图，多个取消共享同一 capture 的可退额度。数量恒等式 ordered=reservedNotShipped+shipped+canceled（本例首次预留已成功、无退货；发货前预留，发货时同时消耗在手与预留）。available=onHand-所有活跃预留，要求非负。在同一实际 PG 事务中核租户/行/当前版本、资源竞争、授权与唯一操作 ID，锁定或条件更新必要库存/订单行及本地结果；固定资源顺序可降低死锁，仍处理数据库实际失败并按原身份重试，不把锁顺序当绝对无死锁。另一个订单 O2 若请求 X3,Y3，O1 已预留后 X仅余2、Y仅余2，必须整单拒绝且无一行残留预留；并发次序反转时核总容量而非强制 O1 获胜。单独负例：O1 已预留后 O3 请求 X1,Y3，X 可满足而 Y 不足；不得因先写 X 而遗留 X1 预留。不同仓库/数据库若是独立权威则本地事务不足，不能套用此不变量；只有明确允许部分预留及补偿时另建有权合同。

| 阶段（纸面顺序，只有 O1） | X (在手,预留,可用) | Y (在手,预留,可用) | O1 行事实 |
|---|---|---|---|
| 初始 | (5,0,5) | (4,0,4) | 未预留 |
| 原子预留 X3 Y2 | (5,3,2) | (4,2,2) | X剩预留3，Y2 |
| 发货 X1 Y1 | (4,2,2) | (3,1,2) | X发1剩2，Y发1剩1 |
| 取消 X1 Y1 | (4,1,3) | (3,0,3) | X发1、取消1、预留1；Y发1、取消1、预留0 |
| 后续取消 X1 | (4,0,4) | (3,0,3) | X发1、取消2；Y发1、取消1 |

每个合法动作保持行数量恒等式，取消释放预留而非增加在手；不允许把已发货件当取消。实际退货需独立验收、物理退回和账务合同，不在本例。金额计算以已获权单位、行快照及准确比例为准，复用 [T25b-4](T25b-4-exact-numbers-locale-bidi.md)。本例取消金额 R1=1000+500=1500，R2=1000；已履约金额1500。折扣分摊、税、手续费及不同币种未获权，不将单价乘数量自动作为现实退款政策。

### 1.2 实际部分退款协议与本地额度控制

实际 Stripe API v1 Refunds Create 文档说明可对原 Charge/PaymentIntent 多次部分退款直至额度用完，超剩余额度会拒绝。其 v1 幂等合同在 endpoint 开始执行后保存首次响应（包括500），同 key 同参数重试，参数不同拒绝；key 可在至少24小时后清理，重用已清理 key 会当新请求；参数校验或并发请求冲突而未执行时不保存幂等结果。这里引用在线 API 文档（示例 Stripe-Version: 2026-11-18.endive），不宣称全部版本/支付渠道/SDK 的结果、时间或资金结算。业务成功依据实际 provider 权威收据与状态，非仅 HTTP 2xx、事件签名或幂等响应；T07-C04 签名验证仅接收真实性边界。

教学本地假定 capture 的唯一退款发起权在本系统，外部人工退款如出现则暂停发起并对账，不能无视外部活动。取消和退款 intent/额度预留在本地事务共同登记，远端实际调用在事务外，使用稳定 R1/R2 身份及获权参数；R1 的退款意图包括 captureId、currency、amount、取消行身份和版本、发起许可及允许重试边界；每次发送尝试 ID 独立。已确认成功金额 S、尚未确定或仍待执行的承诺 P（互斥集合，按相同 capture/currency、含 UNKNOWN）满足 S+P≤已确认可退上限4000，同时每个意图不超过合法未退款取消明细。余额不由本地支付 API 响应推断；若 provider 可用余额与本地不符或存在无法归属退款，进入对账/冻结，不自动建立新意图。所有尚未确认结果保留额度，不因超时或取消 UI 即释放。

纸面：
- 第一次取消后 R1=1500，S=0,P=1500，尚未承诺2500。发送后响应丢失，R1 UNKNOWN，P 仍1500。实际 provider 可能已退款、待处理或未发生。
- 后续合法取消 X1 产生 R2=1000，S=0,P=2500，尚未承诺1500。若 R2 权威成功，S=1000,P=1500；本地不是全部已退款。
- 查到与 R1 稳定意图、capture/币种/金额真实相符的 provider 成功事实，原子将 R1 从 P 转 S 并登记一次本地效果/账务引用（不能凭金额相等猜归属）；S=2500,P=0，余1500 对应仍已发货价值。若只能确认 R1 最终未发生且不再可能发生，按获权失败/解除或重新执行政策处理，不凭首次500释放额度。对于未决且幂等窗口未知/过期的请求，不盲目重用旧 key 或新 key；先通过真实可用的权威查证、关联收据或获权人工处置，若 provider 没有充分查询合同保持 UNKNOWN。系统不假定存在按 idempotency key 直接查询的 API。
- webhook 重复或晚于主动查询：验证实际签名/来源、事件身份及相应 refund 资源状态；同一 refund 的同一合法效果只登记一次，先查真实状态，不能按事件到达顺序覆盖成功为旧 pending。真实失败/逆向资金状态另有权合同；不自创成功不可逆假设。采用 [T27c-3](T27c-3-reliable-messaging-outbox-offsets.md) 的本地 outbox/inbox 机制，但外部 Effect 不在本地事务内。

库存释放是本地取消事实，退款 UNKNOWN 不把取消改回未取消；允许的显示如 PARTIALLY_CANCELED + REFUND_PENDING/UNKNOWN，分别表达事实。账务仅教学最小对账子账：原 capture 4000、已确认退款2500、净已确认1500，未决另列；不发明真实总账会计科目、结算或手续费。对账需 capture/每个 refund 的真实身份、币种、金额、状态、实际支付流水及本地取消明细，不能只看总额；两个同金额退款互换会通过总和但失败逐键核对。若出现实际 provider 额外退款500，报告差异500并冻结相关自动动作，而非用人工构造一笔本地退款“平账”。本例实际付款和结算差异未知。

| 独立 Oracle（NOT_RUN） | 必须观察的事实 |
|---|---|
| 两 SKU 并发竞争/第二 SKU 不足 | 任一合法事务前后实际库存/订单行/操作身份，原子预留无部分残留；总 active reserved≤在手 |
| 发货后重复/超量取消 | 行数量/实际在手/可用与已发货量，拒绝已发货部分，重复原操作只读既有事实 |
| R1 ACK 丢失，R2 成功 | 权威库存取消与 refund S/P 各自，S1000 P1500；不得因 UNKNOWN 再发新意图、超额度或假成功 |
| 同意图参数变化、key过期、provider未决 | 冲突拒绝或冻结/查证；确认真实结果、实际重试前置与权限；不靠响应码猜效果 |
| webhook重复/晚到、外部人工退款 | 独立真实 refund/流水及逐键对应；不重复记账，不覆盖较新事实，不静默平账 |
| 合法维护：新增折扣分摊/跨仓资源 | 重新获权分摊和精确舍入、旧订单快照/原退款不变；跨权威不能直接用原事务，先核一致性/部分政策和独立失败窗 |

若业务只允许全额未发货取消，不需要多行部分状态/额度策略；当真实多资源、部分履约和多次退款出现，再抽取窄金额/库存约束、稳定 Effect intent 与对账机制；订单、退款、库存各自保留政策与 Owner，不能创建一个通用 CRUD 状态机吞掉差异。

## 2. B4：有期限委派审批与长时间导出

### 2.1 明确有限审批合同

教学租户 A 的采购申请 P revision7，金额9000最小单位；申请人 U；第一阶段部门 approver D，第二阶段财务 approver F。两阶段顺序且不同真实主体，不允许申请人批准自己的申请；同一人即使具有两个角色也不得完成两阶段。部门可在获权 delegation grant G=(delegator D,delegate E,tenant A,role dept,resource scope,validFrom,validUntil,grantVersion) 下委派，限本租户采购申请金额≤10000，半开时段 [10:00,12:00)（确定时间基准/日期，参 [T25b-2](T25b-2-time-clock-calendar-semantics.md)）；委派授予指定动作而非所有权限，不允许二次转委派。本例 F 不可委派。审批者必须有当前真实身份、权限、有效 grant 和合法阶段；签署行为绑定 revision、实际 actor、授权依据、decisionId，不能只记角色或 delegator。提交点核授权/委派、当前阶段、revision 及去重，参 [T24b-1](T24b-1-business-rule-decision-contracts.md) 与 T26a-2。已合法记录的批准不因事后 grant 过期自动撤销；后续业务变化按明确政策重新审批。本例金额/范围等实质内容修改要求新 revision、原批准只保留历史、从第一阶段重启；非实质备注若有权政策允许，可保留审批绑定原业务内容 identity，不能仅凭文本差异猜测。

纸面：
- 11:59:59 E 以有效 G 提交 revision7 部门批准，权威已提交；12:00 G 到期，历史批准仍有效。若 E 在11:59:59准备而12:00才尝试提交，必须拒绝（时间/授权由权威核，不是浏览器时间）。
- 若 E 已批准第一阶段且也有财务角色，第二阶段仍因实际 actor 重复拒绝；若 U 是 E 则第一阶段即拒绝。F 独立合法批准后才能 APPROVED。若 E 持 grant 预校验后 G 被撤销而 revision 仍7，则旧许可不能提交；已有合法批准与撤销先后关系须实际确认。
- 部门 E 与 D 并发对同 revision7/阶段提交：仅一个有效 decision 推进，另一个以当前阶段/decision identity 判断重复或冲突，不可重复推进或覆盖原 actor。若同一 decisionId 但改内容拒绝。
- 第一阶段完成后申请金额改11000成为 revision8：原 dept decision 仅历史，G 的≤10000不再适用；F 不得基于 v7 批准 v8，即使 stage 名相同；需新的有权批准路径。撤回/取消政策另行获权，不能靠删除审计。

小型固定审批可直接用状态/谓词与事务，不必 BPMN 或通用规则引擎；真实多级/委派/政策变更才需要显式授权来源、步骤及版本。在 T07-C07 的表单校验、T17-C01 的配置状态后继与 T17-C02 的资格谓词之外，增加真实主体、时段、授权版本和提交一致性；未从源码推断这些产品已有本例政策。

### 2.2 长导出：授权、数据快照、制品与交付分别负责

审批资料导出教学合同：同租户中当前有权的审计者可以请求选定日期范围、字段和已批准申请的 CSV；导出使用获权数据 snapshotId S1，承诺内容准确对应 S1，不要求与当前数据实时一致，但**读取范围/字段授权必须保持合法直到实际交付**。假定任何相关授权收窄即使旧内容仍存在，也使旧导出制品不可继续交付；如果要继续只能新授权、新筛选、新制品。后台任务用受限服务身份和原主体授权绑定，不能以 Worker 的广泛 DB 权限替代原 actor。审批资格不自动授予导出资格；签署批准和生成报表分别验证。

选择短实时查询 vs 持久任务：范围小且请求有界可直接查询；当数十万行、超时和跨重启实际需要时，使用有界 Job 与不可公开 staging。Job identity=(tenant,actor,scopeIdentity,authorityEpoch,query,fields,snapshotId,formatVersion,opId)。在获权快照读取、分块 staging 时保留行身份、范围、schema 与 checkpoint；多次独立查询不能仅用同名 snapshotId 伪称同快照，按真实 DB/物化快照合同设计；参 [T27b-1](T27b-1-relational-data-and-transactions.md)、[T35-3](T35-3-complex-general-function-composition.md)。每批使用真实有效执行许可与当前授权，超限拒绝或获权延迟。完成时核全部块与摘要、内容与独立权威快照、许可与实际安全制品；发布只是把不可公开制品登记为可在授权门读取，任务 SUCCESS 不等于已经交付给用户。

下载选服务端授权读取的短批/分块流，不采用不可撤销长时公开 URL。明确本例以每个 chunk 的有权交付准入为披露线性化点，该点必须与撤权有实际受保护顺序；已获准交付的在途字节可能稍后到达，不承诺回收已送/已获准数据，撤权后不能新准入 chunk。若当前技术仅能开始时验一次签名、无法保证该边界，则不满足此教学合同，应选可受控读取方式或获权另一个较弱合同。不要让 UI 过滤或删除链接充当服务端禁止；如需严格到物理字节送达时间的即时撤销，未证明可实现，不作承诺。实际对象存储缓存、Range 重下、代理等每条可读取路径均须受同一当前授权；HTTP no-store 不保证已下载文件删除。过期/撤权后 staging/制品的保留、清理及审计由有权政策决定，不能在无授权下删除历史审计。

纸面：S1 含租户 A 两条记录 p1=9000、p2=3000，B 有 q1=7000。A 审计者 epoch4 允许 p1/p2 两条及金额，Expected 行数2、总12000；若 p2 数据在 S1 之后变为4000，只要授权不变且仍是 S1，旧报告仍标 S1、总12000；不得混用新 p2 得13000。若导出期间 epoch5 撤销 p2 或金额字段权限，本例要求整个旧制品不得再次交付；若 p1 已在 epoch4 合法准入输出，则不能追回，后续 p2 chunk 必须拒绝。新任务可在获权条件下生成仅 p1 或去除金额字段的制品，其 identity/总量语义不同。跨租户相同申请 ID 不允许混入 q1；不能把总19000当全局报表合法。重试按原 job/制品身份，过期许可不能因已完成就续传。

| 独立 Oracle（NOT_RUN） | 必须区分的事实 |
|---|---|
| G 生效前/到期边界、scope/金额/租户不匹配 | 实际 grant、actor、authority time、decision 及原阶段；11:59:59与12:00不同，未获权不推进 |
| E兼财务、U自批、并发 E/D | 两阶段实际不同主体且非申请者，唯一合法 decision；核审计与阶段，不用 role 名代替 |
| G 撤销后旧提交、revision8内容变化 | 旧授权和旧批准不能用于新提交；合法先前批准保留历史，实质变化重启 |
| S1 数据变化、B同 ID、分块崩溃 | 独立同快照行/金额/身份及字段，2行12000；不混租户或新数据，核实际制品 digest 与 checkpoint |
| 生成前/中/后撤权，READY 但未下载 | 旧制品不再新准入，无法证明权限时拒绝，未公开 staging；已合法交付历史不可追回 |
| 流中撤权、直接链接/Range/代理、迟到 UI | 实际各 chunk 许可顺序与输出，撤权后无新准入，所有真实路径相同授权；客户端状态不替代服务端 |
| 合法维护：增加审批级别或导出字段 | 新 policy/version 只作用获权新任务；已有批准与快照的解释、旧消费者、字段权限与拒绝路径分别回归 |

## 3. 来源与限定结论
