# T41-R2 · 流式分析的事件时间、水位、迟到与结果一致性

#654 / #563；K03 计算与事件语义、K02 数据权威、K10 延迟/恢复、K01 结果合同、K05 评价。基线 5ddd7163f1c8e2393426af843a2d237cd1f1d8ee。DA-08 有限选题。复用 T25b-2 时间对象、T27c-3 消费恢复和 T32b-2 版本/血缘；新问题是按业务时间持续计算一个有修订的指标。实际公开工作负载为 Apache Beam Mobile Gaming 示例的 LeaderBoard 团队每小时积分；下列教学合同与数值原创，不宣称运行官方样例或真实业务。全部目标 NOT_RUN。

## 1. 为什么事件时间与处理时间必须分开

固定窗口 [start,end) 以获权事件时间分组，处理时间指计算节点实际处理的时刻，两者可相差很久。一个离线设备 10:55 产生积分、11:10 才上传，若目标是10点那一小时的成绩，它不能按到达时间直接归入11点。只有合同确实要统计接收/处理速率时才按处理或观察时间分组；事件时间缺失/不可信需要明确拒绝、标记、替代规则而非默默换时钟。固定窗口互不重叠；滑动窗口可能让同一事实贡献多个窗口，跨窗口直接加总会重复；session 以约定无活动间隔定义会话，迟到事件可能合并原本分离的窗口，需支持相应结果更正，不把每次暂态 session ID 永久固定。具体窗口规则、时区/时间尺度及边界按实际合同。

Beam Programming Guide §8.4/9 描述 watermark 是流处理系统对输入完整性的进度判断；实际来源可有不同强度保证，启发式水位不证明不会再有旧事件。窗口分配、触发输出时机、允许迟到期限和 pane 累积模式分别设置；默认窗口/触发组合允许迟到为0，不可将“水位触发”当作任意迟到都被吸收。Beam 公开 Java LeaderBoard 示例按 team/event time 固定窗口，使用 AfterWatermark、首个 pane 元素后的处理时间延迟触发 early/late、allowed lateness 和 accumulating panes 后按队伍求和。该示例展示选择原因（离线手机延迟），不证明任何 runner、sink 或任意负载的准时/无重复保证，也不是业务结算系统。

## 2. 独立纸面时间线及输出合同

教学约定同一租户/队伍 X、固定窗口 W=[10:00,11:00)，同一明确时间基准，正整数积分事件身份稳定。仅统计一次每个合法事件；窗口允许迟到30分钟，按窗口结束后的事件时间水位推进限制在线保留，明确在水位超过11:30后本在线修订路径关闭。具体到达与触发是本例给定的观察，不是 Beam runner 实测，也不假定在精确边界的所有 API 行为。

| 顺序 | 事实/实际观察 | W 累积结果 |
|---|---|---|
| 1 | E1 事件10:10，+5，已到达并早期触发 | 5（暂定） |
| 2 | E2 事件10:40，+7，到达；水位随后过11:00触发 | 12（按时输出、非不可更正） |
| 3 | E3 事件10:55，+4，水位11:10时迟到且合法接纳，后触发 | 16（修订） |
| 4 | E3 重传同身份同规范内容 | 16，不新增积分 |
| 5 | E4 事件10:58，+3，在水位11:31之后到达 | 在线16；更正待处理/拒绝按政策，不能改计11点窗口 |
| 6 | E5 事件11:00，+2 | 属 [11:00,12:00)，不改变 W |

若获权另允许跨在线期限的完整离线纠正且E4核验合法，则新重算版本 W=19；保留先前16的记录及覆盖/修订状态，不能静默写成当时已知19。在线关闭只是当前计算路径的保留合同，不证明所有真实事件已齐、源永久不可更正，也不自动产生财务关账。若政策永不修订且明确拒绝超期事件，则16可为该合同的最终结果，同时报告拒绝和范围。若来源某分区空闲/故障，必须依实际进度机制及允许风险处理；盲将最大已见时间当全局水位可能遗漏另一慢分区，停滞水位又可能长期保留状态，不能臆造完整性。

## 3. 累积结果与增量结果不能混用

在步骤1–3三个 pane 的教学输出，累积模式为5、12、16；显示最新完整结果16，绝不能将三次快照求和33。若采用不保留上一 pane 的增量模式且每个合法事件恰在一个 pane 的独立条件成立，则三个增量5、7、4，累加得16；不能只取最新4，也不能对可重放增量无去重地反复加。Beam Programming Guide §9.4.1 给出 accumulating 与 discarding 的不同 pane 内容；这里的积分计算及 sink 行为是独立教学合同，不由 Beam 自动提供。

输出身份至少绑定指标语义/版本、真实队伍与租户、窗口规则及区间、数据覆盖/计算代际和有权发布版本。累积快照 sink 可按权威版本条件替换同一窗口的当前结果，旧版本晚到不覆盖新版本，同版本异值是冲突；修订可以减少值（如合法撤销积分），不能以数值最大代替最新合法版本。版本必须来自真实提交/计算协议，不假定 runner 重放时 pane 序号天然是跨重建的稳定业务版本。增量 sink 需要稳定有效增量身份以及去重与实际加值同一保护边界，或按已登记完整结果重算；若重新分 pane 后身份/内容改变，不能盲继承旧增量去重键，应选择可验证的重建代际/差异方案。重复 E3 的输入去重与重复输出是两处不同问题；同 eventId 异内容按有权修订或冲突处理。

## 4. 恢复、资源与适用条件

源偏移量只是读取位置，不是窗口业务时间或结果已发布；在状态变更、checkpoint 与 sink 之间按实际机制确定可恢复边界。若结果16已发布但进度未确认，重放同一获权输出不应重复增加；若进度已越过E3却状态/结果仍12且无法恢复，则丢失，禁止报成功。可选完整状态与源进度一致 checkpoint，配合可重放/幂等 sink 或真实事务；具体 runner/连接器保证须实际核对，不能用“exactly once”名称覆盖外部业务效果。窗口数、每键去重集合、保留期、迟到积压和热门键都会占状态；若释放去重状态后仍允许旧事件进入同代际，重复风险重新出现，需明确重放范围、拒绝旧代际、或从有权源重建。不凭 TTL 宣称安全。输出修订及外部通知各自有权合同，重建不能重复发放奖励。

若只需每日完整文件批统计且可等源关闭，直接有限批查询可满足，不必流平台；若需持续低延迟的暂定结果并能容忍明确修订、源不按序到达，窗口/水位与相应输出合同才值得引入；若要求绝对完整且来源无可靠关闭/迟到上界，不能承诺某固定时间必完整，须获得更强来源协议或改变承诺。独立纸面检查 W=5/12/16、重传16、超期在线16/有权重算19、E5另窗；累积与增量相加反例、迟到旧快照、checkpoint 崩溃、分区慢源及状态清理分别核权威事实，实际流引擎、性能、源和 sink NOT_RUN。
