# T25c-2 · 网络通信：传输语义、协议分帧与应用结果

## 1. 端点与分层的实际边界

IP 地址帮助寻址/路由，端口帮助主机协议栈区分传输端点；名称经解析取得候选地址，服务身份还涉及应用层名称、认证与配置。一个域名可能有多个地址，同一地址可服务多个应用，连接也不等于用户授权。诊断应区分名称解析、路由/连接、传输、TLS（若使用）、应用请求解析、业务状态及响应交付，不将所有超时归为“网络不通”。协议各层的成功只证明自身合同。

TCP 是面向连接、可靠有序字节流；可靠性机制包括序列号、确认、重传等，不能理解为任意故障下必然交付或内建活性证明。UDP 是数据报服务，应用若需要可靠/有序交付必须采用相应协议，不应重新发明无边界重试。TCP 单连接发送的两次 write 可能被接收端一次 read 读到，也可能分多次；包、系统调用块、消息、业务记录是不同概念。TCP full-duplex 的两个方向可以有独立关闭状态；EOF 可能只是对方停止发送，不能自动推出对方也停止接收或业务已经成功。

## 2. 应用协议：分帧、状态及版本

协议至少规定编码、消息边界、字段类型/长度、合法状态序列、请求/响应关联、错误与版本演进。教学二进制协议：4 字节 unsigned big-endian 长度，后接 N 个 UTF-8 payload 字节；N 必须在 1..65536，长度为字节而非字符数。接收状态 READ_HEADER→VALIDATE_LENGTH→READ_PAYLOAD→DECODE→DISPATCH；剩余字节作为下一帧输入。不得在验证 N 前按不可信长度分配大缓冲。EOF 发生于帧中间是截断；帧边界 EOF 只代表读取方向结束，若仍期待必需响应则任务不完整。重复、未知消息类型或版本的策略由获权协议定义（拒绝、忽略可选扩展或协商），不能默认接受所有未知值。

假设收到 00 00 00 03 41 C3 A9；payload 是 A 加 é 两个用户字符、三字节。若头跨两次 read、C3 与 A9 跨块，仍应解析一个完整合法帧。若 N=4 但仅收到三字节后 EOF，应报截断；如果连续两帧一次到达，应准确分开；N 超限直接拒绝并依合同关闭/恢复，不能无界读取。这是教学协议，不是 HTTP framing 或现有库规定。文本语义见 T25b-1。

请求关联：同连接上允许多个未完成请求时，若协议没有确定顺序，应使用有范围的请求 ID 对应响应，处理未知/重复 ID、并发上限、取消与连接断开。连接断开后重新连接不是恢复原连接的应用状态，除非应用协议提供恢复/重放机制。单连接有序不代表跨连接、多个 worker 或异步业务处理同一全序。

## 3. 发送、确认、结果及故障边界

| 观察事实 | 能说明什么 | 不能说明什么 |
|---|---|---|
| connect 成功 | 已建立相应传输连接 | 目标应用 ready/用户有权/业务成功 |
| write 返回实际接纳量 | 本地 API 按其合同接纳 | 远端应用完整解析/持久化 |
| TCP ACK | 对方 TCP 已确认相应序列空间 | 业务线程处理、数据库提交 |
| 完整应用响应 | 应用返回了指定状态与数据 | 任意未纳入合同的远端副作用 |
| timeout/reset/EOF | 当前等待或连接发生对应事件 | 请求必未执行或可安全重试 |

教学：创建资源的请求已到服务端并提交，返回途中网络中断。客户端没有结果；重发可能重复，除非实际业务去重/权威查询合同支持。也可能请求从未到达，不能断言提交。CON 已规定身份、原子性及远端效果限制，不重复定义幂等机制。根据所需保证设计受理、查询、重试、补偿或保留 UNKNOWN。日志和客户端计时只能提供部分观察，不能代替远端权威状态。

## 4. HTTP 方法、条件请求与响应合同

RFC 9110 §9.2 区分 safe（请求语义主要是读取）与 idempotent（相同请求重复的预期服务器效果相同）。日志等附带副作用可能存在；幂等不要求每次响应、状态码或日志完全相同。PUT/DELETE 与 safe methods 被该规范定义为幂等方法；不能仅由 HTTP 动词推出某个不遵守语义的服务实际可靠去重。POST 并非规范层面幂等，但某具体操作若有明确可核身份/重放合同可支持安全重试。客户端不应自动重试非幂等请求，除非知道其实际语义幂等或可确认原请求未执行。业务允许与重试预算另核。

RFC 9110 §13.1.1 If-Match 使用 strong entity-tag 比较；修改选定表示时可避免基于旧表示的覆盖。教学客户端 A、B 均读 tag "v1"；A PUT 带 If-Match 成功，资源变为 tag "v2"；B 若发送不匹配的 "v1"，源服务端不得执行该请求方法，可返回412；对已应用变更的规范例外可能返回2xx。前提服务端真实执行条件判断与变更的并发合同、选定 representation 与域正确，不能仅在客户端比一次 tag 后无条件写入。ETag 不天然是跨资源业务版本号、哈希或全局事务锁；仅有 tag 也不能证明其他资源未变。读回/错误码依据实际 API。

HTTP 响应区分 200（按方法语义成功）、201（创建资源）、202（受理但处理未完成）及错误类别；202 并不保证最终成功。即使返回2xx，客户端仍需检查实际媒体类型、完整响应、合法数据形状及业务合同；解析失败不能用 HTTP 状态单独作为成果证据。分页/条件缓存、重定向、代理、中间件和认证的详细规则须另读对应协议。未实现 HTTP parser，不把此节当完整 HTTP 手册。

## 5. 期限、连接池、容量与诊断

连接建立、TLS、请求发送、首字节、完整响应、业务完成可分别受不同超时控制；每阶段最大等待与端到端 deadline 不等同。以本地单调时钟计算剩余预算，重试消耗同一预算（见 T25b-2），跨主机传播采用协议明确定义的时间/期限表示，不直接比较本机 monotonic 值。失败后先区分可确认未执行、已确定拒绝、UNKNOWN；退避和随机抖动降低同步重试压力但不证明无重复效果。重试层叠（客户端、代理、服务）可能放大请求数，明确一个整体策略、最大次数及原因。

连接复用可减少握手成本，但池大小不是任务总量限制；等待池的请求、排队字节、未读响应、远端服务并发另控。读者慢时应沿流传递背压；TCP 流控关注传输端的接收能力，拥塞控制关注网络，不等价于应用任务准入或持久化队列。不要在重试时无限积累缓冲。诊断保留请求 ID、实际阶段、地址/端口（安全允许时）、延迟单位、错误来源、尝试与观察结果；不记录凭据或敏感载荷。
