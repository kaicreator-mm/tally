# T34b-2 · 工程度量、人因与独立制品评价

#612；K11 主责，K07 人类协作、K05 验证、K03 实现、K09 维护。复用 [EMP](../../../v2.1.2/software-engineering-knowledge/K11/advanced-empirical-evaluation-and-value-of-knowledge.md)、[T25d-1](T25d-1-probability-statistics-engineering-measurement.md)、[T27a](T27a-detailed-design-representation.md)、[T28c-1](T28c-1-product-quality-assurance-evaluation.md)、[T32a-1](T32a-1-maintenance-refactoring-replacement.md)、[T34a-1](T34a-1-engineering-economics-estimation-sensitivity.md)、[T34b-1](T34b-1-empirical-research-design-causal-evidence.md)。例及 Oracle NOT_RUN；不设员工考核规则，不声称真实人类或模型收益。

## 1. 从构念到观察事实：不要把代理指标当目标

目标概念、测量对象、观察过程、数值和决策分开。例如“正确的抽象”不是类数或接口数，而是结构是否表达真实语义、变化轴、责任及约束；“可维护”不能只看代码长度，而需要真实同类后续变化的成本和错误。为每项指标记录定义、单位、分母、边界、采集方法、缺失、适用范围及可能的替代解释。准确测量代码行数并不证明LOC是适当构念。产品质量下限由有权合同及独立Oracle给出；度量不自行改变业务目标或验收范围。

Forsgren 等的 SPACE（CACM 2021）强调软件开发生产力的多维、多个层级以及相互制约的观测。以下是本章原创选用表，不是其原指标表或统一打分公式：
| 维度 | 例：开发/维护知识辅助流程 | 不当代替 |
|---|---|---|
| S 满意与福祉 | 有权参与者自述工具摩擦、工作体验及可持续性 | 模型自称满意、以键盘在线时间猜心理状态 |
| P 成效 | 获权业务目标、质量合格交付、维护回归 | LOC、提交数或报告篇幅 |
| A 活动 | 真实构建、修改、审查、重试次数 | 次数越多越高效 |
| C 沟通与协作 | 有效交接、需求澄清、他人可接手任务 | 消息条数等于合作质量 |
| E 效率与流动 | 端到端时间、等待/返工、人工占用及阻塞 | 仅统计模型生成速度 |

原文建议跨至少三个维度选少量互补指标，并至少包含一种感知型测量；这是人类开发者生产力评价的建议，不应机械强制所有纯模型试验。区分个体、团队/群组和端到端系统；团队结果不等于每名成员的贡献。仅因PR更多可能是拆分粒度变化或重复返工，也可能是实际改善；须与质量、交付和工作体验共同分析。不以单一总分抵消安全失败。

## 2. 独立评价真实架构与代码：观察合同及判别规则

教学需求：订单、退款共享某些操作状态但业务权威不同，后续新增一个只影响退款的规则。先冻结支持场景、状态/效果、禁止行为、初始仓库和独立验收，允许多种正确实现，不指定某模式/命名为答案。架构评审在首次实现前记录方案和可反驳风险；代码评价必须检查实际源、运行制品、测试发现和真实状态，不从文字设计推定实现。评分可拆如下有界评价项（实际采用时需预定规则和阈值）。
| 评价问题 | 独立证据 |
|---|---|
| 业务语义是否正确 | 权威合同与独立合法/非法输入、持久/外部Effect |
| 结构是否保护真实变化 | 依赖/写集、责任边界、实际变化触及及不变业务的回归 |
| 抽象是否引入伪共性 | 独立政策Owner、不同变化方向的正反例，不按接口数量评分 |
| 交付是否可用 | 实际受支持环境、真实消费者、制品身份及复现记录 |
| 维护是否容易 | 新任务在同一支持合同下的合格完成、实际变更影响与资源 |

先记录逐项 PASS/FAIL/UNKNOWN/NOT_RUN/N/A（N/A需理由）；主质量合格结局只按预先合同中必需项决定，UNKNOWN/NOT_RUN不自动通过。对抽象等需要判断的构念，用定义、决策规则及有区分性的锚定样例培训评价者；规则允许多个正确方案。独立评价者可行时盲于组别、作者与无关格式，必要的源身份/证据仍保留；遮蔽不得移除实际质量事实。先独立判定，再按预定方式解决分歧并保存原始标签及理由；不能先讨论成一致再报告独立一致率。

## 3. 一致性不是有效性：如何检查人工及 LLM 评价

合成二元标签的100个独立评价对象，两名评审对预定义同一项各给合格/不合格（实际若有UNKNOWN须保留或按事前分析规则另报，不擅自二值化）：
| | B合格 | B不合格 |
|---|---:|---:|
| A合格 | 85 | 5 |
| A不合格 | 5 | 5 |

原始一致率=(85+5)/100=.90；二人边际合格率均.90。对于同一对评审、二元名义标签、完整配对，可用 Cohen κ=(p_o−p_e)/(1−p_e)，其中 p_e 为按各自边际独立模型计算的期望一致率=.9×.9+.1×.1=.82，因此κ=.08/.18≈.444。若二人全标合格，p_o=p_e=1，κ分母0而非完美可靠性的数值证据。原始一致率和κ反映不同口径，类别分布影响结果；此例不规定通用阈值。报告原始列联表、类别、分歧及适用方法；多评价者、序数或缺失标签需另选适合的度量，不直接套上述公式。

即使两名评审对所有样本一致，若两者都把代码更短当业务正确，仍可能一致地错。需要用事先独立权威/测试/专家证据检验构念和评价器。教学：100项含20项独立证实的材料缺陷，自动评价器只发现12项且误报4项。缺陷检出率12/20=60%，漏检8/20=40%，告警中真缺陷12/16=75%；如果其余84项均被标无缺陷，则8/84≈9.52%仍为缺陷。此为固定教学样本，不是总体风险估计；不同严重性、数据分布和真实允许UNKNOWN会改变解释。不能将模型之间高一致当成独立金标准。LLM可辅助提取或提供候选评语，实际可观察的语义、专家判据及证据仍需验证；对需要专业判断的评价，用适当人类参考和独立样本校准，保留误判、位置/篇幅偏好与未决分歧。模型不得访问隐蔽答案或以自己刚生成的测试充任唯一Oracle。

## 4. 维护实验与人因数据的完整解释

同一首次任务的不同实现，在交付后面临一个预先冻结但对实现者隐藏的合法维护任务；若需陌生接手能力，应使用隔离的新消费者，保持SDK/环境、时限、权限、真实初始制品和目标相同。维护验收含新行为与原不变合同回归；不能因为首次实现越权而在维护中给它质量豁免。报告完整分派轨迹，未到达维护阶段保留原因；仅首次合格者的维护时长作条件性描述，不能将其直接推广到所有分配。实际维护成本包括理解、查找、修改、验证、返工、人工及工具，避免与同一墙钟重复计价。

教学：A/B各分配10条轨迹，A首次合格8且其中维护合格6，B首次合格6且其中维护合格6。条件维护合格率为6/8=75%与6/6=100%；完整轨迹联合合格率均6/10=60%，不能说B整体交付成功率更高。若A共消耗120资源单位、B共消耗90（含所有失败、实际发生的首次/维护/审查成本），联合合格产出/单位成本为6/120=.05与6/90≈.0667，或每个合格轨迹的组总投入20与15；这不等于成功轨迹自身平均成本，也不包含未观测未来成本。若有关键质量失败须单独报告，不用总成本抵销。没有真实独立分配和不确定性分析，只能说明这些假设数据的差异。

若研究真实开发者体验，采用有权参与、知情、最小必要采集、可退出及不当披露防护；问卷记录题项、量表方向、窗口、有效回答分母及未回应，访谈保留合规记录和不同解释。不能从模型模拟的用户访谈推人类满意度，亦不能从遥测活动量推福祉。按适用组织伦理与隐私规则处理，发布聚合数据注意小组再识别风险。以匿名反馈和客观事实三角核对诊断摩擦，不以个体排行榜强制追逐指标。若问卷20人只有12人回答且9满意，只能说回答者9/12=75%，非全体已知75%；未回应不是不满意也不是满意。

## 5. 区分性 Oracle 与资料

| 教学反例（NOT_RUN） | 独立 Oracle |
|---|---|
| LOC下降但退款规则改变订单 | 权威合同及两种变化的真实回归、依赖边界；不按结构数量评分 |
| 两评审90%一致或全标合格 | 原始列联表和独立权威、评审规则；复算κ及不可定义情况 |
| 自动评价器漏掉8项缺陷 | 隔离参考集及逐项混淆计数、严重性；不以模型共识代替 |
| 只在首次成功者报告维护收益 | 完整分配账本、联合结局与总资源；条件结论单列 |
| 只问工具使用者或模型模拟问卷 | 真实有权参与者和响应分母、偏差/范围记录，不推断人类效益 |
