## 1. 从维护意图到受影响边界

纠错、适配、完善及预防性维护的分类沿用 K09 卷二；同一工作可能有多个目的。先确定当前真实版本及支持合同，复现用户问题或可证实的维护障碍，再判断所需改变是行为修正、内部结构调整、依赖替换还是产品退役。调查源/生成输入、真实调用者、配置与数据格式、公开接口、异步效果、平台/第三方约束及已有验证；不以改动行数决定风险，不把未重现的假说当根因。输出最小受影响范围及未知，不强行建设万能适配层。

教学：导出服务重复维护两套“可导出”判定；三次需求变更均需要同步修改，而一处遗漏导致越权。候选有 (a) 修复遗漏且保留两条路径；(b) 提取共用政策判断且维持各调用边界；(c) 整体替换服务。先隔离已授权缺陷修复与结构优化：确认实际规则、涉及消费者和独立禁止效果；比较变化轴及重复成本。两个条件表文字相同但分别由不同业务责任人管理时，合并会制造不真实依赖；如果是同一权威政策的重复实现，则共享纯判断有可能减少漂移。架构抽象的选择仍由 T27a / T26a-1 负责，维护要证明真实变化成本和消费者边界。

## 2. 可观察行为、基线与渐进重构

Fowler 的 Refactoring Boundary 将小步行为保持及改善理解/修改作为重构的中心，观察边界需解释。这里以获权支持合同定义观察函数 Obs(实现,输入,前状态,环境)：合法输出/错误、排序/单位/身份、持久后状态、外部 Effect，以及合同要求的资源/时限等；内部调用次序与布局仅在确实属于支持合同或改变外部效果时才是必须保持项。对于非确定性系统比较允许的结果/历史集合及必要安全/活性条件，不要求任意两次输出逐字节相同。一次纯重构应保持规定边界的语义；公开行为有意改变（包括修错）需单独给出批准依据和验收，不能借重构标签获得授权。

教学：旧函数 A 在合法有权请求返回记录列表（空结果为 []），无权返回 DENIED，无持久或外部写；计划拆分查询与权限。先建立基线：固定真实调用接口、初始记录、身份/状态/环境，独立由业务合同定义期望；对旧版运行的 characterization test 可揭示事实（例如误将无权返回[]），但现有行为可能是缺陷，不因此变成合法 Oracle。若基线暴露该差异，应把纠错作为独立获权变更并调整相应测试；其余已受支持行为继续保留。避免把旧错误固化为新版必须重复的合同。

小步例：先抽取纯格式函数，不改变外部接口；再把有权判断及查询参数形成可独立验证的边界，保护原授权和数据作用域；最后移除确认无消费者的重复路径。每步先核语法/适用测试及独立行为，保持可集成状态；有意改变合同的提交与证据另标。若实际变更需要整体原子调整才能保持不变量，可按同一有界提交执行，不为小提交形式暴露非法中间状态。例中改变排序、错误码、跨租户过滤或读取后变为写入均不是自动安全的内部调整。

## 3. 渐进替换不是永久兼容层

对于多个调用者依赖同一旧组件，Fowler Branch by Abstraction 提供通过中间边界迁移调用者和供应实现的可选机制；适用于可逐步替换、持续集成且接口语义可明确的情境。教学以旧存储访问组件 O 和新组件 N 为例，步骤如下：

| 阶段 | 责任及完成条件 |
|---|---|
| 捕捉边界 | 在真实调用者间确定共有且获权的操作、身份、错误与效果；不把O全部内部结构复制成API |
| 接入旧实现 | 有界迁移消费者经边界访问O，验证原合同；动态入口/插件/批处理仍需查证 |
| 引入新实现 | 在相同合同及真实环境验证N，区分业务修复和兼容；不因N接口可编译即通过 |
| 受控切换 | 按可独立切换的合法单元（例如隔离租户）设置明确的路由决定及版本，确保同一意图只有一个获权写者，观察真实效果和失败恢复 |
| 移除旧实现 | 满足全部受支持消费者、数据/状态、回退窗口及权限处理条件后删旧代码；中间边界若只服务迁移可一并移除 |

切换不一定可按单请求分割：同一事务、同一资源的互斥写或共享状态若必须保持整体一致，应扩大切换单位或停写原子切换。并行比较可以用只读请求、隔离数据或无副作用模拟；生产写意图不能为比较而同时向 O/N 各执行一次。即使本地写隔离，真实邮件/付款等外部调用仍须禁用或严格隔离。只读也可能触发缓存更新、审计、计费等效果，需核真实合同。若N已产生O不认识的新状态，关闭开关不能恢复旧合法状态；先确定数据/状态兼容、写者隔离及外部未知对账，否则应停止自动回退，进入获权恢复。参见 T32b-1 / T33a-1；不重复定义数据迁移和RTO/RPO。对于明确不支持旧运行时且无需共存的小型工具，可直接替换并按实际旧数据/合法用户合同验收，不强制保留旧入口。

## 4. 弃用、迁移与清理的可观察证据

实际读者包括直接与传递依赖、动态注册、脚本、安装制品外部消费者、长期离线设备。静态引用清单与按合法范围的运行观测可互补但都可能漏报；仅零访问不是不存在支持义务。对已获权弃用，通知适用对象、替代入口、迁移步骤、期限/版本与支持路径；警告需要可行动且在相关使用时出现，防止警告泛滥或无权收集用户数据。Google Software Engineering at Google ch15 的弃用经验主要来自可观测的大型内部生态，外部未知消费者需要更慎重的支持合同和通知方式。

用消费清单逐项记录实际切换证据、允许不迁移的授权、未决/无法联系消费者及期限，确认移除会否破坏仍受支持的制品或历史数据。退役需满足已授权的业务/数据保留与访问撤销，不从无使用日志推导可删除全部历史数据。移除后验证真实新安装/合法升级和预期不再支持的旧入口拒绝；不能只在源码搜索零引用就发布。维护和技术债收益参见 [T34a-1](T34a-1-engineering-economics-estimation-sensitivity.md)，测量相同类型的后续合格变更工时、影响传播、回归缺陷及维护资源，保留失败尝试/条件差异，不以抽象数量或LOC减少宣称收益。

## 5. 区分性反例与来源

| 教学反例（NOT_RUN） | 独立 Oracle |
|---|---|
| 重构后空数组变404或排序变化 | 按获权支持合同及真实消费者核输出/错误/状态；批准修错另列 |
| 旧版无权返回数据，characterization 记录成功 | 独立政策与跨租户负例、持久/外部记录；旧事实非授权 |
| 开关切换时同一写分别到O/N | 独立意图身份、写者及外部效果收据；核唯一获权写者 |
| N生成新状态，切回O报错或误解释 | 实际旧消费者、新状态与恢复合同；不以开关位置当恢复 |
| 静态零引用、离线客户端仍在支持期 | 消费者清单、实际制品与支持合同、通知/迁移事实 |
| 新结构代码少但每次变化跨多个无关模块 | 比较同类实际维护任务、合格结果、传播/返工成本，保留混淆因素 |
