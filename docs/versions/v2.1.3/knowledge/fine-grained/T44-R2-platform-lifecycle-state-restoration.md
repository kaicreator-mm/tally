# T44-R2 · 应用平台生命周期、状态保留及恢复职责

## 1. 界面实例、进程和业务任务具有不同生命期

一个表单提交后可切换应用、旋转、关闭视图或被系统回收进程。用户正在查看某页、某个 Activity 实例存在、应用进程存在、一个请求正在等待，以及服务器上有已受理业务任务，是不同事实。Android 活动的 started/paused/resumed/stopped 等与可见性和焦点有关，不能把 paused 一概解释为完全不可见；系统可能因内存回收杀进程而不是单独杀 Activity。正常 finish 和默认配置变更都可导致 onDestroy，但不能将 onDestroy 当所有进程终止前必达的持久化机会。资源按真实所有权/可见性选择获得及释放时点；摄像头之类独占设备还须按实际平台许可与可见性政策，非本章实验。

教学任务：“填写申请后提交，成功受理的 operationId 可在重启后查询；只在同账号、同租户且仍有权时恢复非秘密草稿；不自动恢复提交动作。”分离：
| 状态 | Owner 与保留要求 |
|---|---|
| 当前焦点、滚动、选项卡、临时弹层 | 当前视图/导航；按实际用户预期及平台恢复 |
| 可恢复草稿、所编辑 recordId/baseVersion | 有权草稿 Owner，若跨退出保存则有实际持久合同 |
| 已提交 operationId / 本地未决操作身份 | 有效期与作用域内的持久操作事实；服务器权威确认 |
| 最终处理结果、授权、当前业务版本 | 业务权威；恢复时重新读取 |
| 临时 listener、观察任务、媒体资源 | 真实活跃生命周期拥有者；不得因恢复累加 |

Android Save UI states 文档区分 ViewModel（内存，可跨常见配置重建但不跨系统杀进程）、saved state（轻量恢复数据，适用系统恢复而非用户完全结束）、持久存储（按产品政策保存应用数据）。系统提供的 saved state 不是写入后立即跨任意死亡/重启可靠的应用数据库，也不证明持久业务受理；只记录足够重建 UI 的小状态，较大数据、长期草稿按真实持久合同。秘密、租户和会话必须按授权清理；不能以视图恢复强行保留越权数据。用户完全退出后的恢复策略可与系统临时回收不同，不能机械要求总是保留。

## 2. 以具体交错选择保存与恢复策略

教学记录 D7、baseVersion=7，草稿金额100，界面 generation g1、会话 S1，用户已授权保存非秘密草稿。旋转产生 g2（同合法会话），若仅将草稿存在旧视图对象则丢失；可恢复状态保存 draftId、baseVersion、当前编辑内容或由受权持久草稿加载，而非复用旧控件对象。远端读取 R1 属于 g1，g2 新请求 R2 后完成；R1 迟到不得覆盖 g2，取消 R1 只停止等待或按实际合同停止任务。若有真实共享 ViewModel，需分离共享数据结果与只允许活跃视图消费的呈现动作；不能把所有 g1 后到的合法源事实都丢弃（可进入获权共享状态，再由当前观察者渲染）。

系统在应用后台杀死进程，g1/g2 内存都消失。若用户要求恢复编辑，只靠 ViewModel 不充分；若轻量 saved state 在真实系统恢复前提下足够则用它，若需求包括用户退出/重启后仍有草稿，则采用受权持久存储。保存恢复所需身份、版本与 schema，加载后检查会话/tenant、当前 recordId/generation 仍有效，baseVersion 若已是8，不以草稿7直接覆盖；允许重新查看当前事实、按业务获权合并或让用户重新确认。若用户换为 S2/租户 B，禁止显示旧 S1/A 草稿与恢复旧请求，除非有权跨会话迁移合同且重新确认；清空视图与权威写操作分别保证。过期、缺失、格式不支持、未授权各为独立结果，不能都初始化成空白并宣称恢复成功。

## 3. 受理与回执丢失不依赖界面恢复

假设提交命令 op42，规范输入 D7/v7/100，客户端在发送前持久记录受权未决身份及必要输入指纹（避免存秘密）；服务器在共同业务事务持久受理并登记唯一 op42；响应途中应用死亡。重启后如果只看默认按钮可用就用新 op43 重新提交，可能重复产生两项申请；如果因为本地 op42 存在就宣称已成功，也不正确。合法恢复：当前仍有权时按 op42 查询权威，区分已受理/已完成、明确失败、未知；仅当实际合同允许并有同一稳定操作身份和规范输入时安全重发原请求。若本地并未保留 op42 或服务器查询不可用，不捏造已提交或未提交；按权威查找/确认路径和未知策略处理。业务结果若已发生，关闭视图或取消等待不撤回；取消业务需独立有权命令及实际最终结果。恢复出的“提交中”只是呈现状态，不是自动重跑副作用的命令。

若只处理本地可丢弃的查询/滚动，恢复可仅有轻量状态，不应引入持久任务平台；若真实需要跨重启接收服务器业务效果，持久权威和重复处理边界来自任务合同而非 Android 生命周期函数。与 T26a-2/ T35-3 原 Owner 保持一致。

## 4. 生命周期资源的可反驳不变量

假定同一界面逻辑拥有者在活跃代际最多登记一个当前观察者；activate(g) 时实际注册身份 (owner,g,subscriptionId)，deactivate(g) 只释放该代际持有资源，重复释放按明确机制成为 no-op；切换前禁止旧代际发新呈现动作。例：g1 注册 L1，deactivate 后 g2 注册 L2，g1 的迟到清理若按 owner 无条件清除 current 会误删 L2；使用与注册相同的 token/身份进行条件释放，且实际注册与当前状态切换有适用的串行化/同步边界。若释放 L1 失败，须记录未完成并按资源合同处理，不先称资源已释放；新资源取得是否允许取决于独占/共享约束。若本例的服务端订阅独立于进程且有 TTL/显式撤销/租约，则进程死亡不等于远端订阅已注销；应由真实资源协议负责恢复或到期。不能从进程内 finally/onDestroy 推出所有远端资源已清理。

更复杂的多窗口、后台服务、Web 页面缓存或桌面进程不同于 Android Activity，只有同一实际观察和所有权语义才共用控制机制。跨平台候选可共用“编辑/提交/待确认/结果”的业务状态与命令、稳定任务身份和恢复规则，UI 控件、触发方式、窗口/导航/生命周期及保存 API 由适配边界负责；不为假设的未来平台先造统一生命周期框架。

## 5. 独立纸面检查（NOT_RUN）

旋转/常规离开/系统回收/用户退出的状态保留分别检查；同会话 g2 恢复与 S2/tenant B 拒绝；源版本7→8 的重新核验；op42 已受理但响应丢失，恢复只查询或按有权同身份重发而不是 op43；旧代际清理不得删除 L2；真实释放失败未决，远端资源不能从进程消失推断结束。实际目标平台需要独立模拟配置变化、进程死亡、背景恢复、用户退出、权限变化及网络交错后才可说产品合同通过，本轮不执行任何 Android app、设备、SDK 或实际目标。
