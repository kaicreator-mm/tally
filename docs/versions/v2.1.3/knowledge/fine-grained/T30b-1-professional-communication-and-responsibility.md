# T30b-1 · 软件工程专业责任、技术沟通与知识交接

## 1. 专业责任和独立判断的实际冲突

ACM/IEEE-CS 软件工程职业伦理 v5.2 将公共利益、客户雇主、产品、判断、管理、专业、同事、自我发展分别纳入职业责任，强调具体情境的判断而非简单规则算法。专业约束包括诚实报告能力/风险、认识自身专业边界、适当验证、尊重隐私、披露无法避免的利益冲突，以及客观记录评审。它不是所有司法辖区自动适用的法律，也不授权接触或披露私有资料。实际法律、监管、职业与组织义务须由有资格主体核查；此处不提供法律意见。

教学案例：客户希望周五上线批量导入；团队已验证正常输入，但发现故障中断时可能产生不可核对的重复记录，尚未确定影响范围。销售称应先写“全部通过”，工程人员如何处理？
- 如实记录已运行范围与实际失败/未知，拒绝把未验证故障路径改写为通过。保留发生条件、可能后果及待核范围。
- 与负责业务、风险和交付的主体讨论不同选择：禁用高风险功能、限制有权范围、推迟发布、修复后重验；不能擅自承诺故障无害或自行替客户接受风险。
- 如果有严重的安全/公共利益问题或被要求隐瞒，按合法保密与授权边界向适当责任/监督渠道报告，必要时获取专业帮助；内部沟通不可行/有危险的情况需按实际条件处理，不机械要求公开全部原始材料。
- 若本人负责实施且存在利益冲突，披露事实并引入有适当能力、权限及独立判断的评估者；不同角色不是自动独立证据。

准确陈述软件特征（6.07）、报告纠正错误（6.08）、重大权衡/不确定估计（3.01/3.09）、客观评审（7.04）是本例的参考条款。没有执行、数据或相应权威，就只能写明确的不确定性，不能用专业术语替代事实。合法业务授权也不自动解决公共利益或隐私义务。

## 2. 技术写作先确定读者和任务

同一事实面向不同读者需要不同表达，而不是不同真相。先明确读者要完成的任务/决定、已具备的知识、使用情境、需要多少细节。术语首次定义，条件及单位可理解，步骤应可执行；避免只有作者熟悉的缩写、过期截图或把命令示例误当已运行结果。以“接手人员能够在支持环境恢复任务”为目标，比“写满所有实现细节”可检验。

| 文档 | 读者/主要任务 | 必要内容与非目标 |
|---|---|---|
| 技术方案/ADR | 实现者、维护者、决策者 | 问题/范围/约束/备选/决定/代价/重新评价条件；不把未来候选当既成事实 |
| 接口参考 | 消费者 | 支持版本、参数/单位、输入/输出、错误、时序、权限和兼容例；不复制内部实现 |
| 操作指南/runbook | 操作者 | 起始状态、合法权限、依赖、操作、可观察预期、停止/恢复与升级途径；危险操作条件明确 |
| 教程 | 新手 | 最小环境、逐步成功路径及解释，区分演示和实际产品保证 |
| 状态/缺陷报告 | 负责人、维护者 | 实际版本与范围、观察、复现条件、影响与未知、下一步及责任；不夹带无关秘密 |

读者同为工程师也可能不熟悉本语言或本项目。必要时用图/表解释跨组件关系，但必须注明图中箭头/边界含义及状态；不是所有接口都需要新图。把规范性规则、理由、教学示例和观测结果区分，保持唯一正式定义并链接到来源。维护文档时标注适用版本、有效期、Owner，变更后检查消费方；新文档不能静默覆盖仍有效合同。代码注释说明为何选择、假设、难以看出的不变量，避免逐行重复代码。

## 3. 事实、假设、预测与承诺的报告

教学交付记录（虚构，NOT_RUN）：
| 类型 | 内容 |
|---|---|
| 观察事实 | 候选版本X、环境E；正常输入20组已观察符合预期；故障中断后2条重复记录 |
| 假设/未知 | 可能是恢复路径重复提交；尚未核跨版本、外部效果和受影响真实数据 |
| 建议 | 暂停该故障路径的正式发布，定位提交/恢复边界，评估有限禁用 |
| 估计 | 假设能获得隔离环境且不需外部提供方配合，预计1–2工程日调查；不承诺完整修复期限 |
| 决定/责任 | 有权负责人决定发布范围；工程/验证负责人分别提供修正与独立验证；未决定前不能报接受 |

原始事实需身份、日期/版本、观察点、可核材料及范围；推断需说明竞争解释、支持和反证条件。若同一报告从测试20组推广到“所有平台通过”，应拒绝该扩大。若只有历史版本证据，不用它覆盖当前候选。报告应使读者能采取行动，不把不确定性隐藏在脚注。对外说明尽可能使用业务语言描述影响/缓解/限制，内部技术报告可保留更多诊断，但都不能泄露密钥、客户隐私或未经授权数据。度量不能成为诱导不实行为的目标：按缺陷数量评价人可能诱发不报告，按文档数量不证明知识可用；评价真实成果/风险发现、支持与学习，并尊重情境及证据限制。

## 4. 协商与代码评审：把争议缩到真实问题

需求/方案协商遵循 T24a 与 K02 权衡；这里补同事间日常技术评审。评审关注修改内容、风险、解释和证据，不评价人格；明确必须修的合同违反、非阻断建议、待澄清问题。Google Engineering Practices 的评论、冲突处理指导是一个组织的实践参考，不是所有团队的强制审批规则。

教学争议：开发者使用内存队列，评审者希望改为持久队列。
- 不适当评论：“你设计错了，必须用某框架。”无场景、影响和证据。
- 有区分力评论：“当前受理承诺跨进程重启保留；本路径返回受理后任务只在内存，若此刻进程中断，任务可能丢失。请明确已有持久权威或改变受理机制，并用受控中断/读回核该合同。”
- 如果需求尚未获权，提出需要确认的条件，而非评审者发明强制规范。若只是不影响合同的命名偏好，标建议而非阻断。
- 作者可回应具体事实和替代方案，指出原推断不成立的条件；评审者核实际代码/结果后更新意见。仍不一致则选择有能力的第三方或有权负责人，记录决定及未决风险，不以沉默视作同意。

协商需要区分立场（使用某技术）与利益（数据不丢、交付及时、维护简单）。可提出多个满足底线的方案，讨论可逆性及机会成本，不能通过投票改变已批准业务约束。对受影响同事公平听取、允许质疑和记录异议；管理者不能要求为了进度隐藏风险。快速口头交流可解决语境问题，但重要决策应写回可追溯记录。

## 5. 知识转移、接手验证与团队学习

交接目标不是发送消息而是接收方有足够合法信息独立执行其职责。原 K07 定义状态/身份；此处具体化给人使用的交接材料：实际版本与支持范围、业务目标/不变量、环境和权限申请入口（不复制凭据）、真实构建/启动/验证步骤、观察位置、常见失败及恢复、未解决风险、联系/升级渠道、后续维护责任。依赖/许可证及数据权利有疑问时明确需获权核实，不在本章作普遍法律裁决。

分层转移：说明/演示→接收者复述关键合同→在隔离环境由接收者独立执行代表性任务→反馈其遇到的缺失信息→修订正式资料。不能用作者现场代操作后的成功作为接手独立完成证据。接手方在缺权限、版本错误、关键步骤不明或无法观察完成事实时有权拒绝不安全操作；交接完成与后续业务完成仍是两件事。对高风险恢复任务可用桌面演练、受控演练或陪同操作，分清纸面与实测。

事故学习复用 K06 的竞争假设和事实链。Google SRE Postmortem Culture 建议从贡献原因及预防行动学习、减少指责压制报告的风险。非指责不等于取消责任、忽略故意违规或改变事实；应记录当时可得信息、控制缺口、恢复动作、改进Owner与验证条件，敏感材料仅向有权者提供。教学：某工程师按旧文档操作导致回归，先核文档版本、工具提示、权限与审核机制；改进可包括更新指南及让独立接手者验证，而非只写“以后更小心”。将实际复盘的可复用机制回流知识，保留适用条件；单一案例不能证明全组织普遍规律。

## 6. 可检验的专业实践与来源

| 教学场景（NOT_RUN） | 可观察预期 |
|---|---|
| 要求把未运行的测试写成通过 | 报告保持 NOT_RUN/实际观察；明确风险、责任及可行选项 |
| 两个读者使用同一接口文档 | 能分别找到任务相关合同、版本、错误与步骤，不需猜作者环境 |
| 评审者用个人偏好阻断 | 提出实际合同或降为建议；保留有权决定及异议 |
| 接手人员不知道启动权限/失败停止条件 | 停止不安全操作，说明缺口；补充后以独立受控任务验证 |
| 事故分析只责怪最后执行人 | 重建当时信息与因果假设、可执行防止复发措施和独立验证，保留事实 |
