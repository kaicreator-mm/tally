## 综合演练：一次需求变化引起的不同层次判断（原创纸面 NOT_RUN）

假定内部设备服务从短时手工任务演变到有界批量计划；目标是安排全部获权任务，同一台设备同时至多一任务，实际占用以权威提交为准；历史合同只需查询实际承诺时采用的设备资格版本和当前任务状态，不要求完整资格认知历史。两个任务 A/B 的合法边同 R3：A 可 X/Y，B 仅 X；应先选 A→Y、B→X。R1 的 Start/Disable/ReduceQuota 在实际提交前若改变资格或配额，旧计划不能直接获准。计划与执行责任不同，选择算法是纯候选生成，不自动成为状态写者；若承诺必须全批原子，在单权威用真正保护联合约束的提交边界，否则获权部分结果/重新计划须改合同。不存在共同事务且业务拒绝暂态时，不能凭一个协调模块承诺强原子。

R2 的表示选择：当前任务状态加不可静默改写的承诺版本及资格依据足以支持上述限定查询，前提是该版本所需事实仍可读取；只有实际新增“按某记录版本查询历史生效资格”才补有效与记录维度。无需因任务事件存在默认 event sourcing。R4 的能力选择：手工选择和批计划可共享同义的资格谓词与受保护提交机制，仍各自有不同的结果及原子承诺；只有一个固定实现，无必要公共 provider registry。如果外部长期消费者要求稳定读取，另立有权读合同，不能将计划者的批量写权限一并公开。若政策变成到达即承诺，则未来 B 不可知，R3 离线全量匹配不能作为当前线上可实现承诺。若允许已承诺任务继续运行但禁止设备新启，则 R1 的不变量及合法历史须改变。故不同变化分别影响算法、状态表示、提交及公共接口，不把所有变化归为同一架构层。

独立纸面区分：计划得全量2并不证明提交已成功；资格改后旧计划按当前权威检查；同样当前状态但承诺资格版本不同仍要区分；手工和批量共享资格不意味着同一输出；若任务只有一个且无历史要求，局部直接实现可能充分。上述为教学合同，不使用真实服务、真实设备或实际用户记录，不是新产品蓝图或效用实验。
