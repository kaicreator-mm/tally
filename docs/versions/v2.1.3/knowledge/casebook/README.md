## 1. 案例层次

| 层次 | 需要表达的内容 |
|---|---|
| L1 产品 | 软件类型、实际用途、部署/交互形态、系统边界、主要子系统及数据/控制流 |
| L2 子系统 | 业务或技术能力、状态及资源 Owner、通信与失败域、依赖及可替换关系 |
| L3 模块 | 职责内聚、公开合同、依赖方向、内部组成、生命周期与变化轴 |
| L4 功能 | 需求/场景、输入输出、状态转换、错误与边界、替代实现及 Oracle |
| L5 代码抽象 | 函数/类/接口/数据结构/算法、机制与政策区分、复用与不复用条件、反例 |
| L6 演进 | 原合同与新合同、实际变更/历史版本/重构取舍、负面经验、迁移与回归证据 |

层次是观察粒度而非强制层级。可交叉标引。同一项目拥有多种架构机制；同一功能可由多种软件类型、语言和部署方式实现。

## 5. 新案例收录和 Agent 使用

案例 ID 唯一、原 Owner 与已有知识点关联。至少记录真实任务情境、主要功能、观察粒度、实际源定位与身份、职责/依赖/状态/资源、设计原因（区分原作者明确理由与本库推断）、适用/不适用条件、可替代方案、坏抽象、反转条件及验证方法。实际行为证据和待验证建议必须分开；无源则标原创、未运行则 NOT_RUN；真实源码观察也不等于合格的架构优胜证明。一个文件不支持完整应用架构时只标局部视图。不要未经核对使用项目许可证或复用代码；优先自己的解释、引用出处及有限结构图，不复制源项目。

使用步骤：先识别当前软件类型、功能、目标质量属性与约束，找相同功能/机制的多条候选；读取相应原 Kxx 原理；对比项目规模、环境、部署、状态所有者、失败模型、真实消费者及变化轴；提取最小适用机制，保留可复核的例外；将候选转为本项目的具体设计、反例及 Oracle。若源不充分或候选仅表面相似，明确 UNKNOWN 或继续查源，禁止按知名度/Stars/代码长度选择。不要求每次查全库，不为简单功能强制引入模式，不需要当前 DomainHarness。
