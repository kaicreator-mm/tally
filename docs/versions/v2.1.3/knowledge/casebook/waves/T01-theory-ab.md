## A1 · 架构边界是多个正交的关系，不是目录树（K02.F2.1 / K02.F3.1 / K02.F4.2）

一个设计可同时拥有逻辑职责边界、源码依赖边界、数据所有权边界、资源/进程边界、部署/故障隔离边界及团队维护边界。它们可重合，也可一对多。例如一个领域模块含多个文件，一个进程容纳多个模块，同一数据源服务多视图，跨进程适配仍可能只承载同一功能。不要由目录拆分推出独立部署，更不能由类型引用方向推出写权限。

判断步骤：先列必须保持的业务不变量及 Owner；画逻辑依赖、运行时调用、读写、资源生命周期四个必要视图；明确某条边是直接调用、数据观察、授权写入还是部署依赖；提出一项真实变化并追踪必须修改的职责。若变化跨边界，检查是必要的合同变化还是泄漏内部选择。参考 T02-C02/C03/C04/C08，分别观察依赖、模型/视图、Parent/Owner、入口/库的不同边界；并非把四个项目统一成同一架构。

原创反例：把支付代码分成 controller、service、repository 三目录，但三者都写支付状态且各自决定失败重试，属于权威边界未分离；把一个无独立变化的纯转换拆三进程则可能过度设计。最小检查：替换存储/展示时业务规则不被重复改变；每条状态变更从受权 Owner 发生；异常后可追踪资源清理。若没有真实变化轴，停止在已有边界。

## A2 · 抽象替换的语义条件（K03.F2.1 / K03.F5.1 / K02.F2.2）

以当前合同的合法输入集合 D、每个输入可接受的观察结果集合 R(x)（含错误、副作用、状态与资源）为模型。对需要保持的旧消费者，替代实现至少接受原有合法输入，并产生属于旧合同允许的行为；仍须满足原合同规定的必然行为与活性义务，不能仅减少允许结果就假定所有条件成立。对于两个不同合同，共享纯机制可以仅定义它们确有共同的输入及性质；各自包装器负责合法域转换、差异错误与政策。多实现的共同接口不能借由可选字段隐藏不兼容合同。此为原理推导，而非声称已完成形式证明或某语言类型检查。

反例对照：旧合同允许空字符串返回空结果，新实现将空字符串视为非法并抛错；表面类型相同也不兼容。另一场景两个调用者分别允许空串/禁止空串，但共享内部已校验非空字符串的编码函数，合法域明确时共享可成立。检测：对原合法输入、边界输入、资源/错误及授权条件做等价/精化核对；只有有权改变合同才按增强或重写验收。对真实多实现替换需求未知时不引入 Strategy。

## A3 · 数据表示、别名、可变性及相等关系（K03.F1.2 / K02.F3.1）

对象身份、值相等、底层资源身份与业务主键不是同一关系。复制容器不保证复制内部资源，深相等不代表授权相同；将可变对象作为索引键会影响可检索性。T02-C07 观察 NumPy 共享 buffer 的视图，R6 观察相同 ID 替换内容失败；它们揭示不同问题：资源共享和业务确认，不能相互替代。

先说明调用者是否允许后续修改、传递/保留引用、独立快照还是视图；再选择复制、只读视图、共享可变状态或所有权转移；明确相等/哈希的稳定字段、生命周期和释放。反例：从配置列表创建浅副本后继续暴露可变嵌套规则，而用户合同要求冻结快照；另一边大量数组只读切片要求低复制，强制深拷贝增加成本。检验引用替换、嵌套变更、释放原对象、不同业务身份同值；没有独立性合同不武断判定必须拷贝。

## B1 · 合同义务与证据的量化范围（K05.F1.1 / K05.F1.2 / K05.F5.3）

“指定范围全部合格”是对有权义务集合和每项声明覆盖的全称要求，不是对请求中自选记录的全称；“存在合格反例”是存在要求。形式直觉：对指定范围 U，只有 U 被确认完整且非空、每个 u 有合格的适用观察，才能报告该范围内通过；有限执行并不证明所有输入。一个真正违反合同的反例即可推翻相应普遍主张，但不一定否定其他义务。此非一般全称命题的数学性质，而是声称实际验收通过的证据门槛。已确认合法空义务集合按合同记 N/A（无适用义务）；遗漏、未知范围、未执行或未观察不得当作 N/A 或 PASS。明确“完整集合”只针对本次声明范围，不要求收集全软件所有行为。

构造最小反例：义务 A/B，已核验 A 通过，B 未观察；若请求只提交 A，不改变全集 U。应保留 B 未知而不是通过；若 B 有合格失败且未被同范围矛盾阻断，则报告局部/总体失败依据。R6 实际观察到省略普通材料冲突导致候选支持，这只是机制缺陷的有限实例，不是外部权威事件。适用真实需求、证据汇总、数据查询限额；纯函数完整输入没有外部全集时无需发明验证服务。

## B2 · 先对齐观察单元，再解决冲突和汇总（K05.F4.2 / K06.F1.3 / K08.F1.1）

至少区分合同版本、目标/源码/制品身份、执行身份、环境、适用输入域与观察类型。对同一单元的合格相互矛盾记录先保留冲突；不同输入、时间或执行可能合理产生不同结果，不自动互斥。再对不受冲突影响的其他单元保留独立反例，最后做声明范围汇总。不能用“FAIL 总优先”“最后一条为准”或“通过数量多”替代语义。R6 的同一 run FAIL 与 NOT_RUN 复现证明具体实现漏了先决冲突检查；不推广成所有多次执行的不一致都等于 CONFLICT。

版本相同不是身份完整：同源码配不同合同版本或运行制品可能不能比较；过期需确认版本关系/时效，无法确认则 UNKNOWN。教学三组：同一 run 的执行/未执行矛盾；不同 run 一个通过一个失败且有非确定性合同；其他独立范围的有效失败。对三者分别给证据资格、状态及聚合原因。建议检查遗漏、置换、重复、过期和范围分割，实际未运行。

## B3 · 可证伪设计与证据不足的停止条件（K05.F1.2 / K11.F2.3）

对每个设计结论说明它依赖哪个实际变化/需求，何种观察会使判断反转。区分设计约束（有权必须）、专业建议（适用条件）、实际观察（范围）、未知（待查）。同样代码可以在不同合同下是适当或错误抽象，不做绝对排序。反例必须有独立预期，不能由被测实现生成 expected 后自证。行为证据和性能/维护成本证据分别要求：前者限定行为，后者需实际比较或真实后续变更，未测不得承诺收益。没有材料性决策风险时不扩大分析；未解决的授权只阻塞相关部分。
