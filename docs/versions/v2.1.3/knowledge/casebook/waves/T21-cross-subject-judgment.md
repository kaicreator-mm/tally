# T21 · 跨专业知识综合工程判断

[#580](https://github.com/kaicreator-mm/tally/issues/580) / #563；冻结输入基线 eddfc89124e9aed7355b33187b63379e893c165f。三个原创综合推演 J01–J03，不是三个新增案例，不增加原165概念、142案例或143外部来源Blob计数。承接 T13 的只读选知演算，深化为跨专业判断的相互制约、逐阶段交付及条件反转。本文场景为明确的教学假设，不代表 Tally/参考项目真实需求授权；选用结论都是有条件的候选，所有实现、Oracle、实际消费、A/B、成本/性能测量 NOT_RUN。未启动 Agent 或运行外部项目。

## 1. 知识不是固定步骤或设计模式清单

在当前真实任务，先读取有权需求、现有合同和代码环境；只选择会改变当前判断的知识。L1 主要明确目标、领域不变量、权限、验收语义及未知；L2 比较实现架构、职责/事务/依赖及质量权衡；L3 将获准设计具体化为函数、数据结构、错误处理和真实调用路径；之后按真实项目过程安排构造、验证、审核、发布和维护。这里 L1/L2/L3 是工程决策阶段，不是案例库 L1–L6 观察粒度，也不是强制全任务流程。简单变更可以合并阶段，不得省略材料性合同或必要证据。K04/K07 约束交付及协作，K05/K06/K08/K09/K10/K11 根据当前风险进入，而非最后统一补文档。

每个推演输出：假设和 UNKNOWN → 当前决策所需的专业知识和实际案例 → 候选及被拒理由 → 具体实现边界 → 有区分力的 Oracle、实际验收对象及退出 → 哪个条件变化会推翻该判断。先满足业务权限、正确性及必要质量下限，再比较成本；缺少业务决议时，针对缺口保留条件方案或停止有副作用的实施，而不是由模型猜政策。知识冲突先核对适用条件、版本和权威，不以案例数量或项目名投票。现有授权、Task、Review、Release 事实由原有权威决定，本材料不增设状态权威或运行门禁。

## 2. J01 · 订单取消：状态检查、库存和外部退款

**教学输入。** 单部署、一个关系数据库存储订单及库存；已支付且未出库的订单可由所属商户有权操作者取消；假设本地取消与释放库存必须原子，不允许部分订单行释放；支付服务在数据库外，退款成功后才能向用户声明已退款。暂时接受“取消已受理/退款待定”的明确响应；要求已受理的退款可恢复且禁止重复退款。具体退款权限、金额、外部 provider 去重/回读能力与时限 UNKNOWN（未实际给定）。没有真实项目批准。

**阶段与知识组合（原创推演）。**
- L1：K01.F3.2/F3.3/F4.1 定义取消命令、合法前置条件及拒绝后库存不变；明确 CANCEL_ACCEPTED 与 REFUND_CONFIRMED 是不同事实，不把按钮可点击当授权。K02.F4.3 要求租户/权限边界；跨租户拒绝，不信请求中的商户 ID。退款金额/有权规则由实际业务 Owner 决定，缺失时不能执行真实退款。
- L2：K02.F2.1/F3.1/F3.2 与 K03.F3.1/F4.1 约束订单、库存的写所有权和同库事务；T17-C01 的允许跳过级联不满足本例原子不变量，拒绝直接照搬；T17-C02 的资格谓词可为 UI 提示，但写边界须重检当前履约条件；T17-C03 扩展点只在出现真实可选模块时考虑，当前单部署优先直接函数。T18-C01/C02 无独立耐久待办，不能满足已接受退款可恢复；C03 的持久任务记录提供候选基础，不保证外部退款 exactly-once。选择单库事务中写取消、库存释放和持久退款意图（以实际数据库合同验证）；提交后处理该意图，按 K10.F3.1/F3.2 和 K03.F3.2 核实外部稳定业务身份、去重期限/参数或可信回读以及 UNKNOWN 处理。不是把远端 HTTP 纳入本地事务。无法确认 provider 能力时不盲目重放，保持退款未确认，阻止自动退款路径上线或由有权者确定人工恢复。
- L3：候选函数 cancelOrder(actor, orderId, expectedVersion)；在事务内查询身份/权限及未出库条件，按当前版本条件或合适锁防止与出库竞争（包括所有有权写入路径），检查全量库存不变量，再落本地状态和唯一退款意图。Worker 处理时不得信陈旧权限或错误订单身份；用实际合法业务动作授权模型，验证稳定退款身份和请求参数；读取实际结果后更新独立退款状态。K03.F5.1/F5.2、K10.F2.1 区分拒绝/冲突/本地失败/远端 UNKNOWN，日志记录关联 ID 与阶段，不泄漏支付凭据。具体字段/约束、provider 适配及金额算法留实际 L3 合同，不为它们虚构权威。
- 验证与交付：K05.F1.2/F2.2/F3.1 从上述教学不变量推导 Oracle，而非接受 Builder 现有输出。正例取消且本地库存按合同释放，真实事务及意图可读；反例非法角色/跨租户、出库与取消交错、任一库存行失败均不允许部分本地写入；故障例本地 commit 后进程停止、远端成功 ACK 丢失、provider 去重过期，分别查持久状态、远端证据与恢复结果，禁止虚报退款。实际 provider 资格缺失时仅能验证本地合同、远端模拟不能替代真实副作用。K04.F2.1/F3.1、K07.F4.1/F5.1：先固定原子不变量与接口，再实现；共享 schema/迁移由同一 writer 控制；独立审核 Exact HEAD，必要真实集成证据与业务验收分开。K11.F3.1/F3.2：退款不可逆风险高，不能为减少步骤跳过实质验证。

**条件反转：** 未支付订单且无需任何独立外部效果时，单库同步事务足够，不引入持久 worker；若业务明确允许逐行部分取消，则重新定义状态和补偿/验收，原全量原子选择不再必需；若需求允许外部效果丢失且严格不重放 UNKNOWN，可靠重放所需机制不应机械强加，但必须核实真实重复执行路径。若库存改为外部独立服务，单库原子方案不再成立，重新比较可接受的业务中间状态/协调方式，先由 Owner 定义失败后果。以上均 NOT_RUN。

## 3. J02 · 订阅刷新：多入口复用、恢复与故障定位

**教学输入。** 一个阅读器有单订阅刷新与批量刷新；单条请求需等本地刷新结果；批量允许先返回，待办可从订阅的下次检查状态重算，允许重启丢失尚未接收的批量触发；条目允许独立增量提交，不要求全快照原子；外部通知可失败且不影响本地刷新结果。假设需控制总并发和积压，但未给实际负荷/延迟预算，不虚构固定数字。身份/授权、部署实例数、用户编辑与刷新交错政策需核实际产品；不等同 Miniflux 的正式合同。

- L1：K01.F1.3/F4.1/F4.3 分开单条本地完成、批量请求接受与实际完成，定义部分成功及通知失败是否可见。K02.F2.2 不因相同 HTTP 状态就认定相同合同；是否提供批量进度由真实用户需要决定。
- L2：T19-C01 显示 API 与 Worker 共用 RefreshFeed，逐条事务、元数据另写、集成异步；它不是完整安全或可靠性保证。T18-C01/C02 分别解释同步/进程内异步与延期/积压语义；C03 持久队列在本假设尚无不可丢失待办要求，不优先选择。结合 K02.F2.1/F3.1、K03.F2.1/F3.3、K10.F3.3，候选共用业务刷新函数，API 同步调用与批量受控工作池调用；同一业务逻辑但各自入口合同，限制全部实际入口的资源预算（不只 worker 数），明确 producer/队列容量、满载拒绝或等待和取消。持久订阅状态可作为重算基础，须验证扫描完整性及重启行为，不能由 nil error 或重算意图认定无丢失。原子范围选逐条 entry，元数据字段/版本更新独立；不得用原项目结构自动证明并发安全。
- L3：K03.F1.2/F4.1/F4.2/F5.1：按实际查询和规模定义条目标识、批量界限、缓存条件、事务失败与资源关闭。FetchJobs 遍历必须判断终止错误，返回部分列表时按明确合同拒绝或标注部分结果；错误阈值正值启用才应用，非正值禁用。此为参考 T19 修正后的 S02 缺口而提出的候选，不改 Miniflux。若刷新能覆盖用户配置，先核写入字段和读回，再决定字段级更新/版本条件或同订阅串行。K10.F2.1/F4.1：分别观察请求延迟、实际完成延迟、积压及失败阶段；未知负荷暂不选线程数，先用真实代表负载确定容量。
- 故障推演（非真实事故）：用户报告“204 但漏更新”。K06.F1.1/F1.2/F2.2 区分三个竞争解释：H1 查询未完整（预测扫描结束错误、选择 ID 缺失）；H2 已选择但未接收/执行（预测请求 ID 关联的选中项存在、接收/完成证据缺失）；H3 已执行但条目/元数据写失败（预测 worker 执行与数据库部分状态/错误证据）。用同一环境、关联 ID、选中/接收/执行/提交/回读分阶段事实判断第一失败点；不能只增加线程或持久队列掩盖未知根因。K06.F4.1/F4.2 最小因果修复，测试故意使旧实现漏检迭代错误或错误宣称全量完成。
- 验证与成本：K05.F1.2/F3.1/F5.1 用授权后的真实合同分别测试单条、批量未执行、查询中途错误、并发 producer、进程停止后重算、第一条已提交而第二条失败、通知失败及用户修改交错；按所选数据库及实际入口验证，Mock 不证明提交/恢复。K08.F4.1 确认实际 API/Worker 均选择新路径。K11.F1.2、K10.F4.3 比较直接调用、进程内池及持久队列的维护面和负载观察，未有代表数据则成本/性能 NOT_MEASURED；K04.F4.1/F5.3 只研究会改变容量或恢复方案的缺口。

**条件反转：** 如果批量一旦接受就不得丢失，重算无法区分特定用户请求的完成义务，必须重新设计持久接受/查询/恢复；如果全订阅快照必须原子发布，逐条事务不适用；如果操作仅是低频单条同步且不要求后台处理，则可去掉工作池。若真实负荷证明池是瓶颈才扩大并发或分离部署，不能用源代码线程上限直接推导吞吐。全部 NOT_RUN。

## 4. J03 · 维护公共函数：接口收敛与必要能力恢复

**教学输入。** 一个已有库有 app 便捷入口和显式 transport，两个受支持消费者仍用便捷入口；另有独立并发包装函数仅支持调用，真实需求要求清理仍排队的待办并使其 Promise 拒绝，不能撤回已获许可的执行。假设允许一个兼容发布窗口，但未指定真实版本号/期限；具体受支持消费者/环境需项目 Owner 确认。两个问题是并列维护对象，不声称 HTTPX 与 p-limit 属于一个真实产品。

- L1：K09.F1.1/F3.1 与 K01.F5.3 分别分类：移除公共入口是有可观察行为变化的迁移，不是纯重构；增加清理方法及拒绝语义是新能力/合同修复，不是内部简化。兼容期限、清理责任及默认行为须获权，不由 Reviewer 自动改变产品需求。
- L2：T20-C01 pytest 的内部 helper 简化不能外推为公共入口无损删除；T20-C02 HTTPX 的弃用后显式 transport 是有条件迁移参考，旧消费者未迁移时保留兼容窗口。T20-C03 p-limit 的委托已有 clearQueue 可避免重写队列；结合 K02.F2.2/F2.3、K03.F2.1、K09.F2.3 选择最小公共变更：复用现有 transport，旧入口发清晰提示；包装层仅暴露受权清理能力，不暴露整个底层对象。源码已显示出队许可与实际函数调用有间隔，仍排队项才可被 clearQueue 清理，不把“未开始执行”直接等同可撤回。
- L3：同步/异步构造的显式 transport 与旧入口优先级、警告、环境代理差异按实际代码核对；不要复制 HTTPX 某版本的代理变化当本库必要设计。队列包装运行接口、类型声明、文档与测试同步（K03.F2.2、K02.F2.2），委托同一 owner 的清理逻辑；rejectOnClear 策略及默认行为由当前受权合同确定，不能从历史项目默认值照搬。若 wrapper 本身不拥有队列，先明确清理授权。
- 实施及发布：K04.F2.1/F3.2、K07.F3.3/F5.1，固定两个问题各自写集，只有确实独立的才并行；不让多个 writer 同改公共声明/版本文件，给 reviewer 当前差异与最小知识闭包。K08.F1.1/F3.2/F4.1、K05.F3.1/F4.1：语法/类型、受影响运行测试、实际消费者入口/目标制品分别记录真实版本、执行发现和结果；测试 patch 不算通过。K09.F2.1/F4.1/F4.3 核实兼容与回归：旧消费者在窗口内仍成功且符合原协议，显式路径实际命中，旧入口退出后按新版本合同拒绝；并发1时连续两次调用同步清理，第一项可能已获许可但函数尚未运行，后续仍可运行，第二项仍排队按新合同拒绝；另测独立 wrapper、已运行任务和类型/运行一致性。使用故意省略清理委托的实现检查 Oracle 是否能发现。退出旧接口须有实际消费者迁移证据与合法版本决议；不凭库内部测试替代。K11.F1.2/F4.1 记录初始改动、迁移工时、回归/缺陷、维护成本的真实观察；T20 历史代码差异不是经济收益证明。

**条件反转：** 若受支持消费者全部迁移且有权废弃窗口已结束，可删除兼容入口；若公共兼容仍必须长期保留，不能以减少 LOC 为理由强制删除。若清理权限属于外部 owner 或无需清理，包装不应暴露该操作；若需求还包括撤回已获许可但尚未开始的任务，clearQueue 委托不足，需要另定义 admission/cancel 协议及竞态 Oracle，不能假装现有修复满足。全部 NOT_RUN。
