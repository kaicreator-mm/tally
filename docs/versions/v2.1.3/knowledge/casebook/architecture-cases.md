## AR-001 · SQLite：嵌入式数据库的分层执行

**分类：** 数据存储/嵌入式库 · L1/L2 · 分层、编译执行、事务边界。**知识：** K02.F2.1 K02.F3.1 K03.F1.3 K03.F4.1。**证据：** [S01](source-register.md#s01--sqlite)。

- **来源实际支持：** 官方架构图描述 SQL 编译为字节码，经虚拟机执行；下层 B-tree、Pager 和 OS 接口各负其责；选定版本 pager.h 确有页面引用、写入与事务方法。
- **抽象架构视图：** 调用 API → SQL 编译 → 字节码执行 → B-tree → Pager → OS。事务与页面一致性的职责不应重复放在 SQL 调用层。
- **适用与不适用：** 复杂查询语义、数据结构和存储介质各有独立变化；小型单一记录文件不一定需要字节码或 B-tree。
- **方案比较：** 对本地 KV/文档应用比较直接事务库、嵌入数据库、独立 DB 服务。先明确多写者、查询和故障要求。
- **验证/反证建议（NOT_RUN）：** 事务中断后读回一致状态；改变存储介质不改变 SQL 合同。未实际运行、不能宣称任意配置断电可靠。

## AR-002 · Git：内容对象与可变引用分离

**分类：** 版本管理/CLI · L1/L2 · 内容寻址、不可变对象、可变指针。**知识：** K01.F3.3 K02.F3.1 K03.F2.1 K08.F1.1 K09.F4.3。**证据：** [S02](source-register.md#s02--git)。

- **来源实际支持：** Pro Git 对象模型区分 blob/tree/commit 等；refs.h 定义一组引用更新的事务接口。
- **抽象架构视图：** 对象库保存版本内容及关系；refs 表达当前指向；命令层组织工作树、索引与对象的操作。不要把当前名称当内容身份。
- **适用与不适用：** 需要历史快照、可追溯内容和版本切换；若只有无历史的临时状态，复制完整对象图会过度设计。
- **方案比较：** 比较版本记录+指针、数据库行版本、普通文件替换；对象内容 identity 与可见当前版本分别确定。
- **验证/反证建议（NOT_RUN）：** 同内容多次写入的对象身份、引用冲突、更新失败后的旧指针；不同配置与引用后端需独立核对。

## AR-003 · Kubernetes：声明状态与控制循环

**分类：** 分布式基础设施/控制平面 · L1/L2 · 控制循环、Owner、状态协调。**知识：** K02.F3.1 K02.F3.2 K03.F3.1 K10.F3.2。**证据：** [S03](source-register.md#s03--kubernetes)。

- **来源实际支持：** 官方 Controllers 概念强调期望与实际状态的持续协调；Deployment 源码在收养 ReplicaSet 前重新获取对象并检查 UID。
- **抽象架构视图：** 声明期望 → 读取实际状态 → 有条件变更 → 再观察。Controller 负责自身对象范围；缓存是观察而非无条件权威。
- **适用与不适用：** 外部资源长期变化、操作可重复、进程可能重启；一次确定性的短函数通常不需要控制循环。
- **方案比较：** 比较一次执行命令、持久状态机、持续协调器；确认观察能力、所有权和失败后重试条件。
- **验证/反证建议（NOT_RUN）：** 旧 UID/同名重建、部分操作完成、重复事件及重启后收敛；不能把最终一致宣传为瞬时一致。

## AR-004 · NGINX：事件驱动服务器与阶段扩展

**分类：** 网络服务/网关 · L1/L2 · 事件循环、处理阶段、模块。**知识：** K02.F2.1 K02.F2.3 K03.F3.3 K10.F3.3。**证据：** [S04](source-register.md#s04--nginx)。

- **来源实际支持：** 官方开发指南描述进程、事件循环及 HTTP 阶段；读取 ngx_event.c 的事件/定时器循环入口。
- **抽象架构视图：** 连接事件 → 协议/请求处理阶段 → 上游或响应；模块在合适阶段参与。事件处理与业务策略分开，耗时工作不能任意阻塞 I/O。
- **适用与不适用：** 大量并发网络连接或明确扩展点；简单低并发任务用阻塞 I/O 或线程可能更易维护。
- **方案比较：** 比较线程/请求、异步事件、混合工作池；按延迟、阻塞风险、资源及运行环境选型。
- **验证/反证建议（NOT_RUN）：** 慢上游、大响应、连接中断、超时下观察延迟与清理；文档支持机制，不支持本库吞吐数字。

## AR-005 · VS Code：扩展宿主与运行位置

**分类：** IDE/插件平台 · L2 · 宿主隔离、能力、扩展生命周期。**知识：** K02.F2.3 K02.F3.1 K03.F4.3 K09.F3.1。**证据：** [S05](source-register.md#s05--vs-code)。

- **来源实际支持：** 指定源码声明本地进程、Web Worker、远程三类宿主；官方指南说明扩展宿主运行位置和激活。
- **抽象架构视图：** 编辑器功能 → 公共扩展合同 → 选定宿主 → 扩展。位置与扩展功能正交；调用方式不应把所有能力误当本地可用。
- **适用与不适用：** 第三方扩展或远程工作区确需隔离/位置选择；单一程序内私有 helper 不需要宿主 RPC。
- **方案比较：** 比较进程内插件、单独进程、远程宿主；分别处理延迟、能力限制、错误传播、版本兼容。
- **验证/反证建议（NOT_RUN）：** 扩展失败不应错误修改其他资源；远程工作区调用实际发生在约定环境。此处未检查隔离强度或整个 VS Code 源码。

## AR-006 · Django：Web 框架中的请求链

**分类：** Web 应用框架 · L2 · 中间件组合、应用逻辑、适配。**知识：** K02.F2.1 K02.F2.2 K03.F2.1 K03.F5.1。**证据：** [S06](source-register.md#s06--django)。

- **来源实际支持：** 官方 Django 5.2 中间件说明和 BaseHandler.load_middleware 的反向组装、适配同步/异步方法。
- **抽象架构视图：** HTTP 入口 → middleware 链 → view → 反向响应链；通用处理与领域 view 区分。中间件顺序具有合同意义。
- **适用与不适用：** 多个端点需一致处理通用关注点；只涉及一个领域操作的校验不宜无条件放进全局链。
- **方案比较：** 比较直接函数调用、每组 endpoint decorator、全局 middleware；明确短路、异常和执行顺序。
- **验证/反证建议（NOT_RUN）：** 某 middleware 提前返回时 view 不应执行；异步适配、错误与清理必须有针对性检查。仅请求子系统，不宣称完整 Django 结构审计。

## AR-007 · Prometheus：监控采集与查询分离

**分类：** 可观测性/数据平台 · L1/L2 · 拉取采集、存储、规则、查询。**知识：** K02.F2.1 K03.F3.3 K10.F2.2 K10.F4.1。**证据：** [S09](source-register.md#s09--prometheus)。

- **来源实际支持：** 官方概览支持指标采集、时间序列存储、查询、告警协作；scrape Manager 依赖 storage.Appendable 并用锁保护配置。
- **抽象架构视图：** 目标 → scrape manager → 时间序列存储 → 查询/规则 → 告警/可视化。采集失败不等于服务本身不可用；采集数据不是业务权威账本。
- **适用与不适用：** 长期周期性指标、跨目标分析及告警；简单单机日志问题可能无需完整时序平台。
- **方案比较：** 比较本地统计、集中推送、拉取式采集；按网络拓扑、样本体积、时钟及故障域判断。
- **验证/反证建议（NOT_RUN）：** 配置热变更、目标不可达、重复标签、高基数；观察数据缺口而非补零。未实测性能或容量。

## AR-008 · Electron：桌面 UI 与系统能力的进程边界

**分类：** 桌面应用 · L1/L2 · 多进程、IPC、特权隔离。**知识：** K02.F2.2 K02.F3.1 K03.F4.2 K10.F5.1。**证据：** [S13](source-register.md#s13--electron)。

- **来源实际支持：** 版本固定的官方进程模型文档：单 main 进程负责应用入口/窗口，renderer 负责窗口内 Web 内容；此条为项目文档观察。
- **抽象架构视图：** UI renderer ↔ 明确 IPC 合同 ↔ main/受控系统能力。建议把权限和资源所有者放在明确可信边界，不把 UI 当授权主体。
- **适用与不适用：** 桌面 Web UI 需要访问原生文件/系统能力；小型纯 CLI 不应为了统一引入浏览器进程。
- **方案比较：** 比较原生单进程 GUI、Electron、Web+独立后端；依据分发体积、系统集成、权限和交互。
- **验证/反证建议（NOT_RUN）：** renderer 非法请求、重复调用、窗口关闭后的资源行为；进程分离本身不是安全证明。

## AR-009 · Airflow：依赖驱动的可调度数据任务

**分类：** 工作流/批处理平台 · L2 · DAG、调度、执行依赖。**知识：** K04.F3.1 K04.F3.3 K03.F3.3 K08.F3.3。**证据：** [S14](source-register.md#s14--airflow)。

- **来源实际支持：** DAG 类的源文档明确方向依赖、调度及历史运行依赖。未读取完整 scheduler/executor。
- **抽象架构视图：** 工作定义与任务依赖 → 调度判定 → 执行 → 观察结果。执行位置与依赖是否满足是不同问题；这是参考视图，不是完整 Airflow 内部调用图。
- **适用与不适用：** 有可表达的跨任务依赖/计划运行、历史状态与恢复需求；简单顺序函数应优先直接调用。
- **方案比较：** 比较顺序脚本、有限 Worklist、持久调度 DAG；按实际并行性、失败恢复、业务时间域选择。
- **验证/反证建议（NOT_RUN）：** 前置失败、重复调度、同任务不同数据窗口的 identity；不从 DAG 声明推断实际并行或 exactly-once。

**分类：** 企业管理/ERP · L2/L3 · 业务模块、显式依赖、资源声明。**知识：** K01.F3.1 K02.F2.1 K02.F2.3 K08.F1.3 K09.F4.1。**证据：** [S16](source-register.md#s16--odoo)。

## AR-011 · WordPress：可扩展内容管理中的 Hook 边界

**分类：** CMS/插件生态 · L2/L3 · 事件回调、过滤链、扩展顺序。**知识：** K02.F2.3 K03.F2.1 K03.F5.1 K09.F3.1。**证据：** [S17](source-register.md#s17--wordpress)。

- **来源实际支持：** WP_Hook 持有回调集合；apply_filters 无回调直接返回值，并记录嵌套层级及优先级迭代。
- **抽象架构视图：** 核心提供已定义的扩展触点，插件回调参与指定处理；这是 Hook 子系统参考视图，不是完整 CMS 架构。
- **适用与不适用：** 长期存在真实扩展消费者及兼容需求；少数固定模块之间直接调用往往更清晰。
- **方案比较：** 比较显式调用、事件通知、可变值过滤链；规定顺序、重入、异常及回调变更语义。
- **验证/反证建议（NOT_RUN）：** 零回调、不同优先级、嵌套调用、回调修改列表；不能把 Hook 自动等同事务或授权机制。

## AR-012 · Celery：生产者、消息与任务 Worker

**分类：** 后台任务系统 · L2 · 消息分发、执行/ACK分离、重试。**知识：** K02.F3.2 K03.F3.2 K10.F3.1 K10.F3.2。**证据：** [S07](source-register.md#s07--celery)。

- **来源实际支持：** 官方任务文档区分任务调用发消息和 Worker 执行；Worker Request 源码实际存在不同重试/失败/确认路径。
- **抽象架构视图：** 任务提交 → broker → worker → 结果/ACK（各有不同职责）。业务提交与消息确认是不同事实，不用一次 success 覆盖所有失败路径。
- **适用与不适用：** 耗时任务、独立执行者、重复或重启风险；短且同步完成的操作不一定需要 broker。
- **方案比较：** 比较同进程执行、持久任务表、消息队列；先定可靠性、幂等、退避和任务可观测性。
- **验证/反证建议（NOT_RUN）：** Worker 在业务副作用后 ACK 前失效、主动 retry、失败与取消；禁止默认承诺精确一次。
