# Tally v1.5.3 Local Validation & Release Gate

## Purpose

This document is the local/build-host handoff for v1.5.3 Git Engineering Authority. GitHub Actions / CI are intentionally **not** used as development, PR, closure, or release gates.

Implementation branch: `feat/v1.5.3-git-engineering-authority`

Handoff baseline before local validation:
- branch contains the current `main` baseline used by the implementation
- Git Engineering domain contracts, Local Git adapter, GitHub-first remote provider, Git Authority policy, GitActionRecord audit/provenance, CompletionContract integration, accepted-awaiting-merge semantics, merge-result revision propagation, and focused/Hidden Validation carriers are implemented
- full empirical repository + real Git/GitHub validation is still required

Allowed validation statuses are only:
- `PASS`
- `FAIL`
- `NOT_RUN(reason)`
- `ENV-BLOCKED(reason + evidence)`

Never convert an unexecuted check into PASS.

## 0. Checkout / evidence header

Record before any validation:

```bash
git fetch origin
git checkout feat/v1.5.3-git-engineering-authority
git pull --ff-only origin feat/v1.5.3-git-engineering-authority
git status --short
git rev-parse HEAD
git rev-parse origin/main
go version
git --version
```

Evidence must include command, environment, result, revision and timestamp.

Gate condition: clean working tree and the tested revision must be explicitly recorded.

## 1. Focused v1.5.3 tests

Run first so failures are attributable to this version:

```bash
go test -count=1 ./internal/engineering/...
go test -count=1 ./internal/gitengineering/...
go test -count=1 ./internal/controlplane/...
```

Then run targeted high-signal cases (test names may be inspected with `go test -list .`):

```bash
go test -count=1 -run 'Git|Replay|Lifecycle|Completion' ./internal/engineering/...
go test -count=1 -run 'Authority|WrongBase|Stale|Push|Review|Merge|Tag|Release|Replay' ./internal/gitengineering/...
go test -count=1 -run 'GitAction|Awaiting|Completion' ./internal/controlplane/...
```

Required semantic assertions:
1. denied authority never becomes successful completion evidence
2. duplicate record ID is rejected
3. replayed logical action is rejected
4. required Git operation missing => task cannot be DONE
5. verification/review/acceptance PASS + unmerged PR => accepted/awaiting-merge semantics
6. authorized successful merge => merge result revision is preserved and CompletionContract may advance task to DONE
7. failed/blocked Git action remains audit evidence but does not satisfy CompletionContract

Gate: all focused tests PASS.

## 4. Hidden Validation — Local Git

Use a disposable temporary repository and a local/bare remote. Do not use the production repository for destructive cases.

Required cases:

### HV-GIT-01 Wrong base
- policy expects `main`
- attempt PR/open/update semantics with a disallowed base
- expected: authority blocks before provider mutation; record status `blocked`; no CompletionFact produced

### HV-GIT-02 Stale head
- capture expected head SHA
- create another commit so HEAD changes
- attempt guarded push/merge with stale expected SHA
- expected: `stale_head` (or equivalent governed failure), no completion evidence

### HV-GIT-03 Push failure
- use invalid/unreachable local remote or rejected ref
- expected: failed GitActionRecord with reproducible error code; task must not advance

### HV-GIT-04 Duplicate / replay
- append same record ID
- append new record ID with same replay key
- expected: both are rejected according to duplicate/replay contract

Gate: all Local Git hidden cases PASS and leave no uncontrolled side effects.

## 5. Hidden Validation — Real GitHub provider

Use a **disposable validation repository** or an explicitly approved sandbox repository. Do not create test releases/tags on a production release namespace.

Required scenario chain:

1. create issue
2. create branch from expected base revision
3. commit + push
4. open PR against governed target base
5. verification evidence recorded
6. independent review records `REQUEST_CHANGES`
7. repair commit + push
8. re-review and approve
9. attempt unauthorized merge => blocked before provider mutation
10. provide required human authority
11. merge with expected head SHA
12. assert returned/result revision equals actual merge result revision
13. create tag on accepted baseline
14. attempt tag mismatch / wrong release baseline => blocked
15. publish release only from accepted baseline
16. replay a material action => duplicate/replay guard fires
17. inspect GitActionRecord trace links and audit provenance

Required trace fields, where applicable:
`Project → PlanningRevision → TaskDAG → TaskNode → TaskContract → Run → ChangeSet → Verification → Review → Acceptance → Release`, plus Actor, AuthorityDecision, Timestamp and ResultRevision.

Gate: Issue/Branch/Push/PR/Review/Merge/Tag/Release traceability PASS; GitHub remains provider only, not workflow authority.

## 6. Critical Journey

Execute one complete governed task:

```text
TaskNode
→ Frozen TaskContract
→ Issue
→ Branch/Workspace
→ Agent Run
→ Commit
→ Push
→ PR
→ Verification PASS
→ Independent Review PASS
→ Acceptance PASS
→ ACCEPTED / awaiting merge
→ authorized Merge
→ Result Revision
→ Task DONE
```

Assertions:
- before merge, CompletionContract requiring merge is not satisfied
- after merge, exact merge result revision becomes downstream provenance
- no GitHub status/check result is used as Engineering Authority
- no GitHub Actions / CI gate is introduced

Gate: Critical Journey PASS end-to-end.

---

## 7. Failure handling during local validation

When a test fails:
1. preserve failing command/output and tested revision
2. classify as code defect vs environment defect
3. for a code defect, fix on `feat/v1.5.3-git-engineering-authority`
4. add/strengthen a regression test before or with the fix
5. rerun the focused failing layer
6. rerun `make check`, `go test ./...`, Hidden Validation affected by the change, and Critical Journey if behavior changed
7. push the repair commit to the same branch
8. update the validation Issue with evidence and new tested revision

Do not weaken/remove tests merely to obtain PASS.

## 8. Final Release Gate

v1.5.3 can be marked **Release Qualified** only when all material items below are PASS on the same final revision:

- [ ] focused v1.5.3 tests
- [ ] `make build`
- [ ] `make test`
- [ ] `make test-runtime`
- [ ] `make check`
- [ ] `go test ./...`
- [ ] required integration regression (`make test-integration` when part of release baseline)
- [ ] Local Git Hidden Validation
- [ ] real GitHub provider Hidden Validation
- [ ] Request Changes → repair → re-review journey
- [ ] unauthorized merge blocked
- [ ] stale head / wrong base / push failure behavior
- [ ] merge result SHA/revision correctness
- [ ] tag mismatch / wrong release baseline blocked
- [ ] duplicate/replay action handling
- [ ] audit/provenance completeness
- [ ] Critical Journey
- [ ] independent review of final diff
- [ ] no `.github/workflows` change introduced by v1.5.3
- [ ] no GitHub Actions/CI result used as a release gate

Any material `FAIL`, `NOT_RUN`, or `ENV-BLOCKED` means **NOT Release Qualified** until resolved or explicitly re-scoped by an authorized frozen product/architecture decision.

After the Gate is fully PASS:
1. update the validation Issue with the final revision and evidence summary
2. mark the v1.5.3 PR ready for review
3. perform independent final diff review
4. merge to `main` using the reviewed head SHA
5. verify merge result revision
6. only then create the approved v1.5.3 tag/release baseline if the release policy requires it
