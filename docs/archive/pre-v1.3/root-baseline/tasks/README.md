## 每个任务文件的结构

```
## 前置        —— 必须先完成的任务
## 目标        —— 一句话
## 交付物      —— 具体到文件
## 验收标准    —— 机器可检查的条件,做完逐条对
## 不要做      —— 明确排除,防止范围蔓延
## 相关文档
```

**验收标准全部要能机器检查。** 出现「代码质量良好」这种,是任务写错了,改任务。

## 完成的定义

一个任务算完成,当且仅当:

1. `make check` 全绿(含架构测试,含 INV-9 写路由过登录)
2. 验收标准逐条对过
3. 新增的包有 `doc.go`
4. 提交信息带 `Task: TXX`

**不允许带 TODO 交付。** 做不完就把任务拆成两个,在本文件里登记。

**UI 任务的额外底线**(见 CLAUDE.md「界面的写边界」):写操作只能是「写 git 用户内容」或「入队 jobs 动作」;**不写状态字段、不写事实面**。

## 并行开发规约(多 Claude Code 实例,v3)

架构上业务包互不导入,天然适合并行;`test/arch/` 是协调安全网。

**前提:先用单个实例做完 T00(共享地基,不可并行)。** 其余实例此时做不冲突的预备:收集 logpipe 真实日志样本(必须脱敏)、把 prototype 转模板。

### 分道(T00 之后)

| 道 | 任务链 | 时长 |
|---|---|---|
| 道 1(长轴,**决定总工期**) | T04 → T06 → T08 → T05c | ~7 周 |
| 道 2 | T01 → T03 →(T02 / T05b) | ~4 周 |
| 道 3 | T07 →(并入 T08) | ~1 周 |
| 道 4 | T05a →(支援 T05b/c) | ~2.5 周 |

加第 5 个实例无意义 —— 分支被占满,只卡在道 1 后。**串行 16–18 周 → 并行约 9–10 周。**

### 纪律(违反即混乱)

- **一实例一 worktree/分支**,做完按「一任务一提交」**顺序合并**到主线
- **每实例独立 Postgres**(不同 docker 端口/schema),避免 `make test-integration` 互撞
- **迁移号预分配、不重叠**:0001 事实 / 0002 索引 / 0003 env / 0004 deploy / 0005 failure / 0006 fp / 0007 clause / 0008 trace / 0009 session
- **go.mod 白名单加依赖须串行**,并在 diff 留痕(INV-6)
- **每实例 `make check` 全绿才合并** —— 边界违规由测试发现,不靠人盯人

## 范围外的东西

做任务时发现的问题,如果不在当前任务范围内,记到 `BACKLOG.md`,不要顺手改。

顺手改会让一个提交里混进两件事,以后 `git bisect` 找不到东西。
