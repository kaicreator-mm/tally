# 项目管理与开发环境管理平台 PRD

> 版本 v3.0 · 2026-07-21
>
> **v3 方向变更:** 从「只读维护日志本」转为**带完整写操作的自部署管理平台**。三个新决定:

---

## 这是什么

一个自己用的**管理平台**,管自己手上那十来个项目。它干四件事:

1. **管项目** —— 建项目、把想法问成清楚的需求、拆任务、跟踪、记 bug、放文档
2. **处理构建和部署失败** —— 失败了自动定位,能修的修,修完验证
3. **拉起和维护环境** —— 开发环境、测试环境,用 docker 或 ssh
4. **记住修过的问题** —— 同一个坑不踩第二次

这四件事都通过一个**自部署的 Web 界面**操作:增改内容(项目/需求/文档/笔记)、触发动作(拉起/部署/回滚/诊断)、浏览状态与报表。**界面能写,但不改状态、不改事实** —— 状态从执行记录算出来,事实表只追加。这条边界是平台和「更难用的 Jira」的分界线,见第六部分规则 ①。

**用户是自己。自部署,单用户 + 简单登录,不做多租户,不做产品。**

## 给谁看

这个区分影响很多设计:

- **界面是给人看的。** 覆盖率、失败排行、环境状态,这些是你做判断用的,需要图形界面
- **数据是给 LLM 看的。** 需求条款、验收条件、环境定义,这些 agent 要直接读写,所以存成文件(放 git),不存成数据库记录

早期版本把这两个混成一个,得出了"不需要界面"的错误结论。

## 不做什么

- 不做团队协作:工时、指派、优先级、通知、看板、评审流程(任务状态由执行链算出,**不提供手动状态**)
- 不做多用户账号体系:单用户 + 简单登录即止
- 不碰生产环境。只管开发和测试环境
- **不写部署引擎。**零停机、健康检查、回滚交给 Kamal / Ansible / Compose 去做,只调用和记账
- 不做制品库。用 GHCR / Harbor / 自建 registry
- 不做 CI 已经有的东西:构建日志查看器、实时流水线状态
- 不做运行期错误分析(Sentry Seer 已经做得很好,要用就接它)
- 不做 flaky 测试治理(Harness / Trunk / CircleCI 有现成的)
- 不自己写 git server,不 fork 部署工具(**从 Coolify 抽服务定义不算 fork**,见第一部分)

# 第一部分:环境(你的第 3 项的一半)

**先造这个。** 不是因为它最重要,是因为它不依赖任何其他部分,而且做完当天就在省时间。

## 干什么

每个项目在自己的 repo 里放一份环境定义。工具读它,把开发环境或测试环境拉起来,检查是不是真的活了,然后把"这次是用哪些版本拉起来成功的"记下来。

坏了就推倒重建,不修。这些环境本来就是一次性的。

## 怎么拉

两种方式,按项目选:

- **docker** —— compose 文件,本地或远程 docker 主机
- **ssh** —— 连到一台机器上按脚本执行

不做第三种。要接 k8s 等以后再说。

## 环境定义从哪来:抽,不是从头写

十个项目要用到的底座就那么些——Postgres、Redis、MinIO、RabbitMQ、Elasticsearch、各种自托管工具。每个都自己查文档写一遍 compose,既慢又容易漏配置。

**Coolify 里有两百多个一键服务,本质就是一批被人用过、调过的 compose 定义。** 把它们抽出来,验证一遍,存进自己的 git,以后就跟 Coolify 没关系了。

### 为什么是抽,不是接

之前考虑过两种做法,都不如抽:

| 做法 | 运行时还依赖 Coolify | 要不要养它 | 你得到什么 |
|---|---|---|---|
| fork 它改 | — | **要**(你成了上游) | 一坨代码,是负债 |
| 通过它的接口调用 | **要** | 不要 | 什么也没留下 |
| **抽出来验证后自己存** | **不要** | 不要 | **git 里一批已验证的环境定义** |

抽完就可以完全脱离。Coolify 从"运行时依赖"降级成"一次性的资料来源"。

**这不是 fork。** 不拿它的代码,只拿服务定义,而且拿完要自己验证一遍才算数。

### 怎么抽

```
LLM 读 Coolify 的服务定义 + 上游官方文档
   ↓
产出:一份 compose 定义 + 一份健康检查
   ↓
实际拉起来跑一遍
   ↓
健康检查过了 → 存进 git,记下当时的版本组合
健康检查没过 → LLM 改,再跑;三轮还不行就跳过这个服务
```

**验证器就是"拉起来能不能过健康检查",二值,不用判断。** 和这个工具里其他所有地方一样:LLM 只负责提,机器负责判。

**健康检查通常要自己补。** Coolify 那边的定义未必带,或者带的不是你要的那种。所以 LLM 的产出里必须包含健康检查,而且它本身也要被这一轮验证覆盖——健康检查写错了,后面所有"拉起成功"的记录都是假的。

### 三条规则

**① 只抽你实际要用的,不要批量抽两百多个。**

抽了不用的定义会过期,过期的定义比没有更糟——你会以为有,用的时候才发现坏了。列一份清单(大概十来个),抽完就停。

**② 没通过验证的一律不存。** 不存"抽出来了但还没试过"的定义。这和知识库那边的规则是同一条:未验证的东西看起来和验证过的一样,但你以后会信它。

**③ 许可证要先查,这是开工前的硬节点。**

Coolify 的服务定义大多是社区贡献的 compose 文件。衍生使用的许可和署名要求得单独确认,不能默认可以随便用。这件事要在抽取动作开始之前查完,不是抽完再补。

### 这批定义就是"已知好"的那一半

存下来的每条定义都带着"在什么版本组合下验证过"。这批记录和第五部分的失败知识库是同一件事的两面:

- **这里** —— 什么组合是能跑起来的
- **第五部分** —— 什么组合会炸,以及炸了怎么修

两边共用同一套拉起和验证机制,不用建两遍。

### 其他来源

Coolify 是最集中的一处,但不是唯一来源。上游项目自己的 docker-compose 示例、官方文档里的部署章节,同样可以走这条流程。**流程不变:抽 → 实际拉起 → 过健康检查 → 才入库。**

## 关键规则

**① 环境定义放在项目的 repo 里,不放在工具的数据库里。**

这样环境定义跟着代码走,切分支就切环境,不用两边同步。

**② "拉起成功"必须有明确判据,不能靠人看。**

每个环境定义里要写健康检查:端口通了、接口返回 200、某个日志行出现了。跑完检查才算成功。没有健康检查的环境定义不允许注册。

**③ 拉起成功之后,把当时的版本组合记下来。**

镜像 tag、包版本、运行时版本、操作系统。这份记录就是"已知好的组合",第五部分要用。

不记的话,三个月后依赖升级把环境搞坏了,你没有任何东西可以对比。

**④ 拉起失败也是一次失败,要送进第三、四部分。**

环境起不来和构建失败是同一类事情,走同一条处理流程。

## 界面上要有什么(环境)

- 每个项目的环境现在是什么状态(在跑 / 停了 / 上次拉起失败)
- 每个环境上次成功拉起是什么时候,用的什么版本组合
- 一键拉起、一键推倒重建

# 第二部分:部署(你的第 3 项的另一半)

上面那部分管的是**底座**——数据库、缓存、消息队列这些应用依赖的东西。这部分管的是**把应用本身放上去**。

两件事经常被混在一起,但失败原因完全不同:底座起不来是环境问题,应用部署不上去是制品或配置问题。分开记,后面查指纹的时候才不会互相污染。

范围仍然是**开发环境和测试环境**,不碰生产。

## 核心原则:不写部署引擎

零停机切换、健康检查等待、失败回滚、多机滚动——这些都是解了二十年的问题,已经有成熟实现。**自己写一遍不会更好,但会多出一个要长期维护的东西。**

这个工具在部署这件事上只干三件:

1. **决定部署什么**(哪个制品到哪个环境)
2. **调用成熟工具去干**
3. **把结果记下来**(成功/失败、当时的版本组合、失败日志送进第三部分)

**调度 + 记账,不是部署引擎。**

## 用哪些成熟组件

按项目选一条路线,不要求统一:

| 路线 | 工具 | 适合 |
|---|---|---|
| **容器 + SSH** | **Kamal** | 主力推荐。就是为"把 docker 应用部到几台机器上"设计的,自带零停机、健康检查、回滚,不需要 k8s,配置文件很短 |
| **纯 compose** | Docker Compose(可通过 `ssh://` 连远程 docker) | 最简单的项目,不需要零停机的场景 |
| **非容器 / 系统层动作** | **Ansible** | 装系统包、改系统配置、非容器化的老项目 |

三条都是成熟项目,都有幂等语义,都能被脚本调用并返回明确的退出码。**够用了,不要再加第四条。**

镜像仓库直接用现成的:GHCR、Harbor、或自建 registry。不自己做制品库。

## 关键规则

**① 部署的输入必须是已经构建好的制品,不能在目标机上现构建。**

部署的对象是一个镜像 digest(或一个打好的包),不是"拉代码然后 build"。

理由很实际:在目标机上构建,等于每台机器构建出来的东西都可能不一样,失败了你分不清是代码问题还是那台机器的问题。**指纹也就没法算了**——第三到五部分整个失效。

**② 部署定义放 repo 里,和环境定义一起。**

Kamal 的配置、compose 文件、Ansible playbook,都放项目自己的 repo。工具只是读它。

**③ 健康检查和回滚交给工具自己做,不自己实现。**

Kamal 和 Ansible 都有。你只需要在部署定义里把判据写清楚(哪个接口返回什么算健康),然后读工具的退出码。

**④ 每次部署都要留一条记录。**

至少包含:部署了哪个制品(digest)、部到哪个环境、什么时候、成功还是失败、当时的完整版本组合。

这条记录是后面所有事情的依据——查"这个失败是哪次部署带上去的"、查"上次能跑的是哪个版本组合"、查"这次改动关联哪条需求",全靠它。

**⑤ 部署失败和环境拉起失败分开记,但走同一条处理流程。**

分开记是因为它们的指纹维度不同(部署失败关心制品和配置,环境失败关心镜像版本和资源)。走同一条流程是因为处理方式一样:压日志 → 算指纹 → 查库 → 提方案 → 重跑验证。

**⑥ 重跑验证 = 重新部署同一个 digest 到隔离环境。**

不要在正在用的测试环境上验证修复,会把别人的调试搞乱。用一个专门的一次性环境,验证完就销毁。

## 以后要接生产的话

不在当前范围内。但因为部署动作本身是外包给成熟工具的,以后要加生产环境,是**配置问题不是架构问题**——加一个环境定义即可。

真到那天只需加两条约束:生产部署必须人工确认;生产失败**不允许自动修复**,只允许提方案。

## 界面上要有什么(部署)

- 每个环境现在跑的是哪个制品、哪次部署上去的
- 部署历史:时间、制品、结果、版本组合
- 一键回滚到上一个成功的制品

# 第三部分:日志收集与清洗

单列出来是因为两件事:构建、部署、环境三个来源都产日志,处理方式一样,不该各写一遍;而且**这一步做砸了,后面全废** —— 指纹算不准知识库就永远查不到,喂太多 LLM 就贵,漏了脱敏就把密钥送出去了。

## 从哪收

| 来源 | 怎么拿 |
|---|---|
| 构建 | CI 平台 API 拉完整日志,或在 CI 里加一步把日志当 artifact 传出来 |
| 部署 | Kamal / Ansible / Compose 的标准输出、错误输出和退出码。这些工具的输出通常已经半结构化了 |
| 环境 | 拉起脚本的输出 + 各个容器的日志(取失败时刻前后一段)。多容器要分开收,标明来自哪个服务 |

**只在失败的时候收。** 成功的日志不留(只留那条版本组合记录)。成功日志没有诊断价值,但会占掉大量空间。

**被动触发,不做常驻日志管道。** 不装 Loki / ELK,不做实时采集——那是运行期可观测性,不在范围里。

## 收多少、留多久

原始日志留一份,但设上限(比如单次 10MB,超了从中间截断,保留头尾)。

**留原始日志只有一个用途:抽取规则改了以后能重跑。** 不用于查询,不用于展示。

保留期给一个明确期限(比如 90 天),过期后只保留抽取过的片段和指纹。

## 清洗是两件事,不要混

我之前把它们写成一件了,其实目的完全不同:

| | 目的 | 做砸的后果 |
|---|---|---|
| **第一步:抽取** | 几千行压到几十行 | LLM 又贵又抓不到重点 |
| **第二步:规范化** | 让同一个错误每次算出同一个指纹 | 指纹永不重复,知识库永远查不到 |

顺序是:收集 → 脱敏 → 抽取 → 再脱敏 → 规范化 → 算指纹。

## 第一步:抽取

**动手抽取之前,先做三件事:**

- **去掉 ANSI 颜色码和控制字符。** CI 日志里全是这个,不去掉后面全乱
- **统一换行符和编码**
- **单行超长的先截断。** 有些日志一行几 MB(base64、内嵌的二进制)

**然后按优先级找关键片段:**

1. 有结构化输出就用结构化的 —— 测试框架的 JSON 报告、`docker build` 的错误块、包管理器的结构化错误
2. 按标记定位 —— `error:` `ERROR` `FAILED` `Traceback` `npm ERR!` `fatal:`、非零退出那行,取标记行前后各若干行
3. 兜底 —— 取尾部若干行 + 头部若干行

**两个容易做错的地方:**

**堆栈跟踪要整段取,不能按行切。** 一个 traceback 是一个语义单元,切一半就没用了。做法是:遇到起始标记后一直取到缩进结束或空行。

**并行构建的日志会交错。** CI 并行跑的话,先按任务或 step 分组再抽取,否则不同任务的输出会混进同一个片段。

抽取器按工具链写,来了新工具链就加一个。**这些抽取器自己要有测试**(拿真实日志当样本),因为它们改坏了整条链会静默失效——不报错,只是指纹开始不准。

## 脱敏:必须在进 LLM 之前

构建日志里经常带着 registry 凭证、环境变量、API token、数据库连接串、带 token 的私有仓库地址。

**这些片段是要发给 LLM 服务商的。** 所以脱敏不是可选项,漏了的话你的密钥会同时躺在数据库里、git 里和别人的服务器上。

至少要覆盖:

- 常见 token 格式:`ghp_` 开头、`sk-` 开头、JWT 三段式、超长 base64
- `Authorization:` / `password=` / `token=` / `secret=` 后面的值
- 连接串里的 `user:pass@`
- 项目自己 `.env` 里出现过的值(有名单,可以精确匹配)

**做两遍,先粗后细:** 收集时粗筛一次(防止原始日志落盘就带着密钥),抽取后再细筛一次(片段小了,可以用更严格的规则)。

## 第二步:规范化

**这一条决定整个知识库有没有用。**

同一个错误,每次的日志里路径、时间戳、进程号都不一样。不洗掉的话,每次算出的指纹都不同,永远查不到之前的记录。然后你会得出"这些错误本来就各不相同"的结论,把功能砍掉——**其实只是没洗。**

**必须洗掉的:**

| 类型 | 例子 |
|---|---|
| 绝对路径 | `/home/x/proj/src/a.ts` → `<项目根>/src/a.ts` |
| 时间戳、耗时 | `2026-07-21T10:33:02`、`took 4.21s` |
| 进程号、线程号、端口号 | `pid=48122`、`:53411` |
| 内存地址、UUID、内容哈希 | `0x7f3a...`、`sha256:abc...` |
| 临时目录、随机文件名 | `/tmp/build-xk29d/` |

**绝对不能洗的**(洗了就失真):

- 退出码 —— 137 是内存超限,1 是普通失败,完全不是一回事
- 包名和版本号 —— 这恰恰是指纹最主要的信息
- 错误类型、异常类名

**算两个指纹:**

- **精确指纹** —— 洗完之后直接哈希(保留行号和具体版本)
- **模糊指纹** —— 再去掉行号和版本号之后哈希

两者用途不同,见第五部分。

## 规则改了怎么办

抽取规则和规范化规则一改,所有指纹都会变。所以:

- **规则要有版本号,指纹里带上这个版本号**
- 规则升级之后,拿留着的原始日志重跑一遍,重算历史指纹
- 这就是为什么要留原始日志

没有这套机制的话,你每优化一次抽取规则,历史知识库就作废一次。

# 第四部分:失败处理(你的第 2 项)

## 只管两类失败

- **构建失败** —— CI 里 build 挂了
- **部署和环境拉起失败** —— 应用部不上去、底座起不来、或者健康检查不过

**为什么只管这两类:因为它们重现一次几乎不要钱。**

构建失败要重现,就是 checkout 那个提交再 build 一次。部署失败要重现,就是把同一个 digest 再部一次。而运行期的线上错误要重现,你得专门写一个复现用例,还不一定抓得住当时的条件。

重现便宜,验证就便宜,整条流程才跑得动。

## 处理流程

```
失败发生
   ↓
收集 → 脱敏 → 抽取 → 规范化 → 指纹   (第三部分,全程不用 LLM)
   ↓
查知识库
   ├─ 精确指纹命中 → 直接给出上次的修复方案,一次 LLM 都不用调
   ├─ 只有模糊指纹命中 → 当线索交给 LLM,不直接用
   └─ 都没命中 → LLM 提方案 → 重跑验证 → 通过才记下来
```

## 关键规则

**① 日志先过第三部分,再进 LLM。**

一次构建失败的日志几千行,真正有用的通常就那三五行。收集、脱敏、抽取、规范化全部是规则做的,不用 LLM。

不压直接喂,一是贵,二是噪声会让指纹算不准,三是密钥会跟着出去。

**② 修复必须重跑验证才算数。**

流程是:先确认这个失败能稳定重现(连跑 5 次都失败),然后应用修复,再连跑 5 次全部成功,其他项目的构建也不受影响。

**连跑 5 次不能省。** 只跑一次的话,偶发问题会以"已修复"的身份被记下来,以后每次查到它都会误导你。

**③ 修复能改哪些文件,列白名单。**

- 可以直接改:依赖清单、锁文件、Dockerfile、CI 配置、compose / 部署清单、资源限制、健康检查定义
- 改到应用源码 → 停下来问人
- 改到验证用的东西 → 直接拒绝(不然 LLM 最省事的过关方式是把检查放松)

构建和部署失败的修复面基本就是上面那几类,所以这个白名单能列全。这也是只做这两格的好处之一。

**④ 修不了的要明确归类,不能一直重试。**

| 情况 | 怎么办 |
|---|---|
| 偶发,重现不稳定 | 单独记为偶发问题,**不进知识库** |
| 上游的问题,得等人家修 | 记下来,把版本锁在当前能用的那个,写清楚为什么锁、什么时候解 |
| 环境/基础设施问题(磁盘满了、网断了) | 记为运维事项,**不进知识库** |
| **代码没写错,是需求本身有问题** | **退回第六部分,改需求** |

最后一类最容易被忽略。如果同一条需求的实现反复出问题,多半是需求当初就没写清楚,不是实现的人不行。发现了要往上退,不能一直在下游修。

**⑤ 重试要有上限。**

同一个失败,LLM 提方案 → 验证不通过 → 再提,这个循环最多三轮。超了就归类存档,标成"暂时没有自动修复",以后再遇到直接返回这个结论,不再调 LLM。

不设上限的话,这是整个工具里唯一会闷声烧钱的地方。

## 界面上要有什么

- 最近的失败列表,按指纹归并(同一个问题出现了几次)
- 哪个指纹最值得先修(出现次数 × 影响的项目数)
- 失败次数的时间线,和依赖升级事件对齐 —— 一眼看出是哪次升级把东西搞坏的

# 第五部分:知识记录(你的第 4 项)

## 存什么

每条知识就三样东西:

- **指纹** —— 这个错误长什么样
- **怎么重现** —— 一条命令
- **验证过的修复** —— 加上当时是在什么版本组合下验证的

## 不存什么

- 不存 LLM 的分析过程
- 不存故障描述、复盘文章
- 不存没通过验证的结论,哪怕标注"仅供参考"也不行

**理由很实际:** 一个装满未验证结论的知识库,看起来和真经验一模一样,但你以后查到它会信它。而且这是自己用的工具,没有客户会来纠正你,错的东西会一直错下去。

## 双层:验证库与笔记分开(v3)

平台有一个可编辑的 Wiki 用来随手记经验,但**它和上面那个验证库是两层,绝不混存**:

| 层 | 内容 | 谁能写 | 可信度 |
|---|---|---|---|
| **已验证修复库** | (指纹, 复现命令, 验证过的修复 + 版本组合) | 只能经四道闸验证后由系统写入(git commit) | 高,界面标 `已验证` |
| **Wiki 笔记层** | 经验、复盘、临时记录、还没验证的思路 | 界面上自由编辑(git markdown) | 未验证,界面标 `笔记·未验证` |

**为什么要分两层:** 你确实需要一个能随手记的地方(不是所有东西都到了能验证的程度);但一旦未验证的笔记和验证过的修复长得一样,你就再分不清哪个能信。所以两层在存储(不同目录)、入库方式(一个 gated 一个自由)、和界面标注上**三处都分开**。

- 笔记层**不遵守**铁律 2(它就是用来放未验证想法的),但**必须**在界面上醒目标注「未验证」。
- 验证库**仍严格遵守**铁律 2:界面上**没有编辑入口**,只能通过失败处理流程入库。
- 一条笔记后来被验证了,不是"升级"这条笔记,而是走验证流程在验证库里**新开一条**,笔记可留可删。

界面规格见 `docs/06-ui-spec.md`。

## 指纹怎么来的

见第三部分。指纹的质量完全由那一步决定 —— **洗不干净,这个知识库就永远查不到东西**,而表现出来是"这些错误好像各不相同"。

## 两种匹配,待遇不一样

- **精确匹配**(洗完之后完全一样)→ 直接返回上次的修复
- **模糊匹配**(再去掉行号和具体版本号之后一样)→ **只能当线索给 LLM 参考,不能直接当答案用**

模糊匹配就是"看起来像",而看起来像不等于是同一个问题。它可以帮 LLM 更快想到方向,但不能替代验证。

## 修复会过期

一条八个月前验证过的修复,今天不一定还成立 —— 依赖版本已经变了。

所以:

- 每条修复都记着"验证时的版本组合"
- 查到的时候比对当前版本组合,对不上就标成"可能过期",降级成线索,不直接用
- 依赖升级的时候,重跑相关的重现命令,不再复现的标记为退休(记录保留,不删)

# 第六部分:项目管理(你的第 1 项)

最后造。前三项跑起来之后,你会更清楚这一项该长什么样。

**v3:这一部分通过完整的管理界面操作** —— 建项目、写需求、拆任务、记 bug、放文档、浏览状态与报表。但要害不变:**状态是算出来的,不是填出来的**(规则 ①)。界面负责「写内容、触发动作」,不负责「标记状态」。

## 有什么

- 建项目
- 把想法问成清楚的需求
- 拆任务
- 跟踪进度
- 记 bug
- 放文档

## 关键规则

**① 状态是算出来的,不给手动改。**

一个任务算不算完成,不看有没有人点了按钮,看:代码合了没、构建过了没、测试过了没、部署了没、部署之后稳不稳。

**这一条是这个功能和 Jira / 禅道的唯一区别。** 一旦允许手动改状态,它就退化成一个更难用的 Jira —— 因为手填的状态永远是不准的,而不准的状态没有任何用处。

**v3 重申:** 管理平台加了完整的增删改界面,但**不加手动改状态**。界面上能看到每个任务「合并了没/构建了没/部署了没/稳不稳」——这些从执行链算出来展示,没有一个是可以点的勾选框。这条是有了完整界面之后更要守住的底线。

**② LLM 负责问,不负责写。**

需求内容全部由你产出。LLM 的工作是发现你哪里没想清楚,然后问你。

流程是:你写个粗糙的想法 → 系统检查有哪些必须写的东西没写 → LLM 针对每个缺口问你(尽量给选项,选择题比问答题好答)→ 你回答或改写 → 再检查 → 都齐了 → 你确认签字 → 冻结

**LLM 全程不替你写需求内容。** 一旦它起草你审阅,你就变成了在审别人的思路,而需求本来就应该是你的思路。

**③ 什么叫"写清楚了",要能机器判断。**

不能让 LLM 来评价"这个需求写得够不够好",那是让它当裁判,而它当不了。改成一个检查清单,每条都是机械判断:

| 检查 | 为什么 |
|---|---|
| 每条需求能单独编号引用 | 后面要用编号把代码、构建、失败挂上来 |
| 每条都写了怎么算完成,以及谁来判断(自动化测试 / 看指标 / 人工检查) | 说不出怎么算完成的,那是愿望不是需求 |
| 没有"待定""TBD""二选一还没定" | 悬着的条款永远关不掉 |
| **必须写"不做什么"** | 只写要做什么,LLM 干活时会越界;边界得明说 |
| 同一个概念只用一个词 | 一词多义会让后面所有环节都跑偏 |

这个清单的输出是"第 3 条没写验收标准、第 7 条有个 TBD、没写不做什么",不是"我觉得还不够清楚"。

**④ 只跟踪能对应到实际动作的东西。**

| 要 | 不要 |
|---|---|
| 需求(对应到提交) | 工时 |
| 任务状态(从执行链算出来) | 需求评审流程 |
| bug(对应到失败记录) | 看板 |
| 版本(对应到制品和部署记录) | 权限、通知 |
| 用例(对应到自动化测试) | 人工用例库 |

判断标准就一条:**这个东西有没有对应的机器记录?** 没有就不做,做了也是手填的假数据。

**⑤ 文档就是 repo 里的 markdown。**

不做文档管理模块(上传、分类、检索、版本)。git 已经管了版本,界面负责渲染,就够了。**可编辑的 Wiki 笔记层(见第五部分「双层」)同理**:就是 git 里的 markdown,界面是它的编辑器,版本由 git 管。

**⑥ 需求改了,下游要知道。**

第 3 条改了之后,所有基于第 3 条做的任务、代码、测试、部署记录,都要标成"依据已经变了"。

技术上的做法:挂钩的时候记的不是"第 3 条"这个编号,而是"第 3 条当时的内容"。这样内容一变,旧记录自动就对不上了,不需要额外做什么。

只记编号的话,需求改了图还连着,看起来一切正常,实际全是过期的。

## 和前面几部分怎么连

一条链:

```
需求条款 → 提交 → 构建 → 制品 → 部署 → 失败指纹
```

每一段都能从机器记录里推出来,不需要人去标注。

连起来之后能回答两个问题:

**A. 某条需求的实现一共炸了多少次**

> REQ-12 多租户隔离 —— 8 次提交,23 次构建失败,其中 14 次是同一个指纹

这不是在说谁写得差。失败老是集中在一条需求上,通常说明这条需求当初没写清楚。这是需求层面的信号,不是实现层面的。

**B. 某个指纹影响了哪些地方**

> 指纹 a3f9c2(原生模块 ABI 不匹配)—— 出现 6 次,横跨 4 个项目,修复验证于 6 月 14 日;其中 HSK 项目的版本已经变了,这条修复可能过期

第二个问题里,"横跨 4 个项目"这部分不需要第六部分就能答,所以第三到五部分先做完就能用。加上第六部分之后才能知道"影响了哪几条需求"。

# 造的顺序

| 顺序 | 做什么 | 依赖 | 大概时间 |
|---|---|---|---|
| 1 | **环境拉起 + 健康检查 + 版本组合记录** | 无 | 1–2 周 |
| 1b | **从 Coolify 抽十来个常用服务定义,逐个拉起验证后入库**(许可证先查) | 1 | 1 周 |
| 2 | **接一个部署工具(建议 Kamal)+ 部署记录** | 1 | 1 周 |
| 3 | **日志收集 + 脱敏 + 抽取 + 规范化 + 算指纹**(先只统计,不修复) | 无 | 2 周 |
| 4 | 失败排行 + 时间线 + 环境/部署状态界面 | 1+2+3 | 几天 |
| 5 | LLM 提方案 + 重跑验证 + 记入知识库 | 3 | 2 周 |
| 6 | 需求格式 + 检查清单 + 问询 | 无 | 1 周 |
| 7 | 把需求挂到提交上(提交信息里写编号,CI 检查) | 6 | 2 周 |
| 8 | 视图 A 可用,视图 B 补上需求维度 | 5+7 | 几天 |

第 2 步之所以短,是因为部署逻辑本身不用写——接一个现成工具、约定配置文件放哪、把退出码和版本组合记下来,就完了。

**v3 说明:** 这个顺序仍是*价值*顺序,继续有效。但平台化之后,界面不再集中在第 4 步一次做完,而是**每个模块自带自己的管理界面**,随各模块落地;第 4 步退化为「把已有数据接上界面」的代表。具体的平台化分期(M0–M4)与任务依赖图见 `tasks/README.md`。

## 第 3 步有个特殊性质

**它本身就是那个一直没跑的实验。**

先只做压缩和指纹,不做修复。跑完就知道:你的历史构建失败里,有多大比例能被同一个指纹归并到一起。

这个数字要是很低,先检查是不是没洗干净(见第三部分),而不是直接放弃。

好处是:跑完这一步,你手上有的是一个能用的组件,不是一份报告。

# 已经想过并且否决了的方案

留着是为了以后不再重新想一遍。

| 方案 | 为什么否决 |
|---|---|
| 做一个通用的 AI DevOps 平台 | 验证工具全是开源免费的,门槛为零;而且 2026 年这个赛道有二十多家在打,Resolve AI 估值十几亿美元 |
| 面向中小团队做全生命周期 DevOps 产品 | Coolify 五万多 star 且免费还带 MCP,Dokploy、CapRover、Temps 一堆。这一层已经是负价格 |
| 打包 Gitea + Drone + k3s 分发 | 没人会为了用你的 AI 换掉现有工具链;而且你要为四个开源软件的所有 bug 负责 |
| 做禅道的竞品(**作为产品去竞争**) | 禅道自己早就有 DevOps 版本,已经打通了需求到上线,而且是从更强的那一侧进来的。**v3 注:** 本平台确实做项目管理,但**不以产品身份去竞争** —— 单用户自用、状态从执行链算出(不是手填)、与自身的构建/部署/失败闭环紧耦合。这是它和禅道/Jira 的分界(见第六部分规则 ①),不是要做它们的竞品。 |
| fork Coolify / 自己写 git server | fork 不是复用,fork 是你变成了上游。git server 更不能碰 —— 挂了是丢历史 |
| 让 LLM 生成需求和任务 | 没有任何东西能验证"这个需求是对的"。而下游测试全绿会让你误以为验证过了 —— 结果是非常正确地做出了错的东西 |
| 覆盖运行期错误 | Sentry Seer 已经做透了,包括自动开 PR 和生成回归测试,2026 年 1 月起还改成了不限用量的扁平定价 |
| 自己做 flaky 测试检测 | Harness、Trunk、CircleCI 都有现成的 |
| 用命令行代替界面 | 你不用命令行。用它做"到底需不需要界面"的测试是无效的 |

# 一句提醒

这个东西设计过程中反复往大了长 —— 从"一个只会开 PR 的小工具"长到"完整平台"再长回来,来回好几轮。

**判断标准就一条:能不能说清楚这个功能对应哪个机器记录。** 说不清楚的,不做。
