# 界面规格

原型在 `web/prototype/`,`make proto` 可以直接看。**那几个 HTML 是设计基准**,转成 `html/template` 时视觉要一致(任务拆分见 `tasks/README.md`,界面随各模块落地)。

> **v3(平台化):** 界面从「纯只读」转为**带写操作的完整管理平台**,覆盖四大域:项目管理、项目部署、构建部署错误处理、内部知识 Wiki。但两条底线不变 —— **状态不可改**(算出来的,INV-3)、**事实不可改**(只追加,INV-5)。写操作分两种:写用户内容(git)、触发动作(入队 jobs)。

---

## 界面是给人看的,数据是给 LLM 看的

这个区分决定了很多东西:

- **需求条款、环境定义、已验证修复** —— 消费者是 agent,所以是 git 里的文件,不是数据库记录
- **覆盖率、失败排行、环境状态** —— 消费者是你,做判断用,所以要图形界面

早期版本把两者混成一个,得出过"不需要界面"的错误结论。

---

## 设计方向:维护日志本,不是监控仪表盘

这个工具记录的是**发生过什么**,不是**现在控制什么** —— 状态从执行记录算出来,界面上没有一个开关能改它。

所以视觉参考取自工程制图纸和设备维护记录簿,不是 SaaS dashboard。

### 字体

**等宽是主字体,不是点缀。** 屏幕上几乎每个值都是哈希、版本号、退出码、次数,需要纵向对齐。

- 数据与界面主体:IBM Plex Mono
- 散文(说明、注解、空状态):IBM Plex Sans

### 颜色

```
--paper    #E9EBE4   制图纸底色,冷灰绿
--ink      #1C211C
--rule     #C5CAC0   细线
--verified #2C6146   已验证 / 成功
--failed   #9C3328   氧化红 / 失败
--stale    #A5731A   赭石 / 过期、漂移、等上游
--accent   #2C4A61   可交互元素、依赖变更刻度
```

三个状态色各自对应一个明确语义,**不要拿它们当装饰用**。

### 签名元素:指纹条

指纹渲染成 8 个 4px 色块,颜色由哈希前若干位派生。

目的很实际:扫失败列表时,**同一个反复出现的失败先被形状认出来**,再去读十六进制。你会记住"那个红蓝黄绿的",而不是 `a3f9c2`。

同一指纹在任何页面必须渲染出同一个条 —— 这是纯函数,由哈希决定。

## 四大功能域(v3)

每个域的页面分「读」(浏览)与「写」(改内容 / 触发动作)。写操作的边界见 CLAUDE.md「界面的写边界」。

### ① 项目管理

- **项目列表 / 详情**:增改项目(写 git `projects/` 登记)
- **需求条款**:列表、编辑(EARS)、签署态、覆盖率、「依据已变更」标记(写 git `.tally/requirements/`)
- **任务列表**:**状态是算出来的**(合并/构建/测试/部署/稳定五栏展示),**没有勾选框、没有手动状态** —— 这是和 Jira 的分界
- **bug 备注**:关联失败指纹(写 git)
- **版本**:链到制品 + 部署记录(读)
- **文档**:渲染 repo markdown,可编辑(写 git)

### ② 项目部署

- **环境状态**(在跑/停了/上次拉起失败)+ **一键拉起 / 推倒 / 重建**(动作)
- 每个环境跑的是哪个制品、哪次部署上去的(读)
- **部署历史**(时间、制品、结果、版本组合)+ **一键回滚**(动作)
- 动作一律**入队 jobs**,由 worker 执行并产生新记录;界面不直接改 `environment_run`/`deploy_run`

### ③ 构建部署错误处理

- **失败列表**(按指纹归并)+ 指纹条
- **修复排行**(出现次数 × 影响项目数)—— 该先修哪个
- **失败时间线 × 依赖升级对齐** —— 哪次升级把东西搞坏了
- **指纹详情(视图 B)**:影响项目、关联条款(LEFT JOIN)、已验证修复、是否漂移
- **诊断状态**:第几轮(共三轮)/ 五分类;可**触发重诊断**(动作,三轮上限由后端守)

### ④ 内部知识 Wiki(双层)

- **已验证修复库** —— `--verified` 绿 + 「已验证」标,**只读,无编辑入口**:按指纹浏览(指纹条/复现命令/修复/验证组合/过期标记),按工具链·包·状态检索
- **Wiki 笔记层** —— `--stale` 赭石 + 「笔记·未验证」标,**可编辑**(git markdown,`wiki/`)
- 两层**存储分目录、界面分色分标**,视觉上绝不能长得一样(见 PRD 第五部分「双层」)

### 跨域两视图

| 视图 | 回答什么 | 需要需求层? |
|---|---|---|
| **总览** | 什么坏了、坏了多久、之前修过没有 | 否 |
| **需求详情(视图 A)** | 某条需求的实现一共炸了多少次 | 是 |

**视图 B 的"关联条款"列用 LEFT JOIN。** 没有需求层时该列为空,页面其余部分照常工作 —— 这是它可以先上线的原因。

## 进不进界面的判据

**grep 或一条命令能答的,不进;需要图遍历或跨表 join 的,才进。**

第二条判据:**不重复 CI 已经提供的东西。**

| 进 | 不进 |
|---|---|
| 指纹频次排行 | 构建日志查看器(CI 已有) |
| 组合矩阵状态 | 实时流水线状态(CI 已有) |
| 失败时间线 × 依赖升级对齐 | 通用指标仪表盘 |
| 跨项目指纹影响面 | 看板、工时、通知 |
| 条款覆盖率与失效状态 | 条款全文编辑器 |

## 硬性约束

- **状态不可改(INV-3)。** 没有任何改状态字段的路由;任务状态从执行链算出来展示,界面上没有勾选框。
- **事实不可改(INV-5)。** 事实面表只由系统在动作执行时 INSERT,界面无删除/修改入口。
- **所有写操作过登录(INV-9)。** 单用户 + 简单登录(密码哈希 `x/crypto/bcrypt` + `session` 表);公开路由仅 `/login`、`/logout`、健康检查、静态资源;写路由带 CSRF 双提交 token(手写,不引依赖)。
- **写操作只有两种**(见 CLAUDE.md「界面的写边界」):写用户内容(git)、触发动作(入队 jobs)。
- **单二进制。** `go:embed` 嵌模板和静态资源,无前端构建步骤。
- **不引入 npm、打包器、CSS 框架。** 一个手写 CSS 文件够了。
- 表单用 HTMX 局部刷新;**关掉 JS 核心操作仍可用**(表单退化为整页提交)。

## 写操作与表单(v3)

- **编辑即写 git。** 需求、文档、Wiki 笔记的编辑页,提交后落到对应 git 目录并 commit;版本/diff/回滚由 git 管,界面不另存副本。
- **动作即入队。** 「拉起/推倒/重建/部署/回滚/重诊断」按钮 POST 后只入队一个 job,页面返回「已入队,稍后刷新」,真正结果在下次刷新时从事实面读出。
- **破坏性动作要确认。** 推倒重建、回滚这类用 `--failed`/`--stale` 色 + 二次确认,文案说清点下去会发生什么(如「将销毁当前环境并重建,约 2 分钟」)。
- **失败要说明白。** 入队失败、登录失败、编辑冲突(git 被别人/别的会话改过)都要给出明确原因和下一步,不道歉不含糊。

## 文案

- 名字按人认得的方式起,不按系统怎么实现起
- 动作说清楚点下去会发生什么
- 空状态是行动提示,不是"暂无数据"
- 错误说清楚出了什么事、怎么办,不道歉也不含糊

例子:

| 不要 | 要 |
|---|---|
| 暂无数据 | 还没有失败记录。跑一次构建之后这里会出现内容 |
| 操作失败 | 健康检查在 60 秒内未通过。查看 `deploy_run#4821` 的输出 |
| 提交 | 拉起环境 |

## 质量下限

不用宣称,做到就行:

- 窄屏可用(侧栏在 820px 以下折到顶部)
- 键盘焦点可见
- `prefers-reduced-motion` 生效
- 表格在窄屏下可横向滚动,不挤成一团
